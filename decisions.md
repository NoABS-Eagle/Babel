# PCB Editor — Важные архитектурные решения

## Язык и фреймворк
- **C + raylib**
- Приоритет: производительность, простота, нативные инструменты

## Система координат
- **int32_t в микрометрах**
- Диапазон ±2147 метров — достаточно
- Дюймовые единицы (mil) — только на границе импорта/экспорта, конвертация при чтении
- Ошибки округления в единицы микрометров физически неощутимы

## Хранение объектов
- **Tagged union array** с абстракцией через ObjRef `{ ObjType type; int index; }`
- Cache miss не проблема на реальных объёмах PCB
- Переход на per-type массивы возможен без изменения внешнего кода — ObjRef скрывает реализацию

## Удаление объектов
- **Tombstone** — помечать удалёнными, не двигать массив
- Индексы остальных объектов не инвалидируются

## Память для геометрии
- Фиксированные объекты (трассы, виа, пады) — **arena allocator** внутри Board
- Зоны — **исключение**: динамический массив точек через malloc/realloc
- Зоны редактируются активно, arena для них не подходит

## Undo/Redo
- **Full board snapshot** (deep copy)
- Для зон — отдельный memcpy массива точек
- ~5 МБ на снапшот для типичной платы, 20 уровней = ~100 МБ — приемлемо
- Оптимизация до delta snapshot — только если станет реальной проблемой

## Файловый формат
- **Рабочий формат**: Eagle .brd (XML) — читаем и пишем
- **Экспорт**: KiCad .kicad_pcb, Gerber — добавить позже
- Eagle .brd самодостаточен: вся геометрия футпринтов внутри, библиотеки не нужны
- Метаданные которые не редактируем (contactref, designrules, библиотечные ссылки) — хранить как passthrough XML блок
- Round-trip безопасен: меняем только позиции элементов и геометрию сигналов

## Eagle → KiCad экспорт схемы
- Правильный путь: экспорт библиотек из Eagle → импорт в KiCad → импорт схемы
- Гарантированное покрытие всех символов, никакой самодеятельности
- Парсер .lbr переиспользует код парсера .brd

## Слои
- Числовой индекс + таблица свойств `LayerInfo { name, color, visible, locked, is_copper, eagle_id }`
- Фиксированный набор стандартных слоёв + пользовательские (произвольное количество)
- Eagle числа → наши имена через таблицу маппинга при импорте
- Порядок отрисовки — отдельный массив индексов, меняется через CLI (`layer order ...`)
- GUI визард для порядка слоёв не нужен — CLI проще и точнее

## Нетлист и ратснест
- Нетлист читается из Eagle .brd секции `<signals>` — там уже всё есть
- Каждый пад знает свой net_id
- Ратснест = MST (алгоритм Прима/Крускала) по несоединённым падам каждой цепи
- Пересчёт в фоновом потоке, dirty flag на каждой цепи
- **Ратснест контекстный** — показывается не всё сразу:
  - Ничего не выбрано → ратснест скрыт (или бледный по явному запросу)
  - Выбран футпринт → только его соединения
  - Идёт маршрутизация → только текущая цепь

## Rooms (группы компонентов)
- Простой прямоугольник с именем, без привязки к иерархии схемы — в отличие от Altium
- Любая схема, в том числе однолистовая, может использовать rooms без церемоний
- Ратснест **раскрашивается по rooms**: внутриблочные соединения одним цветом, межблочные — другим
- При компоновке можно скрыть внутриблочный ратснест — видна только общая картина связей между блоками
- Начальный импорт: компоненты с одного схемного листа → одна room, расставляются вместе
- Хранить как отдельный объект платы: `Room { name, rect, color }`
- Eagle groups → rooms при импорте (если есть)

## Группы объектов
- Группа — только для быстрого выбора, не блокирует индивидуальный выбор объектов
- Объекты выбираются по одному как обычно; группа выбирается через отдельное поле в интерфейсе
- Группа может содержать любые ObjRef включая rooms
- `Group { name, ObjRef *members, int count }`

## Умное перемещение группы
- При move группы — автоматически подхватываются трассы у которых **оба конца** принадлежат компонентам группы
- Трассы с одним концом внутри, другим снаружи — предупреждение в строке статуса
- Трассы с обоими концами снаружи — не трогаются
- Пересоздавать группу с дорожками вручную как в Eagle — не нужно, редактор знает топологию сам

## Zone Fill
- Библиотека полигональных операций: **Clipper2**
- Пересчёт в **фоновом потоке**, worker спит 16мс между проходами
- **Dirty flag** на каждой зоне — пересчитывать только затронутые
- **Пространственный индекс** — искать только объекты рядом с зоной, не все
- Worker работает с копией данных зоны во избежание гонок
- **Фаза 1**: обновление fill после каждого зафиксированного действия пользователя
- **Фаза 3** (после профилирования): обновление в реальном времени через ghost object

## Рендеринг полигонов
- Триангуляция через **earcut** — один `.h` файл, ~500 строк, поддерживает дырки
- Дырки в fill зоны — результат Clipper2 (зазоры вокруг падов, трасс)
- Триангуляция кэшируется в зоне, пересчитывается только после zone fill (когда dirty)
- Рендер: контур зоны (линии по точкам) + залитая медь (кэшированные треугольники)
- Приоритет зон: `fill_priority` — зона с высшим приоритетом заливается первой
- Пересекающиеся контуры зон — не ошибка на этапе рисования, разруливается при fill

## Выбор объектов (Selection)
- Пад — не объект выбора вообще. Часть футпринта, данные для DRC/ратснест/рендера
- Футпринт выбирается **только по origin** — как в Eagle
- Приоритет при наслоении: **Трасса > Виа > Футпринт origin > Зона**
- ЛКМ — выбрать первый по приоритету
- ПКМ — перебрать следующий объект в стеке под курсором (без меню, без тултипов)
- Флаг `selected` хранится прямо в объекте
- Box select: слева направо — только полностью вошедшие, справа налево — любое пересечение
- Никаких всплывающих свойств при наведении — только явный запрос пользователя

## Фильтр выбора объектов
- Панель тогглов всегда на экране — тип объекта + слой
- Визуальная индикация что сейчас можно выбрать — состояние видно постоянно
- Простой Eagle-подход: чекбоксы по типу (трассы, виа, футпринты, зоны, текст) и по слою
- Сложные фильтры через CLI если нужно, но основной инструмент — GUI панель

## Пространственный индекс
- **Равномерная сетка** — достаточно для PCB, проще R-tree
- Размер ячейки ~1-2мм
- Объект регистрируется во всех ячейках которые перекрывает его bbox
- При хитресте: берём ячейки под курсором + соседние, точная проверка только кандидатов

## Архитектура инструментов
- Каждый инструмент — vtable `Tool` с функциями: activate, deactivate, on_lmb, on_rmb, on_move, on_key, render
- Каждый инструмент — отдельный `.c` файл, своё статическое состояние
- Активен ровно один инструмент, переключение через `set_tool()`
- Инструмент мутирует плату через транзакционный API (board_begin/commit) — undo автоматически
- Добавить новый инструмент = написать один `.c` файл, не трогая остальное
- Ghost/preview рисуется в `render()` инструмента, не затрагивает модель

## Командная строка
- Отдельная сущность — парсер команд с доступом к модели и состоянию редактора
- Мутации через те же транзакции что и инструменты — undo работает автоматически
- Два типа команд: мутации модели (`move C8 (1 5)`) и навигация/состояние (`show C8`, `grid 0.1`)
- Обсудить детально позже

## Принцип CLI vs GUI
- **CLI для действий** — выполнил и забыл (`move C8 (1 5)`, `layer order ...`)
- **GUI для состояния** — должно быть видно постоянно (фильтр выбора, активный слой, сетка)

## Принцип деструктивных операций
- Не спрашивать подтверждения — дать возможность отменить через Undo
- Информировать в строке статуса: "U3: 12 трасс отсоединено"
- Модальные диалоги не использовать

## Набор инструментов первой версии
- **Select** — box left/right + фантомный полигон даблкликом
- **Route+Via** — трассировка + виа одним инструментом
- **Move** — отдельный инструмент, НЕ часть Select
- **Zone** — контур зоны
- **Measure** — расстояние
- **Text** — надпись на слой
- **Line** — линия/дуга на слой
- **Drill** — механическое отверстие
- **Mirror/Flip** — компонент на другую сторону, трассы становятся ратснестом молча
- **Miter/Fillet** — скругление углов трасс после трассировки
- **Dimension** — задание расстояния между объектами (одноразовый constraint solver)
- Place Footprint — не нужен в первой версии, все компоненты из .brd
- Align — не нужен вообще (Eagle 7.7 его не имел, Eagle 9.6 крашится при попытке)

## Инструмент Move
- Клик на невыделенный объект + M → берёт за origin, снапит origin к сетке
- Выделенная группа + M или drag → берёт за точку захвата, двигает всё выделенное
- Одиночный объект — частный случай группового сдвига
- Точное перемещение через CLI: `move C8 +5 0` (относительное), `move C8 (10 5)` (абсолютное)

## Инструмент Route — геометрия
- Режим заданного угла (дефолт 45°, но любой) — обобщение 45° и 90° режимов
- Свободный угол
- Скругление — отдельный инструмент Miter после трассировки, применимо ко всему выбранному сразу
- Безье не нужны

## Инструмент Route — поведение
- Только ручной маршрутизатор — никакого push-objects, никакого автоогибания
- Два режима DRC: свободный (подсвечивает но не блокирует) и строгий (блокирует)
- Переключение режима DRC — одна кнопка, состояние видно в GUI постоянно

## Инструмент Route — параллельность и угол
- Shift+клик на любую прямую на любом слое → snap_angle = угол этой прямой
- Повторный Shift+клик на тот же объект → snap_angle += 90°
- Циклически: параллельно → перпендикулярно → параллельно
- Старт трассировки от пада повёрнутого компонента → snap_angle автоматически = угол компонента

## Инструмент Dimension
- Не аннотация — задание расстояния. Одноразовый constraint solver
- Снап к характерным точкам объектов (центр, края, концы трасс, origin)
- Если угол между объектами больше порогового (настраивается, дефолт ~5°) — не выполняется
- Механика характерных точек переиспользуется в Route и других инструментах

## Операция параллельности
- Не отдельный инструмент — операция над выделенным объектом
- Выделил объект → нажал клавишу → Shift+клик на референс → объект повернулся параллельно
- Повторный Shift+клик → перпендикулярно (та же механика что в Route)
- Применимо к трассам, линиям, футпринтам
- Касательная — не нужна, реальных сценариев на плате нет

## 3D просмотр
- 3D вид — ещё один рендерер той же Board структуры, не отдельное приложение
- Обновляется в реальном времени вслед за изменениями в редакторе
- Три типа изменений с разной стоимостью:
  - Компонент переместился → обновить матрицу трансформации + перегенерировать текстуру меди (быстро)
  - Трасса добавлена → перегенерировать текстуру меди (быстро, тот же код что 2D рендер)
  - Контур платы / отверстие изменились → регенерировать меш в фоновом потоке (медленнее, но редко)
- Текстуры меди генерируются рендером 2D слоёв в offscreen framebuffer — переиспользование кода
- Компоненты — меш-модели из .step/.wrl с матрицей трансформации
- Dirty флаги по типу изменения: `copper_dirty`, `outline_dirty`, `components_dirty`
- Те же dirty флаги что для zone fill — один механизм, два потребителя
- Предусмотреть сейчас: не выбрасывать 3D данные при импорте .brd (путь к модели, offset, rotation, scale)

## Design Rules
- Параметры от производителя, задаются один раз для проекта:
  `min_trace_width`, `min_clearance`, `min_via_drill`, `min_annular_ring`
- Параметры инструментов не дают ввести значение меньше чем в design rules
- При смене design rules — автоматический полный DRC, подсветка новых нарушений
- Acid traps — не нужны, современные производители справляются без проверки

## DRC
- Фоновый поток, та же архитектура что zone fill и ратснест:
  dirty flag → пересчёт только затронутого → обновление списка нарушений → подсветка
- Два режима во время трассировки: свободный (подсвечивает) и строгий (блокирует)
- Пространственный индекс обязателен — проверять только объекты в радиусе max_clearance
- Три фоновых потока с одинаковой структурой:
  - `zone_fill_worker` — dirty zones → новый fill
  - `ratsnest_worker` — dirty nets → новый MST
  - `drc_worker` — dirty objects → новые нарушения
- Возможно объединить в один поток — решить после профилирования

## Автоматический ратснест
- Ратснест обновляется автоматически без кнопок и церемоний
- Положил трассу, соединил пады — ратснест между ними исчез сам
- Пересчёт MST для типичной цепи — микросекунды, нет причин делать вручную

## Многоканальное проектирование
- Многоканальная схема = особый вид библиотечного компонента (иерархический)
- На схеме инстанцируется как обычный компонент, референсы назначаются автоматически
- На плате = модульный футпринт: дочерние футпринты + трассы + виа + геометрия
- Обновил определение модуля в библиотеке → все инстансы на плате обновились
- Маппинг компонентов между каналами не нужен явно — решается иерархией схемы

### Жизненный цикл модульного футпринта: РЕФЕРЕНСНЫЙ экземпляр (дополнено при обсуждении net class)

«Трассы инстансов идентичны» — не предусловие, а целевое состояние, которое механизм
устанавливает и поддерживает. В начальный момент модуль на плате НЕ разведён (если не
вставлен готовым): инстансы — просто группы футпринтов со своими ратснестами.
- Пользователь разводит ОДИН экземпляр и назначает его **референсным** → его разводка
  становится определением модульного футпринта; остальные экземпляры приводятся к нему;
  дальнейшие правки — в референсном, синхронизация во все (аналог multichannel
  replication Altium).
- **Носитель репликации — САМ МОДУЛЬ** (референсность — свойство module-инстанса на
  плате), НЕ room: наши rooms сознательно не привязаны к иерархии (см. «Rooms» выше) и
  остаются простым инструментом компоновки — две фичи не смешиваются, в отличие от Altium.
- Классовый инвариант («один класс внутренней цепи на все инстансы», см. «Net class»)
  с этим циклом согласован: класс — ПРЕДПИСАНИЕ для разводки, существует до первой трассы
  и одинаков для всех; референсный разводится по нему, реплики наследуют геометрию.
- **Синхронизация референс→реплики — только ЯВНАЯ, не автоматическая** (решение
  пользователя): либо активируется вручную на явно указанные экземпляры, либо есть явное
  per-instance отключение (выбор между двумя механизмами — позже). Причина — реальная
  практика: отдельные инстансы модуля вынуждены иметь чуть другую трассировку из-за
  ограничений печатной платы (край, вырезы, крепёж), и полный выход из модульного
  контракта (FLATTEN, см. пересмотренную запись «Detach инстанса модуля») ради этого был
  бы избыточен — терялась бы живая связь для всех остальных правок. Следствие: «идентичность
  трасс» — целевое, но НЕ принудительное состояние; вместо принуждения — видимость
  (индикация «инстанс разошёлся с референсом»), в духе «Принципа деструктивных операций»
  (не блокировать, а информировать и давать откат).
- Открытые вопросы к board IR (зафиксированы, не решены): повороты/зеркала реплик
  относительно референса; DRC/индикация «реплика соответствует референсу / разошлась»;
  выбор механизма явной синхронизации (ручная активация на указанные экземпляры vs
  per-instance opt-out). (Detach как board-операция отменён — выход из модульного
  контракта это схемный FLATTEN THE MODULE, плата следует; см. пересмотренную запись
  «Detach инстанса модуля».)

## Листов как сущности нет. Схема — один бесконечный холст
- Даже в Eagle "лист" уже фактически бесконечный — рамка там не ограничивает координаты, это чисто
  визуальная подсказка дизайнеру, что попадёт на печать. Доводим эту идею до конца: убираем "лист"
  как структуру документа вообще
- Документ = один бесконечный холст верхнего уровня + по одному бесконечному холсту на файл
  каждого инстанцируемого модуля (1-уровневая иерархия, см. ниже)
- Единственная причина, по которой "листы" существовали — контролируемый экспорт в печать/PDF.
  Это не повод тащить структуру страниц в модель данных целого документа

## Рамка — это просто компонент без футпринта, не отдельная сущность IR
- В Eagle так и устроено буквально: рамка — компонент без `<footprint>`. В нашем IR `<footprint>`
  у компонента уже опциональный — значит для рамки не нужен НИКАКОЙ новый тип объекта
- Placeholder-текст в символе рамки резолвится тем же механизмом, что `>MANF#`/`>PACKAGE` у обычных
  компонентов (см. `altium_exporter.py`), просто источник значения — атрибуты ЭТОГО инстанса
  компонента-рамки (а не глобальные атрибуты документа)
- Итого два независимых, уже существующих механизма дают любую нужную комбинацию:
  глобальный атрибут документа + placeholder где угодно → одно значение на весь документ;
  атрибут инстанса рамки + placeholder в её символе → своё значение у каждого размещённого
  экземпляра рамки (можно расставить несколько рамок с разными значениями одного поля)

## Scope label — определяется КОНТЕКСТОМ (файл/canvas), не отдельным типом объекта
- У KiCad есть три разных типа: Local Label / Global Label / Hierarchical Label — это явный выбор
  типа, который пользователь делает руками. Известная дыра: Global Label внутри под-листа молча
  пробивает границу модуля насквозь по совпадению имени с ЛЮБЫМ Global Label в проекте, минуя порты
- У нас эта дыра невозможна структурно: внутри файла модуля просто нет опции "сделать метку
  глобальной" — сам механизм отсутствует, не дисциплина пользователя его не использовать
- **Без исключений для power/ground.** Supply-символы (GND/VCC) внутри модуля — обычный local
  label, как любой другой сигнал. Если канал должен реально получать питание с платы — это явный
  порт модуля, не магическое автоматическое слияние с внешней цепью того же имени

## Junction и pinref — хранятся ЯВНО, не выводятся из совпадения координат
- Пересмотрено: совпадение координат (конец провода = конец другого провода / позиция пина)
  САМО ПО СЕБЕ не доказывает намерение соединить. Два совершенно несвязанных провода могут
  случайно оказаться в одной точке сетки без всякого умысла
- Правило "касание = соединение" — опасно: тихо сливает две разные цепи в одну по случайному
  совпадению, и это не визуальная путаница, а настоящая порча связности, которую легко не заметить
- **Default — противоположный**: касание НЕ означает соединение, пока не зафиксирован явный
  маркер (junction для провод-провод, pinref для провод-пин), который редактор ставит сам в
  момент, когда пользователь реально совершил действие "ветвление/стык", а не постфактум
  по выводу из геометрии
- Рендеринг follows the same logic: есть маркер → точка (реально соединены); провода касаются
  без маркера → рисуем как "один провод перепрыгивает другой", визуально разведены, не соединены
- Подтверждено реальным файлом `wire_test.sch`: Eagle хранит и `<junction>`, и `<pinref>` явно —
  не кэш рендерера, а намеренная защита от той самой silent-merge ошибки

## KiCad-специфика: когда исходный файл реально требует junction для связности

В IR `<junction>` — часть `<net>`/`<segment>` (см. выше), хранится явно по умолчанию. Но при
ИМПОРТЕ из KiCad сам исходник неоднороден: одна и та же визуальная "точка касания" двух
проводов означает связь в одних случаях и не означает в других — это свойство формата
источника, не наш выбор эвристики, и импортёру придётся это различать перед тем, как
материализовать явные `<pinref>`/`<junction>` в IR.

Проверено на синтетической фикстуре `testData/junction/junction.kicad_sch` (4 геометрических
кластера; имена меток на проводах расставлены пользователем ПОСЛЕ проверки реального поведения
в самом KiCad, не угадывались по координатам):

- **Конец провода = конец другого провода** (сколько угодно проводов, чистое совпадение
  концов, ни один не касается ТЕЛА чужого сегмента) — соединено ВСЕГДА, `(junction)` для
  самой связности не обязателен. В фикстуре — `T_NET` (3 провода, 3-way) и `CROSS_NET`
  (4 провода, выглядит как "+", но геометрически все 4 именно ОКАНЧИВАЮТСЯ в точке) — оба
  с junction в файле, оба физически одна цепь (одно имя на оба конца кластера).
- **Конец провода касается ТЕЛА другого провода** (T-стык) или **тело касается тела**
  (настоящий X-перекрест, ни один сегмент не оканчивается в точке) — соединено ТОЛЬКО если
  в этой точной координате стоит явный `(junction (at x y) ...)`. Без него — два независимых
  провода, визуально пересекающихся ("один провод перепрыгивает другой"), РАЗНЫЕ цепи.
  В фикстуре — `NET1`/`NET2` (X, тело×тело, без junction) и `NO_T_NET1`/`NO_T_NET2`
  (T, конец×тело, без junction) — в обоих случаях два разных имени, т.е. реально разные цепи.
  - **Junction здесь — не кэш/декорация поверх уже вычисленной связности, а сам носитель
    факта соединения.** KiCad-редактор САМ автоматически ставит junction при интерактивном
    рисовании провода, чей конец ложится на тело другого ("auto-insert on top of existing
    wire" — задокументированное поведение GUI). Но это поведение РЕДАКТОРА, не инвариант
    формата файла: пользователь сознательно удалил автоматически поставленный junction у
    `NO_T_NET1`/`NO_T_NET2` и перепроверил — имена сигналов по обе стороны разошлись,
    т.е. KiCad реально считает их разными цепями без junction в файле. Значит импортёр
    НЕ имеет права считать "касание тела = связь" самостоятельно по геометрии — только
    по факту присутствия `(junction)` в данной точке.
- **Конец провода = позиция пина** — соединено всегда, `(junction)` тут вообще не участвует
  (правило про junction в принципе не действует на пины — у одной точки пина может быть
  сколько угодно подключений без всякого junction).

**Алгоритм для импортёра (union-find):** объединять два провода в одну цепь, если (а) у обоих
есть истинный КОНЕЦ в общей точке (независимо от наличия junction), ИЛИ (б) в этой точной
координате есть явный `(junction)`-элемент (закрывает и T, и X). Провод↔пин — отдельно, по
совпадению конца провода с абсолютной позицией пина размещённого компонента (с учётом
поворота/зеркала инстанса); junction не участвует. Чистое касание тела/тела без junction —
НЕ объединять.

Формат подтверждён напрямую по файлу: `(junction (at X Y) (diameter D) (color R G B A)
(uuid U))` — самостоятельный top-level элемент `.kicad_sch`, сосед `(wire)`, без какой-либо
ссылки на конкретные провода — только координата (`testData/junction/junction.kicad_sch`,
строки 8–19).

**Дополнение, найденное на реальном проекте (`testData/phil`): `<label>` НЕ подчиняется
junction-правилу выше.** Метка `"NRST"` сидит ровно на ТЕЛЕ длинного провода (не на его
конце) без какого-либо junction в этой точке — и тем не менее реально называет всю цепь
(подтверждено: тот же провод одним концом касается пина `U3.NRST`, другим — кластера с
конденсатором/резистором/выводом разъёма, и КICad показывает это одной цепью `NRST`).
Разница с правилом провод↔провод/пин↔провод осмысленна, не исключение ради частного
случая: второй провод или пин, касаясь ТЕЛА, претендует на НОВОЕ электрическое соединение
(отсюда и нужен junction — снять неоднозначность «совпадение или провод»). Метка же ничего
не соединяет — она просто называет уже существующий проводник, в любой его точке, концом
или серединой. Поэтому при импорте: метка примагничивается к любому проводу, который она
касается (конец ИЛИ тело, без junction), а провод↔провод/провод↔пин — только по правилам
выше. Реализация — `babel/kicad_schematic.py:_build_nets`.

## KiCad: конфликтующие ярлыки на одной цепи — жёсткий отказ

KiCad позволяет разместить два (или больше) ярлыка с РАЗНЫМИ именами на одном электрически
связанном острове (тот же union-find, что и весь раздел выше) — сам KiCad это не запрещает,
только показывает пользователю ОДНО разрешившееся имя в статус-баре как "Connection Name" при
выделении цепи. Confirmed real: `testData/vimdrones.zip` — например `"5v"` и `"FD6288_VCC"`
на одном острове сразу на двух разных страницах (`vimdrones_esc_development_board.kicad_sch`,
`mcu.kicad_sch`), аналогично `"FD6288_VS1"`/`"PHASE_A"` и ещё три такие же пары.

**"Connection Name" нигде не хранится в `.kicad_sch`.** Это вычисляется движком ERC/netlist
самого KiCad на лету (тот же механизм, что строит ratsnest) по внутренним правилам
приоритета (global/hierarchical label > local label > power pin и т.п.) — kiutils, как и сам
файл, этого поля не содержит вообще; единственное, что есть в файле — сырые `label`/
`global_label`/`hierarchical_label` объекты с текстом и позицией.

**Решение — не пытаться угадать/воспроизвести правила KiCad, а отказать во ВСЕЙ конвертации.**
По решению пользователя: два разных имени на одной физической цепи — порочная практика сама
по себе (нечитаемая/потенциально ошибочная схема), не то, что стоит молча разрешать, подбирая
"победителя" по своим собственным (заведомо отличным от KiCad) правилам. Раньше — `print`
предупреждения + тихий выбор первого имени по алфавиту, конвертация продолжалась. Теперь —
`ValueError` в конце `_build_nets`, ПОСЛЕ обхода всех островов всех страниц (не при первом же
конфликте), чтобы одним сообщением перечислить СРАЗУ все конфликты во всём проекте, а не
заставлять пользователя чинить по одному и перезапускать конвертацию раз за разом.

Сообщение об ошибке называет для каждого конфликтующего имени, ГДЕ именно оно находится —
`sheet.kicad_sch @ (x, y)mm`, в тех же raw KiCad-координатах (mm, без тайлинг-сдвига `dy`,
без Y-флипа), которые пользователь видит на экране в самом KiCad, — чтобы можно было прыгнуть
прямо туда и поправить, не пересчитывая координаты вручную. Для конфликта с именем supply-пина
(`sup`-пин ведёт себя как прикреплённый label, см. ir_schema.md "Supply symbol") — координат
нет, вместо этого имя компонента+пина (`R1.GND (supply pin)`), однозначно находимое через
"Find" в редакторе. Реализация — `babel/kicad_project_parser.py` (передаёт `sheet.name`+raw
X/Y в `label_origin`) → `babel/kicad_schematic.py:_build_nets`.

## KiCad-специфика: filled-графика символа — `<shape>`/`<polygon>` уже годятся, заливка дугой — нет

Найдено на `USB_C_Receptacle_USB2.0_14P` (`testData/phil`): декоративная пиктограмма
USB-разъёма внутри символа рисуется через `rectangle`/`circle`/`polyline` с
`(fill (type outline))` (залить тем же цветом, что контур/тело — KiCad-конвенция,
никакой отдельной палитры не нужно). `_add_unit_geometry` эту заливку никогда не смотрел
— `rectangle`/`circle` всегда уходили в голые `<line>`/`<arc sweep=360>`, пиктограмма
превращалась в пустой каркас вместо сплошной иконки.

**Решение: IR уже имеет нужный примитив, просто не используется парсером.**
`<shape outline="0">` (ir_schema.md) — это буквально «залита цветом слоя, без контура»,
никакого нового хранения цвета не требует. `<polygon>` — «заполненный многоугольник» по
определению. Поэтому:
- `rectangle`/`circle` с `fill.type == 'outline'` (и ТОЛЬКО с ним) → `<shape>`
  (`roundness=0`/`100`, `outline=0`) вместо линий/дуги.
- Замкнутая (первая точка = последняя) `polyline` с такой же заливкой → `<polygon>`
  вместо отдельных `<line>`.
- Без заливки (или с любой ДРУГОЙ заливкой) — поведение не изменилось (линии/дуга,
  как раньше).

**Первая попытка ошибочно триггерилась на `fill.type != 'none'` — поймал пользователь.**
`fill type background` (заливка цветом ФОНА РЕДАКТОРА — то, чем у этого же символа залит
большой прямоугольник всего тела) выглядит как «тоже какая-то заливка», но это другая
семантика: не «залей тем же, что контур», а «залей тем же, что подложка канвы» — у IR
просто нет понятия фона канвы, и заодно никакого смысла в этом нет (большой прямоугольник
тела ВСЕГДА снизу по z-order, его заливка не несёт никакой содержательной информации,
кроме «не сделай его прозрачным дыркой в редакторе»). Триггер на `!= 'none'` ошибочно
конвертировал и его в залитый `<shape>` — результат: один сплошной залитый блок (тело
символа) перекрывал ВСЁ остальное, что нарисовано поверх него (контактные площадки,
трезубец, текст). Исправлено: триггер строго `== 'outline'`, `background` (и любое другое
значение кроме `none`) ведёт себя как раньше — голые линии/дуга.

Реализация — `babel/kicad_parser.py:_add_unit_geometry`. `eagle_exporter.export_symbol`
уже умел `<shape>`/`<polygon>` в символе (видимо, написан с запасом на этот случай, не
было повода проверить раньше) — экспорт в Eagle сработал без единой правки на своей
стороне; `<shape roundness=100>` → нативный `<circle>`, `outline=0` → `<rectangle>`
(он у Eagle всегда залит, отдельного флага не нужно).

## KiCad-специфика: filled дуга → круг (точное тождество, не аппроксимация)

Залитая (`fill type outline`) дуга в KiCad-символе сама по себе бессмысленный элемент —
у KiCad нет родного примитива «скруглённый прямоугольник» для символов, поэтому
скруглённые залитые "крышки" пиктограммы всегда собираются как rect (прямые стороны,
залитый) + полуокружность того же диаметра на каждом конце (тоже залитая — отсюда
парные дуги «контур + залитый дубль», раз у KiCad нет единого filled-path на всю
фигуру, только per-примитив fill). Решение пользователя: раз это всегда полуокружность
(`sweep≈180°`) на конце залитого rect ТОЧНО того же диаметра, замена на **залитый полный
круг** того же центра/радиуса даёт МАТЕМАТИЧЕСКИ ТУ ЖЕ область — другая половина круга
просто проваливается внутрь уже залитого rect, ничего лишнего не становится видимым.
Не аппроксимация, а точное тождество для stadium/pill-формы.

**Гейт строго на `sweep`, не на «любая залитая arc».** Применяется только при
`|sweep| ≈ 180°` (допуск `_ARC_SEMICIRCLE_TOL_DEG = 1.0°` — округление координат
source даёт `179.51°`, не ровно 180). Для любого ДРУГОГО sweep (гипотетический залитый
"pac-man"/pie-wedge) замена на полный круг добавила бы видимую лишнюю площадь — такие
дуги (если когда-нибудь встретятся) остаются как раньше, контур без заливки.

Подтверждено на `USB_C_Receptacle_USB2.0_14P`: 2 пары дуг `r=0.635`/конец залитого rect
шириной 1.27мм (= диаметр) → 2 залитых `<shape roundness="100">`; 2 НЕ залитые дуги
`r=1.905` (внешний контур корпуса, без залитого дубля) остались дугами как были.
Экспорт в Eagle — `<shape roundness=100 outline=0>` → нативный залитый `<circle>`,
без единой правки на стороне `eagle_exporter`.

**Побочный баг, найденный и исправленный в той же строке (не связан с заливкой):**
`SyArc`-геометрия (3-точечный fit, `_arc_params`) считается в мм, но код раньше форматировал
`cx`/`cy`/`r` через `_f()` напрямую, без перевода в µm — единственное место во всём
`_add_unit_geometry`, которое хранило координаты в мм вместо µm (ir_schema.md `<arc>`
требует µm везде, как и всё остальное). Затрагивало КАЖДУЮ некруговую (start/sweep ≠
0/360) дугу из любого KiCad-символа, не только залитые. Исправлено на `_um(cx)`/`_um(cy)`/
`_um(r)` — теперь `arc cx="-6985"` вместо `arc cx="-6.985"`.

Реализация — `babel/kicad_parser.py:_add_unit_geometry` (ветка `SyArc`).

**Второй побочный баг, найденный СРАЗУ после первого (раньше единичный фикс маскировал
его): `eagle_exporter._arc_to_wire` инвертировала sweep — `curve = -sweep_deg` вместо
`curve = sweep_deg`.** Пока `cx`/`cy`/`r` были в мм-но-подписаны-как-µm (см. выше), все
партиальные дуги на выходе схлопывались в вырожденную точку у нуля координат — заметить
неправильный ЗНАК было физически невозможно, баг был не виден визуально. После фикса
единиц дуги впервые стали РЕАЛЬНО видны в Eagle-экспорте — и сразу обнаружилась
вывернутость (поймал пользователь). Round-trip-тест (`_arc_to_wire` → `eagle_parser.
eagle_arc`, экспорт→импорт синтетической дуги) подтвердил математически: с минусом
обратное чтение даёт совершенно ДРУГОЙ центр/start/sweep, без минуса — точное совпадение
до округления. Источник истины — `eagle_parser.eagle_arc` (построена на чтении РЕАЛЬНЫХ
Eagle-файлов, не теоретически): `curve_deg` там читается как `sweep_deg` НАПРЯМУЮ, без
инверсии знака — значит и экспорт обязан писать так же. Исправлено: `curve = sweep_deg`.
Подтверждено на реальных данных: координаты концов экспортированных `<wire curve=...>`
у `USB_C_Receptacle_USB2.0_14P` точно совпали (до округления 3-точечного fit) с исходными
KiCad-координатами дуг.

**Третий, того же класса баг, найден по аналогии (не задействован текущими тестовыми
данными — ни один footprint в `testData/phil` не содержит настоящей дуги):**
`_convert_footprint`-ветка `FpArc` (PCB-дуги, не символьные) — та же мм-вместо-µm
ошибка, что была у `SyArc`, просто на стороне футпринта. Исправлено тем же способом
(`_um()` вместо `_f()` для `cx`/`cy`/`r`), не дожидаясь реального тестового случая —
паттерн идентичен, риска в исправлении нет.

Реализация — `babel/eagle_exporter.py:_arc_to_wire`, `babel/kicad_parser.py:_convert_footprint`
(ветка `FpArc`).

## `<segment>` — оставляем как явную структуру, не выводим из геометрии
- По `eagle.dtd`: `<!ELEMENT segment (pinref | portref | wire | junction | label)*>` — контейнер
  без собственного имени, группирует один связный остров цепи
- Решено хранить явно, не вычислять: связность между wire/junction/pinref у нас и так явная
  (см. выше), и привязка `label` к конкретному острову должна следовать той же логике — не по
  совпадению координат, а явной группировкой. `segment` — естественный способ это выразить
- Имя всё равно живёт на родительском `<net>`, не на `segment`

## Component instance на схеме — копия, не ссылка (как Eagle)
- Компонент при размещении КОПИРУЕТСЯ в design-документ целиком (символ + атрибуты), не хранится
  как ссылка/указатель на библиотеку. Документ самодостаточен — открывается без библиотеки рядом
- Привязка к источнику — **только имя библиотеки**, без версии/ID/хэша содержимого
- Сознательно отклонено: версионирование библиотек (Eagle/Autodesk пытались через `urn` +
  `library_version` — по факту бесполезная сложность) и скрытый внутренний identity-маркер для
  разрешения коллизий имён. И то и другое стоит больше, чем дают: версия требует поддерживать
  систему версионирования библиотек самой по себе; скрытый ID нужно открывать в софте чтобы
  увидеть, плюс его уникальность саму надо как-то гарантировать
- Защита от "обновил компонент из неправильной библиотеки с тем же именем и всё сломалось" —
  не предотвращение, а **Undo**, ровно как и для любой другой деструктивной операции (см.
  "Принцип деструктивных операций" выше). Сломалось кардинально — заметишь и откатишь
- Правила "когда обновление возможно, а когда компонент отредактирован слишком сильно для
  авто-обновления" — отложено, решим при проектировании самого механизма обновления

## Формат проекта — `.swprj`, отдельный от `.swlib`, свой корень
- Библиотека (`.swlib`, `<library>`) и проект (`.swprj`, `<project>`) — два разных файла с
  двумя разными корневыми тегами, не один корень на два режима. По аналогии с `<library>` ↔
  `.swlib`, у `.swprj` свой корень, а не переиспользование `<library>` с доп. секцией —
  решение пользователя, см. ir_schema.md «Формат файла».
- **Библиотеки остаются отдельной сущностью** (не растворяются в проекте) — но всё, что
  реально использует дизайн, **копируется в проект целиком**: символ, footprint, pin-mapping
  (та же форма `<symbols>`+`<component>`, что в `.swlib`). `library=` на `<instance>` — это
  происхождение для будущего «обновить из библиотеки», не живая ссылка (см. выше).
- Реализация: `babel/kicad_project_parser.py:convert_project_full`.

## Резолв символов/footprint'ов в проекте — без эвристик, hard-fail на пропуск
- Импорт проекта **требует**, чтобы все используемые библиотеки были явно в архиве проекта
  (`sym-lib-table`/`fp-lib-table` должны резолвиться). Поиск по голому имени среди
  ЗАРЕГИСТРИРОВАННЫХ в этих таблицах библиотек — не «угадывание», это чтение того, что уже
  лежит в архиве (нужен из-за реального кейса: KiCad-экспорт символов не переписывает
  `lib_id` на новый nickname, см. `kicad_project_parser.py` module docstring).
- **Дополнено (решение пользователя, тот же аргумент «читаем то, что уже в архиве»):
  библиотеки, физически лежащие в КОРНЕ архива (`*.kicad_sym`/`*.pretty`), авторегистрируются
  в таблицы, если их там нет** — подтверждено реальным кейсом `testData/multichannel.zip`:
  архив несёт `multichannel.kicad_sym` + `Library.pretty` рядом с ПУСТЫМ `sym-lib-table` и
  вообще без `fp-lib-table`. Это не поиск по файловой системе (только корень проекта, ничего
  за его пределами), записи ДОБАВЛЯЮТСЯ после существующих (приоритет зарегистрированных
  nickname'ов не меняется), каждая авторегистрация — в import log, не тихо. Реализация —
  `kicad_project_parser._augment_lib_tables`, применяется в обоих путях импорта
  (`convert_project` и `convert_project_full`).
- Если после этого символ/footprint всё равно не найден — **жёсткий abort** с указанием
  чего не хватает, а не тихий skip-and-continue. Решение пользователя: «мы не должны
  заниматься поисками, мы перекладываем эту деятельность на пользователя» — если библиотеки
  не хватает, пользователь либо экспортирует нужные символы из своего дизайна, либо
  находит и кладёт в архив недостающую библиотеку сам.

## KiCad: `extends` в проектном импорте — hard fail по предусловию; пустой символ — валидный footprint-only компонент

- **`extends` (derived symbol) в архиве проекта = нарушенное предусловие, не случай для
  skip.** Предусловие импорта («Export Symbols to New Library...» перед архивацией)
  разворачивает derived-символы в полноценные — подтверждено на реальном
  export-произведённом файле (`testData/vimdrones.zip`, `lbr.kicad_sym`: ноль `(extends)`).
  Встретили extends → ValueError с советом переэкспортировать, не тихий skip. Библиотечный
  путь (`kicad_parser.convert`) без такого предусловия — там skip-with-warning остаётся.
- **Символ с нулём юнитов (0 пинов, 0 графики) — НЕ ошибка и НЕ extends, а
  footprint-only компонент.** Старый guard `not symbol.units` сваливал оба случая в один
  skip с ЛОЖНЫМ диагнозом «derived (extends)» — а реальный кейс оказался иным
  (vimdrones `Conn_01x03_Socket_1`/MOTOR_MOUNT1: автор сознательно ободрал графику,
  footprint мотора остался). Skip терял компонент ЦЕЛИКОМ вместе с footprint'ом — мотор
  исчез бы и с будущей платы. Теперь импортируется честно: пустой `<symbol>` (только
  видимые property-плейсхолдеры), `<component>` с footprint, пустой `<pin-mapping>` —
  Eagle-аналогия прямая: package-only элементы (логотипы и т.п.) там легальны.
  Реализация: `kicad_project_parser._convert_schematic_symbol`.

## KiCad: `ir_rot`/`ir_mirror` — литеральное копирование, не формула (пересмотрено ТРИЖДЫ)

**Финальное, подтверждённое решение** (`babel/kicad_schematic.py:_mirror_and_angle`):
```
ir_rot    = eff_angle     # буквальная копия, без минуса и без +180
ir_mirror = 1 if flip_x else 0
```
Никакой компенсации Y-flip между KiCad-space и IR-canvas не требуется — числовой угол
копируется как есть. Подтверждено пользователем напрямую: выставил в реальном Eagle тот же
числовой `rot`, что видел в реальном KiCad для `U6` (90°) — **и тело символа, и все провода
легли на место одновременно**. `eff_angle`/`flip_x` (используются только внутри
`_abs_pin_pos_mm` для позиции пина в KiCad Y-down space) не менялись.

**История трёх попыток и почему первые две "подтверждались", будучи неверными:**

1. **Первая правка** (`ir_rot = eff_angle+180`, `ir_mirror = NOT flip_x`) — выведена
   алгебраически из тождества `Rotate(θ)·MirrorX = Rotate(θ+180)·MirrorY`, "подтверждена"
   визуальным сравнением `lbr:GND` (симметричный треугольник) в KiCad и Eagle — выглядели
   одинаково. Неверна: симметричная фигура физически не может различить два кандидата,
   дающих одинаковую картинку при разных числах.
2. **Вторая правка** (`ir_rot = -eff_angle`, `ir_mirror` не меняется) — выведена перебором
   и алгебраической проверкой на `R17`/`C1`, "подтверждена" сверкой всех 329 `<pinref>` в
   экспортированном `.sch` против позиции, которую Eagle сам вычислит по тем же
   `<instance rot=...>`+`<symbol><pin>` данным — **0 расхождений**. Тоже неверна, и это
   куда коварнее: проверка сравнивала экспортированный файл САМ С СОБОЙ — и `<instance
   rot=...>`, и вычисление ожидаемой позиции пина использовали ОДИН И ТОТ ЖЕ `ir_rot`,
   поэтому любая единая (систематическая) ошибка в самом значении `ir_rot` сокращается и
   не проявляется никогда. Тест реально проверял только то, что имя пина в данной позиции
   не перепутано С ДРУГИМ пином того же инстанса (это и была настоящая проблема, которую
   он поймал раньше на R17 — там КОНКРЕТНО имена пинов внутри одного компонента были
   переставлены местами, независимо от абсолютного угла) — но был структурно слеп к
   вопросу "а тот ли это угол вообще, который видно в KiCad".
3. **Третья, финальная правка (эта запись)**: пользователь напрямую сравнил экспортированный
   `.sch` с реальным KiCad визуально — тело `U6` было развёрнуто на лишние 180° относительно
   исходника, хотя pin↔net проверка (п.2) показывала 0 расхождений. Вручную выставленный в
   Eagle `rot="R90"` (тот же угол, что в KiCad) немедленно исправил и тело, и провода —
   что доказывает: буквальное копирование `ir_rot=eff_angle` было верным решением с самого
   начала, а обе "компенсирующие" формулы (п.1, п.2) были избыточным и ошибочным
   усложнением задачи, которая проще, чем казалась.

**Методологический урок, актуальный для всех трёх попыток**: программная сверка внутри
одного и того же сгенерированного файла (или между двумя формулами, обе выведенными из
одних и тех же промежуточных данных) может быть внутренне самосогласованной и при этом
полностью оторванной от независимого источника истины. Единственная проверка, которая
реально поймала баг — прямое визуальное сравнение с РЕАЛЬНЫМ KiCad, сделанное человеком.
Для трансформаций координат (повороты, отражения, сдвиги) — если есть способ спросить
«а как это выглядит в оригинале», это всегда надёжнее любого количества алгебры.

- Реализация: `babel/kicad_schematic.py:_mirror_and_angle` (`eagle_exporter.py`'s
  `_instance_rot_attr` берёт `ir_rot`/`ir_mirror` напрямую, без своей инверсии).
- Footprint-овский поворот (`kicad_parser._rot_fp`) построен на СХОЖЕЙ, но не идентичной
  логике — на момент той правки **отдельно НЕ проверялся**; проверен и исправлен позже,
  см. следующий раздел «KiCad: `_rot_fp` — БЕЗ инверсии (третий случай)».

## KiCad: `_rot_fp` — БЕЗ инверсии и в footprint-пространстве (третий случай той же формулы)

**Проверено ground-truth-методом 2026-07-08** (тестовая плата `testData/rtfp`, сделана
пользователем в реальном KiCad специально под эту проверку): три SOT23 — R1 (0°, top),
R2 (12°, top), R3 (12°, bottom), у каждого пад «3» повёрнут ВНУТРИ футпринта на
относительные +30° (KiCad хранит 30/42/42 — угол пада АБСОЛЮТНЫЙ, placement запечён,
позиция при этом локальная; та самая половинчатая денормализация, эмпирически известная
по ti-mspm0). Старый `_rot_fp = (-angle) % 360` дал IR `rot=330`; рендер IR показал
наклон пада **зеркальным** реальному KiCad → инверсия ошибочна. Y-flip координат НЕ
меняет знак угла: соглашение углов KiCad уже CCW-на-экране, как и в IR.

- **Правка ПАРОЙ**: `kicad_parser._rot_fp` (теперь без инверсии) + все три footprint-места
  `kicad_exporter` (`_fp_text_style`, fp_text user, pad) — синхронно, KiCad-round-trip
  остался зелёным (vimdrones/multigate/sheets/phil).
- `_rot_fp_placeholder` УПРАЗДНЁН: он существовал только чтобы зеркалить асимметрию
  экспортёра (плейсхолдеры без инверсии, пады/тексты с инверсией), которой больше нет.
  Попутно вскрылось, что его докстринг уже был рассинхронизирован с реальностью
  (`_fp_text_style` инвертировал) — пара плейсхолдеров была тихо несимметрична.
- Итог по всем поворотам KiCad↔IR: **инверсии нет нигде** — символы, метки, footprint-пады,
  footprint-тексты, плейсхолдеры. Единственные оставшиеся инверсии знака — 3D-повороты
  rx/rz (отдельная, независимо выверенная пара).
- Попутные находки rtfp (для будущего board-импорта): (1) вычитание placement-угла верно —
  R2(12°) даёт пакет, побайтово равный R1(0°); (2) **bottom-футпринт приходит с платы с
  запечённым Y-зеркалом координат** (R3 ≠ R1 по знаку Y) — `_convert_footprint` это НЕ
  нормализует; при board-импорте пакет должен быть ОДИН, сторона — свойство инстанса,
  нормализацию flip'а предстоит сделать.

## KiCad: `_abs_pin_pos_mm` — тот же класс бага, вторая половина той же правки

**Продолжение записи выше** («ir_rot/ir_mirror — литеральное копирование»). Исправление
`ir_rot` не решило проблему полностью: тело символа и провода `R17`/`C1` (оба симметричные
относительно оси поворота) визуально выглядели правильно, но реальный тест на асимметричном
многопиновом компоненте (`U6`, `SN74LVC1T45DBV`, pin "A" `(-10.16,0)` и pin "B" `(10.16,0)`
— НЕ на одной оси симметрии) показал: провод, который в реальном KiCad подходит к пину 4
(B), в Eagle-экспорте физически совпадал с позицией, куда Eagle сам поместит совсем ДРУГОЙ
пин при том же `<instance rot="R90">`. Симптомы в точности совпадали с описанием
пользователя: провод визуально касается пина, но перемещение компонента его не тащит,
новая линия из пина подхватывает чужое имя цепи — RE-появление того же бага, который
исправление `ir_rot` вроде бы устранило на `R17`.

**Причина: `_abs_pin_pos_mm` (`kicad_schematic.py`) — отдельная функция, вычисляющая
абсолютную позицию ПИНА для `<net><line>`/`<pinref>` — несла ТУ ЖЕ лишнюю Y-компенсацию,
что уже была убрана из `_mirror_and_angle` для позиции ИНСТАНСА, но забыта здесь.**
Раньше функция принимала RAW KiCad Y-down `inst_y` и возвращала RAW KiCad Y-down
результат — вызывающий код инвертировал знак Y ОДИН РАЗ в конце (при записи в XML),
симметрично тому, как пишутся `<instance x/y>`. После убирания Y-компенсации из `ir_rot`
эта пара "raw-in → raw-out → инвертировать один раз в конце" перестала быть эквивалентна
canonical IR-повороту (`svg_renderer.py:_inst_point`/Eagle `<instance rot=...>`) — те
работают ЦЕЛИКОМ в IR-space (Y-up) без всякого промежуточного захода в KiCad-native space.
Симметричные тестовые пины (`R17`/`C1`, оба на оси Y=0 локально) не могли поймать это,
потому что при `pin_y_mm=0` Y-flip самой точки — no-op, расхождение возникает только через
взаимодействие с ПОВОРОТОМ, которое проявляется лишь на пинах, реально смещённых по обеим
осям локально (или, как здесь, лежащих по разные стороны X от центра при повороте на 90°).

**Исправление**: `_abs_pin_pos_mm` теперь принимает УЖЕ Y-flipped (IR-space) `inst_y` и
возвращает результат В ТОМ ЖЕ IR-space — тот же самый плоский `canonical_rotate`, что и
везде. Вызывающий код (`kicad_project_parser.py`) передаёт `-sym.position.Y` вместо
`sym.position.Y`, и инвертирует результат обратно в raw-KiCad ТОЛЬКО там, где это реально
нужно (`_stray_check`, работающий в raw-space по историческим причинам — сравнивается с
`frame_y0/y1`, тоже raw) — а для `pin_points` (сравнивается с `wires`, которые сами тоже
raw KiCad) инвертирует обратно перед добавлением в список, сохраняя прежний контракт этого
списка (`_build_nets` ожидает raw KiCad space для всех точек одинаково).

Подтверждено на `U6`: pin "B" теперь корректно привязан к `WS2812_SIGNAL` в той самой
точке (`y≈-95.25`), которую Eagle само вычисляет для `<instance rot="R90">`+`<pin
x="10.16" y="0">` — независимым ручным пересчётом (не через тот же самый программный
pin↔net cross-check, который уже дважды не смог поймать этот класс бага, см. запись выше).

Реализация: `babel/kicad_schematic.py:_abs_pin_pos_mm`, `babel/kicad_project_parser.py`
(оба вызова — stray-check bbox и pin_points).

**Подтверждено и для МЕТКИ (`<label>`) на схеме — той же визуальной проверкой пользователя**
(перегенерировал `vimdrones.sch` с эксперименальной формулой без инверсии, открыл в реальном
Eagle — метки легли на место). Это ОТДЕЛЬНАЯ функция (`_rot_fp` в `kicad_parser.py`,
изначально написана для footprint-геометрии), не `_mirror_and_angle` — структурно та же
формула (`-angle % 360`), но другой код, другой потребитель (схемная метка, не символ),
повторно подтверждённый отдельно, не унаследованный "по аналогии". Исправлено ТОЛЬКО для
метки (`kicad_project_parser.py`, инлайн `_f(angle % 360)`, без вызова `_rot_fp`) — три
ОСТАЛЬНЫХ вызова `_rot_fp` (footprint text/pad) остаются нетронутыми, той же логике пока
не доверяем без отдельной проверки на КАЖДОМ из них (контекст там другой — есть ещё
`- placement_angle`, компенсация поворота всего footprint при размещении на плате, не
проверенная сама по себе).

Заодно — две независимые мелкие правки на стороне Eagle-экспорта метки (не связаны с
поворотом, отдельные пожелания пользователя по виду в реальном Eagle):
- **`layer="97"`** (Info), не "91" (Nets) — `eagle_exporter.py`'s `_LYR_INFO` уже
  существовала, просто не использовалась для `<label>`. IR-овский атрибут `layer` на
  `<label>` (хранит `'nets'`) при этом остаётся НЕ читаемым ни одним потребителем
  (`eagle_exporter.py`/`svg_renderer.py` оба берут слой из своих собственных констант
  напрямую) — известный, задокументированный inline пробел, не лосс данных (источник —
  KiCad — вообще не различает "слой метки", это чисто IR/Eagle-side decorative choice).
- **`xref="yes"`** — подтверждено по `eagle.dtd`: `xref` валиден именно в контексте
  `<net>`'s `<label>`, заставляет Eagle показывать метку как флажок (cross-reference),
  не просто текст.

## Компонент без футпринта — ровно две причины, не три
- Подтверждено мануалом Eagle ("Devices without packages"): frame, supply, external — общий
  механизм "device без package". У нас остаются только первые две — **external отклонён**:
  практические применения нишевые (SPICE-симуляция, документирование тестового стенда/внешнего
  модуля — всё либо отдельная неподключаемая фича, либо тривиально решается текстовой заметкой).
  К тому же исходная причина существования `_EXTERNAL_` у Eagle — заглушить ожидание/warning
  "у компонента должен быть футпринт" — у нас этого ожидания нет изначально, футпринт и так
  опциональный, нечего глушить
- **Frame** — сигнал: геометрия на слое `frame-boundary` (см. ниже)
- **Supply symbol** — сигнал: пин с электрическим типом `sup`, **отдельным от `pwr`**
  (подтверждено `eagle.dtd`: `PinDirection` включает оба значения как разные варианты;
  `PortDirection` — БЕЗ `sup`, у портов модуля этого неявного поведения нет, они и так явные).
  `pwr` — обычная ERC-классификация, явное соединение проводом как у любого пина. `sup` —
  единственный триггер неявного label-поведения (пин ведёт себя как прикреплённый к нему label
  с тем же именем, без необходимости рисовать видимую метку или провод)
- Подтверждено практически: Eagle не даёт разместить footprintless-компонент на схеме, если у него
  есть пины, но среди них нет `sup` — ровно то же правило, что мы вывели по исключению
- **У Eagle Value supply-символа берётся из имени СИМВОЛА, а имя цепи — из имени ПИНА** — два
  независимых источника, которые могут разойтись (символ `GND`, пин `0V` → Value показывает одно,
  цепь называется другим). Мы так не делаем: у supply-символа ровно один источник имени — имя
  пина, используется и для связности, и для отображения (если Value вообще нужен для этого типа
  компонента). Не два факта, которые могут разойтись, а один
- **Ровно один `sup`-пин на символ, без исключений** — редактор символов явно запрещает добавить
  `sup`-пин, если в символе уже есть любой другой пин (даже второй `sup`). Смешивать `sup` с
  обычными пинами или иметь несколько `sup` не даёт ничего, кроме неоднозначности "это supply
  или гибрид с обычным выводом?". Валидный supply symbol = ровно один пин, и это `sup` — больше
  никаких комбинаций, проверка валидности становится однозначной

## Net class — задаётся в схеме, действует на плате
- Net class (ширина трассы/зазор) физически про плату, но НАЗНАЧАЕТСЯ в схеме — там видно
  семантику цепи (высоковольтная, силовая и т.п.), на плате этого не видно
- `<net>` получает опциональный `class`-атрибут (как у Eagle: `name="..." class="..."`), значение
  передаётся дорожкам при разводке
- Сама семантика (какие правила привязаны к имени класса, как уживается с глобальными
  `min_trace_width`/`min_clearance` из Design Rules) — отложена до проектирования board IR,
  сейчас фиксируем только факт существования атрибута

## Слой `frame-boundary` — определяет границу печати, живёт только внутри символа
- Геометрия = сигнал одновременно "это рамка" и "вот её граница" — один факт, не два
  рассинхронизируемых (булевый флаг + где-то отдельно вычисляемая граница)
- **Ровно один прямоугольник** на этот слой в одном символе — не ноль, не несколько
- Редактор: на этом слое доступен только инструмент Rectangle (треугольная печатная рамка
  никому не нужна — бумага прямоугольная)
- Редактор: слой рисуется только в редакторе символов — рамки не существует вне компонента,
  значит и её граница не может существовать как отдельный объект на холсте схемы
- Вся остальная графика рамки (ГОСТовские поля-таблички, текст, логотип) — обычные слои,
  без всяких ограничений на инструменты. Ограничен только сам слой границы, не рамка в целом
- Группировка компонентов для компоновки — другая, не связанная задача. Использует уже описанный
  `Group` (decisions.md, "Группы объектов"), не этот слой

## Импорт рамок — у всех трёх форматов граница задана структурно, эвристика не нужна
- **Eagle**: подтверждено по `eagle.dtd` — есть отдельный EMPTY-элемент `<frame x1 y1 x2 y2
  columns rows layer border-left/top/right/bottom>`, не линия/прямоугольник. `x1..y2` → наш слой
  `frame-boundary`. `columns/rows/border-*` — decorative (сетка координат по краю), сохраняем как
  опциональные атрибуты на этой же геометрии для лосслесс round-trip обратно в Eagle
- **Altium**: `Sheet Size` — свойство документа, не нарисованная пользователем геометрия. Границу
  берём оттуда напрямую
- **KiCad**: размер страницы + `.kicad_wks` (page layout) задают границу структурно; `Title Block`
  с явными полями (Title/Date/Rev/Company) мапится прямо на наши глобальные атрибуты документа
- Для Altium/KiCad на импорте синтезируем "неявный символ-рамку" из этих структурных данных
  (граница → `frame-boundary`, поля → атрибуты, декоративная графика штампа → обычные слои)

## Рамка — маркер для экспорта в печать, не декорация и не структура документа
- Рамка — обычный графический объект (контур + текст-placeholder) где угодно на холсте, не влияет
  на семантику дизайна никак. Можно не использовать вообще
- Графика рамки/штампа — обычный символ в пуле (тот же механизм placeholder'ов, что уже реализован
  для `>MANF#`/`>PACKAGE` в `altium_exporter.py`)
- **Печать/PDF-экспорт = указание рамки (или нескольких).** Экспортёр обрезает холст по границе
  каждой выбранной рамки и печатает как отдельную страницу
- `>SHEET`/`>LASTSHEET` — номер текущей рамки среди НАБОРА рамок, выбранных для конкретного
  экспорта; вычисляется в момент экспорта, не хранится в IR (как junction из геометрии проводов)
- Если рамок нет или не выбрано ни одной — экспортёр пытается напечатать весь холст целиком;
  закономерно не влезет в разумный формат бумаги — это сигнал пользователю расставить рамки,
  не повод встраивать пагинацию в модель данных
- **Подтверждено реальным файлом `eagle_frame.sch`**: `SHEET`, `DRAWING_NAME`, `LAST_DATE_TIME` —
  встроенные вычисляемые переменные Eagle, у них нет `value=` вообще, не хранятся как данные.
  `DRAWING_NAME` = имя файла, `LAST_DATE_TIME` = таймстамп последнего сохранения — то есть даже
  "дата" и "название" — НЕ атрибуты документа в общем случае, а производные от файла/VCS.
  Расширяет принцип "не хранить выводимое" дальше, чем казалось: реальных ручных атрибутов
  (которые пользователь вписывает осознанно) меньше, чем список полей классического штампа —
  Rev/Company/Document Number и подобное, но не Date/Title если они равны имени файла/таймстампу
- **Зарезервированные computed-имена placeholder'ов** (по аналогии с Eagle text variables) —
  отдельный namespace имён, которые ВСЕГДА вычисляются контекстом, никогда не читаются как
  атрибут: `>SHEET`/`>SHEETNR`/`>SHEETS` (номер/всего рамок в текущем экспорте),
  `>DRAWING_NAME` (имя файла), `>LAST_DATE_TIME` (таймстамп сохранения),
  `>PLOT_DATE_TIME` (момент именно этого экспорта/печати, отдельно от LAST_DATE_TIME)
- Title/Rev/Date/Company и т.п. (то, что реально вводится руками, не равно имени файла/таймстампу)
  — глобальные атрибуты документа БЫЛИ задуманы как умолчание (без оверрайда per-рамку),
  **пересмотрено для KiCad на реальных данных**: `title_block` в KiCad — свойство ФАЙЛА
  (= листа), не проекта. Подтверждено на `testData/pic_programmer.zip` (2 страницы одного
  проекта) — `date`/`rev` РЕАЛЬНО различаются между страницами (`"05 jan 2014"`/`"2"` vs
  `"Sun 22 Mar 2015"`/`"3"`). Если бы импортировали как глобальный атрибут документа, одно
  из двух значений тихо потерялось бы. Для KiCad — per-instance `<attr>` на каждой рамке
  (механизм, который уже был предусмотрен как «особая запись», просто оказался ОСНОВНЫМ
  путём для этого формата, не редким исключением). Другие форматы (Eagle/Altium), где
  Title Block реально один на документ, — глобальный атрибут остаётся уместным умолчанием.
- IR схемы и трассировки — **один файл** на проект (не два разных документа). Атрибуты документа
  общие для обеих частей; контекст различается префиксом имени атрибута при необходимости

## Импорт страниц источника: X, не Y (пересмотрено — было вертикальным столбцом)

Многостраничный источник (KiCad `top_level_sheets`, будущий drag-and-drop) тайлится в
единый холст **горизонтальным рядом** — первая страница слева, каждая следующая правее
предыдущей (сдвиг = сумма ширин предыдущих страниц + 0.5" зазор). Раньше был вертикальный
столбец (сдвиг по Y).

**Почему X, не Y**: направление положительной оси X — единственная координатная конвенция,
в которой KiCad/Eagle/IR совпадают. Y инвертирован между KiCad (вниз) и Eagle/IR (вверх) —
тайлинг по Y требует решить, прибавлять сдвиг или вычитать, ЗАВИСИМО от того, в какой системе
координат (KiCad raw или уже IR-инвертированной) применяется формула на данном конкретном
шаге пайплайна. Именно эта развилка стала источником реальных багов дважды подряд (см.
«KiCad: ir_rot/ir_mirror — вывод формулы» — оба пересмотра формулы поворота отчасти
случились из-за путаницы, в какой системе координат применяется сдвиг страницы). Тайлинг по
X эту развилку убирает целиком: `dx` прибавляется к сырой KiCad X-координате объекта ДО
любой Y-инверсии, единообразно, без разбора случаев.

Реализация: `kicad_project_parser.py:convert_project_full`, `dx` (было `dy`) — накапливается
по ширинам (было высотам) предыдущих страниц. Тот же принцип уже отражён в ir_schema.md
«Импорт страниц источника → тайлинг на холст» — общий механизм, не специфика только для
KiCad-пути.

## Eagle-экспорт: sheet_shift ПО X (только X, не Y) — ВОЗВРАЩЕНО 2026-07-19

Было (2026, дата утеряна): `export_schematic` вычислял `sheet_shift` (X И Y) отдельно для
каждого `<sheet>`, подгоняя рамку под `(0,0)` — чисто косметически. Убрано целиком тогда:
подгонка под квадрант — забота пользователя в Eagle, а вычисление сдвига само стало
источником бага (спутали Y-flipped IR-координату с сырой KiCad — `U6` в vimdrones получил
необъяснимо смещённый Y).

**Возвращено 2026-07-19, но ТОЛЬКО по X**, найдено на реальном тайловом проекте
(`testData/freq`, 9 тайлов, KiCad-проект с pinless-страницами → `_flatten_pinless_pages`):
IR держит один непрерывный холст с накапливающимся тайл-смещением по X (297мм+зазор на
страницу); нетронутое, оно уходит за какое-то ВНУТРЕННЕЕ предельное значение координаты в
самом Eagle — после этого порога редактор Eagle сам сбрасывает координату обратно к нулю,
рассыпая геометрию именно на дальних листах (симптом пользователя: «половина символов на
Connectors уехала», отследили на LED6 — абсолютный X там больше 2 метров).

Фикс — НЕ пересчитывать сдвиг заново (это и вызвало прошлый баг), а вычесть уже известную,
проверенную границу тайла: `frames[i][0][0]` (левый край рамки страницы, тот же bbox, что
уже используется для sheet-containment split компонентов). Y не трогаем вообще — именно Y
сжёг прошлую попытку. Реализация: единственный финальный проход по каждому `<sheet>` перед
сериализацией, сдвигает атрибуты `x`/`x1`/`x2` везде внутри него (инстансы, декоративная
геометрия, провода/метки/junction'ы, сама рамка) — не точечно на месте каждой эмиссии.

## Stray-валидация — правило хорошего тона, применяется и на ИМПОРТЕ, не только на экспорте

Найдено через реальный кейс: декоративные `polyline` (лого) далеко за пределами листа в
`testData/vimdrones.zip` тихо проходили внутрь IR, потому что stray-проверка существовала
только на экспорте в Eagle, и только для `<instance>` (см. "IR → Eagle: экспорт схемы"
ниже). Пользователь сформулировал принцип шире и строже:

- **Все компоненты должны лежать ВНУТРИ печатной рамки — иначе схему невозможно нормально
  распечатать/просмотреть.** Это не Eagle-специфичное ограничение (раньше так казалось,
  потому что только там стояла проверка) — это общее правило хорошего тона для ЛЮБОГО
  формата. Если источник (KiCad/Eagle/Altium) сам не следит за этим — Babel заставит
  пользователя быть опрятным, не молча смолчит и не подвинет геометрию сам.
- **Применяется при ИМПОРТЕ, не только при экспорте.** Раньше ловилось (если вообще
  ловилось) только в момент экспорта в Eagle, далеко от первопричины — пользователь видел
  невнятный warning в чужом редакторе вместо понятного сообщения "в файле X компонент Y
  торчит за рамку". Идеально — поймать сразу на импорте, с привязкой к исходному файлу.
- **Касается ВСЕХ объектов на холсте, не только `<instance>`.** Провод, линия, прямоугольник,
  декоративная графика, текст — что угодно. Источник этого решения — ровно тот случай с
  лого, который проверка instance-only пропустила бы и дальше, просто в другой форме.
- **Проверяется ПОЛНЫЙ bbox объекта, не одна точка.** Линия/провод, начинающийся внутри
  рамки и кончающийся за ней, — stray. Прямоугольник, частично торчащий за границу, — stray.
  Окружность — недостаточно проверить, что центр внутри: вся окружность (центр ± радиус по
  каждой оси) должна лежать внутри. Половина фигуры внутри рамки — всё равно нарушение, не
  "в основном поместилось".
- **Рассмотрена и отвергнута мягкая альтернатива** — "достаточно ХОТЯ БЫ ОДНОЙ координаты
  внутри рамки = не stray" (давала бы однозначное присвоение странице без анализа bbox).
  Отвергнута, потому что не решает, а ПЕРЕНОСИТ проблему: объект, пересекающий границу
  рамки (один конец внутри, другой — за пределами или в СОСЕДНЕЙ рамке), при таком правиле
  не падает, но и не даёт однозначного ответа, какой странице принадлежит — то, ради чего
  затевалась проверка. Решение: пересекающий объект — ВСЕГДА stray, падение, без исключений.
- **KiCad-импорт — однозначный случай, рамка уже известна структурно** (`sch.paper`, см.
  "Импорт страниц источника"/"Frame") — есть единственная рамка размера страницы, проверка
  прямолинейна: bbox каждого объекта ⊆ bbox рамки.
- **Eagle-импорт — НЕТРИВИАЛЬНЫЙ случай, требует отдельного решения.** В отличие от KiCad,
  Eagle ничего не навязывает: на одном листе может быть 0, 1 или много `<frame>`-элементов,
  в любых позициях, перекрывающихся или нет. Нет единственной "правильной" рамки, к которой
  естественно привязать проверку — нужно отдельно решить, что считать stray в этом случае
  (например: объект должен попасть ВНУТРЬ ХОТЯ БЫ ОДНОЙ рамки целиком; 0 рамок на листе —
  что тогда). **Это решение пока не принято, реализация Eagle-импорта откладывается** до
  отдельного обсуждения — see progress.md.
- Реализация (KiCad-импорт): `babel/kicad_project_parser.py` — после сборки полного списка
  геометрии страницы (instances/wires/junctions/labels) и до записи в IR, bbox-проверка
  каждого объекта против `_paper_dims_mm(sch.paper)`; hard-fail с именем файла и
  объекта/координатами при нарушении, не молчаливое исправление позиции и не дроп.

## IR → Eagle: экспорт схемы (`eagle_exporter.export_schematic`)

Первая реализация — `<schematic>` (инстансы + цепи) → полноценный `.sch` с встроенной
библиотекой, проверена на реальном многостраничном `testData/vimdrones.zip` (через
`vimdrones.swprj`).

- **Рамка → нативный Eagle `<frame>`, не `<part>`/`<instance>`.** Зеркально тому, как
  decisions.md «Импорт рамок» уже трактует Eagle-овский `<frame>` на ИМПОРТЕ — компонент с
  `<shape layer="frame-boundary">` в символе никогда не становится deviceset/part, он
  определяет границу листа и тут же из неё выбрасывается. Текст-placeholder рамки
  (`>TITLE`/`>DATE`/...) идёт в `<plain>` как обычный `<text>`, не как атрибут part'а.
- **N рамок → N Eagle `<sheet>`, разбиение по bbox.** Каждый обычный инстанс должен попасть
  ВНУТРЬ РОВНО ОДНОЙ рамки — иначе hard fail с именами stray-компонентов (decisions.md
  «Рамка — маркер для экспорта в печать»: это давно решено, просто впервые реализовано).
  Сегмент цепи проверяется так же: если его pinref'ы относятся к разным листам — hard fail
  (такого пока не встречалось, физически разнесённые провода не должны пересекать страницы).
  Без рамок вообще — один лист на всё, без `<frame>`.
- **Каждый лист перебазируется в свои собственные координаты, начинающиеся с (0,0).**
  Реальный баг, найденный по ходу: координаты IR — это один общий холст (страницы KiCad
  натилены вертикально вниз, Y становится всё более отрицательным), но Eagle-листы —
  независимые координатные пространства. Без перебазирования второй и последующие листы
  открывались бы в Eagle далеко в отрицательной области экрана (валидно по DTD, но
  неюзабельно — пользователь не увидит схему, не проскроллив). Сдвиг считается per-лист от
  bbox его рамки (без рамки — от bbox реально размещённых компонентов), применяется одинаково
  к рамке/тексту/инстансам/wire/junction/label на этом листе.
- **Библиотека встраивается заново из пула, не копируется.** `<libraries>` содержит ровно те
  symbols/devicesets/packages, что реально использованы обычными (не-рамочными) инстансами —
  через уже существующие `export_symbol`/`export_package`/`export_deviceset`, без нового кода
  конвертации геометрии.
- **`<instance footprint="...">` — какой именно footprint использован, не угадывание
  (исправлено).** Изначально `device=""` ставился всегда — оказалось реальным багом, не
  просто неполнотой: у Eagle `device=""` существует ТОЛЬКО для 0/1-footprint компонента
  (`_device_names`/`export_deviceset`'s own naming convention) — у компонента с 2+ footprint
  такого device попросту нет, реальный Eagle отверг файл (`attribute 'device' references
  undefined object ''`). Фолбэк «взять первый device» тоже оказался неверным НЕ как
  упрощение, а как порча данных: `testData/vimdrones.zip` "R6"/"R11" — это `lib_id="lbr:R"`
  (родовой резистор), но R11 — на самом деле предохранитель (`value="30A FUSE"`,
  `Footprint="...Fuseholder_Littelfuse_Nano2_154x"`), и эта информация у KiCad ЕСТЬ — per-
  instance `property "Footprint"` на каждом размещённом символе, которую парсер и так уже
  читает (чтобы собрать пул footprint'ов компонента), просто не прокидывал её ДАЛЬШЕ, на
  конкретный инстанс. Исправлено на уровне ИМПОРТА (не экспорта): новый необязательный
  атрибут `<instance footprint="...">` (ir_schema.md "Component instance") — пишется только
  когда у компонента 2+ footprint (с одним — никакой неоднозначности, как и раньше).
  Экспортёр теперь резолвит device по этому атрибуту; фолбэк на первый device остаётся
  ТОЛЬКО для случая, когда атрибута реально нет (старый/чужой IR) — с записью в лог
  импорта, не молча.
- **Слои схемы — стандартные номера Eagle** (91 Nets, 94 Symbols, 97 Info) — не из проектных
  данных (в отличие от слоёв футпринта, у которых есть `_IR_LAYER_TO_EAGLE`), поскольку у IR
  schematic-геометрии нет собственного понятия "слой" вообще, кроме как у label/text.
- Валидация: `lxml.etree.DTD('eagle.dtd').validate(...)` — оба пути (`.lbr` и `.sch`)
  подтверждены валидными напрямую по DTD, не только "не упало".
- Побочный фикс (не из этой задачи, найден по соседству): старый `export()` (library-only
  `.lbr`) создавал `<library>` без `name=` — нарушение DTD (`name` `#REQUIRED` даже для
  одиночного файла, хоть по факту он там "никем не читается"). Поправлено заодно.
- CLI-диспетчер (`eagle_exporter.py __main__`) выбирает `export`/`export_schematic` по
  РАСШИРЕНИЮ выходного файла (`.sch` → схема, иначе → библиотека), не по наличию
  `<schematic>` в IR — IR со схемой всё равно можно экспортировать как чистый пул без сцен.

## KiCad: `graphicalItems` — это НЕ только провода, `polyline` там тоже лежит

Найдено через warning'и реального Eagle при открытии `vimdrones.sch` (`invalid value
'8127.15' for attribute 'x1'` и подобные — координаты далеко за пределами разумной схемы).
Причина: kiutils кладёт в один список `Schematic.graphicalItems` ТРИ разных KiCad-токена —
`(wire)` (настоящий провод), `(bus)` (шина — не моделируется, отдельный hard-fail на
`sch.busEntries` уже был) и **`(polyline)`** (инструмент "Graphic Lines" — чисто
декоративная графика, без всякой электрики, KiCad использует её для произвольных рисунков/
лого прямо на схеме). Код безусловно трактовал каждый элемент списка как провод.

- Подтверждено реальными данными: `testData/vimdrones.zip`'s `vimdrones_esc_development_
  board.kicad_sch` содержит 83 `PolyLine`-объекта (видно по `type(w).__name__`, поскольку
  kiutils различает их КЛАССОМ — `Connection(type='wire')` vs `PolyLine`, не общим полем) —
  координаты этого рисунка лежат далеко за пределами реальной схемы (~8000-8100мм против
  обычных 0-300мм), отсюда и переполнение Eagle-координат при экспорте.
  Маскировалось раньше: эти 83 полилинии превращались в одну гигантскую `<net>` с 542+
  крошечными `<line>` сегментами (видно было ещё на этапе самой первой проверки кросс-
  страничной связности в этой сессии — net "N$1" — но тогда это не вызвало подозрений,
  посчитали обычным художеством KiCad-экспорта проводов).
- **Решение: дроп с записью в лог импорта**, не добавление нового IR-примитива для
  декоративной графики на холсте схемы — `<schematic>` в ir_schema.md документирован как
  «только instance/net», заводить под это отдельный механизм ради лого на одном тестовом
  проекте — overkill (пользователь выбрал этот вариант явно, не как временную затычку).
- Реализация: `babel/kicad_project_parser.py` — проверка `getattr(w, 'type', None) !=
  'wire'` в начале цикла по `sch.graphicalItems`, до накопления `wires`/`wire_width`.
- Проверено на `testData/vimdrones.zip`: 132 цепи → 63 (фиктивная "гигацепь" исчезла),
  `.sch` валиден по `eagle.dtd`, диапазон координат `<wire>` в выходном файле — `[-73.66,
  188.41]` мм (реалистичный для схемы), вместо прежних тысяч.

## IR `direction="nc"` — заведён ради совместимости с legacy ERC, не родное понятие IR

**Эта запись ЗАМЕНЯЕТ более раннее решение** ("NC сливается в `pas`, отдельный `direction`
не нужен") — пересмотрено после того, как пользователь показал вырезку из мануала Eagle
(`PIN_DIRECTION.png`, раздел 8.2 "Direction"): ERC Eagle **реально проверяет**, что на пине
типа `nc` нет цепи — в отличие от `pas`, где никаких специальных проверок нет вообще. Это
не просто документная подсказка, это активно используемое инструментом различие — терять
его при round-trip означало бы, что экспортированный обратно в KiCad/Eagle файл либо
неправильно молчит про реально подозрительные неподключённые `pas`-пины, либо (что хуже)
получает заведомо лишние ERC-ошибки на пинах, которые производитель явно велел не трогать.

- **`direction="nc"` добавлен в IR** (`ir_schema.md`) — явно отмечен как существующий
  ИСКЛЮЧИТЕЛЬНО ради совместимости с этой убогой legacy-механикой KiCad/Eagle, не как
  родное для IR понятие связности (IR сам по себе никогда не отличал бы "пин без сети" от
  "пин, которому положено быть без сети" — это разделение существует только в головах ERC
  конкретных инструментов).
- **KiCad: скрытый (`hide yes`) `no_connect`-пин не импортируется вовсе** — визуально
  скрытый пин (весь стержень, не только подпись — см. следующую секцию про сам `hide`-баг)
  неотличим от его полного отсутствия, создавать для него `<pin>` нет смысла.
  **Видимый `no_connect`-пин импортируется как обычный пин** с `direction="nc"` — реальные
  данные (`FD6288Q`/`SIM4X32`, 160 пинов) показывают, что видимые NC-пины — частый, не
  краевой случай (KLC S4.5 разрешает их прятать только когда это не раздувает символ).
- **Eagle: `visible` НЕ имеет отношения к этому различию вообще.** Уточнение пользователя:
  Eagle-овский `visible` (`off`/`pin`/`pad`/`both`) управляет ТОЛЬКО видимостью имени пина и
  имени пада — сам стержень пина Eagle рисует всегда, независимо от `visible`. Поэтому
  Eagle-импорт (`eagle_parser.py`) НЕ применяет "скрытый → не импортировать" — `nc`-пин
  импортируется всегда, его `pinvis`/`padvis` читаются из `visible` точно так же, как у
  любого другого direction, без особого случая. (Раньше код вообще ДРОПАЛ Eagle `nc`-пины
  безусловно — `DIR_MAP['nc'] = None` → `continue` — отдельный, независимый баг, попутно
  исправлен.)
- **Altium: своего электрического типа "Not Connected" попросту НЕ существует** —
  проверено напрямую по `altium_monkey`'s `PinElectrical`/`PIN_ELECTRICAL_NAMES` (8
  значений: Input/IO/Output/Open Collector/Passive/Hi-Z/Open Emitter/Power, ни одного
  NC-эквивалента). Предыдущая запись `'Not Connected': 'pas'` в `_ELECTRICAL`
  (`altium_parser.py`) была МЁРТВЫМ кодом — такая строка никогда не приходит от реального
  Altium-файла, `pin.electrical_name` физически не может её вернуть. Решение: на ЭКСПОРТ
  в Altium IR `nc` падает в `PASSIVE` через обычный dict-fallback (без специальной записи —
  там и так нет на что мапить), имя пина (`"NC"` или как назвал автор) проходит как обычный
  текст. Это осознанная, неустранимая потеря ERC-семантики при экспорте в Altium — у формата
  просто нет соответствующего слота, и это не повод изобретать несуществующее.
- Если КОНКРЕТНЫЙ KiCad-пин уже омичен автором библиотеки (KLC — пин гарантированно никогда
  не подключается И не раздувает символ) — у нас нет повода создавать то, чего нет в
  источнике: footprint-пад без pin-mapping остаётся легальным `<connect>`-less падом и в
  Eagle (`eagle.dtd`: `<connects>` — `(connect)*`, ноль или больше), и в IR.

**Побочный баг, найденный сразу при первой попытке открыть результат в реальном Eagle**
(`invalid/missing attribute 'pin' in tag <connect>`): фильтр "скрытый no_connect не
импортируется" был добавлен ТОЛЬКО в `_add_unit_geometry` (где рисуется символ) — но
`named_pins` (тот же список) отдельно потребляют `_pin_mapping` (строит `<map>`/`<connect>`)
и `kicad_project_parser.py`'s позиционный `zip(named_pins, sym_el.findall('pin'))` для
расстановки пинов на схеме. В результате на скрытый, не нарисованный `<pin>` всё равно
ссылался `<connect pin="NC">` — Eagle совершенно справедливо отказывался открывать файл
(пада без пина не бывает). **Исправлено в одной точке истины — `_named_pins`** (а не в
каждом потребителе по отдельности): пин фильтруется там же, где формируется список,
который ВСЕ остальные части кода молча считают согласованным с тем, что реально нарисовано.

## KiCad: невидимый ПИН (не только его имя/номер) — четвёртый случай той же kiutils-дыры

Пользователь явно сформулировал правило: если у пина в KiCad стоит "не отображать" (весь
пин целиком, не только подпись), при импорте всё равно копируем пин (контакт/связность не
теряем), но ставим `pinvis="0"` и `padvis="0"` — визуально пин должен остаться невидимым и
у нас, как в источнике.

Код уже ПЫТАЛСЯ это делать (`name_hidden`/`num_hidden` уже включали `or pin.hide`) — но
оказалось, что `pin.hide` **всегда `False`**, независимо от реального содержимого файла.
Причина — ровно тот же баг kiutils 1.4.8, что уже исправляли трижды для других токенов
(`Property.hide`, `pin_numbers`/`pin_names` hide): `SymbolPin.from_sexpr` распознаёт только
ГОЛЫЙ атом `hide` (`item == 'hide'`), а реальный KiCad пишет `(hide yes)` — вложенный список
`['hide', 'yes']`, который этой проверке никогда не равен голой строке `'hide'`. Четвёртое
независимое подтверждение одной и той же категории дыры, не новая.

- **Подтверждено прямым тестом**, не выводом по коду: `testData/vimdrones/lbr.kicad_sym`,
  `AP2112K-3.3` — реальный `(pin ... (hide yes) ... (name "NC" ...))`, `pin.hide` читался
  `False` до фикса, `True` после.
- **Осторожность с ground truth**: первая найденная пара "подозрительных" совпадений
  (`USB_C_Receptacle_USB2.0_14P`'s повторяющиеся GND/VBUS) оказалась НЕ примером этого бага,
  а стандартным stacked-pin случаем (несколько физических контактов одной логической цепи,
  KiCad показывает только первый, остальные `(hide yes)` намеренно) — другая, уже отдельно
  решённая история (decisions.md "Stacked pins"). Нашёл реальный, чистый одно-пиновый case
  (`AP2112K-3.3`) отдельно, не спутал две разные причины одного и того же файлового токена.
- **Фикс — на уровне `_read_symbol_lib`** (общая точка для обоих путей импорта — что
  библиотечного, что проектного, поскольку `_resolve_symbol` тоже идёт через эту функцию),
  не дублируется в `kicad_project_parser.py`.
- Привязка флагов к `unit.pins` — **по позиции, ДО `_collapse_stacked_pins`**: тот сворачивает
  несколько физических падов одной логической цепи в одного представителя, после чего
  длины списков (флагов и `unit.pins`) разойдутся и привязка молча не сработает (поймано
  именно так на первом прогоне — flags подсчитаны верно, но `len(flags) != len(unit.pins)`
  после сворачивания, тихий no-op). Реконструкция имени raw-узла — `f'{entryName}_{unitId}_
  {styleId}'`, подтверждена побайтово идентичной тому, что кладёт в файл сам KiCad.
- `(hide yes)`, вложенный внутрь `name`/`number` подсписка пина — это ДРУГОЙ, уже отдельно
  обрабатываемый случай (видимость только подписи, `_pin_label_hidden`), не видимость
  всего пина — проверка нерекурсивная, смотрит только прямых детей `(pin ...)`, не уходит
  внутрь `name`/`number`.

## IR → Eagle: `>VALUE` на footprint — всегда `tValues` (27), `>NAME` не трогаем

По аналогии с тем, что у символа `>VALUE`-placeholder уже безусловно идёт на слой 96
(`_text_layer`), на footprint'е та же подстановка должна идти на `tValues` (27), а не на
тот IR-слой, где текст физически лежит (`fab`/`silk_top`/...). Только `>VALUE` — `>NAME` на
footprint решено НЕ трогать, остаётся на исходном слое (решение пользователя, не пытаемся
симметрировать обе подстановки сразу).

- **Подтверждено реальными данными**: `>VALUE` на footprint'е ВСЕГДА лежит в IR-слое `fab` —
  нейтральном, безсторонном (у пула footprint'а нет понятия top/bottom вообще, оно
  появляется только при размещении инстанса на плате с возможным mirror) — проверено по
  `outputs/vimdrones.swprj`, десятки футпринтов, без единого исключения. Значит присвоение
  `tValues` (27) безусловное, не нужно решать top/bottom (`tValues`/`bValues`) на этом
  этапе — тот же резон, что у символьного `>VALUE`→96 (тоже безусловно, без bValue-аналога).
- Реализация: `babel/eagle_exporter.py:export_package` — `<text>` branch, проверка
  буквального текста `== '>VALUE'` перед использованием `eagle_num` (слоя-бакета).

**Эта запись ЗАМЕНЯЕТ более раннее решение** ("пад без меди → дроп целиком"). Та версия
была написана сразу после первого открытия ошибки в Eagle, до того как стало ясно, что
KiCad вообще-то совершенно официально разрешает пады без меди (UI: pad type — отдельная
ось от pad layers, видно непосредственно в Pad Properties), и что то же самое (`stop`/
`cream`/`thermals` как явные булевы переключатели автоматики, с возможностью нарисовать
вскрытие/апертуру руками вместо них) уже десятилетиями есть и в Eagle. Пользователь явно
сформулировал: "у меня фактически ДВА способа сделать одно и то же, просто первый
несколько более автоматический" — модель ниже следует ЭТОМУ принципу, не реагирует точечно
на один найденный баг.

### Три булевых свойства на паде — по образцу Eagle, не KiCad

`<smd>`/`<pad>` получили `thermals`/`stopmask`/`paste` (Eagle: `thermals`/`stop`/`cream`,
все `%Bool` с умолчанием `"yes"` — `eagle.dtd`). Названия — НЕ калька с Eagle: `cream`
переименован в `paste` (это паяльная ПАСТА, не крем — буквальный перевод Eagle-термина
вводил в заблуждение), `stop` — в `stopmask` (тоже Eagle-жаргон, "stop" значит "solder
stop mask", само слово ничего не говорит без контекста). Только включают/выключают
АВТОМАТИЧЕСКУЮ генерацию редактором-приёмником; как считается размер вскрытия (margin,
design rules платы) — IR не описывает.

Если автоматики недостаточно — выключить флаг и нарисовать форму вручную: на сторону IR
добавлены слои `mask_top`/`mask_bottom` (паяльная маска — раньше не было вообще никакого
слоя для неё) и `paste_top`/`paste_bottom` (переименованные `cream_top`/`cream_bottom`).

### KiCad: чтение technical layers пада, не отдельного свойства

KiCad не хранит `paste`/`stopmask` как явные свойства — вместо этого технические слои
пада (`F.Paste`/`F.Mask` и т.п. в списке `pad.layers`). На импорте МЕДНОГО smd-пада:
`F.Paste`/`*.Paste` в слоях → `paste="1"` (т.е. умолчание IR, атрибут не пишется),
отсутствие → `paste="0"`; аналогично `F.Mask`/`*.Mask` → `stopmask`. **Умолчание при
ОТСУТСТВИИ слоя — `0`, не умолчание IR (`1`)** — раз KiCad явно перечисляет слои, молчание
о слое означает намеренное "не генерировать", а не "не было повода сказать". Остальные
technical layers пада (`clearance`/`zone_connect`/`thermal_bridge_angle` и т.п.) игнорируются
полностью — не имеют отношения к paste/stopmask и не хранятся в IR вообще.

### Aperture-пад (KiCad: "SMD Aperture") — не `<smd>`, а `<shape>` на тех же слоях

Пад без `*.Cu` в layers вообще (медь не выбрана) — это не электрический пад, и в самом
KiCad у него на это нет даже отдельного типа в файле (тот же `smd`, просто без меди в
layers — UI называет это "SMD Aperture" pad type чисто на уровне редактора, не формата
файла). Импортируется как `<shape>` (по форме пада, `outline="0"`, заполнено) — ОДИН shape
на каждый включённый у него технический слой (`F.Paste` → фигура на `paste_top`, `F.Mask`
→ фигура на `mask_top`, оба сразу → две перекрывающиеся фигуры на разных слоях). Если ни
один технический слой не выбран вообще — рисовать негде, пад дропается с записью в лог
импорта (см. ниже).

Подтверждено реальными данными (`testData/vimdrones.zip`, три футпринта `*-1EP` QFN/DFN/
HVSON с открытым теплоотводом): несколько мелких безномерных падов с одним `F.Paste` в
layers (БЕЗ меди) поверх границ настоящего медного exposed-pad (`pad "9"`, `F.Cu`+
`F.Mask`, `pad_prop_heatsink`) — чтобы паста на трафарете печаталась несколькими
кусочками, не одним сплошным пятном. После фикса: пад "9" получает `paste="0"`
(автоматика выключена явно), а 4 paste-фрагмента становятся обычными `<shape>` на
`paste_top` → экспортируются в Eagle как `<rectangle layer="31">`, не как `<smd>`.

### Форма пада — только `<smd>`-точная геометрия проходит без потерь

`circular`/`oval`/`rectangular`/`rounded rectangle` (последнее: `roundness` =
`roundrectRatio × 200`, шкала против `min(width,height)`) ложатся в `<smd>` точно. Всё
остальное — `trapezoid`, `custom` (произвольный полигон), **chamfered rectangle** и
**chamfered with other corners rounded** (на уровне файла — ВНИМАНИЕ: это тот же
`shape == "roundrect"`, что у обычного скруглённого прямоугольника, отличается только
непустым `chamfer`/`chamferRatio` — раньше тихо обрабатывалось как чистый roundrect,
теряя сам факт скоса БЕЗ единого сигнала) — заменяется на обычный прямоугольник
`width`×`height`, со строкой в лог импорта. Контакт (номер, медь, pin-mapping) сохраняется
полностью — теряется только точная форма, не сам факт пада.

Реализация: `babel/kicad_parser.py` — `_smd_shape_exact()` (точное совпадение с IR-моделью
`<smd>`, включая проверку `chamfer`), классификация по `*.Cu` в начале цикла по `fp.pads`,
до построения `pad_name_groups`/`name` (aperture-пады не отъедают порядковые номера у
настоящих безномерных МЕХАНИЧЕСКИХ падов на том же футпринте, `testData/video/sim72.
kicad_mod`). Проверка слоя для классификации медь/aperture — по суффиксу `.Cu`, не по
буквальному `F.Cu`/`B.Cu`: throughhole-пады используют групповую маску `"*.Cu"`
(`PinHeader_1x04...kicad_mod`, `2P_ESC_BAT_PAD...kicad_mod` в том же `vimdrones.zip`).

### Лог импорта — новый общий механизм

`babel/import_log.py` — module-level буфер: `log(*parts)` печатает (как и раньше) И
запоминает строку; `write(output_path)` сбрасывает буфер в `<output>.import.log` при
завершении конвертации (`kicad_parser.convert`, `kicad_project_parser.convert_project`/
`convert_project_full`). Не замена консольных предупреждений — то же самое, плюс файл,
который можно grep/diff'ить при batch/headless прогоне без повторного чтения консоли.
Существующее предупреждение про oval/slotted drill переведено на этот механизм заодно
(было голым `print`, теряло то же самое в headless-режиме).

### `${REFERENCE}`/`${VALUE}` на `fp_text user` — тоже placeholder, не буквальный текст

Найдено пользователем визуально (текст `${REFERENCE}` лез наружу на разных слоях экспорта).
Причина: KiCad-текстовые-переменные `${REFERENCE}`/`${VALUE}` могут сидеть не только на
выделенном `fp_text reference`/`value` (которые код уже превращал в `>NAME`/`>VALUE`), но
и на ПРОСТОМ декоративном `fp_text user "${REFERENCE}"` — отдельная копия рефдеза/значения
на слое документации (обычно `F.Fab`), не связанная с настоящим современным
`(property "Reference"...)` токеном того же футпринта. Все три механизма (`fp_text
reference/value`, `(property ...)`, `fp_text user` с переменной) подтверждённо
сосуществуют на одном футпринте (`testData/vimdrones.zip`, `HVSON-8-1EP...`: настоящий
`Reference`-property И декоративный `fp_text user "${REFERENCE}"` на F.Fab одновременно).

- Решение: `fp_text user`, чей текст РОВНО `${REFERENCE}`/`${VALUE}` (без учёта регистра/
  пробелов) — тоже становится `>NAME`/`>VALUE`, а не буквальным текстом.
- **Поворот — `_rot_fp` (обычный), не `_rot_fp_placeholder`.** Соблазн применить ту же
  asymmetric-инверсию, что у выделенного `reference`/`value` типа, был — но
  `_rot_fp_placeholder` калибрована конкретно под `kicad_exporter._fp_text_style`
  (обратная связь только для ВЫДЕЛЕННОГО типа), не проверена для `fp_text user`. Решено
  не переносить непроверенное правило по аналогии — только смысл текста меняется
  (placeholder вместо буквальной переменной), геометрия/поворот — как у любого другого
  декоративного текста на этом слое.
- Реализация: `babel/kicad_parser.py`, ветка `FpText` — `item.type == 'user'` с текстом
  `${REFERENCE}`/`${VALUE}` отдельной веткой перед общим fallback (буквальный текст).

## KiCad: multi-gate компоненты на канвасе — реализовано (было: hard-skip)

**IR-модель дополнена** (ir_schema.md "Размещение многорежимного компонента"): один
физический многорежимный компонент (`<component>` с `<gate>`) на реальной схеме размещается
НЕ одним `<instance>`, а несколькими — по одному на каждый размещённый gate, с ОДНИМ и тем
же `name` (designator), но разным новым атрибутом `gate`. Раньше `<instance>` вообще не
имел понятия gate — модель неявно предполагала, что весь multi-gate компонент кладётся
одним блоком (см. старую, полуиспользуемую механику `<gate x y>` — смещение внутри пула,
не размещение на канвасе), что не совпадает с тем, как реально работает KiCad (и Eagle):
каждый gate стоит в своей точке схемы, рядом с тем, что он физически обслуживает
(классический пример — счетверённый буфер/вентиль, 4 разных места на схеме).

**KiCad-специфика:** placed `SchematicSymbol` несёт `.unit` (1,2,3,4...) — какой именно
KiCad-unit размещён ЭТИМ конкретным объектом (у одного designator несколько таких объектов,
по одному на unit). Library-side `_group_gates` (`kicad_parser.py`) уже назначает буквы
gate по отсортированным real unit id (`sorted(unit != 0)`, `A` = первый по порядку и т.д.)
при построении пула — но раньше это знание не было доступно на canvas-стороне парсера.
Новая функция **`_unit_id_to_gate_letter(symbol)`** (`kicad_parser.py`) независимо
воспроизводит ТУ ЖЕ сортировку по имени библиотечного шаблона символа, отдавая словарь
`{unit_id: letter}` — используется в `kicad_project_parser.py` для сопоставления
`sym.unit` конкретного placed-объекта с нужным `<gate>` компонента. Отдельная функция, не
выведенная из `_group_gates` напрямую — чтобы не рисковать сломать уже проверенную
геометрическую логику построения пула ради добавления второй, более узкой задачи (letter
placed instance'а никогда не нуждается в геометрии, только в имени).

**Что изменилось в `kicad_project_parser.py`:**
- Убран `n_skipped_multi_unit`/`n_skipped_multi_gate` skip для реального multi-gate случая
  (счётчики остались в коде для действительно нераспознанных случаев — `sym.unit`, не
  найденный в словаре, например `0`/`None` на символе, у которого library-side ЕСТЬ
  реальные gate — по опыту такого не бывает у корректного KiCad-файла, но не hard-fail,
  просто skip с логом, раз это не должно случаться).
- Имя пина для `pin_points`/`<net><pinref>` получает префикс `{letter}.` — та же форма,
  что уже использовалась в `<pin-mapping>` (`A.OUT` и т.п.), теперь применена и к схемной
  связности, не только к footprint pin-mapping.
- `<instance>` получает новый атрибут `gate=` только для multi-gate размещений (однорежимные
  — без него, как и раньше, никакой неоднозначности).
- Per-instance Value-override пишется ТОЛЬКО на gate `'A'` (или `None` для однорежимных) —
  Value физически одно на весь чип, писать его на КАЖДОМ из 4 instance-ов было бы чистым
  дублированием одной и той же строки (KiCad хранит одинаковое Value Property на каждом
  placed unit одного designator — подтверждено на `74LS125`/`U2`, `testData/pic_programmer.
  zip`: все 4 unit несут `Value="74HC125"`).

**Проверено** на реальных данных (`testData/pic_programmer.zip`, `U2` = `74LS125`,
счетверённый буфер, 4 gate A/B/C/D на разных местах схемы) — с временно вырезанным
`(sheet)`-символом того же файла (сам файл содержит настоящую иерархию на другой
странице, никак не связанную с U2, но `_detect_pages` hard-fail'ит на любую иерархию
в файле целиком, что мешало изолированной проверке — не продакшн-обход, только для
локальной валидации этой конкретной правки). `pin_points` для `U2` вышли верно: 20 точек
(5 пинов × 4 gate), разные координаты для каждого gate, правильные префиксы `A./B./C./D.`,
VCC/GND (common unit-0 body) корректно смёржены в КАЖДЫЙ gate.

Реализация: `babel/kicad_parser.py:_unit_id_to_gate_letter`, `babel/kicad_project_parser.py`
(основной цикл `for sym in sch.schematicSymbols`, вывод `<instance>`).

### Проверка на чистом тестовом проекте (`testData/multigate`) — реальный официальный KiCad-символ, "power gate" не 0

Пользователь предоставил отдельный тестовый проект (`testData/multigate`, без иерархии) с
официальным KiCad-библиотечным символом `74AHC04` (гекс-инвертор) — полезнее для проверки,
чем обходной `pic_programmer.zip`, и вскрыл предположение, которое чуть не привело к
ЛОЖНОМУ фиксу: у `74AHC04` "общий" (power) unit пронумерован **7**, не **0** (units 1-6 —
шесть логических инверторов A-F, unit 7 — VCC/GND). Изначально принято за баг
(`_group_gates`'s комментарий говорит про unit 0 как "common to all units" — показалось,
что unit 7 должен был слиться в остальные 6, а не стать отдельным седьмым gate). **Это
неверная интерпретация, не баг**: официальный KLC (Kicad Library Conventions, `S3.8 Multi
unit symbols`) НЕ фиксирует конкретный номер для unit с общими power-пинами — требует лишь,
чтобы он существовал как отдельный unit, без предписания его id. У `74AHC04` он оказался
последним по порядку (7), а не первым/нулевым — и это ПОЛНОПРАВНЫЙ gate ('G'), такой же,
как остальные 6, просто несущий power pins вместо логики. `_group_gates`/
`_unit_id_to_gate_letter` уже (случайно) обрабатывали этот случай верно — letter назначается
по ОТСОРТИРОВАННОМУ списку реальных unit id, независимо от их абсолютных значений, так что
unit 7 корректно стал последней буквой (G), не потерялся. Диагностика подтвердила: все 7
`<instance>` (A-F + G) создавались верно с самого начала — ложная тревога была вызвана
невнимательным чтением собственного отладочного вывода (7 инстансов в списке, gate='G'
просто не сразу бросился в глаза), не реальным отсутствием данных.

**Побочная находка (не связана с multi-gate)**: `testData/multigate/sym-lib-table`
изначально был пуст (`(sym_lib_table (version 7))`, ни одной `lib`-записи), хотя
`multigate.kicad_sym` физически лежит в корне проекта — недосмотр при подготовке тестовых
данных, не намеренная проверка. Добавлена запись `(lib (name "multigate") ... (uri
"${KIPRJMOD}/multigate.kicad_sym"))`, по аналогии с уже настроенным `fp-lib-table` того же
проекта.

## Eagle-экспорт multi-gate: `<instance gate="...">`, разбор `GATE.pin` в `<pinref>`

`eagle_exporter.py:export_schematic` до этой правки ВСЕГДА писал `gate='G$1'` — и на
`<instance>`, и на `<pinref>` — полностью игнорируя новый IR-атрибут `<instance gate="...">`
и `GATE.pin`-префикс в `<pinref pin="...">` (оба введены правкой парсера выше). Для
однорежимных компонентов это давало верный (единственно возможный) результат случайно; для
multi-gate — либо создало бы несколько Eagle `<instance gate="G$1">` одной детали
(некорректно — Eagle ожидает разные gate на разных instance одной part), либо (для
`<pinref>`) сослалось бы на несуществующий пин `"A.OUT"` вместо `pin="OUT" gate="A"`.

- **`<instance>`**: `gate=inst_el.get('gate') or 'G$1'` — читает IR-атрибут напрямую,
  fallback на `'G$1'` только для однорежимных (у которых атрибута нет вовсе, ir_schema.md
  "Component instance" — `gate` пишется в IR только при реальной неоднозначности).
- **`<pinref>`**: `raw_pin.partition('.')` — та же логика разбора `GATE.pin`, что УЖЕ
  существовала для `<connect>` (footprint pin-mapping, `export_deviceset`) — переиспользован
  тот же паттерн (`gname, _, pname = pin.partition('.')`), не изобретён заново. Пин без
  точки (однорежимный компонент, IR pin-имена — чистые идентификаторы, точку не содержат)
  → `gate='G$1'` тем же fallback'ом.

**Проверено на `testData/multigate`** (см. выше, `74AHC04` 7-gate hex-inverter + power-gate)
— полный round-trip KiCad → `.swprj` → `.sch`: все 7 `<instance gate="...">` с верными
координатами, все `<pinref gate="..." pin="...">` корректно разделены (включая power-gate
`G`: `pin="GND"`/`pin="VCC"`, без точки в самих этих pin-именах — совпадение с обычным
"нет точки" fallback'ом было бы ложным срабатыванием, но `gate` для этих pinref'ов реально
пришёл из `GATE.pin`-разбора, не из fallback, т.к. IR-pin-имя было `"G.GND"`/`"G.VCC"`),
`<deviceset><gates>` содержит все 7 gate. Файл подтверждён валидным напрямую по
`eagle.dtd` (`lxml.etree.DTD(...).validate(...)`), не только "не упало".

Реализация: `babel/eagle_exporter.py:export_schematic` (оба места — блок `part_insts` и
блок `<pinref>` внутри `<net><segment>`).

**Побочный баг, найденный РЕАЛЬНЫМ Eagle, не DTD-валидацией — тот же класс "тест не может
поймать то, что не проверяет", что уже встречался в этой сессии дважды на поворотах.**
"Файл валиден по `eagle.dtd`" (см. выше) — правда, но не полная: DTD требует `<parts>` =
`(part+)`, только структуру, БЕЗ уникальности `name` — дубликат `<part name="U1">` (один
на каждый gate-instance, а не один на designator) структурно легален по DTD, реальный Eagle
при открытии отверг его отдельным семантическим правилом ("redefinition of name 'U1' in tag
<part>"), которое DTD не выражает и не может выразить (XML DTD не умеет ID-уникальность
для произвольного атрибута без объявления его как `#IMPLIED ID`, а `name` здесь — обычная
`CDATA` строка). **Причина**: `<part>` — деталь ФИЗИЧЕСКОГО компонента (одна на designator,
Eagle-конвенция), `<instance>` — размещение (несколько на designator у multi-gate) — экспорт
раньше строил `<part>` в цикле ПО `<instance>`, не по уникальному designator, так что
multi-gate компонент получал N дублей одного `<part>`. Исправлено: `seen_parts` set,
`<part>` создаётся только на первой встреченной instance каждого designator.
Однорежимные компоненты (1 instance = 1 designator) везение не различало эту ошибку от
верного кода — баг был невидим до появления реального multi-gate теста.
**Урок**: "прошло DTD-валидацию" ≠ "откроется в реальном приложении" — DTD проверяет
СТРУКТУРУ документа, не семантические инварианты (уникальность имён, ссылочная
целостность за пределами `ID`/`IDREF`), даже когда конкретный формат такие инварианты
реально требует.

## KiCad flat multi-page: `top_level_sheets`, не sheet-символ (пересмотрено)

**Эта запись ПЕРЕСМАТРИВАЕТ более раннюю гипотезу** (была: «sheet, использованный ровно
один раз — это просто страница, безопасно разворачивать»; основана на `testData/
pic_programmer.zip`, где такой паттерн встретился первым). Пользователь, поразмыслив,
решил: **иерархию мы не флэттим вообще, ни при каких условиях** — а проверка на
`testData/vimdrones.zip` (2 листа схемы) сразу же показала, что для этого есть веская
причина: у KiCad оказался **отдельный, однозначный механизм** «просто ещё страница»,
который не пересекается со sheet-символом вообще, так что считать инстансы было не нужно
с самого начала — это было решение по неполной картине, не окончательное архитектурное
решение.

- **Реальный механизм — `.kicad_pro`: `"schematic"."top_level_sheets"`.** Список из 2+
  записей `{filename, name, uuid}` — каждая ссылается на ПОЛНОСТЬЮ независимый корневой
  файл схемы (`sheet_instances` с `path "/"`, не вложен ни во что), просто с разными
  номерами страниц (`page "1"`/`page "2"`...). Подтверждено на `testData/vimdrones.zip`:
  ноль `(sheet)`-символов и `hierarchical_label` в ОБОИХ файлах — структурно их там вообще
  нет, не «использованы один раз», а отсутствуют как класс
- **Связь между страницами — обычный `global_label`, не sheet-pin.** Подтверждено: 142
  `global_label`, 0 `label` (локальных) в обоих файлах — логично: оба листа top-level, по
  модели Scope label (ir_schema.md) там и так нет смысла различать global/local. Никакого
  нового механизма связности — `global_label` уже фидится в `label_points`, как обычная
  метка, и `by_name`-группировка `_build_nets` сводит совпадающие имена с разных страниц
  сама, без единой новой строчки в connectivity engine
- **`(sheet)`-символ теперь ВСЕГДА hard reject, независимо от числа инстансов.** Раз
  настоящий механизм «просто страница» существует и однозначен, у sheet-символа больше нет
  ambiguous-применения, которое нужно было бы разрешать подсчётом — он значит ТОЛЬКО
  настоящую иерархию/модуль, и мы её не флэттим (progress.md «Отложено» п.5/п.10), какой бы
  тривиальной она не казалась. *(Дополнено позже: hard reject снят для глубины 1 — sheet
  теперь конвертируется в IR `<module>`, см. «KiCad `(sheet)` → IR `<module>` — реализовано»
  ниже; вывод этой записи не изменился — sheet означает только модуль, и глубина ≥2
  по-прежнему hard reject.)*
- **Тайлинг — по-прежнему по реальному размеру бумаги, не по bbox** (это решение не
  поменялось, не зависело от способа детекта страниц)
- Реализация: `babel/kicad_project_parser.py:_detect_pages` (читает `.kicad_pro` напрямую,
  не обходит `(sheet)`), `_paper_dims_mm`/`_build_frame_component` (синтез рамки, без
  изменений), основной цикл в `convert_project_full` (sheet-pin-специфичный код удалён —
  мёртвый, раз `(sheet)` теперь всегда отсутствует на успешном пути)

**Побочный баг, найденный перед началом работы над Eagle-экспортом схемы (не из-за смены
модели детекта страниц — баг был и в первой версии тоже): `_build_frame_component`
задвоила центр рамки.** Локальная геометрия `<shape>` стояла в `(width/2, -height/2)`
(центр относительно угла), А ТАКЖЕ инстанс ставился в `(width/2, -(height/2+dy))` (тоже
полагая, что это центр) — итоговая (instance + local, чистая трансляция при rot=0) позиция
получала смещение ДВАЖДЫ. Поймано не визуально, а прямым вычислением полной композиции
(`inst.x+shape.x`, `inst.y+shape.y`) — то, что раньше проверялось «на глаз» по сырому
`instance.y`, совпадало с ожидаемым числом случайно (центр страницы и его половина
визуально близки), реальная рамка стояла со сдвигом на целый `(width/2, -height/2)`.
Исправлено: локальная геометрия `<shape>` теперь в `(0,0)` (origin символа = центр рамки,
не угол) — ровно то, что уже представляет `x/y` инстанса, дублирования не остаётся.
Проверено на `testData/vimdrones.zip`: `FRAME1` → абсолютный прямоугольник `X:[0,297000]
Y:[-210000,0]`, `FRAME2` → `X:[0,297000] Y:[-432700,-222700]` — обе ровно по размеру
страницы, зазор между ними точно 12700µm (0.5"), весь реальный контент лежит внутри.

## Глубина иерархии схемы — ровно 1 уровень (не рекурсивно, сознательно)
- Решение принято после обсуждения, не архитектурное ограничение по лени — реальная техническая причина
- **Designator-offset перестаёт работать на 2+ уровнях.** Трюк "инстанс модуля N → офсет +100N" даёт
  читаемое `R101/R201/R301` ↔ `R1` в схеме ровно при ОДНОЙ оси повторения. При двух осях (инстанс
  внешнего × инстанс внутреннего модуля) офсет становится композитным (`outer*1000+inner*100+N`) —
  технически возможно, но нечитаемо на сборочном чертеже
- **Межпроектное повторное использование — это НЕ иерархия.** Решается импортом-как-копией (без
  обратной ссылки на исходник), как в Eagle. Живая ссылка между независимыми проектами вредна:
  требования разойдутся, а обновление "из источника" будет затирать локальную доработку
- **Группировка компонентов для компоновки платы — это НЕ повод для иерархии.** Rooms (см. ниже)
  уже не привязаны к иерархии схемы; группировка решается маркерами/группами, не вложенностью листов
- Единственный легитимный сценарий вложенности — многоканальная схема (повтор одного блока N раз
  внутри одного проекта), и для него 1 уровень достаточен и единственно читаем
- **Импорт исходника с глубиной >1 — жёсткий отказ, не флэттинг.** Это НЕ то же самое, что
  multi-gate flatten в KiCad-экспортёре (потеря только визуала, нетлист остаётся корректным) —
  тихое сплющивание вложенности рискует тихо ПОРТИТЬ связность (две разные локальные метки с
  одинаковым именем в разных инстансах вложенного модуля слипнутся в одну цепь после сплющивания).
  Принцип: конвертируем хорошо и предсказуемо, или не конвертируем вообще — никогда не угадываем
  там, где ошибка может незаметно изменить схему
- **Контраргумент "иерархия даёт структурную схему бесплатно" рассмотрен и отклонён.** Это
  единственный реальный плюс многоуровневой иерархии помимо многоканальности — но накладные
  расходы на оформление схемы листами сопоставимы (или выше), чем просто нарисовать структурную
  схему отдельным документом руками. Единственный профит многоуровневого подхода — единый источник
  истины (структурная схема не может рассинхронизироваться с реализацией) — слишком мал, чтобы
  оправдать рост сложности
- Назначение референсов многоканальной схемы — особый случай схемного редактора

## Net class: цепь модуля, выходящая через порт, отдаёт И ИМЯ, И КЛАСС родителю

Спека — ir_schema.md «Net class»; реализовано (KiCad `net_settings` → `<classes>` +
`class=` на цепях, Eagle-экспорт с номерами классов). Ключевые решения пользователя:

- **Ровно один класс на цепь** — KiCad-стиль множественной принадлежности с приоритетной
  агрегацией отклонён (внутренние правила чужого движка, тот же принцип, что «Connection
  Name»); 2+ класса на цепь при развороте паттернов — hard reject.
- **Симметрия имени и класса на границе модуля**: цепь, выходящая через порт, ПРИНАДЛЕЖИТ
  родителю — родительская цепь перезаписывает и имя, и класс внутренней. Класс внутри
  модуля осмыслен для локальных (не выходящих) цепей; у локальной цепи класс живёт на
  ОПРЕДЕЛЕНИИ модуля (один на все инстансы; per-instance расхождение при импорте —
  hard reject, в IR невыразимо). Имена цепей модуля при развёртке — префикс имени
  инстанса (`MD1:OUT`), как у designator'ов.
  - **«Один класс на все инстансы» — не произвольное ограничение, а следствие физики
    модульного футпринта** (обсуждено с пользователем повторно, подтверждено): модуль на
    плате = модульный футпринт с трассами, разведёнными ОДИН раз («Многоканальное
    проектирование» выше) — трассы всех инстансов физически идентичны, а класс и есть
    предписание для трасс (ширина/зазор). Per-instance класс внутренней цепи означал бы
    разную разводку одной и той же трассы — ломает концепцию. Модуль на то и модуль,
    чтобы быть одинаковым везде; там, где per-instance вариативность осмысленна, она уже
    есть: ВНЕШНИЕ подключения каждого инстанса получают классы свободно (портовая цепь
    принадлежит родителю), спроектированные различия сборки — через per-instance ВАРИАНТ
    (именованный diff, известный автору модуля), не через классы.
- **Паттерны/директивы источника не переносятся как механизм** — разворачиваются при
  импорте в явные `class=`-факты (паттерн по иерархическим именам `/CH1/OUT` прогоняется
  по фактическим цепям). Проверено на пользовательском ground truth (multichannel:
  паттерн `/CH1/OUT`→PWR — портовая цепь → класс лёг на РОДИТЕЛЬСКУЮ суммирующую шину
  N$2, как и велит правило). Определения классов: board-тройка `track_width/via_drill/
  clearance` → `<class width/drill/clearance>` (спарс), схемная косметика KiCad
  (wire_width/цвета/line_style) не переносится. `netclass_flag`-директивы — пока warning
  в лог (нет фикстуры), `netclass_assignments` — warning.

## Варианты сборки — принцип модели, спека спроектирована; импорт вариантов сознательно отложен

Спека — ir_schema.md «Варианты сборки». Решение пользователя по объёму работ: импорт
вариантов из внешних форматов пока НЕ реализуем — переносится только БАЗОВЫЙ вариант
(KiCad 10 — свежая фича с багами обкатки, реальных проектов с ней ещё нет; по Altium нет
надёжных данных; Eagle-схемный импорт ещё не написан). Реализовано сейчас: базовый флаг
сборки — KiCad `dnp` → `<instance populate="no">`; `on_board=no` — отклонён (warning в лог;
«не на плате» в IR выражается структурно — отсутствием footprint). Eagle-экспорт флага —
честная деградация с логом (у Eagle вне вариантной системы понятия populate нет).

**`bom` как отдельный флаг убран из модели (июль 2026, обсуждение с пользователем).**
Изначально был перенесён из KiCad `in_bom` как вторая независимая ось рядом с `populate` —
пересмотрено: аргумент пользователя — «все компоненты, которые УСТАНАВЛИВАЮТСЯ на плату,
должны попасть в BOM; если закупать не надо, это решает отдел закупок, не EDA-инструмент».
Единственный кейс, оправдывавший `bom=no` при `populate=yes` (тест-пады, крепёж) сам
пользователь закрыл: такие «ненастоящие» компоненты и так помечаются `populate="no"` —
DNP уже означает выпадение и из сборочного чертежа, и из BOM разом, отдельная ось не
добавляла независимого факта. `<instance>` несёт только `populate`; KiCad `in_bom=no`,
заданный БЕЗ `dnp` (KiCad это допускает, IR — нет), при импорте не переносится, а логируется
warning'ом (`babel/kicad_project_parser.py`). Экспорт в KiCad восстанавливает `in_bom`
из одного и того же `populate`/`dnp` (`babel/kicad_project_exporter.py`). Eagle-экспорт
предупреждает только про `populate`, `bom` в тексте предупреждения больше не упоминается
(`babel/eagle_exporter.py`).

Ключевые элементы спроектированной модели (детали в ir_schema.md):
- Базовый вариант = сама схема; `<variants>` объявляет только дополнительные; вариант =
  `<variant name>`-diff на инстансе: `populate` + `<attr>`-переопределения; непрописанный
  diff = инстанс идентичен базе.
- **Варианты модуля — выбор PER INSTANCE** (`<instance module=... variant="...">`, свой
  `<variants>` у `<module>`): разные экземпляры одного модуля с разными вариантами в одной
  сборке — главный кейс (DC-DC с разными выходными напряжениями из одного модуля).
  Подтверждено ground truth формата Eagle: `<moduleinst modulevariant=...>` в eagle.dtd.
- Известное ограничение модели device (заметка пользователя, сознательно не решаем
  сейчас): device = символ + footprint(ы) + атрибуты, понятия Eagle technology нет —
  отлично для микросхем, хуже для пассивов; вариантные attr-overrides это частично
  компенсируют (номинал+артикул per вариант).

Принципиальное решение (предшествовало спеке):

- **Вариант сборки = именованный diff поверх базовой схемы, по designator'у:
  `{populate: yes/no, attr-overrides (value/mpn/...)}`. Footprint в diff НЕ
  входит — принципиально, навсегда.** Плата — физический объект: медь/отверстия/footprint'ы
  отштампованы до всякой сборки, Gerber один. «Вариант», меняющий footprint — это ДРУГАЯ
  ПЛАТА, т.е. другой проект, а не вариант сборки. Паять в вариантах можно только другие
  компоненты НА ТЕ ЖЕ footprint'ы. (`bom` в diff'е никогда не было отдельной осью нужды —
  см. «`bom` как отдельный флаг убран из модели» выше, тот же принцип применяется и здесь.)
- Соответствие форматов: Eagle `<variant populate/value/technology>` — ложится 1:1;
  Altium Assembly Variants (`.PrjPcb`: Not Fitted / Alternate Part / ParamVariation) —
  ложится, причём Alternate Part и в самом Altium подменяет деталь В ТОТ ЖЕ footprint;
  KiCad 10 design variants — позволяет варьировать footprint per вариант, это смешение
  «варианта сборки» с «вариантом платы» (шиза тула, см. «не потворствовать»): при импорте
  KiCad-варианта, меняющего footprint, — hard reject с объяснением, не перенос.
- KiCad `dnp` — свойство БАЗОВОЙ конфигурации инстанса (`populate="no"`), не вариантная
  система; в KiCad 10 это же — «default»-вариант, что согласуется. `in_bom` — см. «`bom`
  как отдельный флаг убран из модели» выше. `on_board=no` (компонент с footprint, не
  передаваемый на плату) — экзотика, отклонено + warning при импорте.

## `<note>` — markdown-заметки в схеме И на плате; печатаемость решает слой

Спроектировано в обсуждении с пользователем (полная спека — ir_schema.md «`<note>` —
markdown-заметка схемы»), реализация в редакторе — будущее; конвертеры уже используют
(KiCad `text_box` → `<note>`):

- **Зачем**: документирование прямо в схеме — пояснения работы, обоснование номиналов,
  осциллограмма-картинка у тест-пада — одна из целевых функций редактора; во внешних
  документах это немедленно рассинхронизируется. Markdown-поток требует контейнера с
  шириной — поэтому note это блок (x/y/w, высота авто от контента).
- **Наш автоперенос ≠ отклонённый TEXTBOX KiCad**: отказ от textbox был про невозможность
  воспроизвести ЧУЖОЙ рендер (KiCad не хранит разбиение на строки); note рендерит НАШ
  редактор своими метриками — детерминизм внутри одной системы. Побочно это дало лучший
  маппинг импорта: `text_box` несёт ровно то, что нужно note (сырой текст + ширина) —
  пересмотрено вчерашнее «text_box → text одной строкой + shape-рамка», прожившее один
  день.
- **На плате note тоже нужен** (решение пользователя, пересмотр первоначального «note
  никогда не печатается»): типичный кейс — таблица распиновки/джамперов на шелкографии.
  Разграничитель НЕ тип объекта, а СЛОЙ — как у любой геометрии платы: doc-слой → только
  просмотр, шелкография → Gerber ПРЯМЫМ ВЕКТОРОМ (единственный шрифт редактора векторный,
  текст+линии таблиц векторизуются точно, potrace не участвует).
- **Картинки: только в схемных note** (`![](...)`, сайдкары как model3d). В board-note —
  жёсткий запрет (валидация): растр не векторизуется шрифтом; для растра на плате есть
  отдельная сущность изображения-на-слое (potrace + интерактивная подгонка размера —
  «Изображения на плате» ниже), которой markdown не нужен и не поможет (markdown-картинку
  нельзя тянуть/зумить по месту).
- **Подмножество markdown фиксировано** (ir_schema.md), таблицы ВКЛЮЧЕНЫ (главный
  board-кейс), ссылки/code-блоки отложены.
- **Экспорт в legacy** — честная деградация: plain-текст (сырой markdown) + запись в лог;
  картинки при экспорте теряются (логируется).

## Round-trip как линтер: KiCad→IR→KiCad полезен САМ ПО СЕБЕ

Наблюдение пользователя, зафиксировано как назначение продукта (дополняет «Babel — путь
ухода из KiCad», не заменяет): даже «бессмысленная» конверсия KiCad→IR→KiCad очень полезна
для исходного проекта — она ОЧЕНЬ ЯВНО подсвечивает всё несовершенство оформления и
логические ошибки. Каждый наш hard reject / warning — это де-факто диагностика реальной
проблемы проекта: конфликтующие метки на одной цепи, объекты за рамкой листа, шины (в
проекте быть не должны — пережиток, пользователь убирает сам), глубокая иерархия,
нерезолвящиеся библиотеки, глобальные метки/supply, тихо пробивающие границы модулей.
Исправил в IR (редактора пока нет) → экспортировал обратно → проект стал строго лучше.

~~**Гарантия для будущего IR→KiCad экспорта схем: НИКАКИХ глобальных меток в выхлопе,
никогда.**~~ ПЕРЕСМОТРЕНО при реализации экспорта (см. «IR → KiCad: экспорт схемного
проекта» ниже): тотальный запрет глобальных меток разваливал в глазах реального KiCad
КАЖДЫЙ многостраничный проект (scope локальной метки = один файл-лист, между
top_level_sheets KiCad их не сливает — подтверждено vimdrones: 142 global / 0 local).
Итоговое правило пользователя бьёт точно в болезнь, а не вокруг:
**НИКАКИХ глобальных меток В МОДУЛЯХ, никаких локальных меток ВНЕ модулей.**
Top-level (сколько бы ни было страниц) — один неймспейс через global_label = наша
семантика единого холста, KiCad-проект фактически ведёт себя как Eagle; модуль — герметичный
scope, внутри только локальные метки + hierarchical_label на портах. Болезнь KiCad —
глобальность, пробивающая ГРАНИЦЫ МОДУЛЕЙ, — по-прежнему исключена по построению.
Рекомендация «страницы → модули» отвергнута как наркомания: модули нужны ровно для
многоканальных схем, во всех остальных случаях это накладные расходы без профита.

## KiCad `(sheet)` → IR `<module>` — реализовано (глубина 1, KiCad→IR→Eagle целиком)

Первая реализация иерархии по модели ir_schema.md «Модуль (design block + иерархия)».
Ground truth с обеих сторон конвейера: KiCad — `testData/multichannel` (реальный проект,
`channel_strip.kicad_sch` × 4 инстанса), Eagle — `outputs/multigate.sch` (реальный файл,
записанный самим Eagle) + `eagle.dtd`. Ключевые решения/находки:

- **Дедупликация по ФАЙЛУ**: N `(sheet)`-вхождений одного файла → ОДНО определение
  `<module>` (имя = stem файла) + N `<instance module=...>`. Depth-проверка строгая: файл
  модуля, сам содержащий `(sheet)`, — hard reject всей конвертации с цепочкой файлов в
  сообщении (проверено синтетикой: вложенный sheet в копии multichannel).
- **KiCad `position` sheet-прямоугольника — ЛЕВЫЙ ВЕРХНИЙ угол** (Y-down; подтверждено:
  sheet `(74.93, 55.88)` size 40.64×5.08, пин OUT в `(115.57, 58.42)` = правая грань,
  вертикальный центр). IR-центр = `(x+w/2, y+h/2)`, Y-flip один раз при записи.
- **Sheet pins → `<port>`**: сторона по ближайшей грани (не точное равенство — защита от
  округления источника); `coord` от центра, для left/right со сменой знака (KiCad +y вниз,
  IR coord вдоль вертикальной грани +вверх). `connectionType` → `direction` тем же enum'ом,
  что label `shape` → `style`, но в ДРУГУЮ цель (электрическое направление порта, не
  презентация): `input`→`in`, `output`→`out`, `bidirectional`/`tri_state`→`io`,
  `passive`→`pas`. KiCad хранит пины на каждом `(sheet)`-вхождении отдельно (раскладки
  могут разойтись) — IR-модель «раскладка у определения» строже: первое вхождение wins,
  расхождение — warning в import log, не отказ.
- **Designator'ы внутри модуля — канонические из самогó файла** (property `Reference` без
  sheet-контекста — то, что видно при открытии файла модуля напрямую в KiCad). Реальные
  per-instance значения (`R19`/`R8`/`R30`/`R41` в `instances.paths` по ключу
  `root_uuid/sheet_uuid`) сознательно НЕ переносятся: по решению пользователя `offset` —
  опциональный Eagle/IR-механизм, которого в KiCad нет вообще; designator'ы инстансов
  пересчитываются потребителем как «префикс имени инстанса» (правило «без offset»,
  ir_schema.md). Коллизии канонических имён невозможны: per-instance множества референсов
  глобально дизъюнктны в проекте, любой срез «по одному на компонент» бесколлизионен.
- **Связность порта на родительском холсте — БЕЗ изменений в `_build_nets`**: позиция
  sheet pin добавляется в `pin_points` как обычный пин (is_sup=False — порт не даёт цепи
  имя), а на записи XML пара `(имя инстанса, имя порта)` по set'у `portref_keys` эмитится
  как `<portref part= port=>` вместо `<pinref>`. Eagle-сторона: `<portref moduleinst=
  port=>` (eagle.dtd), отличие только в имени атрибута. Проверено на реальной топологии:
  4 портовые точки + вертикальная суммирующая шина с 2 junction'ами → одна цепь, 1:1 с
  KiCad.
- **Рефакторинг, а не дублирование**: тело page-цикла `convert_project_full` вынесено
  ДОСЛОВНО в `_collect_canvas` (аккумулятор `_Canvas`), запись XML — в `_write_canvas`;
  модуль = ещё один вызов той же пары с собственным аккумулятором (свой net-space).
  Страницы по-прежнему делят ОДИН аккумулятор (cross-page global-label слияние работает
  как раньше — регрессия на vimdrones: 0 modules, те же 27/153/63).
- **Рамка на канвасе модуля — ЕСТЬ (пересмотрено).** Первая версия не синтезировала Frame
  для модуля («design block — не печатная страница»); пользователь решил иначе: файл
  модуля несёт настоящий paper + title_block, как любой лист, и его холст должен быть
  оформлен/печатаем так же. Теперь модуль получает тот же синтез Frame-компонента и ту же
  stray-валидацию, что страница (без тайлинга — модуль не в ряду страниц). На Eagle-стороне
  Frame-инстанс модуля → `<frame>` в `<plain>` модульного sheet (как на top-level), не
  `<part>`; frame-компоненты исключены из module `<parts>`/`used_components` симметрично
  top-level.
- **Eagle-порт — это пин 0.2" НАРУЖУ от периметра, точка подключения провода — его дальний
  конец (найдено пользователем в реальном Eagle).** KiCad присоединяет провод прямо к
  периметру sheet, IR хранит KiCad-геометрию (канонично, source-faithful) — поэтому без
  компенсации провода в Eagle-экспорте физически не доставали до порта на 5.08мм. Фикс на
  стороне ЭКСПОРТЁРА (Eagle-специфика не протекает в IR): провод, чей конец совпадает с
  точкой порта на периметре, ПОДРЕЗАЕТСЯ — конец сдвигается на 5.08мм наружу, на точку
  подключения пина (убирается ровно тот отрезок, что лёг бы поверх пина, связность не
  меняется). Подрезка только когда безопасна: ровно ОДИН провод сегмента кончается в этой
  точке (не T-стык, чьи ветки отвалились бы), уходит вдоль оси пина и длиннее пина; иначе —
  fallback: короткая перемычка периметр→точка подключения. Реализация:
  `eagle_exporter._port_geometry`/`_PORT_PIN_LEN_UM`/`_emit_segment(port_geom=...)`.
  Подтверждено на multichannel: все 4 провода к OUT-портам подрезаны (115.57→120.65мм),
  перемычек не потребовалось.
- **Синтез портов из supply/global_label внутри модуля** — закрыта тихая потеря связности:
  KiCad supply-символы и global_label ГЛОБАЛЬНЫ (пробивают границу листа по совпадению
  имени; локальные supply появились только в KiCad 10), первая версия импорта молча делала
  их локальными метками → GND/+12V/+1V1 каналов были электрически оторваны от верхнего
  уровня. По решению пользователя — «вывести в виде портов»: каждая такая цепь → настоящий
  `<port>` (direction `pwr` для supply, из `shape` — для global_label) + на каждом инстансе
  синтезированный хвостик 7.62мм наружу + `<label>` с именем цепи + `<portref>`; label
  закрывает контур через штатный by-name-merge `_build_nets` (ноль нового кода связности).
  **Размещение — ВСЕ синтезированные порты на ОДНУ сторону** (наименее занятую настоящими
  портами, tie → left; слоты 2.54мм от центра, при нехватке — продолжение ряда за углы ТОЙ
  ЖЕ стороны): первая версия раскладывала каждый порт на «наименее занятую» сторону
  индивидуально — и хвостики соседних инстансов через зазор 7.62мм легли ровно друг на
  друга (GND с bottom CH1 на +1V1 с top CH2; поймано conflict-check'ом `_build_nets`) —
  противостоящие стороны соседних блоков направляют хвостики навстречу ПО ПОСТРОЕНИЮ,
  единая сторона исключает встречу. Плюс post-guard: конец хвостика, совпавший с чужой
  connection-точкой, — hard reject (разноимённое слияние ловит conflict-check, а
  ОДНОИМЁННОЕ слилось бы молча — обе коллизии от нашего автоплейсмента, обе наружу).
  В Eagle хвостик (7.62) длиннее пина порта (5.08) — штатная подрезка оставляет видимые
  2.54мм с label за концом пина. Реализация: `kicad_project_parser._synth_port_side` /
  `_alloc_port_slot` / `_SYNTH_PORT_TAIL_MM`, module-ветка + page-loop
  `convert_project_full`.
- **Eagle-структура зеркальна top-level**: `<module>` несёт свой `<parts>` и полный
  `<sheets><sheet>` (подтверждено multigate.sch), сидит между `<classes>` и `<parts>`;
  `<moduleinsts>` — между `<plain>` и `<instances>`. Для проектов без модулей эти элементы
  не эмитятся вообще — выход байт-в-байт как до правки. Компоненты, размещённые ТОЛЬКО
  внутри модуля, добавлены в `used_components` (их deviceset/package/symbol нужны в
  `<libraries>`). Имя порта проходит `_eagle_designator` так же, как имя цепи — иначе
  связь порт↔цепь (по имени) тихо порвалась бы на переименовании.

Реализация: `babel/kicad_project_parser.py` (`_collect_modules`, `_sheet_ports`,
`_Canvas`/`_collect_canvas`/`_finish_nets`/`_write_canvas`), `babel/eagle_exporter.py`
(`_export_module` + факторинг `_emit_part`/`_emit_instance`/`_emit_segment`/`_emit_deco`),
`babel/svg_renderer.py` (блок с портами на верхнем холсте; `render_schematic(root,
canvas_el=<module>)` — рендер холста модуля).

## IR → KiCad: экспорт схемного проекта — реализовано (round-trip замкнут)

`babel/kicad_project_exporter.py`, `export_project(ir_path, output_dir)`: .swprj → полный
самодостаточный KiCad-проект (.kicad_pro + страницы + модульные .kicad_sch +
.kicad_sym/.pretty + sym/fp-lib-table). План: `plans/dynamic-bouncing-cerf.md`
(утверждён 2026-07-03). Round-trip-линтер замкнут: `roundtrip_kicad.py` гоняет
zip → IR#1 → KiCad (наш экспорт) → IR#2 (наш же импорт на собственном выхлопе) и
сравнивает структурно (компоненты, классы, порты модулей с координатами, инстансы с
gate/footprint/rot/mirror/populate/bom, цепи с классами и числом pinref/portref) —
multichannel и vimdrones зелёные полностью. Ключевые решения/находки:

- **Версия формата — 20250114 (KiCad 9), сознательно**: ни одного .kicad_sch, сохранённого
  реальным KiCad 10, в testData нет — токен версии v10 и синтаксис supply LOCAL будут
  взяты с ОДНОГО ground-truth файла пользователя (KiCad 10 читает v9 и апгрейдит при
  сохранении, ничего не блокирует). До этого supply внутри модульных листов эмитятся БЕЗ
  LOCAL — безвредный двойной коннект с портовой связностью при до-10 семантике (та же
  цепь), TODO-маркер в докстринге модуля.
- **`(power global)` обязателен у supply-символов** — ground truth
  `testData/multichannel.kicad_sym` (записан реальным KiCad 9). Без него реимпорт теряет
  `isPower`, sup-пин перестаёт именовать цепь, и каждый supply-остров рассыпается в свой
  N$ (7 цепей → 21, поймано первым же round-trip). Заодно это и есть та самая ручка
  global/local: LOCAL почти наверняка = `(power local)` — но НЕ угадываем, ждём ground
  truth. `_PIN_DIR` дополнен `sup → power_in`.
- **Пустой `(pin_numbers)` не эмитится** (только с `(hide yes)`): реальный KiCad его
  опускает, а kiutils `Symbol.from_sexpr` на пустом блоке падает (безусловный `item[1]`)
  — наш собственный импорт не мог прочитать наш собственный выхлоп.
- **Правило меток (пересмотр первоначальной гарантии, решение пользователя): никаких
  global_label В МОДУЛЯХ, никаких локальных меток ВНЕ модулей** (см. пересмотр в
  «Round-trip как линтер» выше). Top-level страницы — global_label со `shape` из IR
  `style` (`crummy` → `passive` + лог: простой текст бывает только у локальных; ground
  truth формата — vimdrones, justify голый left/right без bottom); внутри модулей —
  только локальные + hierarchical на портах. KiCad-проект ведёт себя как Eagle: единый
  неймспейс холста, герметичные модули. Grep-ассерт в тесте двусторонний (нет глобальных
  в модульных файлах, нет локальных в корневых).
- **Линтер-эффект supply-иерархии** (плановый пункт «отметить в decisions»): импортные
  синтезированные supply/global-порты + хвостики экспортируются как есть (порт → sheet
  pin, хвостик+label → провод+label) — KiCad получает ЧЕСТНУЮ иерархию вместо глобального
  протекания питания сквозь границы листов.
- **hierarchical_label порта ЗАМЕЩАЕТ метку одноимённой цепи** внутри модульного файла
  (связность гарантирована — та же точка). Для цепи без метки (synthesized supply-порты) —
  якорь на первом конце провода цепи. `pwr` не имеет hier-label shape → `passive` + лог;
  round-trip-компаратор нормализует `pwr→pas` (в KiCad sheet-pin направления «power» нет
  вообще — честная деградация).
- **N$-имя с классом МАТЕРИАЛИЗУЕТСЯ меткой** (исключение из «N$ не материализуются»):
  netclass_pattern в .kicad_pro матчится точной строкой имени — безымянная в KiCad цепь
  молча потеряла бы класс (лог, не тихо). Проверено: `/N$2` PWR у multichannel выживает
  round-trip.
- **Пин ровно в УГЛУ блока** (synthesized-порт на блоке 5.08мм высотой, слот ±2.54 = угол):
  классификация стороны в `_sheet_ports` рвала tie флоат-шумом по-разному для инстансов
  ОДНОГО файла (GND left↔top). Дистанции округляются до целых µm, tie — фиксированный
  порядок left/right/top/bottom (тот же, что `_synth_port_side`).
- **Схемные проекты без платы легальны**: наш выхлоп не содержит .kicad_pcb (KiCad создаёт
  плату лениво) — `_extract_embedded_models` больше не падает на отсутствующем файле.
- rot/mirror — обратный литерал `_mirror_and_angle`: angle = ir_rot, ir_mirror=1 →
  `(mirror y)`; формул нет (урок трёх пересмотров). Углы sheet-пинов на top/bottom
  сторонах ground truth не имеют (в multichannel только right) — right=0/left=180
  подтверждены, вертикальные стороны судит визуальная проверка пользователя.
- UUID детерминированные: uuid5 от namespace проекта + стабильный ключ (designator/имя
  цепи/координата) — воспроизводимые диффы между прогонами.

## KiCad PWR_FLAG — ERC-директива, не supply (структурное различение, не по имени)

Найдено на testData/Pocket-Lab-Bench-Power.zip: conflicting-label check «зарубил» 5 цепей,
на всех — «PWR_FLAG» против настоящего имени рейла (+5V/GND/+3V3/...). Причина: импортёр
грёб ВСЕ `(power)`-символы под supply-правило «Value именует цепь через sup-пин», а
PWR_FLAG — не рейл, а бюрократическая ERC-затычка KiCad («у этой цепи есть драйвер»),
присутствующая практически в каждом реальном проекте. Различение СТРУКТУРНОЕ, KLC-каноном,
не по имени: supply-символ (S7.1) = `(power)` + ровно один **power_in** пин → sup-коллапс;
`(power)` + **power_out** пин = ERC-директива → импортируется ОБЫЧНЫМ компонентом
(размещён, отрисован, подключён — его пин никогда ничего не именует), лог на символ.
Подтверждено на ground truth проекта: PWR_FLAG = power_out, +5V/GND = power_in.
Реализация: `kicad_parser._is_erc_power_source`, обе isPower-ветки
(`_convert_symbol` / `_convert_schematic_symbol`). Round-trip PLBP после этого зелёный
целиком.

**Судьба флага дальше по конвейеру (решение пользователя, второй заход).** Первая версия
экспортировала PWR_FLAG в Eagle обычным part'ом — нелегально: в Eagle пин существует ради
связи с падом, единственный пин без пада — supply (`sup`); бескорпусная деталь с
`pwr`-пином — ошибка. Сделать пин `sup` прямо В IR нельзя: имя sup-пина именует цепь (наша
же семантика, ir_schema.md «Supply symbol») — «PWR_FLAG» снова передрался бы с настоящим
именем рейла в нашем же `_build_nets`, т.е. вернулся бы исходный конфликт. Итог: **IR
хранит честное KLC-направление (`pwr`), а правило «у бескорпусной детали пины могут быть
только sup» реализовано на Eagle-ГРАНИЦЕ** — `eagle_exporter._packageless_symbols` +
коэрция в `export_symbol` (лог на пин; символ, разделяемый с корпусной деталью, не
трогается — коэрция сломала бы её пин). Проверено: в plbp.sch не осталось ни одного
non-sup пина у бескорпусных деталей; multichannel — ноль коэрций (настоящие supply уже
sup). Семантическое место самого ФАКТА «питание входит в цепь здесь» — будущие PI/ERC
аннотации swift (не псевдокомпонент); тогда же закроется и in/out-неразличимость IR `pwr`
(экспорт в KiCad пока отдаёт power_in — перевывезенный PWR_FLAG теряет power_out-ность,
ERC KiCad попросит драйвера заново).
Открытый вопрос к визуальной проверке в реальном Eagle: как он ведёт себя с sup-пином
«1» на цепи с другим именем (ожидание: грузится, ERC-warning; риск: авто-переименование
цепи при редактировании).

## KiCad-импорт: толщина линии материализуется НА ГРАНИЦЕ (0 ≠ факт, 0 = «дефолт тула»)

Найдено пользователем на Pocket-Lab-Bench-Power: stroke width 0 у провода KiCad означает
«возьми wire_width КЛАССА цепи» (Default = 6 mil; поля wire_width/bus_width/
default_line_thickness в .kicad_pro — В МИЛАХ, в отличие от соседних pcb-полей в мм), у
канвасной графики — schematic.drawing.default_line_thickness. Импорт клал 0 в IR как есть,
и каждый экспортёр изобретал дефолт сам: eagle_exporter подставлял константу `_WIRE_W`
(комментарий честно признавался «lost during import»), KiCad-экспорт писал 0 обратно и
реальный KiCad «угадывал» правильно — два независимых дефолта, совпавших по величине.
Теперь ширина — явный µm-факт на каждом `<line>` уже в IR («один факт — одно место»):
провода резолвятся по классу цепи В МОМЕНТ записи (класс уже известен; multichannel: цепь
класса PWR с wire_width 12 mil получает 305µm, остальные 152µm), графика — по
default_line_thickness. Огр: цепи ВНУТРИ модуля пишутся до присвоения классов —
материализуются на Default; если класс с собственной шириной прилетает позже — лог
NET_WIRE_WIDTH, не молча.

## KiCad-импорт: заливка канвасных фигур была ИНВЕРТИРОВАНА

Найдено пользователем там же: незалитые прямоугольники оригинала экспортировались solid.
`_collect_canvas` проверял `fill.type != 'outline'` — ровно наоборот от правильной (и уже
задокументированной в символьной ветке kicad_parser!) семантики KiCad: `outline` = заливка
ЦВЕТОМ ЛИНИИ (solid), `color` = заливка явным цветом (solid), `none` = нет заливки,
`background` = ловушка цвета канваса (визуально пусто). Плюс контурные прямоугольники
разбирались на 4 отдельные `<line>` — зря и лишь для Eagle (который сам умеет разложить
`<shape outline=w>` на wires в своём экспортёре): теперь контурный rect — честный
`<shape outline=w>`, KiCad-экспорт отдаёт нативный незалитый rectangle.

## Автоимена цепей N$k обязаны обходить занятые имена (+ безопасный якорь меток)

Пара багов, пойманных одним round-trip'ом на пользовательской версии multichannel (с
netclass-паттерном — выяснилось, что multichannel.zip старее каталога и классов не имеет,
паттерны в тестах до этого не покрывались):
- **_build_nets автонумератор** раздавал N$k не глядя на занятые имена: экспортёр
  материализует метку «N$2» (ради сохранения класса), а на реимпорте другой безымянный
  остров независимо получал автоимя «N$2» → тихое слияние двух цепей by-name. Теперь
  автонумератор пропускает имена, занятые реальными источниками (метки + sup-пины). Это
  не только наш кейс: живой KiCad-проект тоже может нести метку «N$2».
- **Якорь синтезированных меток** (и fallback hierarchical_label в модулях) ставился в
  «первый конец провода» цепи — а эта точка может лежать НА проводе чужой цепи
  (пересечение без junction); метка в KiCad цепляется ко всему, что проходит через её
  точку → физическое слияние. Теперь `_label_anchor`: перебор концов и середин своих
  проводов с проверкой `_collinear_between` против геометрии всех остальных цепей; если
  чистой точки нет — лог LABEL_ANCHOR, не молча.
- Компаратор round-trip: автоимена N$k сравниваются одним бакетом «N$*» (перенумерация
  между прогонами — не идентичность; класс/сегменты/pinref'ы/ширины различают их
  структурно). Именованные и классифицированные цепи сравниваются по-прежнему точно.

## KiCad 10 supply LOCAL — реализовано с ground truth; триггер замены kiutils СРАБОТАЛ

Ground truth от пользователя (KiCad 10.0, version **20260306**: сделал локальным #PWR048
в channel_strip.kicad_sch). Устройство: локальность живёт на КОПИИ символа в
lib_symbols-кэше ФАЙЛА — `(power local)` vs `(power global)`; KiCad форкает копию
(`GND_1`) и целит в неё размещённый символ через `(lib_name "GND_1")` при сохранённом
lib_id (тот самый detachable placeholder). Локальность — свойство размещения в файле
(применилась ко всем 4 инстансам channel_strip разом). Прогноз пользователя подтверждён:
в библиотеке никто не дублирует power-символы local/global — модифицируют по месту; это
ПЕРВЫЙ случай, где размещённый символ законно отличается от библиотечного референса.

**Триггер замены kiutils сработал** (первый подтверждённый silent loss, ровно на
предсказанном кандидате): kiutils 1.4.8 читает оба варианта в одинаковое `isPower=True` —
аргумент молча выброшен, а его писатель отдаёт вообще голое `(power)`. Первый шаг
миграции по плану — raw-sexpr side-channel `_power_locality` (тот же приём, что
_decode_embedded_files); полноценный свой тонкий s-expr-ридер — отдельная задача
(deferred). `lib_name` kiutils отдаёт — связка инстанс→кэш-копия через него.

Семантика в обе стороны:
- **Импорт**: `(power local)` supply в модуле = сознательно изолированная цепь → порт НЕ
  синтезируется (лог LOCAL_SUPPLY); синтез портов теперь только от ГЛОБАЛЬНЫХ supply.
  Смешанный случай (часть GND локальные, часть глобальные) → цепь всё же течёт → порт
  синтезируется. Top-level: на единственной странице локальность вакуумна (= global,
  лог); на многостраничном проекте page-scoped supply НЕВЫРАЗИМ на едином IR-холсте →
  hard reject с советом.
- **Экспорт**: в модульных .kicad_sch ВСЕ supply-копии кэша получают `(power local)`
  (равномерный per-file флип — форк GND_1 не нужен, у нас нет смешения внутри файла;
  scope модуля герметичен, порт = sheet pin), на top-level — `(power global)`.
  Версия файла — 20260306 (с того же ground truth). Round-trip замкнут: реимпорт
  нашего выхлопа не синтезирует порты заново (все supply локальные), порты приходят
  sheet-пинами и совпадают с IR1.
- IR не меняется: локальность не хранится — внутри модуля всё локально ПО ПОСТРОЕНИЮ,
  глобальность supply-«протекания» источника материализуется портами на импорте.

## KiCad: поворот/зеркало ЛИСТА — не состояние, а запечённая раскладка (ground truth)

Пользователь повернул CH1 на 90° и отзеркалил CH4 в НАШЕМ ЖЕ выхлопе в реальном KiCad 10
(сохранено как фикстура `testData/multichannel_rotated/` — outputs чистится, ground truth
нельзя было там оставлять). Механика: у `(sheet)` НЕТ угла/зеркала в формате вообще —
поворот перекладывает геометрию вхождения: 90° меняет местами `size`-стороны, `at`
пересчитывается (центр блока неподвижен), пины переезжают на другие грани с новыми
углами; зеркало по горизонтали — лево↔право у пинов при тех же `at`/`size`. Именно
поэтому KiCad хранит sheet-пины на каждом вхождении: «повёрнутый инстанс» = вхождение с
другой раскладкой. Попутно этот же ground truth дал все 4 угла sheet-пинов:
**right=0, left=180, top=90, bottom=270** — прежние top/bottom (270/90, экстраполяция
без ground truth) были инвертированы, исправлено в `_SIDE_ANGLE`.

Отсюда поддержка повёрнутых/зеркальных инстансов модулей (в Eagle-проектах пользователя
`moduleinst rot` — живая реальность):
- **Экспорт IR→KiCad — ЗАПЕКАЕМ (СДЕЛАНО 2026-07-07)**: `_emit_sheet` трансформирует
  размер (swap при 90/270, центр неподвижен), сторону+coord каждого порта — функция
  `ir_util.rotate_port_side`. Формула подобрана по 32 эталонным точкам
  `testData/modtest.sch` (все 8 комбинаций rot×mirror, пользователь повернул руками в
  реальном KiCad 10), НЕ выведена алгеброй: чистый поворот вектора не работает — при
  mirror два порта одной стороны разъезжаются на разные итоговые стороны.
  `new_side=angle[(θ+rot)%360]` не-mirror / `angle[(180-θ-rot)%360]` mirror;
  `new_coord=coord*(cosθ_rot∓sinθ_rot)`.
- **Импорт KiCad→IR — КАНОНИЗАЦИЯ ОТМЕНЕНА, теперь HARD REJECT (пересмотр 2026-07-07)**:
  пробовали распознавать поворот вхождения перебором 8 преобразований эталона — провалилось
  на `multichannel_rotated/CH1`: пользователь повернул лист на 90° в KiCad, и пин 1V1 НЕ
  поехал с остальными — **KiCad поворачивает лист БАГОВАНО**. Плюс структурно: у `(sheet)`
  вообще НЕТ полей угла/зеркала — «повёрнутый лист» и «лист с переставленными руками
  пинами» в файле неотличимы. Распознавание = угадывание бага KiCad. Отказались:
  `_collect_modules` теперь ТРЕБУЕТ идентичной раскладки у всех вхождений одного модуля,
  иначе `ValueError` с именем инстанса+порта. Это [[babel_purpose_kicad_exit]] в чистом
  виде: не консервируем дефект KiCad, требуем нормальности. Повёрнутые модули НЕ теряются —
  направление Eagle→IR→KiCad их держит (Eagle хранит угол честно, экспорт запекает); отказ
  только когда KiCad ИСТОЧНИК. `multichannel_rotated` теперь = тест на reject.
- Остаток (не блокер): `eagle_exporter._port_geometry` при экспорте В Eagle использует
  простой `_rotate_vec` (Eagle-собственная механика rot, рабочая на импорте); svg_renderer
  ещё не рисует rot/mirror moduleinst.

## KiCad-символы: styleId 0 — ОБЩЕЕ тело, не альтернатива (пересмотр выбора тел)

Найдено пользователем: у PL:TVS2200DRV (Pocket-Lab-Bench-Power) в конверсии пропали
внутренний блок «Det & Drv», его связи и оба текста. Причина: в .kicad_sym суб-тело
`NAME_0_0` — это (unit 0, style 0), и style 0 зеркалит семантику unit 0 УРОВНЕМ НИЖЕ:
«общее для всех body-style», рисуется в КАЖДОМ виде. Стандартный вид = СУММА _0_0 + _0_1
(+ юнит-специфичных), а не выбор одного. Старый `_pick` (предпочесть style 1, иначе 0)
молча ронял всё содержимое второго слота. Теперь `_group_gates._unit_bodies` складывает
style 0 + style 1 каждого юнита (De Morgan ≥2 по-прежнему отброшен). Слияние поглотило оба
выросших на пикере легаси-костыля: пины в style 0 под настоящим юнитом (MSPM0G3507SPTR) и
«всё под unit 0» (power:VCC) — оба случая теперь общий путь, не special-case.

## KiCad-символы: отрезок и полигон — ОДИН токен `(polyline)`; три дефекта шва

Подозрение пользователя подтвердилось: в символах KiCad нет отдельного «отрезка» —
2-точечная polyline; «полигон» — N-точечная; замкнутость = только совпадение последней
точки с первой; заливка — просто `(fill ...)`, и KiCad рендерит её ДАЖЕ у незамкнутой
polyline (заливает неявное замыкание, обводит только нарисованные рёбра). Исправлено
попутно с пересмотром styleId (все три — один шов):
- **импорт**: полигоном считается polyline «замкнутая ИЛИ залитая» (раньше только
  замкнутая — залитый треугольник из 3 точек без повтора первой рассыпался в голые линии
  с потерей заливки);
- **импорт**: `fill (type color)` (явный цвет, v7+) считается заливкой во ВСЕХ четырёх
  символьных ветках (polyline/rect/circle/arc) — раньше только 'outline', симметрично
  канвасному фиксу;
- **экспорт** (`_sym_geom`): IR `<polygon>` пишется с ПОВТОРОМ первой вершины (иначе
  KiCad недорисовывает одно ребро обводки, а наш же импорт разбирает фигуру обратно в
  линии) и с fill из атрибута полигона (0 → none), а не хардкодом solid.

## Числовой форматтер s-expr: НЕ `%g` (kiutils не понимает экспоненту)

`_f` (kicad_exporter, общий для библиотечного и проектного экспорта) писал `%g`: (a) для
|v| ≤ 1e-05 мм — экспоненциальная запись (`1e-06`), которую sexpr-токенизатор kiutils не
признаёт числом → строка → TypeError на арифметике при нашем же реимпорте (float-мусор от
тригонометрии mid-точек дуг, пойман round-trip'ом PLBP); (b) 6 ЗНАЧАЩИХ цифр — молчаливое
съедание микронов на координатах >1000мм (достижимо хвостом горизонтального тайлинга
страниц). Теперь фиксированная запись `.6f` с обрезкой хвостовых нулей.

## Иерархия футпринтов
- Футпринт может содержать дочерние футпринты — рекурсивная структура
- Рекурсивный обход дерева проще чем два разных кода для разных уровней
- Максимальная глубина вложенности — константа `MAX_NESTING_DEPTH`
- Ограничение глубины — одна проверка в одном месте, не затрагивает рекурсивный код
- Реальных сценариев глубже 2 уровней нет, но архитектура не ограничивает
- Финальное решение по максимальной глубине — после дополнительного обдумывания

## Тип Shape
- Отдельный тип в модели данных — не рассыпается на линии, редактируется как единое целое
- Параметры: `pos, size_x, size_y, roundness (0-100), width (0=залитая, >0=контур), rotation, layer`
- Круг: `size_x == size_y`, `roundness == 100`
- Залитый квадрат: `size_x == size_y`, `roundness == 0`, `width == 0`
- Line — отдельный примитив для произвольных линий, Shape использует его концептуально но не хранит
- Геометрия генерируется на лету при рендеринге из параметров
- **Выбор по контуру** — консистентно с зонами и линиями

## Тип Pad
- TH и SMD — два отдельных типа, не объединять
- Причины: разная логика в DRC, zone fill, Gerber экспорте, фильтре видимости
- Форма пада: `size_x, size_y, roundness (0-100)` — вместо enum типов
- Круглый пад: `roundness == 100`, квадратный: `roundness == 0`
- Восьмиугольник и овал при импорте → круг (ошибки округления подсветит DRC)

## Принцип консистентности как документация
- Все объекты выбираются по контуру — зона, Shape, линия, незалитая и залитая фигура
- Все инструменты используют Shift+клик для параллельности
- Все деструктивные операции молча выполняются и отменяются через Undo
- Пользователь выучивает паттерн один раз — документация для базовых операций не нужна

## Термобарьеры
- Настройки: включено/выключено + зазор между падом и полигоном
- Ширина спиц = width полигона
- Ориентация спиц = угол пада (как в Eagle)
- Четыре спицы, всегда — фиксированный разумный дефолт
- Особые термобарьеры для конкретного участка — отдельный полигон с нужными настройками и приоритетом
- Никакой отдельной системы назначения термобарьеров падам — полигон уже является единицей настроек

## Модули (многоканальные схемы)
- Модуль — отдельный файл платы (.brd), открывается и редактируется как любая другая плата
- Никакого "редактора внутри редактора" — просто открыл файл модуля, отредактировал, сохранил
- При открытии основной платы Swift проверяет timestamp файлов модулей и предлагает применить изменения:
  `Модуль power_channel.brd изменился. Применить к 3 инстансам? [Применить] [Пропустить]`
- Работает и для модулей используемых в нескольких проектах — тот же механизм бесплатно
- Инстанс модуля на плате = ссылка на файл + позиция/трансформация

## Футпринты vs Модули
- **Футпринт** — неизменяемый, геометрия определяется физическим компонентом, хранится в библиотеке совместимой с Eagle
- **Модуль** — редактируемый файл платы, специфичен для проекта, не библиотека
- Два разных объекта с разной семантикой — не объединять

## ~~Detach инстанса модуля~~ ПЕРЕСМОТРЕНО: detach на плате отменён, вместо него — FLATTEN THE MODULE в схеме

Ранний план (detach как board-операция: развернуть инстанс в плоские объекты платы,
пометить для будущей синхронизации со схемой) — **отменён решением пользователя**. Выход
из модульного контракта — операция СХЕМНОГО редактора, плата следует за схемой:

- **FLATTEN THE MODULE**: один конкретный инстанс модуля превращается в кусок обычной
  схемы на холсте — модульный инстанс исчезает, всё содержимое модуля появляется как
  самостоятельные объекты.
- **Переименование при flatten — ничего нового, материализация уже зафиксированных правил
  развёртки**: портовые цепи получают имена РОДИТЕЛЬСКИХ цепей, к которым были подключены
  («родитель перезаписывает имя и класс», см. «Net class»); локальные цепи и designator'ы
  — префикс имени инстанса (`CH2:N$3`, `CH2:R1` — правило «без offset»); классы локальных
  цепей сохраняются с определения.
- **Board-сторона автоматически**: нетлист развёрнутого куска стал плоским → инстанс
  модульного футпринта на плате превращается в обычные объекты с сохранением всей
  геометрии — не отдельная операция, а следствие. Старый «Открытый вопрос — detach и
  схемный редактор» (синхронность двух сторон) этим закрыт: сторона одна, схемная.
- Разграничение с «sync off» остаётся в силе, стало только чище: sync off — свобода
  ГЕОМЕТРИИ при живой модульной структуре (board-механизм); flatten — выход из модульного
  контракта целиком (схемный механизм), плата следует. Сценарий «канал стал особенным
  после разводки» покрывается flatten'ом без потери сделанной работы (геометрия
  сохраняется при развороте).
- Необратимо (кроме Undo) — предупреждение оправдано, как и планировалось для detach.

## Инструмент Route — подсветка запретных зон
- При активной трассировке подсвечивать зоны куда трасса не пройдёт по DRC
- Технически: expand(obstacle, clearance + width/2) — тот же Minkowski sum что при zone fill
- Только объекты рядом с курсором через пространственный индекс — быстро
- Полупрозрачная заливка запретных зон — пользователь сразу видит куда пролезет
- Лучше чем push obstacle: не двигает ничего, просто показывает реальность
- Пересчёт при каждом движении мыши только в радиусе нескольких миллиметров

## Изображения на плате (логотипы, штрихкоды)
- Принимаем только растр (PNG/JPG) — SVG не поддерживаем, пользователь конвертирует сам
- В редакторе рендерится как растр, масштабируется и перемещается как обычный объект
- При экспорте Gerber — автоматическая векторизация через potrace
- DRC шелкографию не проверяет — пользователь смотрит в 3D вид
- Инвертированный текст — полигон на шелкографии + объект с флагом subtract

## Инструмент Split (разрезание трассы)
- Два клика — начало и конец вырезаемого участка
- Сегмент удалён, пользователь ставит новый нужной ширины
- Явное действие пользователя — явный результат, ничего автоматического
- Автосужение трасс не делаем — ширина трассы выбирается осознанно и не должна меняться незаметно

## Инструмент Route — отмена действий
- Backspace во время трассировки — отменить последний сегмент, остаться в инструменте
- Esc — отменить всю трассу, выйти из инструмента
- Ctrl+Z после завершения — отменить всю трассу как одно событие
- Перезаливка полигона происходит после каждого зафиксированного сегмента — не ждёт конца трассировки
- Undo оперирует транзакцией (вся трасса), рендер обновляется постоянно — два разных механизма

## Умный буфер обмена
- Ctrl+C / Ctrl+V работает между разными открытыми проектами
- При вставке: референсы переименовываются автоматически (R1→R5 если R1-R4 заняты)
- При вставке: сети с общими именами (GND, VCC) соединяются с существующими, уникальные создаются новыми
- Копирует и схему и трассировку вместе
- Внутри одного проекта — инструмент для быстрого повторения каналов без модулей
- Не требует документации — люди будут пользоваться инстинктивно

## Модули — уточнение концепции
- Единственная причина использовать модуль — живая связь: изменил в одном месте, обновилось везде
- Для всех остальных случаев повторного использования — умный буфер обмена
- Модуль как "квадратик для читаемости" не нужен — на бесконечном холсте без листов читаемость решается зумом

## Скриптинг
- Встроенный язык скриптинга — **Lua**
- ~300 КБ весь интерпретатор, встраивается в C за час
- Полный доступ к модели данных — читать и модифицировать компоненты, трассы, сети, свойства
- Простые скрипты — просто набор CLI команд в файле
- Сложные скрипты — Lua с биндингами к модели, как ULP в Eagle и Python в KiCad
- Lua проще ULP, документации больше, ChatGPT пишет скрипты по описанию

## Импорт BSDL для создания компонентов
- BSDL файлы содержат имена и типы всех пинов чипа — идеально для создания УГО
- Правильный workflow: свой проверенный футпринт + имена пинов из BSDL = готовый компонент за секунды
- Не использовать Ultra Librarian BXL для футпринтов — качество низкое, много мусора
- При открытии редактора УГО явно показывать варианты импорта включая BSDL — discoverability важна
- Редактор должен намекать на существование BSDL чтобы пользователи не узнавали об этом случайно через 15 лет
- Настройка рендеринга слоёв (цвет, прозрачность, заливка) — GUI, не CLI, нужен мгновенный визуальный фидбек

## Полигоны — пересмотр подхода
- Стоит протестировать Eagle-подобный scanline/штриховочный алгоритм против Clipper2
- Eagle работал быстрее KiCad именно из-за простоты линейного алгоритма vs тяжёлые полигональные операции
- Width параметр полигона как защита от производственного брака — не баг а фича
- Штрихованный полигон естественно маппится на сетку сопротивлений для PI анализа
- Clipper2 для этого требует дополнительного шага мешинга

## GPU DRC и рендеринг
- Растровый DRC: каждый пиксель = 1 микрон нашей системы координат
- Максимум GPU текстуры ~16384x16384 — при 1мкм/пиксель покрывает только 16x16мм
- Решение: тайловая система — одна большая составная текстура как MegaTexture (id Software, Quake Wars 2007)
- Детальные тайлы подгружаются по мере приближения камеры, вдали — низкодетальные
- DRC считается только локально вокруг курсора на детальных тайлах
- Три SDF шейдера покрывают всю геометрию платы: круг, прямоугольник/отрезок, дуга
- Нарушения DRC показываются визуально на плате — красные области, не текстовые отчёты

## Lua и важное
- Lua рантайм + raylib биндинги = технически можно запустить Doom
- Это будет лучшей рекламой для Swift

## Импорт платы Eagle — решения Этапа-0 (via + полигоны/анти-слои)
Контекст: началось проектирование board-контейнера IR (`.brd` → IR). Скоуп этапа —
«геометрия сначала»: DRC, физический stackup, net-class-тройка (width/clearance/drill)
отложены. Вход — проект (.sch+.brd), заливки полигонов берём ТОЛЬКО как контур
(fill Eagle пересчитает сам при ratsnest).

### VIA — только сквозные (through), как ОСОЗНАННОЕ ОГРАНИЧЕНИЕ
- `<via>` несёт `x/y/drill/diameter` (+ опц. `shape`). НИКАКОГО `extent`/from-to —
  по определению «через все слои насквозь». Ось стека не вводим, пока нет потребителя.
- Blind/buried отложены до первой реальной нужды — тогда и расширим модель.
- ИМПОРТ из любого КАДа: не-сквозной via (blind/buried) → **HARD REJECT** всего импорта
  (диагностика: «via X,Y — blind/buried слои A–B, IR выражает только through»).
  ПЕРЕСМОТРЕНО с раннего варианта «through + WARNING»: подмена blind→through не косметика —
  сквозной барабан пробивает inner-слои и пересекает чужие заливки → импорт ФАБРИКУЕТ
  короткие замыкания, которых в оригинале не было. По общему принципу «не выражаем →
  hard reject, не деградация». На практике blind/buried редки — могут подождать
  расширения модели.
- ЭКСПОРТ: все via сквозные → `extent` = весь стек (topmost–bottommost). Тривиально.

### VIA как носитель атрибутов (свободный мешок, без зарезервированных ключей)
- via может нести атрибуты имя-значение, ТОЧНО как компонент. Board-only: никогда не
  идут в BOM/ERC/нетлист и не переносятся в другие КАДы (у Eagle/KiCad нет родного
  «атрибута на via» → при экспорте теряются, в import_log). Round-trip только внутри
  нашего формата.
- Назначение: автоматическая манипуляция via — отличать машинно-сгенерированные (ground
  stitching, thermal, fanout) от размещённых руками, чтобы потом удалять/менять их пачкой.
- НЕ вводим зарезервированные ключи (`generator`/`group` и т.п.) в IR. Обсуждалось и
  отклонено: IR — носитель факта, а не место политики. Консистентность ключей
  гарантирует ГЕНЕРАТОР, который их пишет и читает, а не формат (формат всё равно не может
  принудить свободный текст). Инвариант «не размножить machine-origin копированием»
  обеспечивает РЕДАКТОР (запрет копирования не-пользовательских via), а не структура
  хранения. Мешок пар имя-значение уже полностью выражает и происхождение, и группу.

### Полигоны: solid/hatch — БЕЗ ИЗМЕНЕНИЙ (уже решено)
- Шкала `fill 0..100` (100=solid, 0=только контур, промежуточное=штриховка) остаётся.
  Три Eagle-стиля solid/hatch уже растворены в одну числовую ось (см. ir_schema.md).
  Эта сессия их НЕ трогает.

### cutout + tRestrict/bRestrict → АНТИ-СЛОИ (растворение двух Eagle-механизмов в один)
Проблема: один физический факт «здесь этого материала нет» Eagle выражает ДВУМЯ способами —
(а) полигон `pour="cutout"` на медном слое, (б) ЛЮБОЙ объект (line/circle/rect/arc/text/
polygon) на слое tRestrict(43)/bRestrict(41). Плюс два дефекта: `cutout` слое-зависим
(бывает только на меди), а restrict-слои есть только для top/bottom, НЕ для inner — Eagle
сам непоследователен.

Решение: у КАЖДОГО объекта — булево свойство АНТИ (принадлежность к слою расширяется).
Запись: объект на слое `21` — обычный, на слое `!21` (черта над номером, по аналогии с
инверсными электрическими сигналами) — ВЫРЕЗ.
- Любой примитив легален на анти-слое (line/arc/circle/rect/shape/**text**/polygon).
  АНТИ — свойство объекта, ортогональное его типу.
- Анти-объект вычитается ТОЛЬКО из `<polygon>` на своём (базовом) слое, поверх которых
  лежит — из ВСЕХ пересекаемых. Не-полигонная аддитивная геометрия на слое НЕ затрагивается
  (линия/текст — конечные штрихи, «дырявить» их бессмысленно; полигон — единственная
  заполняемая область).
- Нет полигонов на слое → анти-объекты ИНЕРТНЫ: ни нагрузки, ни вычитания, ни
  предупреждения (нечего дырявить = ничего не произошло).
- Плоская модель: никакой рекурсии/двойного отрицания, никаких rank'ов при вычитании.
  Вычитание — **ПО-ПОЛИГОННО, с сохранением идентичности**: для КАЖДОГО полигона слоя
  отдельно `полигон_i − union(пересекающие его анти-объекты)`. Результат остаётся тем же
  полигоном (та же сеть, тот же `fill`, тот же `rank`) — просто с дырками. Полигоны РАЗНЫХ
  сетей никогда не объединяются между собой; анти-объекты между собой объединять можно
  (они идентичности не несут). Порядок стадий: анти-вычитание режет РЕГИОН полигона,
  затем регион заливается/штрихуется по своему `fill` (штрихи клиппятся к порезанному
  региону — холодный путь, платит только полигон, тронутый анти). (Осознанно проще
  Eagle-rank.)
- Анти-объект всегда вычитает свой **ЗАЛИТЫЙ регион**: `fill`/`width` НА АНТИ-СЛОЕ
  игнорируются (полигон трактуется как fill=100, фигура/линия — как залитый контур своей
  толщины). Иначе штрихованный полигон можно было бы получить ДВУМЯ способами — fill<100
  на базовом слое ЛИБО «решето» анти-штрихами — амбивалентность запрещаем явно:
  один факт (плотность заливки) живёт в одном месте, на базовом объекте.
- Движок: вычитание считает Clipper2 (уже на столе). Каждый примитив полигонизируется в
  контур(ы) — это приведение нам нужно и БЕЗ анти-слоёв (рендер, Gerber), text → глиф-контуры.
  «Оперируем полигонами» — про внутреннее представление движка, НЕ ограничение на вход.
- ИМПОРТ Eagle: `pour="cutout"` → полигон на `!L`; объект на tRestrict/bRestrict → тот же
  объект на `!top`/`!bottom`. Оба входа сходятся в ОДНО IR-представление.
- Обобщение, которого нет ни в одном КАДе: анти работает на ЛЮБОМ слое, вкл. inner-медь
  (Eagle не умел) и не-медные. Пример — буква «О» (и любая с окном) на шёлке: в старом Eagle
  выразить полигоном на silk было СЛОЖНО, тут выходит само (диск на silk минус диск на !silk).
- Прямое следствие — ИНВЕРСНЫЙ ТЕКСТ меток на шёлкографии: метка = белый залитый
  прямоугольник (полигон на silk), из которого текст ВЫРЕЗАН (тот же текст на !silk). В старом
  Eagle такие метки было довольно сложно создавать — здесь получается само собой, композицией
  уже существующих примитивов.
- Граница (не потеря): Eagle-restrict — ещё и DRC-сущность (гонит трассы/пады прочь, не
  только режет заливку). На этом этапе анти-слой несёт ТОЛЬКО геометрическое вычитание;
  DRC-эффект (запрет трасс через зону) — при проектировании DRC, вместе с net-class-тройкой.
  «restrict → anti-layer» НЕ означает, что весь смысл restrict перенесён.

### Анти-слой vs «нет булевой обрезки контура» (следствие №5) — НЕ конфликт
Следствие №5 модели штриховки (см. «Представление полигонов» в eda_ir_design.md) удаляет
ОБЯЗАТЕЛЬНУЮ повсеместную операцию «обрезать заливку по СОБСТВЕННОМУ контуру полигона» —
именно на ней Clipper2 тормозил/глючил, и она была бы на каждом полигоне (горячий путь).
Анти-слой добавляет ОПЦИОНАЛЬНУЮ редкую операцию «полигон − явный чужой вырез» — только там,
где пользователь сам положил анти-объект (холодный путь, платит лишь тот, кто пользуется).
Разные стадии, разные цели: fill/штриховка = «сколько меди и как залить» (обрезки нет,
следствие №5 в силе); анти-слой = «где материала нет» (вычитание по запросу). Горячий путь
не воскрешаем. Аналогия: «убрали GC из горячего цикла» + «оставили ручное освобождение по
запросу» — не противоречат.

### Слоевая модель платы — знаковый номер + имя (полностью в eda_ir_design.md)
Вся классификация слоя РАСТВОРЕНА в номере — никаких полей side/function/is_copper/mirror_to.
- **Слой = знаковый int (первичный ключ) + опц. глобально-уникальное имя.** `0` запрещён.
- **Знак = сторона** (`n`=top, `−n`=bottom). **Спутник = ±n конструктивно** (симметрия и
  биекция невозможны к нарушению, не валидируются). Слой создаётся ПО ОДНОМУ; пара — два
  создания. Standalone = нет слоя с противоположным знаком → MIRROR на месте. MIRROR = смена
  знака (единственная операция, которой нужна парность → пару не храним как связь).
- **Медь = `|n| < 100`, вычислимо из номера.** Рождается из СТЕКА, вручную не создаётся.
  top=1, bottom=−1, inner=2,3,… ВСЕГДА standalone (переворот стека требует stackup — отложен).
  Inner положительны, но НЕ «top»: мнемоника для них читается через другую часть правила —
  нет отрицательного соответствия → standalone, слой БЕЗ стороны (знак кодирует сторону
  только у ПАРНЫХ слоёв).
  Валидатор «сеть только на меди» = `assert |layer| < 100`. `function`-enum не нужен (был про
  Gerber, отложен). Потолок 99 = ~3× запас (Eagle 16/KiCad 32/Altium ~32), не отд. константа.
- **Не-медь = `|n| ≥ 100`, формула `наш = Eagle + 100`** (tPlace 21→121, bPlace 22→−121…).
  Смысл — UX-МОСТ для Eagle-беженцев (121 напоминает Eagle-21). ПРЕЕМСТВЕННОСТЬ ≠ ЗАВИСИМОСТЬ:
  `+100` — формула импорта в таблице ПАРСЕРА, не определение наших слоёв; Eagle НЕ канон,
  KiCad получит свою таблицу в те же числа. Свои ПАРНЫЕ пользовательские слои разрешены
  (Eagle не давал): создал 200, потом ЯВНО создал −200 → стали парой. Пока −200 не создан,
  200 — standalone: MIRROR зеркалит геометрию на месте, слой не меняет (общее правило
  standalone, ничего специального). Eagle-ПОЛЬЗОВАТЕЛЬСКИЕ слои (100–255) все непарные →
  при импорте все идут в ПЛЮС как standalone.
- **Импорт ВЫБОРОЧНЫЙ**: ~20 из ~200 Eagle-слоёв. Слой в IR если есть объект ИЛИ в белом
  списке значимых. Мусор (tGlue/bGlue/tTest/bTest/vRestrict-сирота) не переносим → проблема
  «непарный 143» не возникает.
- **Анти (`!`) ⊥ сторона (`−`)** — две независимые унарные оси, НЕ коллизия: `!-121` валидно
  («анти нижнего шёлка»). Черта над именем — только ОТОБРАЖЕНИЕ инверсии, не арифметика.
- **Номер слоя — ПУБЛИЧНЫЙ API (CLI/хоткеи), не внутренняя деталь.** В этом КАДе CLI активен;
  хоткеи «включить набор слоёв» и скрипты адресуют слои ПО НОМЕРУ (имя произвольно/переименуемо/
  локализуемо — ненадёжно). Следствия: (1) схема нумерации = СТАБИЛЬНЫЙ КОНТРАКТ, `+100`/знак/
  `|n|<100` менять после релиза нельзя — сломает пользовательские хоткеи (ужесточает выбор
  `+100`, преемственность 121≈21 = ещё и API-мнемоника); (2) CLI принимает номер И имя, номер
  канонический (в скрипты пишется он); (3) знаковая схема выбрана В Т.Ч. за CLI-эргономику —
  `show 121,-121`=«шёлк обе стороны» читается формулой, KiCad `show 37,38` нет; (4) GUI
  показывает ИМЯ (голого числа не видно), CLI — число печатают, там оно мнемонично.
- Цепочка опровержений (side/function-поля → mirror_to-связь → знак номера) — в eda_ir_design.md,
  чтобы не переоткрывать.

### Контейнер платы `<layout>` — ОДНА схема, N плат (LibrePCB-модель)
Мотивация — реальная боль: (1) перебор компоновок копированием дизайна теряет правки схемы
при откате; (2) одна схема → две платы разного форм-фактора (девборд + миниатюра) при копии
теряет связь схема↔плата. Обе — один корень: копирование рвёт «схема и плата = представления
одной сущности». LibrePCB развязывает: одна электрическая истина, N физических реализаций.
- **`<project>` = одна электрическая истина (schematic + modules) + N `<layout>`.** Кардинальность
  1-схема-N-плат. Удалил неудачный layout → схема и остальные платы целы; правки схемы видны
  во всех layout.
- **SHARED (из схемы, общее всем платам):** компоненты, нетлист, атрибуты (вкл. value).
  **PER-LAYOUT (физика, своё у каждой):** placement, медь/трассы, board outline, via, pour.
  Электрика общая, пространство — на плату. Совпадает с делением «схема=связность, плата=место».
- **Электрическая связь ⟺ наличие PAD (smd/th). Единственный критерий.** «Board-only» — НЕ
  категория, а «объект без падов» (вычислимо, не хранимый флаг — как медность=`|n|<100`).
- **Беспадовые объекты (лого/репер/крепёж) — два легальных пути, выбор пользователя:**
  (A) прямо в layout из библиотеки → PER-LAYOUT (на одной плате); (B) компонент символ+футпринт
  БЕЗ пинов/падов в СХЕМУ → ALL-LAYOUTS (виден везде, ведётся из схемы). Оба корректны
  ([[feedback_no_pandering]]). «Слишком велик на mini» и т.п. — ответственность пользователя,
  не запрет системы (позже — DRC-предупреждение).
- **Глобальные атрибуты — PER-DOCUMENT.** Каждый документ-холст (schematic И каждый layout)
  несёт свой набор глобальных атрибутов (имя платы, версия, дата, форм-фактор…). У devboard и
  mini они РАЗНЫЕ — это разные физические изделия. `>DOCUMENT@VERSION` в титульном блоке
  разрешается в атрибуты ТЕКУЩЕГО холста → на каждой плате свой (тот же механизм, что пересчёт
  плейсхолдеров при смене варианта, только ось = layout). НЕ путать с shared-атрибутами
  компонентов (те общие всем платам).
- **Вариант сборки × layout — ОРТОГОНАЛЬНЫ** (вариант = что populate + значения; layout = где
  лежит). Devboard и mini каждый собираются в любых вариантах.
- **Набор компонентов ОДИН на все layout** (прямое следствие shared-нетлиста). Плата,
  требующая ДРУГИХ устройств, — это ДРУГОЙ дизайн (другой проект): живую связь между
  проектами с разным составом сознательно НЕ обеспечиваем — принципиально слишком
  хлопотно, граница модели. Различия в НАЧИНКЕ одного состава (что запаяно) — это ось
  вариантов, не layout.
- **Идентичность компонента = REFDES. UUID в IR НЕТ и НЕ БУДЕТ.** Placed `<element>`
  ссылается на shared-инстанс по REFDES; переименование — обычная транзакция редактора
  по одному файлу (каскад на все layout). UUID в KiCad — легаси-костыль: схема, где R1
  на схеме и R1 на плате — разные сущности, не проект, а бессмыслица, поддерживать её
  представимость незачем. При импорте из KiCad компоненты скорее всего тоже резолвим по
  refdes (уточнить при KiCad-board-импорте: действующий СХЕМНЫЙ импорт связывает
  footprint↔symbol по path/UUID — при расхождении refdes'ов схема/плата это кандидат
  на hard reject как «бессмысленный проект», см. выше).
- **ИМПОРТ Eagle создаёт РОВНО ОДИН layout** (Eagle = 1 схема + 1 плата, N не умеет). Модель
  проекта под N layout закладываем, но импортёр наполняет один; N — фича редактора. (Тот же
  приём, что плейсхолдеры/варианты: модель шире наполняемого импортом.)

## Унификация слоёв футпринта и платы — контейнеры упразднены

**Найдено пользователем при ревизии board-раздела ir_schema.md (2026-07-08):** механизм
слоёв был реализован ДВАЖДЫ — футпринт кодировал слой ТЕГОМ-КОНТЕЙНЕРОМ
(`<silk_top>…</silk_top>`, закрытый список из ~10 имён, все парные), плата — атрибутом
`layer` со знаковым числом. Симптомы: семистрочная таблица соответствия «футпринт↔плата»
в ir_schema.md (один факт, два кодирования — нарушение редукционизма); словарь контейнеров
кода разошёлся со словарём документа (`cream_top` vs `paste_top`, слой `labels`,
отсутствие масок); геометрия футпринта на standalone-слое (Milling-паз, Holes, Document)
была НЕВЫРАЗИМА вовсе — парсеры молча дропали; Eagle tNames(25)/tValues(27) сливались в
один `labels` и на экспорте оба уезжали на 25.

**Решение: подход к слоям в библиотеке (и редакторе футпринтов) — ТОТ ЖЕ САМЫЙ, что в
редакторе плат.** Геометрия футпринта — прямые дети `<footprint>` с `layer="[!][-]N"`;
знак в футпринте стороно-относителен (`+` = сторона монтажа); резолв при размещении —
чистая арифметика (`side="bottom"` — сменить знак парным, standalone не трогать,
геометрию отзеркалить); таблица соответствия растворилась. `<smd>`/`<pad>`/`<hole>` слоя
не несут (медь по построению / сквозные), редкий far-side smd — явный `layer="-1"`.

- Правка: ir_util.py (канонические константы, `is_copper`, `parse_layer`), все три
  парсера (kicad/eagle/altium), все три экспортёра, svg_renderer, ir_schema.md.
- Побочные улучшения точности: Dwgs.User/Cmts.User → честный бессторонний `148`
  (Eagle Document 48, не tDocu); tNames/tValues разделились (125/127); B.Fab/B.CrtYd/
  B.Mask у KiCad перестали дропаться; standalone-слои в футпринте выразимы.
- Проверено: KiCad round-trip зелёный (vimdrones/multigate/sheets/phil), rtfp-harness
  (rot=30 сохраняется), Eagle-экспорт несёт правильные номера (1/21/27/39/48/51),
  Altium-экспорт собирается (DbLib/PcbLib на phil).

### Standalone-слой в футпринте при переносе на другую сторону — БЕЗ автосоздания пары

Прямой вопрос пользователя («если футпринт использует непарный слой — создавать ли
парный автоматически при переносе на bottom?») — ответ НЕТ, полагаемся на существующие
слои документа:
1. Автосоздание не может быть единообразным: легитимные standalone-слои футпринта
   (Milling, Dimension, Drills, Document) — БЕССТОРОННИЕ физические факты, авто-`−146`
   был бы слоем-фантомом; выборочное автосоздание = угадывание намерения = эвристика.
2. Правило ЕДИНО с уже решённым MIRROR: парный → смена знака; standalone → зеркалится
   на месте, слой не меняется.
3. «Слой создаётся явно» — уже закон (пара = два явных создания); размещение компонента
   не должно молча рождать слои.
Следствие (осознанное): результат переноса детерминированно зависит от текущей таблицы
слоёв документа — пользователь управляет одним явным действием (объявить пару).

### Схемные слои НЕ унифицируются с платными — осознанно (2026-07-08)

Прямой вопрос после унификации футпринтов: «а схемная часть? там тоже слои». Ответ —
оставляем строковые имена (`NETS`/`SYMBOLS`/`NAMES`/`VALUES`/`INFO`/`GRAPHIC`/`USER`/
`FRAME`), НЕ переводим на числа:
1. Это НЕ двойное кодирование одного факта: схемный объект никогда не попадает на плату —
   нет ни перехода, ни таблицы соответствия, ни объекта, живущего в обоих мирах (в отличие
   от футпринтов, где один объект пересекал границу). Редукционизм не нарушен.
2. Схемный layer структурно инертен (даже NETS/FRAME определяются контейнером/ролью, не
   атрибутом) — на нём висит только цвет/группировка, переделка в любой момент дёшева.
3. Числовая машинерия платы (знак=сторона, |n|<100=медь, анти, flip) на схеме не имеет
   референта — был бы мёртвый груз. Причём Eagle-числа 91–97 взять «как есть» нельзя —
   коллизия с медным диапазоном.
Единственный настоящий открытый вопрос — единая ли CLI-адресация слоёв схемного и платного
холстов в БУДУЩЕМ РЕДАКТОРЕ (номер = публичный API объявлен для платы). Это решение уровня
редактора; пересмотреть при проектировании его CLI, не раньше.

### Производные каналы отображения — слои редактора, которых нет в данных (2026-07-09)

Возникло из вопроса «а via не получают слоя?» при разборе junk-списка board-импорта
(Eagle 17/18/19/23/24 дропаются). Расцепили два уровня, которые Eagle склеивает молча:

1. **Слой как факт в данных.** Via/pad слоя НЕ несут — тег уже полный факт («вся ось
   стека»), атрибут `layer` был бы двойным кодированием (только что выкорчеванным из
   футпринтов). Airwires в данных не существуют вовсе (вычислимы из contactref минус
   разводка). Одиночный номер и не выразил бы будущие blind/buried — их выразит span.
2. **Слой как канал видимости редактора.** Смотришь inner-медь — via видеть НУЖНО, и
   переключать одной ручкой. Eagle прав своим слоем 18; неправ тем, что подаёт каналы
   в общем списке как равноправные данные-слои.

**Решение: производный канал отображения** — номер, существующий только в машинерии
рендера/редактора; членство по ТИПУ объекта, не по хранимому атрибуту; **в файл эти
номера не пишутся никогда**. Диапазон `|n| >= 900` в файле нелегален (резерв каналов).
Канон: 901 Vias, 902 Pads, ±903 Origins (пара — сторона элемента), 904 Airwires,
905+ резерв (DRC/ERC-маркеры при появлении). Константы — ir_util.py.

Перебор прочих кандидатов дал границу понятия:
- Чистые каналы — только Vias/Pads/Origins/Airwires (членство по типу, в данных слоя нет).
- **Производные вклады в существующий данные-слой** — НЕ канал: маска/паста (129/131)
  несут и явную геометрию (aperture-пады), и вычисленные раскрытия падов; Drills/Holes
  (144/145) — и юзерскую графику, и отрисовку drill-атрибутов. Канал уже есть, вычисленная
  часть — ещё один источник отрисовки на нём.
- Заливка полигонов (контур хранится, fill вычисляется) — режим рендера своего слоя,
  не канал.
- Понятие общее, не board-частность: на схеме пин-имена/номера (Eagle 93/94) — те же
  каналы; пригодится при рендере схемы.

Попутно смягчена формулировка ir_schema.md про via: «только сквозные» — осознанное
ограничение v1 с явным путём расширения (span-атрибут, отсутствие = through), а не
«по определению навсегда»; hard reject blind/buried при импорте остаётся.

### Drills/Holes — тоже каналы, и ОДИН канал, не пара (2026-07-09)

Продолжение производных каналов. Вопрос «зачем Eagle разделяет 44 Drills / 45 Holes» —
это PTH/NPTH-граница (металлизированное сверло падов/via против голого крепёжного
отверстия; у фабрики это разные файлы сверловки и разные проходы процесса). Первый
порыв — завести ДВА канала по образцу Eagle — опроверг пользователь из практики:
в гербер-выходе сверловка всегда сливается в один слой (сам Eagle своим штатным
CAM-джобом льёт 44+45 в один Excellon — отсюда классическая болячка «крепёж
металлизировали»).

Решение: PTH/NPTH-факт живёт в ТИПЕ объекта (`pad`/`via` = plated по построению,
`hole` = нет) — терять нечего; канал семантики не несёт, это ручка видимости, и
смотреть сверловку хочется целиком. Один `CHANNEL_DRILLS = 905`. Граница всплывёт
в CAM-экспорте из типов, когда до него дойдём.

Попутно вычищен рудимент вчерашнего механического маппинга «+100»: `LAYER_DRILLS`/
`LAYER_HOLES` (144/145) удалены из ir_util/PKG_LAYER_MAP/kicad_exporter/ir_schema —
Eagle 44/45 суть каналы отрисовки drill-атрибутов, объектов-носителей на них не
бывает (невозможный залётный объект упадёт в формулу +100 как юзерский слой).
Гибридом «данные-слой + вычисленные вклады» остаются только маска/паста 129/131.

### Резы и металлизация: слияние 20+46 → 120, слой 147 PLATING (2026-07-09)

Длинная цепочка с тремя разворотами — фиксирую целиком, чтобы не перепройти.

**Проблема.** Металлизированные пазы: KiCad/Altium выражают их овальным отверстием
ПАДА — модель не берёт Г-образные пазы (реальная практика пользователя). Обобщать
drill на овал ЗАПРЕЩЕНО: drill = сверление, сверлом, только круг; паз = фрезеровка,
другой процесс. Флаги документа (KiCad Board Setup «plated edge») — дерьмо собачье:
похоронено в настройках, визуально незаметно. Металлизация — геометрический факт,
жить должен на холсте.

**Двойственность Eagle 20/46.** Слой 20 участвует в DRC (полигоны держат зазор),
Milling 46 — нет, и это НЕ баг, а нужная степень свободы: металлизированному пазу
медь нужна ВПЛОТНУЮ (гальванике врастать), участие в DRC отогнало бы её. Практика
пользователя: паз на Milling + свой юзерский слой PLATED (156) поверх края + слова
в комментарии к заказу.

**Решение (вердикт пользователя, 4 пункта):**
1. Слои 20 и 46 сливаются в ОДИН слой резов `120` — «здесь материала нет» один факт;
   внешний контур = самый внешний режущий контур, не сущность.
2. Канонический слой `147 PLATING` (данные-слой, standalone): стенки реза
   металлизированы там, где рез накрыт залитым следом маркера. Частичная
   металлизация = маркер короче реза, сегменты контура резать не надо (главный
   аргумент против атрибута plated на сегментах).
3. Импорт Eagle: 46 → рез на 120 ПЛЮС копия-маркер на 147 (Milling на практике =
   «паз, который фабрика металлизирует»). Юзерский Eagle 156 ↔ 147 канонизирован
   (иначе 147 не round-trip'ится).
4. PLATING — часть МОДЕЛИ: будущий DRC/пересчёт заливок — голый рез отталкивает
   медь (зазор), накрытый PLATING — зазор снят, медь вплотную; маркер БЕЗ реза на
   120 под ним = ошибка «plated edge in an unexpected place» (нет торца — нечего
   металлизировать), в т.ч. для маркеров из футпринтов при размещении.

**Семантика геометрии резов — результат, не процесс** (как у полигонов: контур, не
заливка). Снимает двойственность «след фрезы или нулевой контур» — легальны обе
манеры, у каждой одно значение: width>0 = удаляется залитый след этой ширины
(скругления = след круглой фрезы, физически честно); width=0 = рез по линии,
ширина реза не утверждается (компенсация фрезы — CAM/фабрика).

**Кастелляции** — выразимы композицией, без новых сущностей: smd-пад + полигон меди
+ раскрытие маски + линия PLATING в футпринте; ставить только поверх линии контура
на 120 (то же DRC-правило).

**Экспорт в Eagle** — детерминированная инверсия импорта, без геометрии: рез на 120
с ТОЧНОЙ копией на 147 → ОДИН объект на 46 Milling (копия не эмитится; Eagle-DRC не
гонит медь от паза) — реализовано в eagle_exporter (_geom_sig-фолд в export_package,
понадобится и board-экспортёру); прочие 120 → 20, прочие 147 → 156 PLATING
(задекларирован в data/eagle_layers.xml, magenta) + лог «сообщить фабрике словами».
KiCad: резы → Edge.Cuts, PLATING → Dwgs.User (видимая заметка; Edge.Cuts сделал бы
маркер резом).

**Отложено:** импорт KiCad-плат с ОВАЛЬНЫМИ отверстиями падов (USB-C и т.п. —
массовые): drill строго круглый, овал придётся раскладывать (пад + рез с PLATING?
hard reject?) — решать на живом файле при KiCad-board-импорте, для Eagle-плана
блокера нет. LAYER_MILLING=146 удалён из ir_util; PKG_LAYER_MAP 46→'120',
_PKG_LAYER_COPY {46:'147'} (единый вход convert_geometry_mapped — футпринт и плата).

### ОТЛОЖЕНО: семантика контура полигона — вершины vs граница меди (2026-07-09)

Замечено пользователем на рендере luminoso: границы pour идут ТОЧНО по вершинам,
width не учтён. Расхождение семантик: Eagle — медь = контур + width/2 НАРУЖУ (штрих
входит в заливку), KiCad/Altium — контур зоны И ЕСТЬ финальная граница меди. IR
сейчас молча хранит Eagle-семантику (вершины + width как есть) — прямой экспорт в
KiCad/Altium даст медь, УСОХШУЮ на width/2 по периметру.

Правильное направление (не решено окончательно): канон IR = «контур — финальная
граница меди» (принцип «результат, не процесс», как у резов) + нормализация при
импорте из Eagle офсетом контура на width/2 наружу. НЕ делается мимоходом: офсет
полигона с дуговыми рёбрами (vertex curve) — настоящая вычислительная геометрия
(самопересечения, вырожденные углы); тот же вопрос затрагивает анти-полигоны и
роль width как минимальной ширины штриха заливки. Решить ДО первого экспорта
плат в KiCad/Altium; для Eagle→Eagle round-trip расхождения нет (семантика
симметрично обратна на выходе).

### Board-only элементы и модули×плата — два решения интеграции (2026-07-09)

**Board-only беспадовые элементы** (luminoso: U$1/U$2 арт-текстуры, TEXTUREREF1/2 —
в схеме ОТСУТСТВУЮТ). Реализован записанный случай (А) «беспадовый объект прямо в
layout»: `<element name footprint="PKG">` БЕЗ схемного инстанса, сам `<footprint>`
embedded прямо в `<layout>` (per-layout по построению, несёт library=). Инвариант
проверяем: без инстанса разрешено ТОЛЬКО с footprint-атрибутом и ТОЛЬКО если в
футпринте нет падов; пады без схемы → hard reject («электрическая связь ⟺ пад»).

**Модули на плате** (modtest). Ground truth: Eagle расплющивает module-инстансы
ДВУМЯ орфографиями — `NAMUR3:C1` НАТИВНО (инстанс без offset; ровно наш канон) и
численно `C101` = C1 + offset 100 (offset записан в moduleinst). Канон IR:
`<element name="INST:REFDES">` — адрес = дизайнатор модульного инстанса + внутренний
refdes; импорт нормализует численную орфографию вычитанием ЗАПИСАННОГО offset (чистая
арифметика), экспорт восстанавливает её же. Иерархия схемы не тронута. Автопредсказание
offset НЕ понадобилось: без offset Eagle сам пишет двоеточие.

**Цепи модулей на плате**: Eagle переименовывает module-crossing цепи в мусор
(N$1009, '1AI1') — имя сигнала = board-факт, хранится как есть со строкой в лог
(«no schematic net, kept as board fact»); связность держат contactref. Цепи,
дошедшие до топ-уровня через порты, носят топ-имя и валидируются по нему.

**Round-trip критерий (шаг 7) ЗЕЛЁНЫЙ**: roundtrip_eagle_board.py — структурное
сравнение (элементы package/x/y/rot; сигналы contactref/wire/via/polygon; plain
по слоям) с допуском 2 µm (Eagle хранит суб-µm координаты трассировки под углом,
канон IR — целые µm; квантованное округление флапает на границах вёдер → парная
сверка с толерансом). luminoso (105 эл., 54 сигн., 4 слоя) и modtest (56 эл.,
104 сигн., модули обеих орфографий) — OK.

### Канон дуги — КОНЦЕВАЯ форма (x1 y1 x2 y2 curve), не центр-форма (2026-07-09)

Найдено на первой живой проверке board-экспорта реальным Eagle (luminoso): по всем
стыкам дуга↔провод Eagle рисовал огрызки airwires на слое 19 — микрозазоры 0.7–0.9 µm.
Причина: старый канон <arc cx cy r start sweep> (целые µm) — концы дуги ПЕРЕСЧИТЫВАЛИСЬ
из округлённого центра и не попадали в квантованный конец соседнего сегмента. Провод↔
провод не страдал (оба конца квантуются одинаково), страдала только дуга: её концы были
производными.

Решение: канон = форма Eagle — <arc x1 y1 x2 y2 curve width>. Связность меди — контракт
КОНЦОВ; в концевой форме все сегменты на одной µm-решётке, стыки точны ПО ПОСТРОЕНИЮ.
Это ответ на давнее недоумение пользователя «почему у Eagle такие странные дуги»:
неудобная для геометрии форма куплена ради инварианта связности. Центр-форма хранит
процесс, не результат (наш же принцип). Проверено: near-miss стыков в переэкспорте — 0.

Следствия по конвейеру:
- eagle_parser/exporter: конвертация дуг УМЕРЛА (родная форма, атрибут-копия µm↔мм);
  eagle_arc и _arc_to_wire удалены; центр-математика — ir_util.arc_center/arc_params/
  arc_mid/arc_endpoints (единственный дом).
- KiCad: start/end КиКада и есть концы — проходят точно, 3-точечный фит даёт только
  знаковый угол; экспорт вычисляет mid через arc_mid.
- Altium: единственный центр-формный сосед — конвертация на его границе (arc_endpoints
  при импорте, arc_params при экспорте).
- Рендер: SVG-дуги эндпоинт-параметризованы — концы трансформируются как точки,
  зеркало = смена знака curve, угловой бухгалтерии не осталось (и в place_ir_element).
- ПОЛНАЯ ОКРУЖНОСТЬ — НЕ дуга (вырожденная хорда): контурные окружности KiCad/Altium
  теперь <shape roundness=100 outline=...>; ветки «sweep>=360» умерли.
- Остаточный артефакт: 1 µm флаппинг на ровно половинных границах кванта (11.1715) —
  свойство int-µm канона, смежные концы квантуются одинаково, связность не трогает.

### Board-атрибуты элементов: слияние в shared-инстанс, копии при экспорте (2026-07-10)

Пользователь заметил пустые атрибуты у элементов в экспортированной плате и УГАДАЛ
причину: Eagle держит значения атрибутов ПРЯМО на board-элементе, и они могут жить
ТОЛЬКО там — правка/добавление в board-редакторе НЕ синхронизируется в .sch-парт.
Ground truth luminoso: 75 элементов с brd-only атрибутами (486 записей; sch строго ⊂
brd; IC6 LCSC#=C2079 существует только на плате). Прежняя запись «для Eagle рассинхрон
значений невозможен (shared)» ОПРОВЕРГНУТА данными — импорт молча терял эти значения.

Решение (модель атрибутов IR не меняется — один дом значений, shared-инстанс):
- ИМПОРТ: board-значения сливаются в инстанс ОБЪЕДИНЕНИЕМ, детерминированно:
  отсутствовал → добавить (в лог); пустое vs непустое → непустое побеждает;
  КОНФЛИКТ непустых → hard reject («ни одна сторона не авторитетна, примири в Eagle»).
  Модульные части: объединение по ВСЕМ инстансам-сиблингам теми же правилами
  (расхождение непустых между сиблингами невыразимо — канва модуля общая; ground
  truth modtest: расходится только присутствие пустого ANCHOR у F1 — объединение).
- ЭКСПОРТ: копии всех резолвнутых атрибутов регенерируются на элемент
  (display="off", координаты элемента, tValues) поверх shown/hidden-оверрайдов.
- Верификатор: множество (имя,значение) исходника обязано быть ПОДМНОЖЕСТВОМ
  переэкспорта (объединение легитимно ДОБАВЛЯЕТ sch-сторону на плату): luminoso
  486 выживают +257 добавлено, modtest 481 +151.

Попутный капкан: ET.Element БЕЗ ДЕТЕЙ — falsy; `dict.get(a) or dict.get(b)` молча
терял найденные инстансы без <attr>-детей (ровно те, ради которых слияние). Только
явный `is None` — который deprecation-warning питона и так требует.

### VALUE на board-элементе: регистровый канон + деривация Eagle (2026-07-10)

Пользователь заметил потерю VALUE в переэкспорте; вскрылись три факта разом:

1. **Концепция VALUE в IR ЕСТЬ** — это атрибут `value` (нижний регистр) на shared-
   инстансе: схемный импортёр лоуэркейсит имена атрибутов (Eagle-имена регистро-
   нечувствительны, UI показывает верхним). Board-sink нёс имена в ВЕРХНЕМ →
   слияние плодило регистровые дубли (lcsc#+LCSC#), а экспорт искал 'VALUE' и не
   находил 'value'. Канон: на Eagle-границе имена атрибутов лоуэркейсятся на входе
   и апперкейсятся на выходе; сравнение/дедуп — по нижнему регистру.

2. **Eagle ЗАПЕКАЕТ неявный value в element@value** (в отличие от .sch-парта, где
   отсутствие value= достаточно): деривация = deviceset + technology + device.
   В IR это компонент-имя (оно и есть deviceset+technology после per-technology
   split) + вариант футпринта (несёт имя device дословно, с ведущим дефисом).

3. **uservalue="yes" отменяет деривацию**: значение — текст пользователя, и ПУСТОЕ
   легально (luminoso SJ1/SJ2: uservalue=yes, value='' в .brd при том, что у
   CJ78L05 с uservalue=no запечено 'CJ78L05-5-SOT89'). Правило экспорта:
   resolved value → если пусто И uservalue!=yes → деривация → иначе как есть.

Верификатор дополнен: element@value входит в поэлементное сравнение. Оба борда
зелёные (486/+29 и 481/+23 атрибутных записей).

### КОНЦЕПТ (редактор библиотек): характерный набор атрибутов библиотеки (2026-07-10)

Из разбора организации библиотек (разъёмы CON-2P против диодов):

**Правило главной оси**: главная ось библиотеки = то, что известно В МОМЕНТ рисования
схемы; решаемое позже — варианты футпринтов, запрашиваемое иначе — атрибуты + фильтр.
Разъёмы: интерфейс тривиален (N пинов) → группировка по пинам ПРАВИЛЬНА, семейство =
отложенное до layout решение (вариант) + FAMILY/PITCH-атрибуты для закупочного запроса.
Диоды: проектный запрос сам параметрический → идентичность = партномер, корпуса =
варианты, характеристики = атрибуты. Дерево — это VIEW над атрибутами, не хранение
(редукционизм); браузер пула строит дерево на лету по любой оси.

**Характерный набор атрибутов библиотеки** (вердикт пользователя): у библиотеки может
быть объявленный РЕКОМЕНДУЕМЫЙ набор атрибутов, наличие которых на каждом девайсе —
хороший тон: диоды — Vmax/Vdrop/Imax; МК — FLASH/RAM/MAX_FREQ. Принуждение МЯГКОЕ
(линтер-предупреждение при сохранении/ревью библиотеки, НЕ reject) — та же механика,
что строгость вычислителя `=`. Смысл: параметрический фильтр честен, только когда
атрибут есть у всех (иначе молча врёт пропусками). BOM не взрывается by construction:
маршрутизация по type уже в модели — sim/general-атрибуты в BOM не идут, колонки =
объединение реально присутствующих bom-атрибутов.

Гигиена девайсов (сегодняшний CON-2P/DS1069M): девайс = ФИЗИЧЕСКИЙ вариант; закупочные
альтернативы одной физики — атрибуты, не девайсы. Линтеру библиотек (УТОЧНЕНО
пользователем): сигналить, когда ОДИН девайссет несёт один и тот же футпринт два и
более раз (внутри компонента пакет продублирован — как CON-2P с B2B-XH-A дважды) →
предложить схлопнуть в один девайс с атрибутами. РАЗНЫЕ девайссеты, использующие общий
пакет — норма (каждый второй 0603 на свете), линтер молчит.

### РЕШЕНО (реализация отложена): диспетчеризация 3D-модели по атрибуту (2026-07-10)

Проблема: «один футпринт — одна модель, соответствие по имени» вынуждает размножать
футпринты ради внешности (LED0603_RED/GREEN — атрибут COLOR, запечённый в имя =
двойное кодирование; конфликтует с гигиеной девайсов, толкающей цвета LED в атрибут).

Переборка «где ещё» дала КЛАСС случаев (критерий пользователя «не вводить механизм
ради одного случая» пройден): одно посадочное место, параметричная внешность —
LED (цвет), штыревые гребёнки/стойки (высота пластика), тактовые кнопки (актуатор),
мезонинные разъёмы (stack height — геометрическая правда для контроля столкновений),
клеммники (цвет), радиальные электролиты (банка, когда courtyard совпадает).
Второй домен той же формы — выбор SIM-модели по атрибуту (BC847A/B/C) — отложен
вместе с PI/SI, но синтаксис условия делается общим заранее.

Механизм (ПЕРЕСМОТРЕН по UI-флоу пользователя — ключ БЕЗ имени атрибута): вариант
модели = `<model3d variant="RED" ...>`; ключ — голое ЗНАЧЕНИЕ. Рационале: футпринт
создаётся РАНЬШЕ девайсов, имени атрибута (COLOR/TINT/...) в этот момент не
существует. Резолюция по инстансу — поиск ключей среди ЗНАЧЕНИЙ ВСЕХ его атрибутов:
0 совпадений → безусловная запись (fallback); ровно 1 → она; ≥2 РАЗНЫХ ключа →
КОНФЛИКТ: маджента-заглушка + лог/DRC («X=RED и Y=BLUE оба претендуют — дай детали
один составной ключ»), никогда не «первый попавшийся». Правило: у футпринта ОДНА ось
внешности; композитная внешность = композитное значение (двухцветный LED =
COLOR=RED-GREEN со СВОЕЙ двухцветной моделью; клеммник зелёный корпус/оранжевый
рычаг = GREEN-ORANGE). Линтер библиотеки ловит опечатки: вариант, чей ключ не
встречается ни в одном значении атрибутов девайсов библиотеки → предупреждение.
UI-флоу (вердикт пользователя): ПКМ на футпринте → ASSIGN 3D MODEL; моделей не было
→ сразу 3D-вьюпорт (первая запись = fallback автоматически); модель была → модальное
окно с именем нового варианта.
УТОЧНЕНО (вопрос пользователя про метаданные размещения): диспетчер размножает
ЦЕЛЫЕ <model3d>-записи — каждая самодостаточна и несёт СВОЙ tx/ty/tz/rx/ry/rz
(T·R — факт о паре «файл × посадочное место», живёт в футпринте, ниже девайса;
у гребёнок разной высоты origin STEP-ов гуляет, общие метаданные не работают).
Имя файла по-прежнему НЕ хранится (канон «имя = имя футпринта» расширяется, а не
ломается): условная запись выводит имя как <footprint>_<VALUE> (LED0603 + COLOR=RED
→ LED0603_RED), безусловная — как раньше. Ранний набросок с file= отменён. Tint/перекраска одной модели ОТВЕРГНУТА
(перекрасить колбу, но не выводы = знать, какое тело колба = эвристика по STEP).
Экспорт в Eagle/KiCad/Altium: футпринт размножается на ВЫХОДЕ (LED0603_RED)
автоматически — дублирование переезжает в ограниченные форматы, где ему место.

Дополнение (демо/позиционирование): механизм требует образцовых демо-проектов с
контрастом «KiCad: все LED серые / swift: у каждого свой настоящий цвет». Суть
питча: 3D — ПРОЕКЦИЯ ДАННЫХ, не иллюстрация (серые LED KiCad = модель-файл,
отвязанный от данных). Демо бьёт в одну точку тремя проявлениями одного факта:
смена COLOR на инстансе синхронно меняет 3D-колбу, строку BOM и fab-подпись
(>COLOR) — модели можно верить, ей неоткуда разойтись с платой. Кандидаты:
luminoso (LED-арт, цвет — суть устройства); гребёнки/мезонины с высотами —
инженерный вариант («поменял партномер атрибутом — 3D показала столкновение
с корпусом»). UI-концепт обсуждён: «правило модели» с прогрессивным раскрытием
(умолчание — одна строка как сегодня; кнопка «зависит от атрибута…» → WYSIWYG-
таблица when-списка с обязательной строкой fallback и живым предупреждением о
непокрытых значениях); автоподбор файлов по суффиксу — ТОЛЬКО как предзаполнение
формы, подтверждаемое человеком; значок-цепочка у атрибута на инстансе
(«участвует в выборе 3D»); нерезолвнутый инстанс в 3D — маджента-заглушка по
courtyard, не тихий пропуск; CLI: `model FP by ATTR VAL=file.step *=fallback.step`;
будущий sim-диспетчер обязан выглядеть ТАК ЖЕ (один жест на все условные привязки).

Дополнение (статус реализации): Eagle-сторона ОСТАЁТСЯ одномодельной («1 футпринт —
1 модель» в сайдченнеле; вердикт пользователя — переделка его редактора моделей и
тестирование НЕ сейчас; расширение формата <!--3d:...--> ключом "variants" обсуждено
и отложено НА БУДУЩЕЕ). В IR множественность закреплена СПЕЦИФИКАЦИЕЙ уже сейчас
(ir_schema.md "<model3d>": variant-атрибут, правила резолюции) — формат готов принять
редактор, не ломаясь; импортёры порождают максимум одну безусловную запись.

## Формула стека платы + КОНЦЕПТ редактора: пресеты и визуализатор (2026-07-11)

Спецификация — ir_schema.md «Формула стека»: `stack="35[100:4.3]35[1240:4.6]35"`,
весь физический стек одной строкой (развитие идеи Eagle layerSetup: у Eagle порядок
в формуле, толщины отдельными UI-полями — неизящно; мы сливаем). `copper=` упразднён
(число слоёв производное), core/prepreg не различаем (решение фабрики; при будущих
via-спанах вычислимо из скобок ламинации), диэлектрик несёт опциональные `:ε:tanδ`
(дефолты опишет SI-пакет swift; этим знание стека для SI исчерпывается). Via-спаны —
эскиз вложенных скобок = дерево последовательной ламинации; ГИПОТЕЗА «частично
перекрывающиеся спаны нефизичны» проверяется по литературе ДО канонизации.

КОНЦЕПТ редактора (тривиальное, но обязательное — формула голым текстом пугает,
опыт Eagle):

- **Пресеты стеков**: разумный набор дефолтных формул (типовые 2/4/6-слойки

- **Визуализатор стека**: рендер формулы как сечения сэндвича — формула УЖЕ
  является сечением, записанным текстом, так что это механическая отрисовка
  поверх обязательного парсера грамматики; заодно UI-валидация (глазами видно,
  что набрал). Человек смотрит на картинку — формула живёт в файле.

### Внешность платы: MASK_COLOR/SILK_COLOR/FINISH — конвенциональные атрибуты layout (2026-07-11)

Спецификация — ir_schema.md «Внешность платы». Суть: цвета изготовления — факты
ЗАКАЗА, per-layout; живут в общем мешке <attr> холста под конвенциональными

## Заливка полигонов: МОДЕЛЬ ПЕРА (штриховка), булевы движки отвергнуты как ядро (2026-07-11)

Контекст: экспорт pour->KiCad zone поднял отложенную семантику контура; перебор
библиотек (Clipper2/CGAL/CavalierContours/Boost.Polygon/GEOS/своя) упёрся в
вопрос пользователя: «а нужны ли нам вообще БУЛЕВЫ операции над полигонами?»
Ответ: нет. Канон:

- **Полигон = просто замкнутый контур из тех же line/arc + параметры.** Не
  уникальный объект. Семантика хранимого контура: ОСЕВАЯ ЛИНИЯ ПЕРА + width
  (Eagle-семантика дословно): медь = обводка контура пером w ∪ внутренность.
- **Заливка (swift) = модель пера/штриховки** — родная модель Eagle (заливал
  штрихами толщины width; отсюда скруглённые углы, width=мин-медь, fill% =
  скважность; корни — векторные фотоплоттеры). Вычислительно: скан-строки,
  интервалы допустимых центров пера = 1D-неравенства на SDF примитивов
  (квадратики для линий/дуг, точные корни). Строки независимы -> GPU/все ядра,
  инкрементальный пересчёт задетых строк. Дуги аналитичны — ноль угловатости
  (угловатость Clipper = уплощение дуг, не вкусовщина). Тот же SDF-оценщик,
  что рендер и мех-DRC 3dview — ОДИН геометрический мир.
- Следствия бесплатно: мин-ширина меди невыразима-по-построению (у полигонов
  её ДЕТЕКТИРУЮТ erode/dilate-трюком — источник скруглённых внутренних углов
  KiCad); термал-спица = штрих через центр пада; связность/ratsnest/острова =
  union-find по перекрытиям интервалов соседних строк; анализ (токи/тепло/PI)
  получает ГОТОВУЮ структурированную сетку — штрих = цепочка резисторов,
  перекрытие = узел, R(точка,точка) = разреженная линейная система.
- **Явный векторный контур нужен только на границах системы**: (а) Babel ->
  KiCad zone: офсет контура наружу на w/2 (жёсткая граница KiCad) — одна
  дуго-нативная функция, самопересечение результата -> hard reject + лог до
  первой живой платы; (б) CAM swift (герберы) — редкая офлайн-операция, можно
  сколь угодно медленно (изолиния на допуске или точечная векторная математика
  — выбор при проектировании CAM); фабрики принимают и старые диалекты,
  распухание файлов в 2026 — не аргумент. Clipper2 остаётся в заднем кармане
  ТОЛЬКО как пограничный инструмент, в ядро не входит.
- Babel заливок не касается вообще (не редактор): контур+параметры насквозь,
  KiCad перезаливает по-своему. KiCad-ИМПОРТ zone (граница -> осевая линия):
  знак/величина офсета — по GT fill-семантики KiCad при реализации импорта.

## Термо-релиф: зазор ≡ clearance, ширина спицы производна (2026-07-12)

Обсуждение при отладке верхнего GND-полигона tolmach (в KiCad доезжали дефолтные
термо-свойства). Два решения, оба по «один факт — одно место»:

1. **Зазор термо-релифа ≡ clearance полигона.** Отдельного параметра термозазора
   в IR НЕТ (пользователю не нравится независимый параметр, и это лишний факт).
   Эффективный зазор = max(явный `isolate`, min clearance из `<rules>`) —
   min clearance жёсткий пол от фабрики, isolate только ДОБАВЛЯЕТ к нему
   (Eagle isolate=0 → DRC min). И локальный clearance зоны, и thermal_gap
   пишем этим max (иначе KiCad подставляет свой дефолт 0.5 мм). Eagle `slThermalIsolate` (напр. 10 mil) БОЛЬШЕ НЕ
   НЕСЁМ. KiCad-экспорт: `thermal_gap` = разрешённый clearance зоны (чинит баг
   «дефолт 0.5 мм»). KiCad-импорт: у них `thermal_gap` и `clearance` раздельны —
   расходящийся `thermal_gap` роняем в лог (независимый термозазор не моделируем).

2. **Ширина спицы производна от `pad.thermals`** (шкала 0–100, уже в IR), не
   хранится абсолютом. Пол ширины = `width` полигона (модель пера: заливка —
   штрихи одной толщины, спица тоньше одного прохода пера не существует).
   `thermals=100` → спица = `width` (жёсткий физ-упор, интерполяции не нужно);
   меньше `thermals` → шире. Экспорт: `thermal_bridge_width = max(width,
   f(thermals))`. Вырождение «перо толще пада» KiCad/фабрика разрулят сами
   (KiCad зажимает `thermal_bridge_width ≥ min_thickness`) — фиксировать отдельно
   не стоит (здравый смысл: заливок 2 мм пером не бывает). Обе чужих модели
   (Eagle «спица из width+пада», KiCad «bridge ≥ min_thickness») ПОДТВЕРЖДАЮТ
   наш вывод из пера. Бонус DRC swift: «перо слишком грубое для релифа пада» —
   готовый линт из width + размера пада.

### Контур из ДВУХ вершин: дуга и её хорда — настоящая площадь (2026-07-30)

`ir_util.offset_contour` требует трёх вершин, и это ограничение МОДЕЛИ, а не
приговор контуру. Две вершины охватывают пустоту только пока оба ребра
прямые; стоит одному нести `curve` — и получается сегмент круга, дуга плюс
замыкающая хорда. Ground truth из живой библиотеки, `CAP_SMD_6.3X7.7`
компонента `CPOL` в Base:

```xml
<polygon width="102" layer="151">
  <vertex x="-2200" y="2150" curve="88.5815" />
  <vertex x="-2200" y="-2150" />
</polygon>
```

Хорда 4300 µм, дуга 88.58°, радиус 3079 µм, стрелка 875 µм, площадь
2.59 мм² — метка полярности электролита на tDocu. Перу здесь нечего
скруглять: углов в контуре нет вовсе, есть только стык дуги с хордой, а
смещение наружу для такой пары — отдельная формула, которой в модели нет.

Поэтому такой контур сейчас НЕ ЭКСПОРТИРУЕТСЯ, и лог говорит именно это
(«a real area the pen model cannot offset yet, NOT exported»), а не «нечего
заливать». Формулировка важна: сообщение читает человек, который иначе
спишет запись в мусор и пойдёт дальше. Текст исключения в самой
`offset_contour` поправлен там же и по той же причине.

Ветка «две вершины и обе прямые» оставлена ради полноты, но, по замечанию
пользователя, такой полигон, похоже, невозможно создать ни в Eagle, ни в
KiCad — редакторы не дают замкнуть контур в отрезок. Если это подтвердится,
ветку можно будет убрать вместе с гвардом.

Чинить не стали сознательно: единственный известный случай — вариант
корпуса, который ни один экземпляр на плате не выбирает (`used by no element
on the board` в логе). Браться, когда такой контур встретится на
размещённом футпринте.

## 3D-модели в KiCad-экспорте платы: встраивание, checksum V1, закон поворотов (2026-07-15)

Полная цепочка Eagle+3D → IR → .kicad_pcb отлажена на maximus (654 модели,
622 top / 32 bottom, включая специально добавленный несимметричный U2 на
bottom) — визуальный ground truth: все модели на местах. Три факта:

1. **Встраиваем в плату, не sidecar-путь** (решение пользователя): KiCad-выхлоп
   и так неорганизован, embed ничего не ухудшает, и Altium позже тоже потребует
   встраивания — уникального пути всё равно не будет. Для Eagle и IR sidecar
   остаётся единственным каноном (бинарники в текстовый формат не встраиваем).
   Наш же проектный импорт требует embedded — теперь round-trip замкнут на
   собственном выхлопе. Формат: zstd + base64 (перенос по 76 символов,
   `|`-делимитеры), дословно по testData/video/video.kicad_pcb.

2. **Checksum embedded-файла ФАТАЛЕН и это MurmurHash3 с багом («V1»).**
   Релизный KiCad 10.0 не только пишет, но и ВАЛИДИРУЕТ checksum при загрузке:
   неверное значение → LoadBoard молча возвращает null, плата «не открывается»
   (найдено живым pcbnew-бисектом: скелет/данные подменялись по одному).
   Алгоритм: инкрементальный MurmurHash3 x64_128, seed 0xABBA2345, по
   РАСЖАТЫМ байтам, формат %016X h1‖h2 — но с багом хвоста: последний
   неполный блок дополняется нулями до 4-байтового выравнивания и ДОПОЛНЕННАЯ
   длина идёт и в tail-switch, и в финальный микс (mmh3_hash.h addDataV1).
   Master исправил хвост (канонический murmur), но V1 принимает как legacy —
   а вот релиз 10.0 канонический V2 НЕ принимает. Пишем V1 — валидно для
   обоих. Воспроизведено 23/23 на testData/video. Реализация:
   `kicad_board_exporter._kicad_mmh3`.

3. **Закон трансформации модели — порядок осей Эйлера, не знаки.**
   Offset: µm→mm, оси НАСКВОЗЬ без отрицания Y (offset живёт в MCAD-фрейме
   модели, не в Y-вниз фрейме футпринта). Поворот: IR компонует Rx·Ry·Rz,
   KiCad-файл хранит ОТРИЦАННЫЕ углы композиции Rz·Ry·Rx (диалог свойств
   показывает неотрицанные). Для чистых Z-поворотов порядки совпадают —
   поэтому наивная перестановка знаков «работала» на всех плоских корпусах
   и сломалась только на двухосевом LQFP100 (IR (0,−90,−90) ≡ диалог
   (90,0,−90)). Общий случай — пересборка матрицы:
   `kicad_exporter.model3d_kicad_xyz`, общая для библиотечного и board-путей.
   Bottom: model-блок в ЛОКАЛЬНОМ фрейме футпринта, flip KiCad применяет сам
   поверх нашей запечки — подтверждено визуально (U2).
   ИМПОРТУ из KiCad предстоит ровно обратная операция: разложение
   Rz·Ry·Rx-матрицы в Rx·Ry·Rz-углы + offset насквозь.

Попутно: проектный Eagle-импорт теперь копирует sidecar STEP-файлы
(`<src_stem>/` рядом с .brd → `<out_stem>/` рядом со .swprj,
`eagle_project_parser` → `_copy_step_files`); `<model3d>` в board-путь
протекал и раньше через общий `convert_package`. Модель без sidecar-файла =
документированная деградация (лог, плата валидна).

## Стек → KiCad (stackup): эмиссия сделана, правила импорта зафиксированы (2026-07-15)

`(stackup ...)` — опциональный блок ПЕРВЫМ в `(setup)` .kicad_pcb (KiCad пишет
его только после захода в Board Setup → Physical Stackup; без него KiCad
показывает дефолты 35µm/FR4). Экспорт (`kicad_board_exporter._emit_stackup`)
эмитит его всегда, из формулы стека:

- медь `(layer "*.Cu" (type "copper") (thickness мм))` — поячеечно из формулы;
- зазор `(layer "dielectric N" (type core|prepreg) (thickness мм)
  [(epsilon_r)] [(loss_tangent)])` — ε/tanδ ТОЛЬКО если есть в формуле;
  отсутствуют → поля не пишем, `material "FR4"` НЕ пишем никогда (не выдумывать
  SI-факты; pcbnew грузит без них — проверено оракулом в обеих ветках);
- core/prepreg НЕ моделируем (решение фабрики): метки по дефолтному генератору
  самого KiCad — один зазор = core, несколько = крайние prepreg, внутренние
  core; НА ИМПОРТЕ type игнорируется (в формулу не попадает);
- маски/пасты/шелк — константный шаблон KiCad (Mask 0.01), copper_finish
  "None"; внешность (FINISH/MASK_COLOR/SILK_COLOR) НЕ связана со stackup —
  решение пользователя 2026-07-15 (v1 = только толщины/ε/tanδ), цвета/finish
  на импорте — дроп с логом;
- сумма stackup ≡ `(general thickness)` автоматически (одна формула).

ПРАВИЛО ИМПОРТА (код будет в board-импортёре): stackup есть → толщины меди +
[thickness:ε:tanδ] → формула; stackup НЕТ — НЕ hard reject (штатное состояние
KiCad-платы): синтез формулы из числа слоёв + дефолтов KiCad (35µm медь,
диэлектрик добивается до general thickness) с записью в import log.

Верификация: verify_kicad_board.py сверяет каждую ячейку эмитированного
stackup с формулой IR (maximus 31[100]35[1000]39[200]40 — зелёный).
Попутно: последний след `copper=` убран из print eagle_board_exporter.

## Импорт KiCad-плат: v1 (плоский толмач) — замкнутый круг зелёный (2026-07-15)

`babel/kicad_board_parser.py` — обход СЫРОГО s-expr-дерева (только токенайзер
kiutils, НЕ его объектная модель — side-channel по построению, прецеденты
потерь токенов уже были). Врезан в `convert_project_full` (плата только в
составе проекта); иерархический проект → плата отложена с логом (обратный
маппинг сплюснутых refdes TM1:C1→C101 и иерархических имён цепей — следующий
этап). Оракул `verify_kicad_board_import.py` — полный круг Eagle→IR₁→KiCad→
(пересохранение в KiCad 10 руками)→IR₂, сверка IR₁↔IR₂ поячеечно:
толмач — 48/48 элементов (x/y/rot/side, обратная запечка bottom),
484/484 меди (line/arc+curve/via/contactref), 917/917 свободной геометрии.
Отложено с логом: зоны (+что в них уехало: pour-полигоны, анти-кольца
футпринтов), rules, dimensions/groups/targets.

Находки пересохранения (диалект v10, зафиксировано по ground truth
testData/new_kicad):
- **Цепи только по имени**: resave выбрасывает ЧИСЛЕННУЮ таблицу цепей
  целиком, все ссылки нормализуются в `(net "ИМЯ")`. Наш свежий выхлоп
  (legacy `(net N "имя")`/`(net N)`) v10 принимает — импортёр читает обе
  формы (`_net_name`).
- **`(fill no|yes)`** — resave-нормализация наших `(fill none|solid)`;
  плюс старая вложенная `(fill (type none))`. Все формы читаются
  (`_fill_none`).
- **Направление дуги нормализуется** (swap концов + негация curve = та же
  дуга) и **квантование съедает точность sweep** (90° → 89.999955 после
  3-точечного фита) — снап к целому градусу в пределах шума фита
  (`_snap_sweep`); верификатор сравнивает дуги в канонизированном виде.
- **ε/tanδ материализуются** (см. запись «Стек → KiCad»): формула `[1000]`
  возвращается как `[1000:4.5:0.02]` — принимаем как факт файла, верификатор
  помечает, не фейлит.
- **KiCad-текст платы = всегда штриховой шрифт = Eagle "vector"** —
  импортёр ставит `font="vector"`, атрибут переживает круг честно.
- **`(paper "User" W H)` — числа буквальные**, ориентация запечена в них;
  «ландшафтная» перестановка _paper_dims_mm применима только к именованным
  форматам (был баг: рамка 260×179 читалась как 179×260 → ложные strays).

## Замкнутый круг как линтер: улов первой охоты на толмаче (2026-07-15)

Пользователь глазами поймал два симптома (цепь VDD_3V3 переименована в 3.3V
на схеме при VDD_3V3 на плате; потеря всех атрибутов устройств) — раскопка
дала ПЯТЬ дефектов, все закрыты, все оракулы зелёные:

1. **Supply-имя: Value power-символа = имя sup-ПИНА, всегда.** KiCad именует
   цепь по Value инстанса; Eagle — по имени sup-пина; отображаемое value
   Eagle-девайса («3.3V») — НЕ имя цепи. Экспорт теперь пишет имя пина в
   Value и инстанса, и библиотечного символа (расхождение отображения — в
   лог, консистентность важнее текста). Попутно это склеило раскол
   GND/GND@1 (компоненты-тёзки из разных Eagle-библиотек: у обоих Value
   теперь GND).
2. **Обратная сторона — per-instance power rename (легальный KiCad-идиом:
   поставил GND, вписал Value=AGND).** В IR имя цепи живёт на sup-пине
   символа — один на символ. Импорт РАСЩЕПЛЯЕТ: каждое отличное Value =
   свой клон-компонент `{entry}@{value}` (не guess и не reject); базовый
   компонент без оставшихся дефолтных инстансов дропается (фантом ловил
   roundtrip). Ground truth: multichannel `+1V1`→`vbias`.
3. **Атрибуты инстансов на импорте собираются ВСЕ** (кроме
   Reference/Value/Footprint; Datasheet→`datasheet`), с дедупом против
   компонентных дефолтов; Value=имя-компонента (fallback «нет значения» у
   обоих тулов) не материализуется.
4. **ЗЕРКАЛО ИНСТАНСА: KiCad-угол при mirror входит в IR С ОТРИЦАНИЕМ.**
   KiCad компонует mirror-ПОСЛЕ-rotate, канон IR — mirror-потом-rotate:
   M·R(θ) = R(−θ)·M. Идеально симметрично Eagle-находке «MR{α} → IR −α».
   Доказано таблицей истинности 12 ориентаций (4 угла × none/x/y),
   оракул — netlist самого kicad-cli: ненегированная форма промахивается
   мимо пина во ВСЕХ mirror+90/270. Прежние «подтверждения» литеральной
   формулы покрывали только незеркальные и mirror@rot0/180 случаи (там
   композиции совпадают). Симптом: у зеркальных R/C пины 1↔2, у Q1
   (IRLML9301 — тот же корпус, что в баге зеркальных полей!) пины
   потеряны. Фикс — одна строка в kicad_schematic._mirror_and_angle,
   протекает согласованно в пины И в сохранённый rot.
5. **Плата ПРИНИМАЕТ схемные имена цепей по связности** (schematic owns
   identity): голосование contactref'ов через pin-mapping; анонимные
   board-имена (N$…, Net-(…), unconnected-(…)) переименовываются с логом,
   расхождение ИМЕНОВАННЫХ = hard reject («запустите F8, почините
   исходник»); переименование двухфазное (свежая схемная N$-нумерация
   коллидирует с бордовой). Верификатор сравнивает анонимные цепи
   структурно (канонический ярлык из contactref-множества).

Метод дня: kicad-cli sch export netlist = дешёвый машинный оракул
связности KiCad — идеален для таблиц истинности ориентаций (никакого
ручного «посмотри глазами» на 12 комбинаций).

  в KiCad ВСЕ атрибуты живут на символе, большинство невидимы — видимость и

  сломан был обратный конец: библиотечный экспорт писал Value ВСЕГДА видимым
  → круг синтезировал >VALUE, которого в оригинале нет. Теперь Value скрыт
  при отсутствии >VALUE у исходного символа (power — исключение, там Value =
  отображаемый ярлык рейла; инстансный эмиттер уже делал это правильно).
- **Синтез плейсхолдера — ВЕРХНИМ регистром** ('>' + KEY.upper()): Eagle
  распознаёт только >UPPERCASE (нижний тихо не отображается — сам симптом);
  ключи атрибутов сохраняют свой регистр, матчинг везде регистронезависимый
  (Eagle, svg_renderer, kicad_exporter.attrs_lower).

### Та же охота, финал: пер-инстансные размещения полей (smashed) через KiCad (2026-07-15)

Симптом «плейсхолдеры не видны» после ручной проверки пользователя (он
руками вернул записи IC2 и дал диф): Eagle-инстансы почти все smashed, а
KiCad-плечо теряло размещения В ОБЕ стороны — экспорт ставил поля по
библиотечным местам, импорт не восстанавливал записи вовсе (smashed без
записей у Eagle 9 = всё скрыто). Сделано:
- **Экспорт** (`_abs_style`): IR `<instance><text>`-оверрайды теперь
  первоисточник позиции поля (флип→поворот по канону IR, угол записи
  локальный → абсолютный); suppression-запись (hidden без геометрии) →
  hide на property.
- **Импорт** (`_field_overrides`): точная обратная — оверрайд только при
  ОТЛИЧИИ от библиотечного дефолта (позиция под полевым трансформом с
  негацией θ при зеркале, угол/размер/якорь), «один факт — одно место»;
  скрытое поле при видимом плейсхолдере → suppression-запись.
- **kiutils-гэп №4**: `(hide yes)` на properties РАЗМЕЩЁННЫХ символов
  kiutils тоже не читает (как и у библиотечных) — sidechannel-скан по
  uuid размещения (`_instance_hidden_prop_keys`).
- **Углы текста: свёртка mod 180 с сохранением justify** — и KiCad, и
  Eagle рисуют перевёрнутый текст читаемым вокруг того же якоря
  (ground truth `_norm_text_angle`); локальный угол записи канонизируется
  в [0,180), сравнение — по модулю.
- **ВАЖНО, уточнение зеркального фикса**: негация угла при mirror живёт
  ТОЛЬКО в пин-математике импортёра (eff_angle) — файловый угол KiCad
  ЛИТЕРАЛЕН (netlist-оракул это подтвердил на паре экспорт+негация:
  зеркальные 2-пиновые перевернулись), и сохранённый ir_rot ЛИТЕРАЛЕН
  (первая версия фикса гнала 90→270 и клала все smashed-записи на 180°).
Резолвед-сверка полей (оверрайд-или-дефолт): 97 расхождений → 7, все
оставшиеся — FRAME1 (маппинг title_block↔Eagle-рамка, отдельная тема).
Остаток: записи не несут слой (все 96 вместо NAMES/INFO источника).

## ЕДИНЫЙ полевой трансформ KiCad: kicad_schematic.field_to_kicad/from_kicad (2026-07-15)

По требованию пользователя «починим раз и навсегда»: правило трансформации
полей (плейсхолдер библиотеки ИЛИ smashed-запись инстанса — это ОДИН вид
записи) жило в трёх местах (дефолт-ветка _abs_style, оверрайд-ветка,
обратная в _field_overrides) и чинилось вразнобой. Теперь одна пара функций
в kicad_schematic.py, все три места — вызовы; юнит-тест тождества
inverse∘forward на 8 ориентациях в коде сессии.

Правила (каждое приколочено эмпирикой, источники в докстринге):
- позиция: флип локального X при зеркале, поворот на −θ при зеркале
  (шесть hand-placed IRLML9301), +θ без;
- **угол: ПОЛЕ ВРАЩАЕТСЯ ВМЕСТЕ С СИМВОЛОМ** — abs = θ±lrot со свёрткой в
  [0,180) при сохранённом justify. Прежний «ground truth» («KiCad не вращает
  поля — C на rot=90 держит поля под 0») описывал поведение KiCad UI при
  вращении, а не то, как ДОЛЖЕН выглядеть Eagle-исходник: RC-прогон —
  пользователь увидел правильные координаты при неповёрнутых надписях,
  ручная правка ТОЛЬКО угла ставила всё на место.
_inst_point в kicad_project_exporter удалён (правило переехало в общую
функцию).

### Поправка к полевому трансформу: угол поля — ЛОКАЛЬНЫЙ (2026-07-15, RC)

Ошибка предыдущей правки «поле вращается вместе с символом» (θ±lrot):
KiCad ХРАНИТ угол поля относительно тела символа и САМ добавляет
поворот/зеркало символа при отрисовке. Доказано рендером RC через
kicad-cli (объективный оракул — как KiCad показывает НАШ файл): у
повёрнутого-90 конденсатора C1 надписи ВЕРТИКАЛЬНЫ (верно, как в Eagle)
только при property-угле 0; при угле 90 KiCad рисует их горизонтально
(90+90=180). Метод измерения: экспорт SVG, bbox глифов по `<desc>`-меткам
(w<h ⇒ вертикаль). Кросс-проверка — KiCad-owned пересохранение step4:
KiCad сам пишет property-угол 0 для всех rot-90 символов. Итог: и
field_to_kicad, и field_from_kicad прогоняют угол насквозь (только свёртка
[0,180)), без слагаемого ir_rot; позиция — по-прежнему полный трансформ
(она была верна). Позиция абсолютна, угол локален — таков формат KiCad.

### Позиция поля при зеркале: поворот на +θ, не −θ (2026-07-15, RC Q9/Q10)

Финальная поправка полевого трансформа. Для зеркального символа позиция
поля бралась через R(−θ)·My — при mirror+rot90/270 смещение вставало ровно
на 180° неверно (наш Q3 давал (+3.81,+0.254), эталон — (−3.81,−0.254)).
Верно: My (негация локального X), затем поворот на +θ — та же композиция
mirror-потом-rotate, что у IR везде (svg_renderer._inst_point). Эталон —
KiCad-родные зеркальные копии Q9/Q10 в RC (та же ориентация, что наши
Q3/Q7, но поля расставил сам KiCad). +θ воспроизводит их точно и НЕ трогает
случаи mirror+rot0/180 (там композиции совпадают, всё и так было верно).
Прежнее прочтение −θ («Баг 1», 6 hand-placed IRLML9301) компенсировало
что-то, отрефакторенное с тех пор. field_from_kicad — обратное (−θ всегда).

### ПРИНЦИП: источник истины — библиотечный символ, не инстанс (2026-07-15, RC/tolmach)

Симптом: у зеркального Q1 (tolmach) текст полей вставал не с той стороны —
justify=left вместо right. Раскопка: библиотечный >NAME обоих (P-MOSFET) =
center-right, но в ИНСТАНСЕ Eagle при зеркалировании ЗАПЕКАЕТ флипнутый
align (center-right → center-left, атрибут ещё и rot=MR270 держит текст
читаемым). KiCad же при `(mirror y)` justify НЕ флипает (замерено рендером:
right-justify тянет текст влево независимо от зеркала) — отсюда рассинхрон.
Тот же символ в RC (Q7) в исходнике хранил center-right (не флипнут) —
инстансы РАЗНЫХ дизайнов модифицированы по-разному.

Решение пользователя, возведённое в ПРИНЦИП: **оперируем библиотечными
определениями, не инстансами.** justify/стиль/выравнивание — факт СИМВОЛА,
наследуется из библиотечного плейсхолдера; хранимое в инстансе значение
игнорируется (его слишком легко по-разному исказить прямо в дизайне —
smash, зеркало, ручная правка — и гоняться за этим = бесконечные частные
случаи). Смашится осмысленно только ПОЗИЦИЯ поля (человек реально двигает
подпись); угол/размер тоже берём из записи, но горизонтальный align —
всегда из библиотеки. Реализация: kicad_project_exporter._abs_style —
`lalign = styles[key][4]` поверх любой инстанс-записи. Итог: и Q1, и Q7 →
right (библиотечный center-right), регрессии зелёные. Согласуется с
[[project_editor_ui_principles]] «поля наследуются из символа».

### Eagle smash-модель: набор атрибутов инстанса = плейсхолдеры СИМВОЛА (2026-07-15, RC KiCad-импорт)

Симптом (KiCad→IR→Eagle, RC): инстанс R1 вернулся с ОДНИМ атрибутом
DESCRIPTION (мусорным) и потерял NAME/VALUE/PACKAGE/TOLERANCE/ALLOCATED —
в Eagle они перестали рисоваться. Формат Eagle (ground truth: пользователь скопировал инстанс без записей и
нажал "Restore Position" — Eagle материализовал ВСЕ плейсхолдеры символа как
`<attribute>` на библиотечных позициях): видимый текст показывается ТОЛЬКО
если инстанс несёт `<attribute>` на каждый плейсхолдер. Инстанс `smashed` БЕЗ
записей = НИ ОДНОЙ надписи (это и был баг R1). Поэтому инстанс с видимыми
полями ВСЕГДА эмитим smashed со всеми плейсхолдерами (несдвинутые — на
библиотечном дефолте, сдвинутые — по override); без плейсхолдеров (рамка,
footprint-only) — plain.

Две причины, обе — нарушение принципа «источник истины — символ»:
1. KiCad не знает про smash: на импорте по «один факт — одно место» пишем
   override ТОЛЬКО для сдвинутых полей → у R1 (ничего не двигали) ноль
   записей, кроме мусорного >DESCRIPTION (KiCad сам добавил пустое поле
   Description со `show`). Фикс импорта: поле = видимый плейсхолдер ТОЛЬКО
   если библиотечный символ его определяет (`lib is None` → это
   device-атрибут по значению, не смашенная надпись). Убивает DESCRIPTION.
2. eagle_exporter строил `<attribute>` из instance-текстов (что накопилось),
   а не из плейсхолдеров символа. Фикс: `_gate_placeholders(comp, gate,
   pool)` перечисляет `>X` символа; смашенный инстанс эмитит по одной
   записи на КАЖДЫЙ плейсхолдер (сдвинутый — по override-позиции, прочие —
   по библиотечному дефолту); стиль (size/align/layer) ВСЕГДА
   библиотечный; не-смашенный (нет override) — без записей, Eagle
   расставит сам. Результат: R1 un-smashed (все 5 полей видны), зеркальный
   Q3 смашен со всеми 3 плейсхолдерами P-MOSFET. Чистый Eagle-путь
   (sch→IR→sch) не задет: R1/C1 возвращают полный набор. Board + KiCad
   round-trip зелёные.

### Плата: видимый текст element'а — из плейсхолдеров ФУТПРИНТА (2026-07-15, RC board)

Board-двойник схемного smash-фикса. Симптомы KiCad→IR→Eagle: у element'а
R1 не рисовался refdes (>NAME), а RESTORE добавлял ранее не существовавший
>VALUE. Причина: `_emit_element_attribute` строил `<attribute>` из
instance-текстов element'а (в KiCad-круге их НЕТ) → element не smashed,
видимого NAME нет. Eagle element показывает текст ТОЛЬКО через `<attribute>`;
RESTORE материализует по одной записи на плейсхолдер ПАКЕТА. Фикс (принцип
«источник истины — библиотека»): видимые силк-надписи берём из плейсхолдеров
ФУТПРИНТА (`>NAME`/`>VALUE`), element ВСЕГДА smashed; NAME→tNames(25) видим,
VALUE→tValues(27); плейсхолдер на НЕ-силк слое (KiCad кладёт value-fp_text
на F.Fab=151, к тому же hidden) — НЕ показывается. Позиция — override если
поле двигали, иначе футпринт-дефолт. Итог: R1 несёт видимый NAME (слой 25),
VALUE-на-фабе пропущен — структура как в оригинале. Связность пин↔пад в той
же цепочке чинится сама, если гнать СВЕЖИЙ экспорт (устаревший hand-resaved
RC_kicad имел пады P$1/P$2 и пустой pin-mapping — артефакт старого экспорта).
Board + KiCad round-trip зелёные.

### kiutils gap #5: (hide yes) на fp_text не читается → спурьёзный >VALUE (2026-07-15)

Продолжение RC board. Даже после board-фикса у ПАКЕТА оставался лишний
>VALUE. Корень: `.kicad_mod` пишет `(fp_text value ... (hide yes))` на
F.Fab (наш же KiCad-экспорт), но kiutils 1.4.8 читает `item.hide` = False
для value-fp_text (тот же read-gap `(hide yes)`-формы, что уже обходили для
property/pin). `_convert_footprint` пропускал только `item.hide`, так что
скрытый value порождал >VALUE-плейсхолдер, которого в оригинале не было.
Фикс: sidechannel `_footprint_hidden_fptext` (сырой s-expr) в
`_read_footprint`, проверяется в FpText-ветке. Итог: R1206 несёт только
>NAME — как оригинал. Board + KiCad round-trip зелёные. Пятый обход
kiutils-hide-gap этой сессии (property символа, pin_names/numbers,
property размещённого символа, теперь fp_text).


## IR `<module>` → Altium: ИЕРАРХИЯ, стадия 1 (2026-07-29)

Первый пункт бэклога после экспорта платы. `altium_project_exporter` больше
не отбрасывает `<module>`: модуль превращается в sheet symbol на родителе +
отдельный `.SchDoc`, порты матчатся с sheet entries по имени, весь набор
попадает в `.PrjPcb`. Ground truth — корпус testData/altium (BC2087: 14
sheet symbol'ов на TopLevel.SchDoc, 302 компонента на плате):

- **Sheet symbol**: `location` = ВЕРХНИЙ ЛЕВЫЙ угол, `x_size`/`y_size` — в
  10-mil единицах; `SheetName` = `U_<имя инстанса>` (это и есть имя комнаты,
  плата повторяет его дословно), `FileName` = имя дочернего файла.
- **Sheet entry**: `side` 0/1/2/3 = left/right/top/bottom, `distance_from_top`
  — от ТОГО ЖЕ верхнего левого угла (компилятор считает точку entry как
  `location.y - distance*10`), IR `coord` (знаковый, от ЦЕНТРА грани)
  пересчитывается в неё. `io_type` из `<port direction>`; `pwr`/`pas` → 0
  (Unspecified) — в Altium нет для них типа, врать нельзя.
- **rot/mirror инстанса модуля ЗАПЕКАЮТСЯ** в стороны entry через общий
  `ir_util.rotate_port_side` (тот же трансформ, что у KiCad-экспорта): sheet
  symbol в Altium всегда axis-aligned.
- **Порт на дочернем листе — это и есть ярлык цепи там**. Ярлык портовой
  цепи эмитится как `Port`, а не `NetLabel`. Отдельная ветка: цепь,
  названная ИЗНУТРИ (питание — своими power-символами), ярлыка не имеет
  вовсе — тогда `Port` синтезируется на безопасном якоре (`_label_anchor`),
  иначе sheet entry родителя остался бы без пары и связь, которая в IR ЕСТЬ,
  исчезла бы из нетлиста.
- **Связь платы с иерархией** (этого не было вообще): `SOURCEUNIQUEID` —
  ПУТЬ `\<uid sheet symbol>\<uid компонента>` для детей и `\<uid>` для
  верхнего уровня, `SOURCEHIERARCHICALPATH` = `TopLevel` /
  `TopLevel\U_<комната>`.
- **`NetIdentifierScope` (HierarchyMode) = 4 (STRICT Hierarchical)**, когда
  в проекте есть модули, и **все страницы верхнего уровня сливаются в ОДИН
  лист**. Это не выбор стиля, а единственная комбинация, воспроизводящая
  модель модуля из IR: через границу проходит РОВНО то, что модуль объявил
  как `<port>`, и ничего больше. Ground truth, что это требование, а не
  аккуратность: maximus — 8-канальный изолированный термометр, и сама Eagle
  на плате называет земли каналов `TM1:GND … TM8:GND`, отдельно от верхней
  `GND`; нестрогий режим сварил бы все девять в одну цепь и закоротил
  изоляцию. Измерено на синтетике: одноимённый ярлык на двух корневых листах
  = ДВЕ цепи при режимах 1/2/4 и ОДНА при 0/3, а «Automatic» сваливается в
  иерархический, как только в проекте есть sheet entries (док Altium) — то
  есть многостраничный верх, склеенный ПО ИМЕНИ (что и дают Eagle/KiCad),
  под иерархией распадается при любой настройке. Отсюда слияние страниц:
  холст в IR ОДИН, страницы — пагинация исходника, а рамки в Altium мы и так
  не рисуем. Без модулей ничего не меняется — проект уходит с дефолтом, и
  страницы остаются страницами.
- **Вертикальный Port ставится ЛОКАЦИЕЙ на провод.** У горизонтального порта
  соединяются оба конца (`location` и `location.x + width`), у вертикального
  дальний конец не выводится ни одним потребителем из горизонтальной ширины —
  сдвинутый вниз порт оставил C8.1 каждого канала maximus висеть отдельной
  цепью. Тело порта может лечь на провод; связность важнее.
- **Designator части внутри модуля — ОДНО правило на все экспортёры**:
  `ir_util.flat_designator` (offset, если он задан на moduleinst: C1 @ 100 →
  C101; иначе колоночная форма `INST:REFDES`) + `ir_util.designator_resolver`
  для адресов `<element>` платы. Раньше это правило жило копией внутри
  `eagle_board_exporter`; теперь у факта один дом, и схемный designator,
  платный designator и Eagle-плоскость обязаны совпадать по построению.

**Стадия 2 — НАСТОЯЩАЯ многоканальность Altium — СДЕЛАНА в тот же день.**
Один `.SchDoc` на МОДУЛЬ, на него ссылаются N sheet symbol'ов; документ,
упомянутый несколькими sheet symbol'ами, Altium сам считает многоканальным.
Что из этого следует и как решено (решения пользователя 2026-07-29):

- **Имена каналов считает Altium**, по шаблону проекта
  `ChannelDesignatorFormatString`. Арифметики в шаблонном языке нет, поэтому
  эйгловский `offset` (C1 @ 100 → C101) там невыразим. Выбран альтиумовский
  дефолт `$Component_$RoomName` → `C1_DCDC1`; эйгловская нумерация на
  Altium-пути СОЗНАТЕЛЬНО не сохраняется. Рассматривалась и отвергнута
  альтернатива «дополнить канонические имена нулём (C01) и взять шаблон
  `$ComponentPrefix$ChannelIndex$ComponentIndex`» — она воспроизводит C101,
  но работает только пока offset кратен 100.
- **Одно правило имени — один дом**: `altium_exporter.channel_designator`
  (+ константа `CHANNEL_DESIGNATOR_FORMAT`). Через него проходят и плата, и
  оба верификатора; `ir_util.flat_designator` (offset/двоеточие) остаётся
  правилом Eagle-пути, у которого своей канальной машинерии нет.
- **Формат пишется в `.PrjPcb`** (`[Design] ChannelDesignatorFormatString`)
  — оттуда его читает и компилятор altium_monkey
  (`NetlistOptions.from_prjpcb`), так что верификатор судит ровно ту
  нумерацию, которую сделает Altium.
- **Имя комнаты — имя инстанса из IR** (`DCDC1`), без альтиумовского
  префикса `U_` (26 из 26 в корпусе), потому что префикс не несёт
  информации, а в шаблоне давал бы `C1_U_DCDC1`. Плата повторяет комнату в
  `SOURCEHIERARCHICALPATH`.
- **ECO-путь при общем листе**: uid компонента ОДИН на все каналы, различает
  их uid sheet symbol'а — `SOURCEUNIQUEID = \<uid листа-символа>\<uid
  компонента>`. Ключ связи схема↔плата — АДРЕС элемента IR (`DCDC1:C1`), а
  не написанный designator.
- Комнаты (Room) на плату не пишутся — Altium создаёт их при первом ECO;
  одна строка в import log, не молчание.
- **Имена цепей канала — АЛЬТИУМОВСКИЕ, и спрошены у компилятора**
  (2026-07-29). Внутри канала Altium зовёт цепь `SW_DCDC1` (именованную) или
  `NetC1_DCDC1_2` (безымянную), а не `DCDC1:SW` из IR; плата с IR-именами
  давала на первом «Update PCB» стену переименований. Формулу НЕ
  воспроизводим: экспортёр пишет `.PrjPcb` до платы, компилирует только что
  записанный проект и сопоставляет цепи **по множеству выводов** — тому
  единственному, что обе стороны заявляют независимо. Смена правил у Altium
  тогда не переименует не ту цепь, а вылезет как несопоставленная цепь в
  логе.
  - Сопоставление требует свести пады к обозначениям выводов схемы: вывод
    может владеть несколькими падами, и обозначения выводов символа взяты из
    ПЕРВОГО футпринта компонента, тогда как инстанс размещён другим (CON5 в
    step4 — XT30 с падом `+`, а символ построен по JST, где это пад `2`).
  - Верификатор платы сверяет цепи по множеству ПАДОВ, а не по имени: имя
    теперь законно отличается от IR.
  - **Имя, которое компилятор даёт НЕСКОЛЬКИМ цепям, отвергается.** На
    maximus (8 ИЗОЛИРОВАННЫХ каналов) компилятор зовёт восемь разных земель
    одинаково — `GND`; принять это имя значило бы сварить изоляцию в одну
    цепь, то есть написать в плату короткое замыкание, неотличимое от
    задуманной цепи для любой проверки ниже по течению. Такие цепи остаются
    с IR-именем, строка в лог. Плюс отдельная проверка: два разных сигнала
    платы не могут получить одно имя — иначе жёсткий отказ.
  - Цепь без единого `<contactref>` (голая медь) не сопоставляется вовсе:
    у неё пустое множество выводов, сравнивать нечего.
- **Скомпилированную сетку читаем через `babel/altium_netlist.py`**
  (2026-07-29) — и экспортёр платы, и верификатор, иначе они судят разные
  дизайны. Там же живёт коррекция дефекта altium_monkey: при STRICT-области
  компилятор теряет связь sheet entry ↔ port, как только родительская цепь
  несёт символ питания. В Altium явная связь входа листа с портом действует
  при любой области видимости (область правит ИМЕНА, не провода). Без
  коррекции на step4 «отваливались» VIN, GND и VDD_5V всех четырёх каналов,
  а EN — чья родительская цепь именована обычным ярлыком — проходил.
  Коррекция была в верификаторе с самого начала; новое сравнение с платой
  сперва прочло сетку без неё и подняло ложную тревогу.
- **Что первый ECO ДОЛЖЕН предложить, и почему это не расхождение**
  (2026-07-30, по живому Update PCB пользователя на step4). Altium сам
  выводит из схемы: комнаты, классы компонентов, класс канала, параметры
  компонентов на плате и правила Supply Nets. Мы их не пишем: параметр
  живёт в строке DbLib, на которую ссылается схема, а копия на плате —
  ПРОИЗВОДНАЯ, которую Altium обновляет на каждом ECO тем же значением.
  Писать её самим значило бы завести второй дом факту, и притом такой,
  который инструмент всё равно перезапишет. Строка в лог, чтобы это не
  выглядело сюрпризом.
  - Тот же ECO вскрыл ДВА настоящих бага, которых верификаторы не видели
    (обе стороны сверки были согласованы между собой и обе неправы
    относительно Altium): DesIntf в MAP_DEFINER и Design Item ID на плате.
    Живой ECO — проверка, которую скриптами не заменить.
- **`Supply Nets` пишем САМИ** (2026-07-30, ground truth — плата
  пользователя после реального ECO). Altium строит по одному правилу
  `SupplyNets` на каждую цепь питания ИЗ СХЕМЫ и предлагает их на КАЖДОЙ
  синхронизации, пока плата не несёт свои: у пользователя пять строк
  `Modify ... InNet('GND') -> ... InNet('GND')` (обе половины печатаются
  ОДИНАКОВО) повторялись после каждого выполнения. Форма записи скопирована
  дословно: `NAME='Schematic Supply Nets'` и далее `_1`, `_2`…, приоритеты в
  обратную сторону, `VOLTAGE=' 0.000'` (с ведущим пробелом),
  `DEFINEDBYLOGICALDOCUMENT=TRUE` — этот флаг у всех прочих наших правил
  `FALSE`, и, вероятно, именно он делал правила Altium'а «чужими». Какие
  цепи считать питанием, выводим сами: та, на которой висит символ с выводом
  направления `sup`. Пишем только для цепей, реально существующих на плате.
  **Проверено пользователем: зацикленный ECO замолчал.**
- **Зазор корпус-к-корпусу (`ComponentClearance`) = 0** (2026-07-30).
  Источник о нём не говорит НИЧЕГО — у Eagle такой проверки нет вовсе, и
  плата под неё не разводилась, а штатные 10 mil из шаблона Altium зажигают
  нарушения на исправной плате. Сначала попробовали 8 mil и это оказалось
  ошибкой (проверено пользователем): любое положительное число — наша
  выдумка, оно лишь двигает порог, а нарушения возвращаются там, где детали
  стоят плотнее. Ноль говорит правду: ограничения нет.
- **Пустые `<signal>` не доезжают до IR** (2026-07-30, решение
  пользователя). В `Base.brd` 86 сигналов без единого `contactref` и без
  меди — `1AI1`…`16AI2`, `SW1`…`SW8`, `3V3` и 34 машинных `N$…`, ни одного
  из них нет в схеме. Сигнал, который ничего ни с чем не соединяет, не факт,
  а мусор файла; отбрасываем на ИМПОРТЕ (`eagle_board_parser`), а не на
  экспорте — тогда чинится сразу для всех выходных форматов. Условие узкое:
  только полностью пустой. Медь без падов (островок заливки, обрубок
  дорожки) остаётся — ей нужна цепь. Иначе Altium показывал их пачкой
  `Remove Nets` на первом же ECO.
- **Комнаты каналов НЕ рисуем** (решение пользователя 2026-07-30). Комната —
  это ГЕОМЕТРИЯ, а в IR её взять неоткуда: понятия комнаты нет ни в одном
  исходном формате корпуса. Габаритный прямоугольник по компонентам канала
  был бы выдумкой. Altium при первом ECO создаёт комнату сам —
  прямоугольником 2000×1000 mil в точке (0,0) (ground truth: `VX0=0mil …
  VX1=2000mil`, `VY2=1000mil` в файле пользователя), поэтому ВСЕ компоненты
  оказываются вне своей комнаты и плата загорается нарушениями Room
  Confinement (70 из 70 на step4). В лог пишем, что это будет, и предлагаем
  два выхода: нарисовать самому или удалить правила.
- **`Comment` НЕ синхронизируется с базой** (2026-07-30). Значение —
  величина ЭКЗЕМПЛЯРА (`2.2u`), а строка базы общая для всех деталей с этим
  номером, и её колонка `Comment` несёт имя компонента (`C`). С флагом
  синхронизации первое же «Update From Database» переписало бы номинал
  каждого конденсатора на `C`. Правило «атрибут уровня экземпляра не
  синхронизируется» в коде уже было — просто не применялось к `Comment`.
- **Board-only элемент остаётся PCB-only, ECO будет предлагать его удалить —
  и это ОСОЗНАННО** (решение пользователя 2026-07-30). Eagle разрешает
  элементу жить только на плате (логотипы U$1/U$2 в step4), у Altium такого
  понятия нет. Проектная галка `ECO Generation → Remove Components → Ignore
  Differences` вылечила бы симптом ценой предохранителя: она глушит ВСЕ
  удаления компонентов, то есть деталь, убранная со схемы, молча осталась бы
  на плате. Вариант «безвыводной символ на схеме» отклонён (в исходнике
  такого объекта на схеме нет, а позицию пришлось бы выдумывать). Итог: две
  строки в ECO, которые пользователь снимает галочкой, и строка в лог с
  прямым предупреждением НЕ включать ту настройку.
- **Design Item ID платы = design_item_id схемного компонента**
  (2026-07-30). Altium сверяет на ECO именно его, а плата заявляет его в
  `SOURCELIBREFERENCE`. Слали имя записи SchLib (`C`) вместо номера из базы
  (`C_C0603`) — 70 из 121 строки первого ECO. Верификатор платы проверяет,
  включая канальные компоненты.
- **DesIntf в MAP_DEFINER — имя вывода на СХЕМЕ, не пад** (2026-07-30).
  Карта отвечает «на каких падах сидит вывод, которого зовут X», а
  обозначения выводов символ берёт из ПЕРВОГО футпринта компонента, каким
  бы футпринтом ни размещён инстанс. Писали пад с обеих сторон — для CON5
  (символ по JST, где `+` это пад `2`; инстанс XT30, где `+` это пад `+`)
  карта говорила `+ -> +`, Altium такого вывода не находил и предлагал снять
  компонент с цепей. Одно правило — `altium_exporter.pin_pad_pairs`.
- **Футпринт ЗАПЕКАЕТСЯ в размещённый компонент** (2026-07-29). Ссылки на
  строку DbLib недостаточно: Altium пишет «Footprint of component ... cannot
  be found» даже при ПОДКЛЮЧЁННОЙ базе и установленном драйвере. Ground
  truth пользователя: компонент, размещённый вручную из той же DbLib,
  приезжает с моделью, а наши — нет. Значит модель — свойство ЭКЗЕМПЛЯРА на
  листе, а база лишь поставляет её в момент размещения. Пишем модель того
  футпринта, которым размещён именно этот экземпляр (`<instance
  footprint=>`), плюс MAP_DEFINER'ы (явная связь вывод↔пад — принцип).
  Колонка `Footprint Ref` в xlsx остаётся: она нужна для «Update From
  Libraries», это не дубль факта, а его же выражение для механизма
  обновления.
  - MAP_DEFINER'ы дописываются ОТДЕЛЬНЫМ проходом перед сохранением листа и
    только В КОНЕЦ списка объектов: `OwnerIndex` — это ПОЗИЦИЯ в списке,
    поэтому вставка в середину молча переподчиняет всё, что идёт следом; а
    `add_object()` на компоненте пересобирает его детей, обходя детей
    реализации, но не их детей — MAP_DEFINER (уровнем глубже) терялся при
    записи следующего параметра.
  - Попутно: карта падов бралась из ПЕРВОГО футпринта для ВСЕХ реализаций —
    у второго и далее выводы подписывались чужими падами, если имена падов
    различаются. Теперь у каждой реализации своя карта
    (`altium_exporter.pad_lists_for`).
  - Верификатор проверяет наличие модели у каждого размещённого компонента.
- **Серый superscript designator'ов** на общем листе (`R4` и рядом бледное
  `(R4_DCDC1, ...)`) — цена общего листа: за одним логическим designator'ом
  теперь четыре физических, и Altium честно рисует их список. В файлах
  этого нет вообще, схема корректна, но выглядит неопрятно. Выключается
  Preferences → Schematic – Compiler → Compiled Names Expansion →
  Designators → `Never display superscript` (и то же для Net Labels).
  Настройка ПОЛЬЗОВАТЕЛЬСКАЯ (DXP prefs), в проект её не записать, а лезть
  в чужой профиль — менять поведение Altium'а во всех остальных проектах;
  поэтому пишем строку в import log с точным путём до галки. Возврат к
  копиям листа ради отсутствия серого текста — плохой размен (дублирование
  дороже).
- Имя дочернего файла не может совпасть с уже занятым: у NAMUR модуль зовут
  как проект, и `NAMUR.SchDoc` модуля затирал верхний лист (поймано на
  регрессии: 0 sheet symbol'ов, 7 компонентов в проекте) — теперь суффикс
  `_2` с записью в лог.

**Верификация без Altium** (`verify_altium_project.py`, переписан):
altium_monkey компилирует ВЕСЬ проект (`AltiumDesign.from_prjpcb`) в том же
режиме иерархии, что записан в .PrjPcb, а IR плющится теми же правилами
(портрефы сваривают цепь родителя с одноимённой цепью внутри инстанса) —
сравниваются РАЗБИЕНИЯ выводов по цепям, а не имена. На multichannel (KiCad
channel_strip ×4): 114 designator'ов, 79 многовыводных цепей — совпадение
точное, 0 расхождений. Известный зазор ИНСТРУМЕНТА, а не выхлопа: в
иерархических режимах altium_monkey не считает power port глобальным
идентификатором (в Altium он глобален везде, кроме Strict) — верификатор
доваривает цепи по имени power-порта сам, это единственная поправка.

**Попутно найдено и починено**: `OBJECTCLEARANCES` (нулевой зазор медь↔
отверстие) снимался со stock-правила Clearance только если IR принёс свои
числа `<rules>`; у любого проекта из KiCad `<rules>` нет вовсе — и опасная
таблица уезжала в выхлоп. Теперь снимается всегда.

### Eagle-корпус вскрыл четыре ПРЕЖНИХ бага Altium-пути (2026-07-29)

Не про иерархию — про то, что tolmach/step4 просто не содержали таких имён
и объектов. Все четыре чинились по принципу «у факта один дом»:

1. **`<instance footprint=>` может держать строку ВАРИАНТА, а не имя**
   (`CON-2P`: устройства `-B2B-XH` и `-DS1069M` оба на корпусе `B2B-XH-A`,
   поэтому импорт пишет уникальный вариант). DbLib-ключ строился матчингом
   ИМЁН → падение на первом же таком инстансе. Теперь ключ считает
   `altium_exporter.part_number(comp, fp)` — и он же строит строки xlsx,
   поэтому размещённый компонент и его строка БД сходятся по построению;
   резолв футпринта — через `ir_util.instance_footprint`. Заодно ушла тихая
   коллизия: две строки xlsx с одинаковым `Part Number`.
2. **Имя записи SchLib — это имя OLE-хранилища**: `CCDN2,5/18-G1P26THR`
   обрезался до `CCDN2,5`, и размещение падало «Symbol not found».
   `altium_exporter.lib_ref()` подставляет тот же набор замен, что и любое
   имя, становящееся файлом (`ir_util.sanitize_filename`), и применяется
   и при записи, и при поиске.
3. **Имя футпринта в PcbLib — однобайтовое**: `2х2` с КИРИЛЛИЧЕСКОЙ «х»
   ронял запись библиотеки (`ascii codec can't encode`). `fp_name()`
   переводит кириллические гомоглифы в латинские двойники (`2x2`), остальное
   非-ASCII → `_`, с громкой записью в лог; применяется во всех местах, где
   имя футпринта пишется или ищется.
4. **Board-only безпадовые элементы** (логотипы Eagle `U$1`/`U$2`, футпринт
   лежит в самом layout) роняли экспорт платы — теперь размещаются как
   PCB-only компоненты (без ECO-линка, каковыми они и являются), а их
   футпринты попадают в PcbLib.

**Зазоры ИНСТРУМЕНТА (altium_monkey), не выхлопа** — верификатор их
компенсирует, каждый на своих данных из самих выхлопных документов:
связь sheet entry ↔ Port при STRICT-режиме (в Altium явная связь работает
при любом scope), объединение одноимённых идентификаторов НА ОДНОМ листе,
и — открытым текстом — компилятор не видит пины ВТОРОЙ секции многосекционного
компонента (в .SchDoc обе части на месте: part 1 с пинами A*, part 2 с B*),
из-за чего на RLT508.01 остаются расхождения по цепям этого разъёма.

### Плата: видимость надписей — ФЛАГ, а не отсутствие объекта (2026-07-29)

Два захода по одной жалобе. Сначала: у винта `SCR1` (футпринт без единого
плейсхолдера) на шелкографии печаталось «SCR1» — это altium_monkey при
размещении СИНТЕЗИРУЕТ designator (и comment), если у библиотечного
футпринта своих текстов нет. Убрали выдуманные объекты — и Altium начал
рисовать на их месте СВОЙ дефолт «Designator1» (пользователь увидел его в
нижнем левом углу платы, ровно там, где стоит SCR1).

Правильная форма — альтиумовская: текст остаётся ВСЕГДА, а видимостью
управляют флаги компонента `NAMEON`/`COMMENTON`. Канон прежний и общий с
Eagle-путём: рисуется то, что футпринт объявил плейсхолдером
(`>NAME`/`>VALUE`), элемент может это только подвинуть или скрыть
(`hidden="yes"`). Ветка «скрыть» в `_apply_text_overrides` тоже больше НЕ
удаляет объект. Верификатор проверяет обе половины: у каждого компонента
designator-текст есть, а видимы РОВНО те, у кого плейсхолдер объявлен и не
скрыт (step4: 72 текста, 66 видимых).

### Многострочный текст: Text Frame, а не String (2026-07-29)

PCB String рисует ОДНУ строку — перевод строки внутри неё выходит мусорным
глифом. Многострочный текст теперь уходит как String с `is_frame`, строки
разделены CRLF, вокруг текстовый бокс (ground truth: `PiMX8MPIODB_r0.1.PcbDoc`
из корпуса, лицензионная плашка хранится ровно так). На схеме то же
разделение: `<text>` с переводом строки → `AltiumSchTextFrame` (запись сама
кодирует переносы как `~1`), `word_wrap=False` — в IR уже сказано, где
переносы, — и БЕЗ клиппинга, чтобы промах метрики не срезал текст. Размер
бокса считает общий `altium_exporter.multiline_box` (шаг строки 1.6 высоты).
