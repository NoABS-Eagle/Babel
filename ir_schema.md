# Babel IR Schema

Babel IR — XML-файл, корневой элемент `<library name="...">`.

---

## Единицы измерения и сетка

- **Все длины — целые микрометры (µm), `int32`.** Координаты, размеры, толщины,
  радиусы, диаметры, длины пинов, высоты шрифта, смещения 3D-модели — везде целые µm.
- **Система координат — Y вверх.**
- **Углы** (`rot`, `start`, `sweep`) — градусы (могут быть дробными); **`roundness`** —
  проценты. Это не длины, на них правило µm не распространяется.

Почему µm, а не µm/нм. Печатная плата — физический объект; минимальная значимая фича
порядка 75 µm (3 mil трасса), сетка трассировки не опускается ниже микрона. Субмикронная
точность не нужна — потеря долей микрона при округлении не имеет физического смысла.
Нанометры были бы карго-культом. Целые µm дают точное соответствие целевому КАДу
(он оперирует `int32` µm), убирают float и связанный с ним дрейф: round-trip
идемпотентен на микронной сетке по определению.

**Округление к микрону выполняется на входе в IR** (в парсерах), а не размазывается по
пайплайну. Экспортёры переводят обратно: µm→µm `/1000` (Eagle, KiCad), µm→mils `/25.4`
(Altium).

`int32` µm даёт потолок ±2.147 м — с гигантским запасом для любой платы.

---

## Структура верхнего уровня

```xml
<library name="mylib">
  <symbols>
    <symbol name="NPN">...</symbol>
    <symbol name="R">...</symbol>
  </symbols>

  <component name="BC547" prefix="T">...</component>
  <component name="BC548" prefix="T">...</component>
</library>
```

`<symbols>` — общий пул символов библиотеки. Один символ может использоваться несколькими компонентами (например, все NPN-транзисторы ссылаются на один символ `NPN`).

---

## Символ `<symbol>`

Дочерний элемент `<symbols>`. Содержит геометрию и пины.

| Атрибут | Описание                                       |
|---------|------------------------------------------------|
| `name`  | Имя символа — уникальная строка в библиотеке  |

### `<line>` — отрезок

| Атрибут        | Описание           |
|----------------|--------------------|
| `x1 y1 x2 y2` | Координаты, µm     |
| `width`        | Толщина линии, µm  |

### `<arc>` — дуга (КОНЦЕВАЯ форма)

| Атрибут   | Описание                                                        |
|-----------|-----------------------------------------------------------------|
| `x1 y1`   | Начало, µm                                                      |
| `x2 y2`   | Конец, µm                                                       |
| `curve`   | Угол дуги, градусы CCW+ (положительный = центр слева от хорды) |
| `width`   | Толщина линии, µm                                               |

Канон — **концы + угол** (форма Eagle), НЕ центр/радиус/углы. Причина фундаментальна:
связность меди — контракт КОНЦОВ; в концевой форме все сегменты живут на одной целой
µm-решётке и стыки точны ПО ПОСТРОЕНИЮ при любом квантовании. Центр-форма хранила
процесс построения, а не результат: пересчёт концов из µm-округлённого центра давал
~1 µm расползания, и Eagle рисовал airwire-огрызки на каждом стыке дуга↔провод
(ground truth luminoso; полная запись — decisions.md «Канон дуги — концевая форма»).
Центр/радиус — вычислимые производные (`ir_util.arc_center`/`arc_params`) для
потребителей, которым нужны (Altium — его родная форма, рендер).

**Полная окружность — НЕ дуга** (вырожденная хорда): контурная окружность = `<shape
roundness="100" outline="толщина">`.

### `<shape>` — прямоугольник или круг

| Атрибут     | Описание                                                     |
|-------------|--------------------------------------------------------------|
| `x y`       | Центр, µm                                                    |
| `w h`       | Полные ширина и высота, µm                                   |
| `roundness` | 0 = прямоугольник, 100 = круг, между — скруглённый           |
| `outline`   | 0 = залитая фигура (без контура), иначе — толщина контура µm |
| `rot`       | Поворот, градусы                                             |

При `roundness=100` используется только `w` (диаметр). При `outline=0` фигура залита цветом слоя без обводки.

### `<polygon>` — заполненный многоугольник

**Один и тот же элемент для медных и немедных слоёв — не два разных типа объекта.** IR не
заводит отдельную сущность «Zone» рядом с «Polygon» (в отличие от KiCad, у которого зона —
структурно отдельный `zone`-токен, привязанный к сети). У нас `<polygon>` рисуется на ЛЮБОМ
слое (`top`/`bottom`/`silk_top`/`fab`/...), и **какие атрибуты имеют смысл — определяется
слоем-контейнером, не самим тегом**:
- **На медном слое** (`top`/`bottom`) — применимы ВСЕ атрибуты ниже.
- **На немедном слое** (шёлкография, документация и т.п. — декоративная заливка, не медь) —
  осмысленны и обрабатываются только `width` и `fill`; `name`/`rank`/`clearance`/`thermals`
  синтаксически допустимы (парсер не обязан их запрещать), но не несут физического смысла
  и приёмник вправе их игнорировать.

| Атрибут     | Описание                                                        |
|-------------|-------------------------------------------------------------------|
| `width`     | Минимальная ширина трассы заливки, µm (≥ 50); 0 = не задана    |
| `fill`      | `0`–`100`, умолчание `100`. **`100` = сплошная (solid) заливка, `0` = только контур полигона (без заливки вообще), промежуточные значения — штриховка разной плотности.** Единая шкала вместо раздельных «стиль + коэффициент заполнения» (см. решение ниже) |
| `name`      | (только медный слой) Имя сети (net name), которой принадлежит заливка |
| `rank`      | (только медный слой) `0`–`100` — приоритет при наложении полигонов разных сетей (прямая аналогия Eagle `rank`): выше `rank` вытесняет ниже в зоне перекрытия |
| `clearance` | (только медный слой) Целое, µm — override зазора DRC от меди других цепей для ЭТОГО КОНКРЕТНОГО полигона, поверх глобального значения платы |
| `thermals`  | (только медный слой) `0`/`1`, умолчание `1` — генерирует ли ЭТОТ полигон термобарьеры для своих пересечений с падами вообще (см. «Thermals — единый процент, не два булевых» ниже — на паде это отдельная, ПРОЦЕНТНАЯ шкала, здесь — только да/нет) |

Дочерние элементы — `<vertex x="..." y="..." curve="..."/>` (вершины обхода CCW, µm;
опциональный `curve` — дуга к СЛЕДУЮЩЕЙ вершине, градусы CCW+, положительный =
выпуклость влево по ходу обхода; без `curve` ребро прямое).

**Почему `fill` — единый процент, не раздельные «стиль + плотность».** KiCad хранит для
штрихованной заливки зоны минимум 5 отдельных параметров (`hatch_thickness`, `hatch_gap`,
`hatch_orientation`, smoothing/minhole ratio) — но `thickness`/`gap` вместе математически
эквивалентны одному проценту (`fill% = thickness/(thickness+gap)×100`): одна и та же
визуальная/инженерная плотность меди достижима бесконечным числом пар `(thickness, gap)`,
а для инженерного смысла (сколько меди физически останется, тепловое расширение при
термоциклах, качество травления на производстве) важен именно процент, не то, КАКИМИ
конкретно линиями он получен геометрически. `hatch_orientation` (угол штриховки) —
самостоятельная, не связанная с «сколько меди» ось; не включена в текущую модель, будет
отдельным атрибутом только если появится реальная потребность, не добавляется заранее.

### `<pin>` — электрический пин

| Атрибут     | Значения                        | Описание                                                             |
|-------------|----------------------------------|----------------------------------------------------------------------|
| `name`      | строка                           | Имя пина (уникально в символе; дубли → `@N`)                       |
| `x y`       | µm                               | **Координаты точки подключения провода («горячая точка»).** Именно сюда присоединяется net/wire в схеме. |
| `rot`       | 0 / 90 / 180 / 270               | Направление вывода **ОТ точки подключения К телу символа.** Тело символа находится на расстоянии `length` в направлении `rot` от точки `(x, y)`. |
| `length`    | µm                               | Длина вывода                                                         |
| `direction` | `in` `out` `io` `pas` `pwr` `sup` `nc` | Электрический тип. `sup` — см. «Supply symbol» ниже. `nc` (not connected) — Eagle-native тип (`eagle.dtd` `%PinDirection`), ERC реально проверяет, что на пине этого типа НЕТ цепи (в отличие от `pas`, на который ERC не накладывает таких ограничений) — заведён ИСКЛЮЧИТЕЛЬНО ради совместимости с legacy-форматом, у которого нет более достойного способа выразить «производитель прямо требует не подключать» |
| `pinvis`    | `0` `1`                         | Видно ли ИМЯ пина. Пишется явно всегда, на каждом `<pin>` — без дефолта-по-умолчанию-через-отсутствие. |
| `padvis`    | `0` `1`                         | Видно ли НОМЕР пина (= имя пада на футпринте). Пишется явно всегда, как и `pinvis`. |
| `function`  | `none` `dot` `clk` `dotclk`    | Визуальный маркер на конце вывода                                    |

**История:** раньше было одно комбинированное свойство `visible` (`both`/`pin`/`pad`/`off`,
эаглового происхождения, опускалось при дефолтном `both`). Заменено на два независимых
булевых атрибута по решению пользователя — `pin`/`pad` в старом enum были неинтуитивны
(означали "видно имя"/"видно номер", а не то, что подсказывает само слово), и комбинированная
форма плохо переживала независимое управление видимостью имени/номера в реальных форматах
(KiCad: `pin_names`/`pin_numbers` — два совершенно раздельных переключателя). Дефолт-через-
отсутствие-атрибута тоже убран — `pinvis`/`padvis` пишутся на КАЖДОМ `<pin>` явно, даже когда
оба `1` (обычный случай).

**Отклонено: отдельный слой `PINS` (Eagle 93).** В Eagle этот слой несёт только зелёный
кружок на точке подключения — визуальная подсказка «сюда электрически подключается провод»,
не самостоятельный графический объект (сам вывод и маркер направления рисуются на слое
`Symbols`/94). В IR точка подключения уже структурно однозначна — это буквально `(x, y)`
самого `<pin>` (см. выше), никакой неоднозначности «с какой стороны» не существует в
принципе. Рендерер (`svg_renderer.py`) просто рисует маленькую точку на этой координате
для каждого пина как часть его обычной отрисовки — это конвенция рендера, не отдельный
IR-слой/объект, заводить `PINS` в номенклатуре слоёв («Слои» выше) нет смысла.

**Вычисление конца вывода (тело символа):**
```
body_x = x + length × cos(rot)
body_y = y + length × sin(rot)
```

Пример: пин с `x=-2540 y=0 rot=0 length=2540` → точка подключения (-2540, 0), тело символа (0, 0), вывод идёт вправо.

Соответствие Eagle → IR для `direction`:

| Eagle | IR    |                        |
|-------|-------|------------------------|
| `in`  | `in`  |                        |
| `out` | `out` |                        |
| `io`  | `io`  |                        |
| `oc`  | `io`  | open-collector         |
| `hiz` | `io`  | high-impedance         |
| `pwr` | `pwr` |                        |
| `sup` | `pwr` | power supply           |
| `pas` | `pas` |                        |
| `nc`  | `nc` (видимый) / — (скрытый) | скрытый `nc`-пин визуально равносилен его отсутствию — не импортируется вовсе, не просто прячется (см. ниже) |

### `<text>` — текстовая аннотация

| Атрибут | Значения                                      | Описание                    |
|---------|-----------------------------------------------|-----------------------------|
| `x y`   | µm                                            | Позиция якоря               |
| `size`  | µm                                            | Высота шрифта               |
| `width` | µm (необязательно)                            | Ширина знака векторного шрифта; отсутствие = дефолтный аспект рендерера **0.85×size**. Eagle-источник НЕ пишет (у Eagle аспект зашит в шрифт — факта нет); KiCad-импорт пишет только при отличии от 0.85×size; экспорт в Eagle при наличии — деградация + лог |
| `rot`   | градусы                                       | Поворот текста              |
| `align` | `bottom-left` `bottom-right` `center` …      | Привязка к якорной точке    |
| `layer` | см. «Слои» ниже — по умолчанию `NAMES`/`VALUES`/`INFO` для плейсхолдеров | Слой отображения |
| `font`  | `vector` (необязательно)                      | Тип шрифта                  |

| `mirror`| `1` (необязательно)                           | Зеркальное чтение (board-домен: тексты нижней стороны; при размещении на bottom флаг ИНВЕРТИРУЕТСЯ) |
| текст   |                                               | `>NAME` `>VALUE` — макросы  |

### Надчёркивание (overbar) — конвенция Eagle, `!TEXT!`

Для обозначения активного-low сигнала (горизонтальная черта над текстом) IR использует
**Eagle-нотацию**: `!` переключает надчёркивание (toggle) — включается на первом `!`,
выключается на следующем (или до конца строки, если второго `!` нет). Это касается
**любого текста** в IR, где он может встретиться — имена пинов, имена/номера падов,
обычный текст на символе/футпринте, значения атрибутов.

KiCad использует свою нотацию — `~{TEXT}` (явные границы фигурными скобками, в отличие
от toggle-механики Eagle). `kicad_parser.py`/`kicad_project_parser.py` конвертируют её
в Eagle-нотацию на импорте (`_kicad_overbar_to_eagle()`): каждая группа `~{...}`
независимо превращается в свою пару `!...!`. Не путать с одиночным `~` без скобок —
это отдельный, несвязанный сентинел "нет значения" (см. `_kicad_blank`), а не
надчёркивание.

```
~{RESET}     ->   !RESET!
A~{B}C~{D}E  ->   A!B!C!D!E
```

**Altium — третья, отдельная нотация, тоже текстовая** (проверено напрямую через
`altium_monkey.altium_sch_svg_renderer.render_text_with_overline`, не предположение):
backslash после символа надчёркивает ровно ОДИН предшествующий символ, не группу —
`R\E\S\E\T\` целиком надчёркивает "RESET" (нужен backslash после каждого символа).
Конвертация IR↔Altium для этой нотации пока не реализована (отдельная задача, не
сделана в рамках этой сессии — сейчас только KiCad→IR).

### Многострочный текст — только в `<text>`, признак — обычный `\n`

Многострочный текст в IR возможен **только в объекте `<text>`** — содержимое XML-элемента
(в отличие от значения атрибута) переживает буквальный перевод строки без потерь.
Значения `<attr value="...">`, имена пинов/падов — однострочные по определению (так же,
как и в KiCad: `VALUE`/`Reference`/другие свойства берутся из Properties объекта, где
многострочный текст запрещён самим форматом) — конвертация туда не применяется и не
нужна.

KiCad хранит перевод строки в графическом `(text ...)` как буквальный двусимвольный
escape `\n` (backslash+`n`), **не** настоящий байт перевода строки — подтверждено на
реальных данных (testData/phil/symlib.kicad_sym). Eagle ожидает обратное — настоящий
перевод строки (подтверждено пользователем напрямую в реальном Eagle). IR принимает
конвенцию Eagle, конвертация на импорте — `_kicad_multiline_to_eagle()`.

```
TEXAS\nINSTRUMENTS   (буквально, два символа \n)   ->   TEXAS<LF>INSTRUMENTS
```

### Плейсхолдеры — режим по первому символу: `>` подставить, `=` вычислить

Плейсхолдер в тексте выводит значение из атрибутов проекта. Первый символ СЕГМЕНТА
выбирает поведение (и парсер — они разные):

| Префикс | Режим        | Парсер                              | Мнемоника        |
|---------|--------------|-------------------------------------|------------------|
| `>`     | подстановка  | ОДНА ссылка `OBJECT@ATTR`           | Eagle `>NAME`    |
| `=`     | вычисление   | арифм. выражение со ссылками внутри | Excel `=A1*2`    |
| (нет)   | обычный текст| —                                   | —                |

Оба — обобщение, которого НЕТ ни у одного КАДа: Eagle подставляет только «свой»
носитель; KiCad держит подстановку (`${...}`) и арифметику (в числовых полях диалогов)
как ДВА несвязанных механизма в разных местах, а межкомпонентного вычисления в тексте
не умеет вовсе (открытый request GitLab #6643, «no possibility yet», апрель 2026);
Altium — тоже нет. Мы сливаем оба в ОДНУ read-only ось доступа `OBJECT@ATTR`
([[feedback_reduction_first]]; ещё довод к [[project_babel_purpose_kicad_exit]] — фича,
которой у покидаемых инструментов нет).

**Подстановка (`>`):**
- **`>VALUE` = `>SELF@VALUE`** (объект по умолчанию — носитель). **`>SHEET` = `>DOCUMENT@SHEET`**
  (глобальный атрибут = атрибут объекта «документ»). «Свой» и «глобальный» — частные случаи
  одного адресного механизма, не разные виды.
- **`>R1@VALUE`, `>LED2@COLOR`** — ссылка на КОНКРЕТНЫЙ атрибут КОНКРЕТНОГО элемента, рисуемая
  откуда угодно (таблица на шелке, выноска, заголовок листа). Ключ — REFDES (уникален,
  нагляден, рефакторится при переименовании; никакого скрытого UID).

**Вычисление (`=`):**
- Пример: `=3.3 * (R1@VALUE / R2@VALUE + 1)`. Excel по арифметике (`* / + - ()` и
  знакомость), но ссылки внутри — ГОЛЫЕ (режим уже задан префиксом `=`, `>`/`$` внутри не
  нужны), а движок — с ИНЖЕНЕРНЫМИ СУФФИКСАМИ (`10k / 4k7` схлопывается; k/M/n/p/u
  обязательны в ядре — иначе фича мертва, подтверждено ground truth KiCad `1in+1mm`).
  Размерный анализ (Ом vs В) — ОТЛОЖЕН (KiCad его тоже не делает).
- Результат ЭФЕМЕРНЫЙ — рендерится в текст, НЕ хранится, НЕ становится номиналом. Отсюда:
  все инварианты (один-факт-одно-место, BoM, 3-way merge библиотеки) не затронуты, и
  **циклы НЕВОЗМОЖНЫ по построению** (результат не становится ничьим входом).
- **Парсинг ссылки — АТРИБУТ ЦЕЛИКОМ, строго.** Значение атрибута под ссылкой обязано
  ЦЕЛИКОМ разбираться как число+суффикс (`10k`, `4k7`, `3.3`, `100n`), иначе вычисление
  падает → литеральный fallback. НИКАКОГО выковыривания числа из строки эвристикой:
  `"10K 1%"` в формуле НЕ работает — и это сознательно ([[feedback_easy_unambiguous_no_heuristics]]).
  Запись `10K 1%` дефективна ПО ПРИРОДЕ: два факта (номинал и допуск) склеены в одной
  строке, и потому ни один не машиночитаем — допуск живёт в СВОЁМ атрибуте (`TOLERANCE`).
  Строгость живёт ТОЛЬКО в вычислителе: импорт грязного VALUE легален (конвертер не судит),
  подстановка `>` — текстовая операция без парсинга (печатает `10K 1%` как есть); морковка
  живых формул достаётся тем, кто держит номиналы чисто — мягкое принуждение к гигиене
  без hard reject.
- **Суффиксы — CASE-SENSITIVE по SI**: `M` = мега, `m` = милли; `k`/`K` — оба кило
  (мнемоника: у кило коллизии нет, у M/m — есть). Полный набор ядра: `p n u m k M G`
  (+ `µ` как синоним `u`). Разделитель дроби — точка И запятая обе легальны на входе
  (`4.7k` = `4,7k`), вклейка суффикса внутрь числа по Eagle-традиции легальна (`4k7`).
- **Формат вывода результата**: инженерная нотация с суффиксом, мантисса 1–999.99…,
  не более 3 значащих цифр после округления, хвостовые нули отрезаются (`3.3`, не
  `3.3000000000000003`; `10.2k`, не `10240`). Десятичный разделитель на выводе — всегда
  точка. Единицу измерения движок НЕ приписывает (размерного анализа нет): единица,
  если нужна — обычный текст соседнего сегмента рядом с формульным.
- **Граница языка — ЖЁСТКАЯ, навсегда**: `+ - * /`, скобки, унарный минус, ссылки,
  числовые литералы с суффиксами. ВСЁ. Функций (`log`, `sqrt`), параллельного `||`,
  условий, строковых операций НЕ БУДЕТ — расширение языка = превращение канвы в
  спредшит, hard reject на уровне дизайна ([[feedback_reduction_first]]).

**Разделитель `@`, НЕ `.`** — точка легальна ВНУТРИ имён (пользователи ставят её вместо
запрещённого пробела: `R.LOAD`), потому разделителем быть не может; `@` в именах не
встречается (мнемоника email). Порядок `объект@атрибут`.

**Fallback (оба режима): неразрешимое печатается БУКВАЛЬНО.** Нет объекта/атрибута
(`>R99@VALUE`), ошибка вычисления (`=1/0`) → рисуется исходный текст как есть.
Само-диагностично (видно, что мертва, не молча пусто — [[feedback_ground_truth_debugging]]);
валидатор может доп. предупредить. Побочно спасает текст, СЛУЧАЙНО похожий на плейсхолдер.

**Триггер — только ПЕРВЫЙ символ сегмента** (как Excel: `=` запускает формулу лишь в начале
ячейки). `support@acme.com` — `@` в середине, нет ведущего `>`/`=` → обычный текст (email на
шелке работает без экранирования). `Vout = 3.3V` — `=` в СЕРЕДИНЕ → обычный текст, не формула.

**Экранирование:** `\>` → литеральный `>` (ground truth Eagle: `\>SHEET` печатает `>SHEET`;
наследуем, не изобретаем). Симметрично `\=` → литеральный `=`. Каскад `\\` → литеральный `\`.
ВНИМАНИЕ на сосуществование escape-механик в одном текстовом поле: `!` — overbar-toggle (см.
выше), `\` в Altium-нотации — overbar одного символа. Порядок разбора (плейсхолдер / overbar /
многострочность) зафиксировать при реализации; в IR-каноне overbar = Eagle `!...!`, так что
`\` свободен под escape плейсхолдера — конфликта нет, но разложить слои явно.

**Только ЧТЕНИЕ.** И `>`, и `=` ОТРАЖАЮТ атрибуты, не переопределяют (значение живёт на
носителе — один факт, одно место). Не «формула, пишущая в ячейку».

**Связь с видимостью:** плейсхолдеров у атрибута может быть N, в разных местах/представлениях.
«Атрибут виден ⟺ есть плейсхолдер ГДЕ-ЛИБО» (см. `<attr>`, видимость).

**Эффективное значение и варианты сборки — плейсхолдеры пересчитываются при смене варианта.**
Значение атрибута — это КАСКАД разрешения (вычислим, не хранится):
`эффективное(attr) = вариант-override ?? инстанс-override ?? библиотечный-дефолт`
(тот же каскад, что «библиотечный vs пользовательский» в `<attr>`, с активным вариантом как
верхним слоем). Плейсхолдеры читают ЭФФЕКТИВНОЕ значение → смена активного варианта сборки
АВТОМАТИЧЕСКИ перевычисляет все `>`/`=`. Следствие, а не отдельная фича: value=атрибут +
вариант=per-instance-override + плейсхолдер=read-only-проекция — три слоя на одном языке
«атрибут» сходятся сами. Пример-киллер: `Vout = =1.25*(R1@VALUE/R2@VALUE+1)` на плате DC-DC
меняется сам при переключении варианта, затронувшего feedback-резистор. Работает для ЛЮБОГО
атрибута под формулой (ток LED, частота таймера, усиление). Это СРЕЗ одного активного варианта;
«все варианты рядом» потребовало бы адресации `@вариант` в ссылке — возможное будущее
расширение, пока не нужно.

**Scope плейсхолдеров:**
- **Плата — ГЛОБАЛЬНЫЙ scope.** Все компоненты на одном канвасе, все REFDES доступны отовсюду.
- **Схема — ИЕРАРХИЧЕСКИЙ (из-за модулей, [[project_deferred_hierarchy]]), видимость
  АСИММЕТРИЧНА** (лексический scope: модуль = функция, top-level = вызывающий):
  - **top-level → вниз: РАЗРЕШЕНО** (не поощряется — компонент модуля на отдельном канвасе,
    неудобно, но REFDES существует, компонент реален).
  - **внутри модуля → наружу: ЗАПРЕЩЕНО.** Плейсхолдер внутри модуля видит ТОЛЬКО компоненты
    своего модуля. Причина: модуль ПЕРЕИСПОЛЬЗУЕМ (design block, возможно многократное
    инстанцирование) — ссылка на внешний refdes сломала бы самодостаточность/переносимость.
  - **Адресация «вниз» — ПЛОСКАЯ, никакого path-синтаксиса** (`>MOD1/R5@…` НЕ нужен). Refdes
    компонентов внутри инстанса модуля уже резолвятся в ГЛОБАЛЬНО УНИКАЛЬНЫЕ имена (см.
    «Модуль», `offset`): режим префикса → `>MD2:R1@VALUE`, режим offset → `>R101@VALUE`. Это
    те же имена, что уедут на плату → один ключ адресации во всех представлениях (иерархия
    схемы и плоскость платы сходятся в одном REFDES). Компоненты модуля СХЛОПНУТЫ в
    прямоугольник на top-level, визуально не видны, но имя выводимо тривиально.
  - **Ответственность — на пользователе** (та же модель, что offset-коллизии в «Модуль»,
    ground truth Eagle): адресовать компонент внутри модуля с top-level легально, имя
    выводимо; кто это делает — достаточно опытен ([[feedback_no_pandering]] — даём мощь, не
    нянчим).

**Скоуп:** фича РЕДАКТОРА (живой текст на канве). Eagle межобъектных `>R1@VALUE`/`=`-формул НЕ
умеет → на board-импорте не встретится; модель закладываем, реализация — с редактором.
Eagle-`\>` при импорте читается в наш литеральный `>` (ноль трения).

## Слои — единая номенклатура для `<symbol>` и `<schematic>`

Опциональный атрибут `layer` на геометрии символа (`<line>`/`<arc>`/`<shape>`/`<polygon>`/
`<text>`) и на декоративной геометрии/тексте схемы (`<schematic>`, см. ниже) использует
**одну и ту же** номенклатуру имён — не два раздельных словаря. Смысл — не только
визуальная сортировка, но и группировка для selection filter редактора (по аналогии с
Eagle, где то же самое уже работает: слой можно скрыть/залочить/фильтровать выделение).

Значение `layer` — свободная строка. Ниже — предопределённые имена с фиксированным
смыслом (по образцу Eagle's schematic layers 91/94/95/96/97 — `Nets`/`Symbols`/`Names`/
`Values`/`Info`); отсутствующий/произвольный `layer` не ошибка, просто не участвует ни в
одной специальной обработке:

| Слой      | Назначение                                                              |
|-----------|--------------------------------------------------------------------------|
| `NETS`    | Провода/сети (`<line>` внутри `<net>`/`<segment>` — см. «Схема» ниже)   |
| `SYMBOLS` | Геометрия тела символа — контуры, пины (то, что раньше называлось `symbol`) |
| `NAMES`   | Плейсхолдер `>NAME`                                                     |
| `VALUES`  | Плейсхолдер `>VALUE`                                                    |
| `INFO`    | Любой другой плейсхолдер (`>ATTR` и т.п.)                              |
| `GRAPHIC` | Декоративная графика — стрелки, разделители блоков схемы                |
| `USER`    | Общего назначения, под произвольные пользовательские нужды             |
| `FRAME`   | Граница печатной области — см. «Frame» ниже. **Ровно один прямоугольник на символ Frame**, геометрическая роль зарезервирована (не просто визуальная группировка, как у остальных слоёв этого списка) |

Дополнительные слои со своими именами (не из этого списка) допустимы — как на символе, так
и на схеме; смысл им придаёт только конкретный редактор/пользователь, IR их не
интерпретирует.

**Структурно закреплены только `NETS` и `FRAME`** — всё остальное (`SYMBOLS`/`NAMES`/
`VALUES`/`INFO`/`GRAPHIC`/`USER`/произвольное имя) чисто визуальное/дефолтное значение,
переопределяемое на любом объекте без ограничений:
- `NETS` — принадлежность определяется КОНТЕЙНЕРОМ (`<line>` лежит внутри `<net>`/
  `<segment>`), не атрибутом `layer` — этот `<line>` вообще не пишет `layer` (см. «Схема»
  выше). Обратное неверно: `<line layer="NETS">` вне `<net>` — обычная декоративная линия,
  просто на слое с этим именем, не становится электрической цепью только от имени слоя.
- `FRAME` — принадлежность определяется РОЛЬЮ (единственный `<shape>` на символе-Frame,
  см. «Frame» ниже), не тем, что где-то ещё стоит `layer="FRAME"` — прямоугольник на этом
  слое внутри произвольного (не-Frame) символа/схемы ничего структурно не запускает, это
  просто декоративная геометрия с таким именем слоя.

Ничто в IR не мешает нарисовать `<shape>` на `NAMES`, `SYMBOLS` или даже `NETS` — если это
не `<line>` внутри `<net>`/не единственный `<shape>` символа-Frame, такой объект остаётся
обычной декоративной геометрией, просто сгруппированной под этим именем слоя.

Схема состоит из размещённых символов — слой на холсте `<schematic>` это надмножество
слоёв, встречающихся в символах: после того как компонент кладётся на холст как
`<instance>`, вся его геометрия (включая `FRAME`) переносится вместе с ним, никакого
отдельного перевода слоёв при размещении не происходит.

### Eagle `technology` — разворачивается в отдельные компоненты, третьего уровня в IR нет

Eagle-иерархия трёхуровневая: `deviceset` → `device` (реальный footprint/package) →
`technology` (например `-1%`/`-5%` — допуск резистора; несколько technology могут
делить один и тот же device/footprint, но нести разные атрибуты MANF#/LCSC#/PACKAGE).
IR двухуровневый: `component` → `footprint`/`variant`. Третьего уровня под этим нет
и не будет — **каждое реально встреченное имя technology становится ОТДЕЛЬНЫМ,
независимым `<component>`**, а не осью/вариантом внутри одного.

Решение пользователя: «линейный регулятор на 1.8В и на 3.3В — это ФИЗИЧЕСКИ РАЗНЫЕ
ДВА УСТРОЙСТВА, логично, что и описаны они будут как ДВА НЕЗАВИСИМЫХ УСТРОЙСТВА» —
то же самое верно для `-1%`/`-5%` резистора: честные раздельные компоненты, не
фиктивная общая сущность с внутренней «осью технологии», которую IR не умеет
выразить. Небольшое дублирование библиотечных данных при этом принято сознательно
(экономия текста в Eagle была для удобства человека, не требование модели данных).

**Правило именования**: `{deviceset_name}{technology_name}` (Eagle-имена технологий
уже сами начинаются с разделителя вида `-1%`, конкатенация без дополнительного
символа) — `R` + `-1%` = `R-1%`. Пустое имя technology (`""`, обычный случай для
devices, у которых нет вариантов вовсе) — САМ deviceset без суффикса (`R`, не
`R-anonymous`). Device, не имеющий варианта под данным именем technology, просто не
включается в компонент с этим именем — окажется только там, где вариант реально есть
(в т.ч. в безымянном `R`, если там есть device с `technology=""`).

**Импорт из Eagle** (`babel/eagle_parser.py:convert_deviceset`): один `<deviceset>` →
список `<component>`, по одному на каждое имя technology. `<part library=
deviceset= technology=>` на схеме резолвится в конкретный компонент через составной
ключ (библиотека, deviceset, technology) — см. `babel/eagle_project_parser.py`.

**Экспорт обратно в Eagle** — НЕ восстанавливает исходную группировку: `R`/`R-1%`/
`R-5%` при экспорте становятся тремя независимыми Eagle `<deviceset>` (решение
пользователя — round-trip не обязан быть 1-в-1 по составу библиотеки, раз каждый
получившийся компонент честно описывает физически иное устройство).

Компонент бывает двух видов — они взаимоисключающие:

**Однорежимный** — атрибут `symbol` указывает на символ напрямую, gate нет, пины в mapping без префикса:

```xml
<component name="R" prefix="R" symbol="R">
  <footprint name="R0402">
    <pin-mapping>
      <map pad="1" pin="1"/>
      <map pad="2" pin="2"/>
    </pin-mapping>
  </footprint>
</component>
```

**Многорежимный** — атрибута `symbol` нет, символы подключаются через дочерние `<gate>`, пины в mapping с префиксом `GATE.pin`:

```xml
<component name="LM358" prefix="U">
  <attributes>
    <attr name="description" value="Dual op-amp"/>
    <attr name="manf" value="Texas Instruments"/>
  </attributes>
  <gate name="A"   symbol="OPAMP"/>
  <gate name="B"   symbol="OPAMP"/>
  <gate name="PWR" symbol="OPAMP_PWR"/>
  <footprint name="SOIC8">...</footprint>
</component>
```

### `<attr>` — пользовательский атрибут

Произвольные пары ключ-значение (BOM-поля, ссылки на дистрибьюторов и т.п.).

**`description` — обычный атрибут, без выделенного элемента.** Раньше в IR был отдельный
`<description>`-элемент компонента; решили, что это избыточно — описание устройства это
просто ещё один атрибут (`<attr name="description" value="..."/>`), как и любой другой,
консистентно для всех источников (Eagle/Altium/KiCad).

Оба целевых формата, у которых есть свой нативный "слот" под описание, вынимают атрибут
`description` из общей таблицы при экспорте и кладут именно туда (не выводя его заодно
ещё раз как обычный атрибут):
- **Eagle** — `deviceset` имеет собственный `<description>` (HTML-блёрб в библиотечном
  браузере); `eagle_exporter` достаёт `description` из `<attributes>`, не дублируя в
  `<technology><attribute>`. На вход (`eagle_parser`) симметрично читается обратно как
  обычный `<attr name="description">`.
- **Altium** — стандартная колонка `Description` в таблице компонентов (xlsx/DbLib,
  `_build_component_rows`); `description` исключён из `_custom_attrs` (туда же, где
  исключён и `value` → `Comment`), чтобы не плодить вторую колонку с тем же содержимым.

У **KiCad** подобного нативного слота нет (Property "Description" у символа — рядовое
поле без какого-либо особого статуса в формате) — там `description` всегда просто
рядовой атрибут без какой-либо специальной обработки ни на импорте, ни на экспорте.

#### Тип атрибута — маршрутизация к потребителю, НЕ видимость

У каждого `<attr>` есть `type` (расширяемый enum): маршрутизирует атрибут к
потребителям, но НЕ управляет тем, где он виден.

| `type`    | Потребитель / смысл                                                     |
|-----------|-------------------------------------------------------------------------|
| `bom`     | попадает в закупочный BoM-выхлоп (MANF#, LCSC#, партномер…)              |
| `sim`     | параметры схемной симуляции (SPICE-модель и т.п.)                        |
| `general` | справка человеку (темп-диапазон и пр.) — видно, но НЕ в BoM              |
| `service` | для скриптов/автоматизации — пока «хороший тон», позже можно принудить   |

BoM = `filter(type=bom)`; вход симулятора = `filter(type=sim)`; и т.д. — всё
ПРОИЗВОДНОЕ от типа, никакой ручной per-project разметки (никаких «BoM-галочек»).

**Видимость ТОТАЛЬНАЯ.** Окно атрибутов показывает ВСЕ атрибуты объекта в ЛЮБОМ
представлении (схема И плата), с индикацией типа. Компонент на схеме и на плате —
одна сущность, два представления → одно полное лицо, а не разные наборы свойств
в разных окнах (это Eagle-scope-видимость, от которой мы отказались — см. ниже).
Партномер правится хоть из board-редактора. Тип НЕ скрывает атрибут, только
маршрутизирует. (Отдельно от значения — placeholder `>NAME`/`>VALUE` рисует атрибут
на канве символа/футпринта; это про отрисовку на листе, не про доступ к значению.)

**Видимости-поля у атрибута НЕТ.** Атрибут виден в каком-то месте (шелк платы, лист
схемы) ⟺ для него ТАМ есть placeholder. «Per-instance управление видимостью» не
существует как понятие — оно тождественно наличию/отсутствию плейсхолдера, а
смэшнутый плейсхолдер свободно перемещается и удаляется. Скрыть значение у одного
плотно стоящего компонента = удалить его плейсхолдер (значение остаётся в атрибуте,
видно в окне атрибутов). Плейсхолдеры независимы per-representation (на плате свой,
на схеме свой). Импорт Eagle: `display="off"` → плейсхолдер НЕ создаём;
`display=value/name/both` → создаём плейсхолдер с координатами атрибута. Массовый
машинный Eagle-`display="off"` (проставлен всему кроме NAME/VALUE по умолчанию —
подтверждено sigtest.brd) растворяется в «нет плейсхолдера»: шум не хранится, только
реально нарисованное.

#### Упрощение относительно Eagle

Eagle разделяет для атрибута: видимость (схема vs плата) и scope прав редактирования/
удаления по уровню (library/schematic/board). Мы СЛИВАЕМ обе оси в общий котёл:
- **видимость** → тотальная (см. выше);
- **право редактирования** → правь откуда угодно.

На ~3–10 атрибутах компонента (даже в сильно документированном дизайне) эти
различия не окупаются и вредят консистентности. Оставлена ТОЛЬКО третья ось —
происхождение значения — и то не как хранимое поле, а как ВЫЧИСЛИМЫЙ факт.

#### Происхождение значения — вычислимо, не хранится

Атрибуты **per-instance**. Библиотечный элемент embed-ится в проект целиком (пул-
компонент рядом). Поэтому «библиотечный дефолт vs пользовательское переопределение»
не хранится флагом, а ВЫЧИСЛЯЕТСЯ сравнением `instance.attr` с `pool_component.attr`:
- значения равны → унаследованный дефолт → при update библиотеки перезаписывается;
- отличаются → пользовательский override → при update НЕ перезатирается;
- есть на инстансе, нет в библиотеке → добавлен пользователем → сохраняется.

**Удаление атрибута инстанса** (закрывает дыру «удалил → библиотека воскресила при
update»; проблема неразличимости «нет значения» от «намеренно удалён» — решена
устранением операции, а не tombstone-флагом):
- библиотечный (унаследованный) атрибут удалить с инстанса НЕЛЬЗЯ (как в Eagle);
- не нужен всем экземплярам → удали в БИБЛИОТЕКЕ (один факт — одно место);
- не нужен здесь и сейчас → очисти ЗНАЧЕНИЕ (пустой override, защищён правилом
  «отличается = сохраняем»);
- удалить с инстанса можно только атрибут, добавленный НА инстансе (библиотека о
  нём не знает — воскрешать нечего).

#### Обновление библиотеки — 3-way merge

Обновление библиотеки — не двусторонний diff, а ТРЁХСТОРОННИЙ merge (base доступен
именно потому, что старый пул-компонент embed-нут в проект):
- **base** = референсный пул-компонент ДО обновления;
- **ours** = инстанс с пользовательскими правками;
- **theirs** = новый референсный из обновлённой библиотеки.

Per-attribute против base: (не менял × не менял)=без изменений; (не менял × изменил)=
берём theirs; (изменил × не менял)=берём ours; **(изменил × изменил)=КОНФЛИКТ**. Три
из четырёх автоматические и бесшумные. Конфликт (обе стороны трогали, в т.ч.
library-delete × user-override) НЕ разрешается молча ни в одну сторону —
ПРЕДЪЯВЛЯЕТСЯ пользователю (как VCS-merge-конфликт), с обеими версиями. Молчаливая
победа любой стороны = скрытая рассогласованность, которую пользователь потом не
поймёт. **Скоуп:** IR-модель обязана это ПОДДЕРЖИВАТЬ (base есть → 3-way возможен);
сам merge-движок с UI разрешения — при проектировании редактора, не в импорте.

#### Варианты сборки (тесно связаны с атрибутами)

Вариант сборки = именованный набор ПЕРЕОПРЕДЕЛЕНИЙ на инстансах поверх базового
дизайна: `populate` (ставить/не ставить компонент — см. [[project_bom_flag_removed]],
покрывает и сборочный чертёж, и BoM), значение/партномер, footprint-вариант.
Механически это тот же per-instance override поверх «базы», что и происхождение
значения выше — то же 3-way-мышление (base = вариант «по умолчанию», ours = данный
вариант). Потому и живут рядом. Eagle `<variantdef>`/`<variant>` богаче нашего
populate — на этом этапе тащим populate + per-variant значение/footprint;
полную Eagle-семантику вариантов НЕ копируем (детали — при реальной потребности).

### `<gate>` — вхождение символа в компонент (только для многорежимных)

| Атрибут  | Описание                                                             |
|----------|----------------------------------------------------------------------|
| `name`   | Имя gate — уникальное в компоненте                                   |
| `symbol` | Ссылка на `<symbol name="...">` в пуле                               |
| `x y`    | Смещение символа на схеме, µm (добавляется ко всем координатам gate) |

Один и тот же символ может быть использован несколькими gate (gate A и B выше оба ссылаются на `OPAMP`).

| Атрибут | Описание                              |
|---------|---------------------------------------|

### `<pin-mapping>` — связь падов с пинами

Для **однорежимного** компонента — просто имя пина:

```xml
<pin-mapping>
  <map pad="1" pin="1"/>
  <map pad="2" pin="2"/>
</pin-mapping>
```

Для **многорежимного** — `GATE_NAME.PIN_NAME`:

```xml
<pin-mapping>
  <map pad="1" pin="A.OUT"/>
  <map pad="2" pin="A.IN-"/>
  <map pad="3" pin="A.IN+"/>
  <map pad="4" pin="PWR.GND"/>
  <map pad="5" pin="B.IN+"/>
  <map pad="6" pin="B.IN-"/>
  <map pad="7" pin="B.OUT"/>
  <map pad="8" pin="PWR.VCC"/>
</pin-mapping>
```

Формат `pin`: `GATE_NAME.PIN_NAME`.

#### Один пин → несколько падов

Маппинг — это **явная connect-таблица на компоненте** (как `<connect>` в Eagle и
`MAP_DEFINER` в Altium), а не неявное совпадение имён. Symbol ничего не знает про пады,
footprint ничего не знает про пины — их связывает только `<pin-mapping>`. Поэтому один
и тот же footprint переиспользуется разными компонентами без переименования падов.

Когда на один пин символа садится несколько падов корпуса (exposed/thermal pad,
параллельные земли/питания), пады перечисляются **через пробел** в атрибуте `pad`
одного `<map>` — это IR-канон, не формат конкретного инструмента:

```xml
<map pad="4 9" pin="PWR.GND"/>   <!-- пин GND ← пады 4 и 9 -->
```

> **Ограничение:** имена падов **не могут содержать пробел** — пробел зарезервирован как
> разделитель списка падов. Designator пада — короткий токен (`1`, `9`, `EP`), пробелу
> там делать нечего. Это даёт бесплатный разделитель без отдельного синтаксиса.

Экспорт:
- **Eagle** — `<connect ... pad="4 9"/>` 1:1, ОДНА строка, пробел как разделитель.
  Подтверждено на нескольких реальных Eagle-файлах (`testData/test.lbr`) — список
  работает независимо от объявленной версии, от типа пада (SMD/сквозной/смешанный) и
  от количества (до 5 падов на один пин в тесте, включая device, созданный нативно
  прямо в Eagle). **Реальное ограничение — designator пада регистрозависим, Eagle
  отвергает строчные буквы в имени пада** (`invalid/missing attribute 'pad'`;
  подтверждено: пользователь вручную заменил заглавные буквы на строчные в рабочем
  файле и получил эту же ошибку). Раньше здесь было неверное предположение про версию
  формата — ошибку вызывала не версия, а синтезированный суффикс дизамбигуации падов
  (`kicad_parser.py`), который по ошибке использовал строчные буквы; исправлено на
  заглавные.
- **Altium** — запись `MAP_DEFINER`: `DesIntf=GND`, `DesImpCount=2`, `DesImp0=4`, `DesImp1=9`
  (нативно поддерживает список падов на пин в одной записи; футпринт-пады не
  переименовываются).
- **KiCad** — несколько падов с одним и тем же `pin name`/номером.

#### KiCad-специфика: «stacked pins» (один СИМВОЛЬНЫЙ пин → несколько падов)

Зеркальный случай тому, что выше: footprint-сторона уже умеет «несколько падов — один
номер», а KiCad-символ умеет «один пин — несколько номеров», потому что у KiCad вообще
нет способа напрямую связать один пин символа с несколькими падами корпуса. Раньше
выкручивались так: рисовали НЕСКОЛЬКО `<pin>`-элементов друг на друге (одна координата),
прятали все кроме одного через `(hide yes)`. С KiCad 10 появился настоящий механизм —
один `<pin>`, а `number` — буквально строка-список `"[A1,A12,B1,B12]"`. Оба формата
встречаются в реальных библиотеках (подтверждено на `testData/pintest.kicad_sym`,
символы `USB_C_old`/`USB_C_new` — один и тот же разъём, экспортированный старой и
новой версией KiCad). Импортёр сводит оба к одному и тому же IR — обычному
`<map pad="A1 A12 B1 B12" pin="GND"/>` выше, ничего нового в схему не добавляется:

- **Новый формат** — `_pin_numbers()` (`babel/kicad_parser.py`) распознаёт `[A,B,C]` в
  `pin.number` и раскрывает в список.
- **Старый формат** — `_collapse_stacked_pins()` группирует sibling-пины ПО КООРДИНАТЕ
  (по решению пользователя — координаты достаточно, имя/поворот/длину можно не
  проверять) в один представительский `<pin>`, остальные номера складывает в
  `_stacked_numbers`. **На `hide` группировка не опирается** — он и ненадёжен для
  чтения (kiutils не понимает `(hide yes)` как вложенный список, та же болезнь, что
  у `Property`/`pin_numbers` — у всех дублей `hide` читается как `False`), и не нужен:
  совпадение координат само по себе уже однозначный сигнал, KiCad не кладёт два разных
  пина в одну точку случайно.

Подтверждено на `testData/phil`: `USB_C_Receptacle_USB2.0_14P` (старый формат) —
15 `<pin>` → 9 после схлопывания, `GND`/`VBUS` получили честный `pad="A1 A12 B1 B12"`/
`"A4 A9 B4 B9"` вместо отсутствующего маппинга (как было бы у нового формата без фикса:
литеральный поиск пада с именем `"[A1,A12,B1,B12]"` среди реальных падов).

### Геометрия корпуса — слои: ТА ЖЕ числовая модель, что на плате

Механизм слоёв в футпринте ЕДИН с платой (см. «Плата (Board IR)» ниже; исторические
тег-контейнеры `<top>/<silk_top>/...` упразднены — они были вторым, параллельным
кодированием того же факта, см. decisions.md «Унификация слоёв футпринта и платы»).
Каждый геометрический объект — ПРЯМОЙ ребёнок `<footprint>` с атрибутом
`layer="[!][-]N"`:

```xml
<footprint name="SOT23">
  <smd name="1" x="..." y="..."/>          <!-- пад: слоя нет, медь стороны монтажа -->
  <line x1="..." ... layer="121"/>         <!-- шёлк стороны монтажа -->
  <text layer="151">&gt;NAME</text>        <!-- сборочный чертёж -->
  <line layer="120" width="2000" .../>     <!-- паз 2 мм (рез, standalone) -->
  <line layer="146" width="2200" .../>     <!-- его металлизация (PLATING) -->
</footprint>
```

Отличие от платы одно: в футпринте знак СТОРОНО-ОТНОСИТЕЛЕН — `+n` = сторона монтажа,
`−n` = противоположная. Абсолютным он становится при размещении `<element>`: у элемента
на top числа проходят как есть, у элемента на bottom парные слои меняют знак, standalone
(`120`, `146`, `148`, юзерские без пары) не меняются, геометрия зеркалится. Никакой
таблицы соответствия — чистая арифметика знака.

Частые номера (канонический список — ir_util.py и «Плата (Board IR)»): медь `1`/`−1`,
шёлк `121`, маска `129`, паста `131`, courtyard `139`, сборочный чертёж `151`,
бессторонние заметки `148` (KiCad `Dwgs.User`/`Cmts.User` — у них и в KiCad нет стороны;
раньше сливались в fab и при экспорте в Eagle попадали на tDocu вместо честного
Document 48), резы (пазы) `120` + металлизация стенок `146` (см. «Резы и металлизация»
в board-части — механизм общий, кастелляции живут именно в футпринте).
`<pad>`/`<hole>` слоя не несут (сквозные по построению);
`<smd>` — тоже, кроме редкого пада ПРОТИВОПОЛОЖНОЙ стороны (явный `layer="-1"`).

Геометрия: `<line>`, `<arc>`, `<shape>`, `<polygon>`, `<text>` (те же атрибуты, что в
символе, плюс `layer`), пады:

### `<smd>` — SMD-пад

| Атрибут     | Описание                                              |
|-------------|-------------------------------------------------------|
| `name`      | Обозначение пада (совпадает с `pad` в pin-mapping; **без пробелов**) |
| `x y`       | Центр, µm                                             |
| `width`     | Ширина, µm                                            |
| `height`    | Высота, µm                                            |
| `rot`       | Поворот, градусы                                      |
| `roundness` | 0 = прямоугольник, 100 = круг, между — скруглённый   |
| `layer`     | НЕТ для обычного пада (медь стороны монтажа по построению); `-1` — редкий пад ПРОТИВОПОЛОЖНОЙ стороны |

`<smd>` моделирует только (скруглённый) прямоугольник/круг — `circular`/`oval`/`rectangular`/
`rounded rectangle` ложатся естественно (`rounded rectangle`: `roundness` = `corner_size × 2`,
относительно `min(width, height)`, та же шкала 0–100, что уже использовалась для `roundrect`).
Любая другая форма пада (`trapezoid`, `custom`, `chamfered rectangle`, `chamfered with other
corners rounded` и т.п. — KiCad даёт их все в одном дропдауне Pad Shape, см. decisions.md
"KiCad: формы падов") заменяется на обычный прямоугольник со сторонами `width`/`height` пада
(без попытки восстановить точный bbox, например, произвольного `custom`-полигона) — со
строкой в лог импорта (см. "Лог импорта" ниже), не молча.
| `thermals`  | `0`–`100`, умолчание `100` — теплового барьера, µm. **`0` = сплошное соединение с полигоном (без барьера вообще), `100` = самый тонкий/малочисленный возможный барьер** (максимальная теплоизоляция от заливки). Промежуточные значения — толщина спиц и их количество, конкретную интерполяцию считает инструмент-приёмник, IR задаёт только шкалу (см. «Thermals — единый процент, не два булевых» и «Термо-релиф на плате» ниже). **Абсолютная ширина спицы НЕ хранится** — она производна; пол = `width` полигона (модель пера) |
| `stopmask`  | `0`/`1`, умолчание `1` — автоматическое вскрытие паяльной маски |
| `paste`     | `0`/`1`, умолчание `1` — автоматическая апертура паяльной пасты |

### `<pad>` — сквозной пад (TH)

| Атрибут    | Обязательный | Описание                          |
|------------|:---:|-----------------------------------|
| `name`     | да  | Обозначение пада (**без пробелов**) |
| `x y`      | да  | Центр, µm                         |
| `drill`    | да  | Диаметр отверстия, µm             |
| `diameter` | да | Диаметр медного кольца, µm (авто не существует — restring запекается импортом, см. «DRC-ядро») |
| `shape`    | да  | `round` / `square`                |
| `thermals` | нет | `0`–`100`, умолчание `100` — та же шкала, что у `<smd>` (см. выше) |
| `stopmask` | нет | `0`/`1`, умолчание `1` — автоматическое вскрытие паяльной маски |

`stopmask`/`paste` — по образцу Eagle `<smd>`/`<pad>` (`eagle.dtd`: `stop`/`cream`, оба
`%Bool`, умолчание `"yes"`). Только включают/выключают АВТОМАТИЧЕСКУЮ генерацию редактором
— как именно считается размер вскрытия/апертуры (margin, design rules платы и т.п.) IR не
описывает, это дело конкретного инструмента-приёмника. `paste` не применим к TH-паду
(`<pad>`) — сквозные отверстия не покрываются паяльной пастой по построению (паста — только
для SMD-монтажа).

### Thermals — единый процент, не два булевых (пересмотрено)

`thermals` был булевым (по образцу Eagle `%Bool`, умолчание `"yes"`) — заменён на процент.
**Решение пользователя**: два раздельных булевых атрибута («нужен ли барьер вообще» + «его
толщина/число спиц») избыточны — одна и та же шкала 0–100 естественно покрывает оба
вопроса разом, включая вырожденный случай `0` («барьера нет» — то, что раньше было
`thermals="0"`). Хранить геометрию барьера отдельно от факта его наличия смысла не было:
инженерный вопрос всегда один — «насколько термически изолировано это подключение», не два
раздельных факта.

**Связь с `<polygon>`'s собственным `thermals` (см. «Заполненный многоугольник» выше,
атрибут `thermals` там ОСТАЁТСЯ булевым)**: генерация барьера требует совпадения ДВУХ
условий — `<polygon thermals="1">` (этот КОНКРЕТНЫЙ полигон вообще генерирует барьеры для
своих пересечений с падами) И пад несёт `thermals > 0` (этот КОНКРЕТНЫЙ пад разрешает
барьер и задаёт его толщину). `<polygon thermals="0">` полностью игнорирует пад-проценты —
всегда solid-соединение, независимо от того, что указано на паде. Асимметрия между булевым
на полигоне и процентом на паде осознанная, не недосмотр: полигон отвечает только на
да/нет-вопрос («в принципе ли я умею барьеры»), пад — на количественный («насколько
конкретно ИМЕННО ЭТОТ пад хочет быть изолирован»). Два булевых на пад дали бы ту же самую
избыточность, которую только что убрали с полигона — по этой же причине пад получает
процент, а полигон нет.

При импорте из источника, где это явное свойство пада (а не отдельный слой) — умолчание
берётся `1` (как у Eagle). Если источник выражает это через technical layers на МЕДНОМ
smd-паде (KiCad: `F.Mask`/`F.Paste` в списке слоёв пада) — отсутствие слоя в явном списке
означает `0`, не `1` (KiCad считает по умолчанию "слоя нет = не генерировать", в отличие от
Eagle, где умолчание для самого свойства — "генерировать"); см. также "KiCad: технические
слои smd-пада" ниже.

Если автоматики недостаточно (нужна **произвольная** форма вскрытия/апертуры — например,
несколько изолированных островков пасты на одном паде, не сводимое к простому
расширению/сжатию) — выключить соответствующий флаг (`stopmask="0"`/`paste="0"`) и нарисовать
форму вручную обычной геометрией (`<shape>`/`<polygon>`) на слое `mask_top`/`mask_bottom`
(вскрытие маски) или `paste_top`/`paste_bottom` (апертура пасты) того же `<footprint>`. Это
осознанно НЕ отдельный атрибут/подэлемент на самом паде — произвольная форма, привязанная к
паду через геометрическое совпадение позиции, а не явную ссылку (тот же компромисс, что и
у любой другой декоративной геометрии слоя; в отличие от pin↔pad маппинга, здесь нет
электрической семантики, которую нужно было бы терять при разрыве связи).

### KiCad: технические слои smd-пада → `paste`/`stopmask`, и aperture-пады без меди

KiCad не хранит `paste`/`stopmask` как явные булевы свойства пада — вместо этого у каждого
пада есть список **technical layers** (вкладка Pad Properties), и присутствие/отсутствие
`F.Paste`/`F.Mask` (или просто `Paste`/`Mask` для двусторонних/THT-падов) в этом списке —
единственный сигнал, который KiCad даёт о намерении. На импорте у МЕДНОГО smd-пада (есть
`F.Cu`/`B.Cu`):
- `F.Paste`/`Paste` в слоях → `paste="1"`, иначе `paste="0"`.
- `F.Mask`/`Mask` в слоях → `stopmask="1"`, иначе `stopmask="0"`.
- Остальные technical layers пада (clearance/zone_connect/thermal_bridge_angle и т.п.) —
  игнорируются, в IR не попадают.

Если пада МЕДИ НЕТ вообще (см. "KiCad: пад без меди" выше) — это уже не электрический пад,
а **aperture-пад**: чистая paste/mask-геометрия без контакта. Такой пад импортируется не как
`<smd>`, а как одна или несколько `<shape>` (по форме пада, см. ниже) — одна на каждый
включённый у него technical layer (`F.Paste` → фигура на `paste_top`, `F.Mask` → фигура на
`mask_top`, оба сразу → две перекрывающиеся фигуры на разных слоях). Если у aperture-пада
вообще не указан ни один технический слой — фигуру негде рисовать, пад дропается с записью
в лог импорта (см. "Лог импорта" ниже).

> В Altium TH-пад — это SMD-пад со сквозным отверстием. `diameter` берётся как `min(sizeX, sizeY)`.
> `diameter` обязателен (см. «DRC-ядро»); экспортёры при его отсутствии в
> устаревших IR синтезируют `drill × 1.8` СО СТРОКОЙ В ЛОГ, не молча.

### `<model3d>` — привязка 3D-модели

У футпринта может быть **несколько** `<model3d>` — диспетчеризация по значению
атрибута инстанса (класс «одно посадочное — параметричная внешность»: цвет LED,
высота гребёнки, актуатор кнопки; полное рационале и правила резолюции —
decisions.md «диспетчеризация 3D-модели по атрибуту», 2026-07-10).

| Атрибут    | Описание                                     |
|------------|----------------------------------------------|
| `variant`  | нет — ключ выбора: голое ЗНАЧЕНИЕ (не имя!) атрибута инстанса (`RED`, `H11`). Запись БЕЗ `variant` — безусловный fallback; максимум одна |
| `tx ty tz` | Смещение, µm (в фрейме платы) — у КАЖДОЙ записи своё               |
| `rx ry rz` | Углы поворота, градусы — **MCAD intrinsic XYZ** (как у Altium)   |

Резолюция по инстансу: ключи ищутся среди значений ВСЕХ его атрибутов; 0 совпадений →
fallback; ровно 1 → эта запись; ≥2 разных ключей → конфликт (заглушка + диагностика,
никогда не «первый попавшийся»); композитная внешность = композитное значение-ключ
(`RED-GREEN` у двухцветного LED).

Имя файла модели не хранится в IR — при экспорте берётся имя корпуса
(`<footprint name="...">`); у варианта — `<footprint>_<variant>` (`LED0603_RED`).
Импортёры сегодня порождают максимум одну безусловную запись (Eagle-сайдченнел —
одна модель на футпринт, осознанно); множественность — задел под редактор.

#### Соглашение о размещении модели (композиция T·R)

Полное преобразование точки модели в координаты платы:

```
world_p = R · model_p + T          (матрично: M = T · R)
```

То есть **сначала поворот** вокруг начала модели (`rx ry rz`), **затем трансляция**
`(tx, ty, tz)` в **фрейме платы**. Следствие: оси сдвига от поворота **не зависят** —
`tz` это всегда высота над платой, как бы деталь ни была повёрнута. Это MCAD-стандарт
(Translate · Rotate). При сборке матрицы размещения нельзя путать с `R · T` — иначе
сдвиг «поедет» именно у повёрнутых корпусов (коварный баг: у неповёрнутых всё выглядит
корректно).

**Конвенция углов — MCAD intrinsic XYZ** (Z-up, как у Altium): `R = Rx(rx)·Ry(ry)·Rz(rz)`.
Altium-парсер хранит углы напрямую. Eagle-парсер применяет `Rx(-90°)·R_eagle` и
декомпозирует в XYZ; Eagle-экспортёр делает обратное: `Rx(90°)·R_mcad`, декомпозирует
в ZYX. KiCad-конвертер — отдельный шаг (см. [progress.md](progress.md)).

#### Соглашение о расположении файлов моделей

Файлы 3D-моделей (`.step` / `.wrl`) хранятся **рядом с импортируемым файлом**, в директории с тем же именем (без расширения):

```
eagle_exp.lbr
eagle_exp/          ← директория с моделями
    SOIC14.step
    SOT23-3.step
    ...
```

Парсер ищет файл `<имя_корпуса>.step` (затем `.stp`, `.wrl`) в этой директории. Если файл найден — байты модели передаются экспортёру для встраивания в целевой формат.

**Sidecar — канон IR.** Сама IR байты модели не несёт, только привязку по имени корпуса.
Встраивание/извлечение — ответственность парсера/экспортёра на границе с конкретным
тулом (симметрично тому, как костыли поворотов живут на стороне «кривого» тула, а не в
ядре IR). Допустимая деградация: если sidecar-файла нет — модель просто теряется, плата
и футпринт остаются. Это приемлемо.

**Политика встраивания при экспорте:**

| Цель        | 3D-модель                                                        |
|-------------|------------------------------------------------------------------|
| Altium      | встраивается в `.PcbLib` (OLE compound — нативно)                |
| KiCad ≥ 10  | sidecar `(model "../<lib>.3dshapes/<file>" ...)` — `embedded_files` для отдельного `.kicad_mod` (вне платы/проекта) невозможен, проверено |
| Eagle       | sidecar-файлы рядом с `.lbr` (Eagle байты не встраивает)         |

Работаем только со **STEP**-моделями: они точны 1:1, поэтому `scale` не поддерживается
(всегда `1 1 1`; при импорте из KiCad ненулевой scale — повод для предупреждения).

#### Подготовка в Eagle

Перед импортом выполни в Eagle Script Console:

```
run export3d pack
```

Эта команда автоматически копирует все 3D-модели из библиотек Eagle (облако / локальные) в директорию рядом с `.lbr`-файлом. После этого `eagle_exp/` будет содержать все нужные `.wrl`/`.step` файлы.

# Схема (Schematic IR)

Рационале и обсуждение альтернатив — в [decisions.md](decisions.md). Здесь только спецификация.

## Общая модель

- **Листов (страниц) как сущности нет.** Документ схемы = один бесконечный холст.
  «Лист» в духе Eagle/Altium/KiCad не существует ни как структура хранения, ни как
  ограничение редактирования.
- **Один файл на проект** — схема и трассировка платы хранятся вместе, не как два разных
  документа.
- **Иерархия — ровно 1 уровень**, только для многоканальных модулей (повтор одного блока
  N раз). Модуль = именованный холст **внутри того же `.swprj`** (не отдельный файл, не
  живая ссылка на внешнюю библиотеку — та же логика, что уже применяется к компонентам:
  копия внутри проекта, не ссылка на внешний источник). Правка модуля видна во всех его
  инстансах ровно потому, что это один и тот же XML-узел документа — не потому, что это
  сквозная ссылка между файлами (модуль, живущий в отдельном файле с живой ссылкой на
  него, был бы одновременно небезопасной «design block»-функциональностью — обычный импорт
  проекта уже даёт copy-paste переиспользование без повторения вручную, а геометрическая
  совместимость модуля между разными проектами ничем не гарантирована). Вложенность
  модуль-в-модуле запрещена (глубина ровно 1). Импорт глубины >1 из внешнего формата —
  жёсткий отказ, не флэттинг (риск тихо слить разные локальные цепи по совпадению имени).
  Подробности — «Модуль (design block + иерархия)» ниже.

## Формат файла: `.swlib` vs `.swprj`

Библиотека и проект — два разных файла, два разных корневых элемента:

- **`.swlib`** — `<library name="...">`, как и раньше: только пул (`<symbols>` +
  `<component>`), без размещения. Переносимая, ни к какому проекту не привязана.
- **`.swprj`** — `<project name="...">`. Та же форма пула (`<symbols>` + `<component>`)
  первыми детьми — **компоненты КОПИРУЮТСЯ в проект целиком** (символ, footprint,
  pin-mapping), библиотека остаётся отдельной сущностью, на неё не ссылаются по пути/версии
  (см. атрибут `library` ниже — это просто происхождение для будущего «обновить из
  библиотеки», не живая ссылка). Плюс один `<schematic>` — холст с размещёнными
  `<instance>` и `<net>`, а также — опционально — чисто декоративной геометрией
  (`<line>`/`<arc>`/`<shape>`/`<polygon>`, см. «Декоративная геометрия схемы» ниже).

```xml
<project name="myproject">
  <symbols>...</symbols>
  <component name="R" prefix="R" symbol="R">...</component>
  ...
  <module name="ChannelStrip" dx="116840" dy="35560">
    <port name="IN" direction="in" side="left" coord="0"/>
    <port name="GND" direction="pwr" side="left" coord="7620"/>
    <instance component="R" library="Device" name="R1" x="..." y="..." rot="0" mirror="0"/>
    ...
    <net name="IN">...</net>
  </module>
  <schematic>
    <instance component="R" library="Device" name="R1" x="..." y="..." rot="0" mirror="0"/>
    <instance module="ChannelStrip" name="MD1" x="..." y="..." rot="0" mirror="0"/>
    <instance module="ChannelStrip" name="MD2" x="..." y="..." rot="0" mirror="0"/>
    ...
    <net name="GND">...</net>
    <shape x="..." y="..." w="..." h="..." roundness="0" outline="100" layer="GRAPHIC"/>
  </schematic>
  <layout name="main">...</layout>   <!-- 0..N плат — см. «Плата (Board IR)» ниже -->
</project>
```

## Component instance

Компонент при размещении на холсте **копируется** в документ целиком (символ + атрибуты),
не хранится как ссылка. Документ самодостаточен. Элемент — `<instance>`, ребёнок
`<schematic>` (см. выше).

| Атрибут     | Описание                                                          |
|-------------|----------------------------------------------------------------------|
| `component` | Имя компонента в пуле ЭТОГО ЖЕ файла (`<component name="...">`)    |
| `library`   | Имя библиотеки-источника (только имя, без версии/пути/хэша)       |
| `name`      | Designator конкретного инстанса (`R1`, `U3`, `#PWR013`, ...)       |
| `gate`      | Только для многорежимных компонентов — какой именно `<gate name="...">` размещён ЭТИМ инстансом. Нет для однорежимных (нет `<gate>` вообще, неоднозначности нет) |
| `footprint` | Нет, если у компонента 0/1 footprint — какой именно из НЕСКОЛЬКИХ `<footprint>` компонента использует этот инстанс (имя совпадает с `<footprint name="...">`) |
| `x y`       | Позиция на холсте, µm                                              |
| `rot`       | Поворот, градусы                                                   |
| `mirror`    | Зеркалирование — `0`/`1` (один флаг, как у Eagle: оба варианта отражения KiCad сводятся к одному через поворот, см. decisions.md) |

Атрибуты компонента можно переопределить per-instance (designator, value и т.п.) — так же,
как «обновить компонент» сверяет копию с текущим состоянием библиотеки по имени. Переопределение
— дочерний `<attr name="..." value="..."/>` у `<instance>`, та же форма, что у `<attributes>`
компонента. Типичный случай — `value` родового R/C/L (`10k`, `0.1uF`, ...): это per-instance
данные схемы, не свойство устройства (см. «Корпус `<footprint>`» и решение про generic-merge),
поэтому у самого `<component>` в пуле этого атрибута нет/он общий шаблонный, а реальное
значение каждого размещения — только здесь.

**Резолв плейсхолдера `>NAME`/`>VALUE`/`>ATTR` при отображении инстанса**: показывается
ЗНАЧЕНИЕ, если оно задано (приоритет: override на `<instance>` → атрибут на `<component>`),
и только если значения нигде нет — литеральный текст плейсхолдера. `>NAME` — особый случай,
заменяется на `name` самого инстанса (designator всегда есть, литералом не остаётся никогда).
В библиотечном просмотре компонента (нет инстанса) `>NAME` показывается как есть (designator
ещё не назначен), `>VALUE`/прочие — по атрибутам `<component>`, тем же правилом.

## ФОРМАЛЬНАЯ МОДЕЛЬ: имя, атрибут, плейсхолдер (канон импорта/экспорта)

Записано после каскада однотипных багов (потерянные надписи, лишний `>VALUE`,
перевёрнутый justify, расхождение атрибутов): каждый чинился отдельно, потому что
модель нигде не была зафиксирована. Все КАДы мешают в кучу РАЗНЫЕ факты — здесь
они разведены. Любой импортёр/экспортёр обязан следовать этим правилам.

### Основание: данные однородны, частные случаи — в импорте/экспорте и редакторе

**Данные максимально ОДНОРОДНЫ.** У объекта есть ровно две вещи:

| | Что это | Дом | Почему так |
|---|---|---|---|
| **Имя** | ИДЕНТИЧНОСТЬ = АДРЕС | XML-атрибут `name` на объекте | единственное особое поле |
| **Атрибуты** | однородные пары ключ→значение | `<attributes><attr name value>` | всё остальное, БЕЗ исключений |

**Имя — единственное особое поле, и особое ровно по одной причине: через него идёт
ДОСТУП.** Адресация — `>OBJECT@ATTR` (`>R1@VALUE`): `R1` это адрес, `VALUE` — атрибут
по адресу. Сделать имя атрибутом = закольцевать адресацию (чтобы прочитать
`>R1@NAME`, надо уже знать `R1`). Поэтому имя — идентичность, а не атрибут;
`>NAME` = `>SELF@NAME` читает идентичность как псевдо-атрибут.

**Всё остальное — рядовые атрибуты, выделенных элементов НЕТ** (`value`,
`description`, BOM-поля, партномера, ссылки). Никаких «своих тумбочек» под конкретное
имя: как только один и тот же факт живёт элементом в одном месте и атрибутом в
другом — каждый импортёр решает по-своему, и получаем каскад частных случаев.
**Частные случаи ОТОБРАЖЕНИЯ и нативные слоты чужих форматов живут в импорте/экспорте
и редакторе, не в данных.**

### ДОМ АТРИБУТОВ: схема — у семейства, значения — у варианта

**Устройство = символ + футпринт + маппинг + атрибуты.** В IR эта пара —
**`<component><footprint variant="-0603">`**: компонент это СЕМЕЙСТВО (символ +
prefix + N вариантов), а каждый `<footprint>` внутри него И ЕСТЬ устройство —
placeable/покупаемая единица. Один резистор с семью корпусами остаётся ОДНИМ
резистором; дробить семейство на N компонентов НЕ надо.

**НАБОР КЛЮЧЕЙ (схема) ОДНОРОДЕН по всем вариантам семейства — различаются только
ЗНАЧЕНИЯ.** Разные наборы атрибутов у разных корпусов одного семейства — авторская
небрежность библиотеки, а не факт природы (правильно было бы доопределить поле всем
вариантам ЛИБО разделить на два семейства). Ground truth такой небрежности: tolmach
`<deviceset name="R">` объявляет `-0402/-1%` девятью ключами (AEC-Q…TOLERANCE), а
`-SQP-5W` пятью и другими (POWER, TOLERANCE) — чип-резисторы и проволочные под общим
символом. **Импорт НОРМАЛИЗУЕТ:** схема семейства = ОБЪЕДИНЕНИЕ ключей всех вариантов.

Отсюда — где что живёт («один факт — одно место»: схему НЕ дублируем в каждый
вариант, полный набор у варианта получается НАСЛЕДОВАНИЕМ):

| Уровень | Что тут живёт | Пример |
|---|---|---|
| `<component><attributes>` | **СХЕМА семейства** (все ключи, объединение; пустое значение = объявление) + факты семейства | `AEC-Q=""`, `POWER=""`, `description`="Resistor" |
| `<component><footprint><attributes>` | **ЗНАЧЕНИЯ варианта** | `package`="0603", `tolerance`="1%", `fp_desc` |
| `<instance><attr>` | **ЗНАЧЕНИЯ экземпляра** | `manf#`="RC0603FR-0710KL" (зависит от номинала!) |

**Разрешение значения: инстанс > вариант > компонент.** Ключ, объявленный на
компоненте и незаполненный ниже, — легальное пустое поле (I5/I10).

Почему BOM-поля объявлены пустыми, а заполняются ниже: партномер резистора зависит
от НОМИНАЛА, который per-instance. Семейство объявляет, ЧТО у изделия бывает;
вариант и инстанс говорят, ЧЕМУ это равно.

**Библиотечные символ и футпринт-ГЕОМЕТРИЯ атрибутов не несут вовсе** — это
поверхности отображения, их плейсхолдеры читают атрибуты устройства (Eagle так же:
`>VALUE` на пакете рисует value девайса). Носитель значений — вариант (привязка
семейства к футпринту), а не сама геометрия.

**КРИТИЧНО: пустое значение — это ОБЪЯВЛЕНИЕ СХЕМЫ, его нельзя терять.** Библиотека,
объявляющая `AEC-Q=""`, говорит «у этого изделия есть поле AEC-Q». Обрезание пустых
на импорте — корень каскада расхождений атрибутов (см. долг кода).

### Третий факт: плейсхолдер

| Факт | Что это | Дом в IR |
|------|---------|----------|
| **Плейсхолдер** | видимый ТЕКСТОВЫЙ СЛОТ | `<symbol><text>&gt;X</text>` / `<footprint><text>&gt;NAME</text>` — x/y/rot/size/align/layer |

Плейсхолдер `>X` рисует значение атрибута `X` устройства; `>NAME` — идентичность.
Плейсхолдер — про ОТОБРАЖЕНИЕ, атрибут — про ДАННЫЕ. Разные факты, все КАДы их путают.

### Инварианты (нарушение любого = баг)

- **I1. Набор плейсхолдеров задаёт ТОЛЬКО символ/футпринт.** Инстанс НИКОГДА не
  создаёт и не удаляет плейсхолдер.
- **I2. Инстанс может ровно две вещи:** СДВИНУТЬ плейсхолдер и ПОДАВИТЬ его.
- **I3. Стиль (size/align/layer/font) — ВСЕГДА библиотечный.** Инстанс не переопределяет.
- **I4. Значение атрибута:** инстанс > устройство (переопределение выигрывает).
- **I5. Атрибут БЕЗ плейсхолдера — норма** (скрытые данные: manf#, lcsc#, aec-q…).
- **I6. Плейсхолдер БЕЗ атрибута** — пустой текст (`>NAME` — всегда идентичность).
- **I7. Видимость = наличие плейсхолдера И отсутствие подавления.** Другого источника нет.
- **I8. Никаких выделенных элементов под атрибут** — `<attr>` везде. Черта:
  `<attr>` = ПОЛЬЗОВАТЕЛЬСКИЕ данные (BOM, партномера, описания); XML-атрибуты
  объекта = СТРУКТУРНЫЕ факты, которыми оперирует сам конвертер (`name` — адрес,
  `prefix` — генерация рефдезов, `symbol`/`variant` — связывание, `library` —
  происхождение). Флагов ПРАВ (Eagle `uservalue`) не храним вовсе — см. ниже.
- **I9. Схема атрибутов — факт СЕМЕЙСТВА и ОДНОРОДНА по вариантам; значения — факт
  ВАРИАНТА.** Разрешение: инстанс > вариант > компонент. Полный набор у варианта —
  наследованием, не копированием. Библиотечные символ/футпринт-геометрия своих
  атрибутов не несут.
- **I10. Пустое значение — это ОБЪЯВЛЕНИЕ.** Атрибут с `value=""` объявляет схему
  изделия и НИКОГДА не отбрасывается при импорте.
- **I11. Экспорт проекта ВСЕГДА выкладывает библиотеки** как самостоятельные
  артефакты рядом с проектом (KiCad: `.kicad_sym` + `.pretty` + lib-table;
  Eagle: `.lbr` на каждую использованную библиотеку — встроенных копий в
  `.sch`/`.brd` НЕ достаточно).

### Смэша как ФЛАГА не существует

**Поле `smashed` в IR отсутствует по построению.** «Смэшнутость» — не факт, а
производная: плейсхолдер сдвинут ⟺ у инстанса есть запись о сдвиге.

| Запись `<instance><text>` / `<element><text>` | Смысл |
|--------|-------|
| `<text x y rot>&gt;X</text>` | плейсхолдер X сдвинут сюда (локальные коорд.) |
| `<text hidden="yes">&gt;X</text>` | плейсхолдер X подавлен |
| записи нет | плейсхолдер на библиотечном месте |

Флаг не нужен, потому что все его функции покрыты:
- запретить случайное таскание плейсхолдеров → **selection-фильтр редактора**
  (забота UI, не данных);
- «вернуть как было» → **RESTORE POSITION** = удалить запись; библиотечный референс
  и так в файле, `smashed=false` не требуется.

`smashed="yes"` — артефакт формата Eagle, вычисляемый на ЭКСПОРТЕ. Eagle 9 по
умолчанию смэшит ВСЁ (в tolmach 95 инстансов из 95) — этот шум растворяется: записи
получают только РЕАЛЬНО сдвинутые. Смэш-запись на имя, которого нет среди
плейсхолдеров символа, невалидна — импортёр её отбрасывает (I1).

Плейсхолдеры независимы per-representation: у схемы свои, у платы свои.

### План импорта Eagle-проекта (канон)

1. **Библиотеки.** Компонент = семейство (Eagle deviceset+technology), его
   `<footprint variant>` = устройство (Eagle device). Схема семейства =
   ОБЪЕДИНЕНИЕ ключей всех `<device><technology>` — все, **включая пустые**
   (I10), кладётся на КОМПОНЕНТ; ЗНАЧЕНИЯ каждого device — на его ВАРИАНТ
   (I9). Копируются символы и плейсхолдеры.
   - Eagle `<deviceset><description>` → атрибут `description`
   - Eagle `<symbol><description>` → атрибут `sym_desc` (в реальных библиотеках
     всегда пусто; переносим только чтобы не терять)
   - Eagle `<package><description>` → атрибут `fp_desc` НА ВАРИАНТЕ (тут бывает
     полезное: ссылки на чертежи, комментарии)
2. **Схема.** Инстансы на БИБЛИОТЕЧНЫХ плейсхолдерах, без записей.
3. **Атрибуты инстансов.** Отдельный проход: переопределения/дополнения там, где
   нужно. **Библиотечное определение компонента остаётся НЕИЗМЕННЫМ.**
4. **Плата.** Атрибуты НЕ трогаем: компонент — одна сущность во всех контекстах,
   всё уже есть из схемы. Board-only значения у Eagle — служебные, не копируем
   (важное для производства — manf/manf# — уже пришло из библиотеки шагом 1).
5. **Плейсхолдеры.** Проход по всем инстансам: записи ТОЛЬКО для реально сдвинутых
   и подавленных (I2), схема и плата независимо.

### Eagle ↔ IR

| Eagle | IR |
|-------|-----|
| `<symbol><text>&gt;X</text>`, `<package><text>&gt;X</text>` | плейсхолдер |
| `<device package=…>` | `<component><footprint variant=…>` — УСТРОЙСТВО |
| `<device><technology><attribute name value>` | атрибуты ВАРИАНТА (все, включая пустые) |
| `<deviceset><description>` / `<symbol>` / `<package>` | `<attr name="description"/"sym_desc"/"fp_desc">` |
| `<instance smashed="yes"><attribute name x y …/>` | запись сдвига (только если сдвинут) |
| `<element smashed><attribute name x y …/>` | то же на плате |

**Правило Eagle (ground truth «Restore Position»):** текст рисуется ТОЛЬКО через
`<attribute>`-записи. Инстанс `smashed` БЕЗ записей = НИ ОДНОЙ надписи. «Restore
Position» материализует запись на КАЖДЫЙ плейсхолдер.
- **Экспорт:** инстанс с плейсхолдерами → `smashed="yes"` + запись на КАЖДЫЙ
  плейсхолдер (сдвинутый — по записи, прочие — по библиотечному дефолту); стиль
  библиотечный; подавленный — `display="off"`. Без плейсхолдеров → plain.
- Плата: `>NAME` → `tNames(25)` видим, `>VALUE` → `tValues(27)`; плейсхолдер на
  НЕ-силк слое (фаб/док) не показывается; атрибуты-данные → `display="off"`.

### KiCad: варианта НЕТ — семейство распадается на атомарные символы

У KiCad-символа ровно одно поле `Footprint`; понятия варианта нет. Поэтому на
экспорте **семейство ОБЯЗАНО распасться: один вариант → один символ библиотеки**
(`R-1%-0603`), со своим `Footprint` и своими атрибутами. Те же «семь резисторов»,
что были бы бредом для Eagle (там семейство выражается deviceset'ом), для KiCad
единственно возможны. Структура семейство/вариант ЖИВЁТ в Eagle и РАСТВОРЯЕТСЯ в
KiCad — это работа экспортёра, не данных.

**Атомарность — ВЫЧИСЛЯЕМЫЙ факт, не хранимый** (как и происхождение значения).
Считается по `lib_id`: в KiCad символ — схемная сущность с library link, два
размещения с одним link = два инстанса одного символа.

| Условие (на один `lib_id`) | Что эмитим |
|---|---|
| **1 инстанс** | **atomic**: все атрибуты ЗНАЧЕНИЯМИ в fields символа |
| **>1 инстанса, атрибуты у всех ОДИНАКОВЫ** | **atomic**: то же |
| иначе | **generic**: символ несёт СХЕМУ (ключи с пустыми значениями), конкретные значения — на инстансах схемы |

Видимость field'а ⟺ есть плейсхолдер (I7) — независимо от atomic/generic.

**Импорт из KiCad — синтез библиотеки из проекта.** Предусловие: пользователь ОБЯЗАН
сделать «Export Symbols» + «Export Footprints» и положить рядом с проектом; иной
библиотечной правды у KiCad нет. Схема атрибутов семейства = **объединение ключей
всех инстансов** данного `lib_id` (если набор правили прямо в схеме — другого
источника не существует). Один `lib_id` → компонент с ОДНИМ вариантом; собирать
атомарные символы обратно в семейство мы НЕ будем — для этого пришлось бы изобрести
имя семейства, то есть угадывать общий префикс (запрещённая эвристика).

**Принятые асимметрии круга** (KiCad-природа, чинить нечем):
- Eagle→IR→KiCad→IR даёт N односоставных компонентов вместо 1 семейства с N
  вариантами — семантически идентично, структурно группировка теряется.
- Экспортируемая KiCad-библиотека — ПРОЕКЦИЯ ЭТОГО проекта, не мастер-библиотека:
  R1=10K один в проекте → atomic с зашитым value=10K; добавили R2=4.7K → тот же
  компонент уедет уже как generic.
- `fp_desc` уезжает атрибутом варианта и обратно в `<package><description>` не
  возвращается.

### KiCad ↔ IR

**KiCad факты НЕ разделяет** — одно `(property "K" "V" (at x y a) (effects … [hide]))`
несёт ЗНАЧЕНИЕ + ПОЗИЦИЮ + ВИДИМОСТЬ, и на библиотечном символе, и на размещённом.
Разведение — работа импортёра.

**Импорт (KiCad → IR):**

| Источник | → атрибут | → плейсхолдер |
|----------|-----------|---------------|
| property библиотечного символа, ВИДИМО | да (дефолт устройства) | ДА, позиция/стиль из property |
| property библиотечного символа, СКРЫТО | да | НЕТ |
| `ki_*` (reserved) | да | НИКОГДА |
| property размещённого символа | значение ≠ дефолта → `<instance><attr>` | НИКОГДА не создаёт; позиция ≠ библиотечной (под трансформом) → запись сдвига; скрыто при живом плейсхолдере → подавление |
| footprint Reference/Value, ВИДИМО | — | `>NAME`/`>VALUE` футпринта |
| footprint Reference/Value, СКРЫТО (`hide yes`) | — | НЕТ (KiCad кладёт value на F.Fab скрытым — это НЕ плейсхолдер) |

**Экспорт (IR → KiCad):**
- Библиотечный символ: property на каждый атрибут; **видим ⟺ есть плейсхолдер**;
  позиция/стиль из плейсхолдера.
- Размещённый: property на каждый разрешённый атрибут; позиция = плейсхолдер + запись
  сдвига под трансформом; **видим ⟺ плейсхолдер и не подавлен**; **justify/стиль
  ВСЕГДА из библиотеки** (KiCad при `(mirror)` justify НЕ флипает).
- **Угол property = ЛОКАЛЬНЫЙ** (относительно тела символа): KiCad сам добавляет
  поворот/зеркало при отрисовке. Эмитить θ+lrot — двойной учёт.
- Полевой трансформ — единая пара `kicad_schematic.field_to_kicad` /
  `field_from_kicad`: зеркало негирует локальный X, затем поворот на **+θ**; свёртка
  угла в [0,180) с сохранением justify.

### `type` атрибута — только для будущего редактора

`type` (`bom`/`sim`/`general`/`service`) — ось для БУДУЩЕГО схемного редактора swift.
Ни у Eagle, ни у KiCad такого понятия нет, выводить его по имени ключа
(`MANF#` → `bom`) — запрещённая эвристика. Поэтому:
- **импорт:** всё приходит с `type="general"`;
- **экспорт:** `type` ИГНОРИРУЕТСЯ — его некуда положить;
- проставляется только руками в редакторе.

### `uservalue` НЕ ХРАНИТСЯ — материализуем значение

Что это в Eagle (ground truth tolmach): **авторская политика библиотеки**, а НЕ факт
правки пользователем и НЕ выводимая из сравнения «референс vs инстанс» величина.

| `uservalue="yes"` | `uservalue` отсутствует (= `no`) |
|---|---|
| R, C, CRYSTAL-4P, SOLDER_JOINT — value набирает человек (10K, 100n) | GND, SUPPLY, SN65HVD232D, LED, STM32F105RBT6 — value ЕСТЬ имя устройства, Eagle ВЫВОДИТ его сам (`deviceset+device+technology`) и запрещает менять |

В IR у обоих `value=""` — у первого не набрали, у второго выводится и не хранится.

**Выкидываем — потому что это флаг ПРАВА РЕДАКТИРОВАНИЯ**, а раздел «Упрощение
относительно Eagle» уже постановил: право редактирования → правь откуда угодно (обе
оси Eagle — видимость и scope прав — слиты). `uservalue` выражает запрещённое нами
понятие, а не просто избыточен.

Что вместо:
- **Импорт материализует выведенное значение.** `uservalue=no` → `value` кладётся
  ЯВНО; для многовариантных — на ВАРИАНТ (`LED-0603`, `LED-0805`), т.к. деривация
  зависит от device. `uservalue=yes` → `value=""` (ключ объявлен, наполнят инстансы).
- **Флаг не храним.** Eagle-экспорт пишет `uservalue="yes"` ВСЕГДА, значение — явно.
- **Цена:** value фиксированных деталей в выгруженной Eagle-библиотеке станет
  редактируемым — прямое следствие уже принятого «правь откуда угодно».
- **Бонус:** пропадает молчаливая деривация в экспортёре (`if not value and
  uservalue != 'yes': value = name + variant`) — данные самоописательны.

### Мелкие правила

- **multi-gate `sym_desc`:** у компонента может быть несколько символов, каждый со
  своим описанием, а ключ один. Практически моот (описания символов в реальных
  библиотеках всегда пусты). Правило: расхождение → лог + первый.
- **board-only атрибуты:** не копируем (шаг 4 плана импорта), дроп → В ЛОГ
  (конвенция «не терять молча»).
- **`<package><description>` не round-trip'ится** — и не надо: единственное ценное в
  нём, 3D-метаданные Eagle (`<!--3d:{...}-->`), парсится в `<model3d>` и собирается
  обратно `eagle_exporter._model3d_comment()`. Проза теряется, 3D — нет.
  Eagle→IR→Eagle вообще только тестовый путь, в дикой природе не встречается.

### Известные ловушки инструментов (все — следствие смешения фактов)

1. **KiCad сам добавляет поля** (пустой `Description` со `show`) → по I1 это НЕ
   плейсхолдер, только атрибут.
2. **Eagle при зеркалировании ЗАПЕКАЕТ флипнутый align** в запись сдвига
   (lib `center-right` → инстанс `center-left`) → по I3 игнорируем, берём библиотечный.
3. **kiutils не читает `(hide yes)`** (property символа, pin_names/numbers, property
   размещённого символа, fp_text) → sidechannel по сырому s-expr, ПЯТЬ мест.
4. **Eagle 9 смэшит всё по умолчанию** → шум растворяется в «нет записи» (I2).

### ⚠ ДОЛГ КОДА (применить в следующей сессии)

**Корень каскада расхождений атрибутов — импорт ОБРЕЗАЕТ пустые атрибуты (I10).**
Ground truth: Eagle `device -0603/tech -1%` объявляет 9 атрибутов, из них 7 пустых;
наш IR несёт 2 (`package`, `tolerance`). Дальше цепь: Eagle материализует ВСЕ 9
копиями на элементе платы → board-импорт видит `aec-q/digikey#/manf/manf#/
operating_temp`, которых в IR нет → 44 записи «BOARD_ATTRS merged into shared
instance» → библиотечные по природе атрибуты оседают на ИНСТАНСАХ, у одного есть,
у другого нет. Чинить:
- **не отбрасывать `value=""`** при импорте библиотеки (eagle_parser, атрибуты
  `<device><technology>` → `<component><footprint><attributes>`);
- затем **убрать BOARD_ATTRS-слияние** (лечило симптом непрочитанной схемы
  атрибутов) — копии на плате станут заведомо избыточны (шаг 4 плана).

**I8:** `<footprint><description>` до сих пор ОТДЕЛЬНЫЙ ЭЛЕМЕНТ (28 шт. в
tolmach.swprj) — переселить в атрибут `fp_desc` варианта. Создатели:
`eagle_parser.convert_package`, `kicad_parser._convert_footprint`; потребители:
`eagle_exporter.export_package`, `kicad_exporter.export_footprint`; skip-списки:
`ir_util.place_footprint`, `eagle_exporter`, `altium_exporter`,
`kicad_board_exporter`.

**I9:** схему семейства (объединение ключей) на импорте НЕ строим — ключи
оседают только на вариантах. Добавить нормализацию (union → компонент).

**`type`:** ни у одного `<attr>` его нет (670 из 670 в tolmach.swprj) при том, что
ir_schema его описывает. Проставлять `type="general"` на импорте; экспорт игнорирует.

**`uservalue`:** хранится XML-атрибутом на `<component>` и порождает молчаливую
деривацию value в `eagle_board_exporter`. Убрать: материализовать значение на
импорте (на ВАРИАНТ для многовариантных), экспорт пишет `uservalue="yes"` всегда.

**I11:** `eagle_exporter.export_schematic` не выкладывает `.lbr` использованных
библиотек (только встроенные копии в `.sch`/`.brd`); `export()` умеет писать
`.lbr` — позвать его для каждой библиотеки проекта. KiCad-экспорт уже верен.

Символы `description`/атрибутов не несут вовсе (0 шт.) — мигрировать нечего.
СТРУКТУРА `<component>` + `<footprint variant>` МЕНЯТЬ НЕ НАДО — она уже верна.
