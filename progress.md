# Babel — Progress

Универсальный конвертер EDA-форматов (Eagle ↔ KiCad ↔ Altium) через XML-IR.
Область применимости: микроконтроллерный мир (STM32 144 пина — ок; FPGA/процессоры
на 400–1000 пинов BGA — вне области, см. ниже почему multi-gate всё равно нужен).

Единицы IR: **целые микрометры (µm), int32, Y вверх**.

## Архитектура IR (актуальная схема)

Полное описание — в [ir_schema.md](ir_schema.md). Ключевое:

### Пул символов + gate
- Символы живут в библиотечном пуле: `<library><symbols><symbol name="..."/></symbols>`.
  Описываются один раз, на них ссылаются компоненты (дедуп: 10 транзисторов → один
  `<symbol name="NPN">`).
- **Одногейтовый (single-mode) компонент**: `<component name="R" prefix="R" symbol="R">`
  — есть атрибут `symbol`, нет `<gate>`, пины в pin-mapping голые (`pin="1"`).
- **Многогейтовый (multi-mode) компонент**: нет атрибута `symbol`, есть дочерние
  `<gate name="A" symbol="OPAMP"/>`, пины в pin-mapping с префиксом гейта
  (`pin="A.OUT"`).
- **Правило определения режима** (в [babel/ir_util.py](babel/ir_util.py)):
  `comp.get('symbol') is None and comp.find('gate') is not None` → multi-mode.
  При парсинге: `len(gates) > 1` → multi-mode.
- Почему не схлопнуть multi в один символ: следующий шаг — импорт целых схем; гейты
  могут быть на РАЗНЫХ страницах, мердж исказит схему. Это не усложнение, а отражение
  действительности.

### Сознательно НЕ хранится
- Eagle gate `add` (next/always/request/can) и `swaplevel` — нужны только редактору схем,
  не для конвертации. У человека, использующего такие компоненты, хватит знаний вручную.
- **Цвета** — не хранятся никогда, ни в каком виде.
- **Заливка БЕЗ цвета — но ТОЛЬКО `fill type outline`** (KiCad: залить цветом контура/тела,
  никакой отдельной палитры не нужно) — теперь хранится: `rectangle`/`circle` с такой
  заливкой → `<shape outline="0">` (уже существующий примитив, `outline=0` буквально и
  означает «залита цветом слоя»), замкнутая `polyline` с такой заливкой → `<polygon>`.
  **`fill type background` — это НЕ то же самое и сюда не входит**: заливка цветом ФОНА
  РЕДАКТОРА, а не «тем же, что контур» — первая попытка по ошибке завела сюда и `background`
  тоже (`!= 'none'` вместо `== 'outline'`), из-за чего большой прямоугольник-тело символа
  превращался в один сплошной залитый блок, перекрывающий всё нарисованное под ним
  (поймал пользователь). Без `fill type outline` — как раньше, `rectangle` → 4 линии,
  `circle` → `<arc sweep=360>`. См. decisions.md «KiCad-специфика: filled-графика» —
  найдено на `USB_C_Receptacle_USB2.0_14P` (`testData/phil`), пиктограмма USB-разъёма
  рисовалась пустыми контурами вместо сплошной иконки.
  **Залитая `arc` (не полный круг) — РЕШЕНО без нового IR-примитива.** Залитая дуга в
  KiCad-символе всегда полуокружность (`sweep≈180°`) на конце залитого rect ТОЧНО того
  же диаметра (нет родного "rounded rect" у символов — так собирают скруглённую "крышку").
  Замена на залитый полный круг того же центра/радиуса — точное тождество, не
  аппроксимация: другая половина круга проваливается внутрь уже залитого rect, лишнего
  не видно. Гейт строго на `|sweep|≈180°` (допуск 1°) — для любого другого sweep (гипотет.
  залитый pie-wedge) замена добавила бы видимую площадь, там — как раньше, контур без
  заливки. См. decisions.md «KiCad-специфика: filled дуга → круг».
  Прямоугольники с заливкой ЦВЕТОМ (Altium-символы ИС, Eagle-транзистор) по-прежнему не
  хранятся — тут заливка реально несёт цвет, который IR принципиально не хранит.
- **Попутно найден и исправлен баг с единицами**: `SyArc`-геометрия (3-точечный fit)
  хранила `cx`/`cy`/`r` в мм вместо µm — единственное место в `_add_unit_geometry`,
  не переведённое в канон. Затрагивало любую некруговую KiCad-дугу, не только залитые.
  Тот же баг найден и исправлен и на стороне футпринта (`FpArc`), по аналогии,
  не дожидаясь реального тестового случая.
- **И сразу следом — баг, который этот фикс ВСКРЫЛ (раньше маскировался первым):**
  `eagle_exporter._arc_to_wire` писала `curve = -sweep_deg` вместо `curve = sweep_deg`.
  Пока дуги были вырожденными точками у нуля (баг с единицами выше), неправильный знак
  было физически не разглядеть; как только дуги стали видны — пользователь сразу
  заметил, что они «вывернуты наизнанку». Round-trip-тест
  (`_arc_to_wire` → `eagle_parser.eagle_arc`, построенная на чтении реальных Eagle-файлов)
  подтвердил математически: с минусом обратное чтение даёт другой центр/start/sweep,
  без минуса — точное совпадение. Исправлено. См. decisions.md «KiCad-специфика: filled
  дуга → круг» (там же все три бага по порядку обнаружения).
- `G$1` — Eagle-автоимя гейта (как `N$1` для цепей). В IR не копируется: у single-mode
  гейта вообще нет имени (только атрибут `symbol`). Это упрощает IR.

### Терминология
- Используем `name`, а не `id` — называем вещи своими именами, а не IT-терминами.
  `name` компонента/футпринта = реальное уникальное имя.

### TH-пады
- Eagle даёт оба свойства напрямую: `drill` (диаметр ОТВЕРСТИЯ) + `diameter` (диаметр
  медного кольца/пада). Оба — часть IR.
- Altium не имеет концепции TH-пада: это SMD-пад с просверленной дыркой. Обычно круглый
  (sizeX=sizeY); если нет — берём МЕНЬШЕЕ из двух как `diameter`.
- KiCad имеет отдельный тип TH-падов («своя шиза» — разберёмся при написании парсера).
- Фоллбэк при экспорте, если `diameter` нет: `drill × 1.8`.

### model3d
- Только `tx ty tz rx ry rz` (соглашение Eagle, повороты ZYX). Имя файла не хранится —
  выводится из имени футпринта.

## 3D-модели — роадмап (решения зафиксированы, код не написан)

Конвенции уже записаны в [ir_schema.md](ir_schema.md), раздел `<model3d>`. Кратко:
- **Размещение = `T·R`**: поворот вокруг начала модели, затем трансляция `(tx,ty,tz)` в
  **фрейме платы** (оси сдвига от поворота не плывут; `tz` = высота над платой). MCAD-стандарт.
- **Только STEP, 1:1.** `scale` не поддерживается (всегда `1 1 1`; ненулевой scale при
  импорте из KiCad → warning).
- **Sidecar = канон IR**: IR байты не несёт, привязка по имени корпуса. Нет файла →
  модель теряется, плата остаётся (приемлемо).
- **Встраивание при экспорте**: Altium → в `.PcbLib`; KiCad ≥ 10 → sidecar (см. ниже —
  `embedded_files` для отдельного `.kicad_mod` оказался невозможен); Eagle → sidecar
  рядом с `.lbr`.

Текущее состояние кода: Eagle-экспортёр пишет `model3d` как комментарий (не настоящая
ссылка); **kicad_exporter теперь пишет настоящий `(model ...)` блок** со ссылкой на
sidecar-STEP, скопированный в `<lib_name>.3dshapes/` (см. «Сделано в этой сессии» выше) —
это sidecar-папка рядом с `.pretty/`, тот же принцип, что у Eagle, только с реальной
рабочей ссылкой вместо комментария — и, как выяснилось позже (см. п.3 ниже),
единственный возможный вариант для отдельного `.kicad_mod`, не временная мера.
[altium_exporter.py](babel/altium_exporter.py) **на самом деле уже умеет**

## Решение: Altium-таргет = DBLIB (не деградируем в «толстый» IntLib)

Обсуждали уход на голый self-contained IntLib (копии символов на компонент, без Excel/ODBC),
т.к. DBLIB исторически поздний и многих отпугивает. **Решение — остаёмся на DBLIB**
(SchLib один-на-пул-символ + xlsx = компоненты, дедуп сохранён). Принцип: не деградировать
логичную IR-структуру ради бедности тула; нормализованные библиотеки делают проект
логичнее. **TODO:** при DBLIB-экспорте выдавать пользователю предупреждение, что для работы
нужна привязка к xlsx через ACE OLEDB (это требование Altium, не наш каприз). См. memory
`feedback_no_pandering.md`.

   (i = 1, 2, …) — настоящий KiCad multi-unit symbol; pin-mapping per-gate (`_build_pin_map`
   с префиксом гейта) уже был готов, просто не использовался по отдельности. Majority-vote
   видимости имени/номера пина (`show_name`/`show_num`) тоже был ограничен первым гейтом —
   расширен на все гейты. Закрывает «Отложено» п.1(c) ниже.

2. **Четыре независимых геометрических/текстовых бага найдены и исправлены** (всплыли при
   ревью геометрии по запросу пользователя, не были описаны в «Отложено»):
   - **`_justify()` выбрасывал вертикальную составляющую align.** IR/Altium align —
     9 направлений (`bottom-left` … `top-right`), функция брала только horizontal
     (`align.split('-')[-1]`), вертикаль (`bottom`/`top`) терялась → текст всегда центрировался
     по вертикали вместо anchor сверху/снизу (смещение на пол-высоты шрифта). Вынесена на
     уровень модуля, принимает `flip_v` (для футпринт-пространства, где Y отражён через
     `_ky`, bottom/top меняются местами). Применена везде, где раньше отсутствовала: тексты
     внутри `_sym_geom` (символьные надписи помимо `>NAME`/`>VALUE`), `_fp_text_style`
     (`fp_text reference/value`), generic `<text>` в футпринте — там justify не было
     ВООБЩЕ (только центрирование по умолчанию).
   - **`_fp_text_style` не инвертировал `rot`** для reference/value placeholder-текстов
     (`'rot': _f(float(...) % 360)` без минуса), хотя generic-текстовая ветка в той же
     функции уже делает `(-rot) % 360` — несогласованность, т.к. Y отражён и для текста
     `>NAME`/`>VALUE` тоже. Приведено к единому знаку.
   - **TH-пад (`<pad>`) игнорировал атрибут `diameter`.** ir_schema.md (`<pad>`, см. выше)
     требует: использовать `diameter`, если есть, иначе `drill × 1.8`. Код всегда считал
     `drill × 1.7` и не читал `diameter` вовсе — единственный из трёх экспортёров с этим
     багом (altium_exporter.py делает именно `diameter or drill*1.8`, eagle_exporter.py
     пишет `diameter` 1:1). Исправлено на `diameter` (если есть) / `drill * 1.8` (фоллбэк).
   - **`roundrect_rratio` для SMD-пэдов был вдвое больше нужного.** IR `roundness` (0–100)
     означает `radius = (roundness/100) * min_dim/2` (см. `svg_renderer._smd`, и так же
     трактует Altium `corner_radius_percent` — оба экспортёра передают его 1:1). KiCad
     `roundrect_rratio` — это `radius / min_dim` (диапазон 0–0.5). Код делил `roundness`
     на 100 вместо 200 → `roundness=100` (полный круг) давал `rratio=1.0` вместо `0.5`
     (KiCad обрезал бы до 0.5, но промежуточные значения были вдвое искажены). Исправлено
     `/ 200`. Проверено на fiducial-пэде `FID` (`roundness=100` → `rratio=0.5`, круг 1×1мм).

3. **Экспорт `model3d` в KiCad — реализован** (роадмап-пункт «3D-модели», `kicad_exporter`
   был последним, кто его не делал; см. ниже). Новая функция `_resolve_model3d()` копирует
   sidecar STEP-файл (`<model3d file="...">`, ищется в `<ir_stem>/` рядом с IR-файлом — та
   же конвенция, что `eagle_parser._copy_step_files` использует при импорте) в
   `<lib_name>.3dshapes/` (сиблинг `.pretty/`, стандартное имя папки в KiCad-библиотеках),
   эмитит `(model "../<lib>.3dshapes/<file>" (offset ...) (scale (xyz 1 1 1)) (rotate ...))`
   в `.kicad_mod`.
   - **Offset**: `tx`→x (без изменений), `ty`→y через `_ky` (отражение, как у всей остальной
     футпринт-геометрии), `tz`→z (без изменений — высота над платой не зависит от 2D-отражения).
   - **Rotate**: IR хранит MCAD intrinsic XYZ (`R = Rx(rx)·Ry(ry)·Rz(rz)`, см. ir_schema.md).
     Футпринт-пространство — зеркало IR по Y (`F = diag(1,-1,1)`). Сопряжение `F·R·Fᵗ`
     для отражения по одной оси даёt: компоненты вращения вокруг ДВУХ других осей (X, Z)
     меняют знак, вокруг отражённой оси (Y) — знак сохраняется (та же алгебра, что уже
     неявно использовалась для знака `(-rot)%360` у плоских Z-поворотов в футпринте, только
     явно выписана для 3D). Итог: `rx' = -rx`, `ry' = ry`, `rz' = -rz`.
     **✓ Подтверждено визуально** (см. «3D-модели — роадмап», п.2 ниже) — пользователь
     открыл `APHBM2012_T` (ненулевой поворот) в KiCad `Footprint Properties → 3D Models`,
     модель встала корректно. Знаки/порядок осей верны.
   - **`scale`** всегда `1 1 1` (по решению — IR не поддерживает масштаб, см. роадмап).
   Проверено на `testData/eagle_src.swlib` (15 моделей с sidecar STEP, включая ненулевые
   `tx/ty/rz` у `SOT23-3`/`C0402` и т.п.) → `eagle_src.3dshapes/` с 15 файлами, корректные
   `(model ...)` блоки во всех затронутых `.kicad_mod`.

   **Баг, найденный на следующем round-trip-тесте (IntLib → IR → KiCad/Eagle,
   `testData/ttt`): `_resolve_model3d` требовал атрибут `model3d/@file`, который пишет
   ТОЛЬКО `eagle_parser` (как побочный, нестандартный атрибут — `eagle_exporter` его даже
   не читает). `altium_parser._do_model_extraction` кладёт реальные STEP-файлы в sidecar-папку

   - **Попутно обнаружилось**: `altium_exporter.py` на самом деле УЖЕ умеет встраивать

     доделали»). У `altium_exporter.py` тоже нет `if __name__ == '__main__'` — вызывать

4. **Размер шрифта при ИМПОРТЕ Altium (SchLib/IntLib) — был неправильной формулой,

   `_font_id()` (документирована эмпирически: Altium-pt не по типографской конвенции

   читал `d.font.size`/`par.font.size` (это УЖЕ значение в points, через
   `SingleFontBindableRecordMixin.font` из `altium_monkey`) и считал
   `size_um = pt * 10 * _MILS_TO_UM = pt * 254` — конфликт единиц (mils-константа
   применена к величине, которая милами не является), константа `254` не имеет отношения
   к эмпирической `×150`. Для типичных 10pt давало `2540` вместо верных `1500`.

   хардкодило `size='1270'` независимо от реального шрифта.

   `_mcad_to_eagle_rot`) — применена во всех трёх местах (designator/`>NAME`,
   parameter/`>VALUE` и др., и label). Round-trip подтверждён:
   `_font_id(lib, '1500')` → `10` (pt) — совпадает с типичным Altium-дефолтом 10pt,
   из которого тот `1500` и получен. Проверено на `testData/ttt`
   (`IND80S28.IntLib` → IR): `>NAME`/`>Comment`/`>Value` теперь `size="1500"` (было
   `2540`); полный прогон через KiCad/Eagle-экспортёры без ошибок.

5. **`>Comment`/`>Value` при импорте Altium не маппились в канонический `>VALUE` —
   пользователь поймал визуально.** Altium хранит «значение детали для отображения на
   схеме» в спец-параметре `Comment` (всегда есть на каждом компоненте) — но
   [babel/altium_parser.py](babel/altium_parser.py) обрабатывал его как ОБЫЧНЫЙ
   параметр: эмитил placeholder `>Comment` на символе и атрибут `<attr
   name="Comment">` — ни то, ни другое не совпадает с тем, что ищут экспортёры
   (`kicad_exporter`: `if txt == '>VALUE'` точное совпадение для стиля, `attrs.pop('value',
   comp_id)` точное совпадение по ключу). В итоге канонiческое значение пропадало:
   KiCad-свойство `Value` падало на `comp_id` вместо реального текста (например
   `AS1115-BSST`), а реальные данные утекали в нестандартное hidden-свойство `Comment`.
   `altium_exporter.py` (направление IR→Altium) уже ДАВНО знал про обратное соответствие
   (`p = sym.add_parameter('Comment', 'Comment', ...)`, `a.get('name','').lower() ==
   'value'`) — асимметрия была видна сразу, как только спросили.

   Заодно нашёлся более общий баг того же класса: `eagle_parser.py` лоуэркейсит ВСЕ
   имена атрибутов при записи в IR (`name.lower()`, см. `convert_deviceset`) —
   установленная, но не задокументированная конвенция: канонические имена атрибутов в
   IR строго lowercase. `altium_parser._clean_param_name` никогда не лоуэркейсил —
   значит `attrs.pop('datasheet', '')` в kicad_exporter тоже промахнулся бы мимо
   `<attr name="Datasheet">`, если бы такой параметр встретился (тот же баг, что с
   Comment, просто непроверенный на текущих тестовых данных).

   Исправлено в [babel/altium_parser.py](babel/altium_parser.py):
   - И `Value`, и `Comment` (оба — Altium-параметры, означающие «значение детали»;
     `Value` — отдельный обычный параметр, который некоторые библиотеки кладут на
     символ напрямую вместо Comment) теперь маппятся на канонический placeholder
     `>VALUE` (точный регистр, для exact-match в экспортёрах) и канонический ключ
     атрибута `value` (lowercase).
   - Для generic-частей (R/C/...) оба по-прежнему исключаются из `<attributes>` —
     это per-instance каталожные данные, не свойство устройства (как и раньше для
     одного `Value`).
   - Все ОСТАЛЬНЫЕ имена атрибутов теперь тоже лоуэркейсятся (`pname.lower()`) —
     общая нормализация, закрывающая и гипотетический `Datasheet`-баг, симметрично
     `eagle_parser.convert_deviceset`.
   Проверено на `testData/ttt`: все `attr name="value"` (было вперемешку `Comment`/
   разный регистр), все `>VALUE` placeholder (было `>Comment` и `>Value`). KiCad-свойство
   `Value` теперь содержит реальный текст (`AS1115-BSST`, `APHBM2012SURKCGKC`, ...)
   вместо `comp_id`-заглушки; Eagle получил `>VALUE` в `tValues` слое (96). `R`/`C`
   (generic) не регрессировали — `<attributes>` пустой, как и раньше.

7. **`kicad_exporter` синтезировал `fp_text reference "REF**"` (и `value`), даже когда в
   источнике их не было — пользователь поймал визуально (огромная надпись на крошечном
   `R0603`/`0805`: дефолт `size=1мм`/`y=-1.5мм` не масштабируется к размеру футпринта,
   `R0603` сам ~2.3×1мм).**

   Первая попытка (по аналогии с Eagle: `eagle_exporter.export_package()` ничего не
   синтезирует, просто транслирует IR-слои 1:1) — убрать `fp_text` целиком, если
   `>NAME`/`>VALUE` не нашлось в источнике. **Не решило проблему**: пользователь
   перезагрузил библиотеку и всё равно увидел гигантские «Ref\*\*»/«Val\*\*» на скрине
   (4-пэдовый `APHBM2012_T`). Проверка показала — в файле действительно НЕТ `fp_text`
   (`grep -c fp_text` → 0), путь к `.pretty` подтверждён правильный. Значит текст рисует
   сама KiCad Footprint Editor — она показывает встроенный плейсхолдер reference/value,
   когда у футпринта нет этих полей вообще, независимо от содержимого файла; убрать
   `fp_text` из файла не подавляет это, только лишает нас контроля над тем, что
   нарисуется. Вдобавок реальные KiCad-библиотеки по KLC всегда имеют поле reference —
   полное отсутствие тоже не соответствует конвенции.

   **Итоговое решение (по запросу пользователя):** `fp_text reference`/`value` теперь
   эмитятся ВСЕГДА (дефолт `size=1мм`, позиция `y=∓1.5мм`, как было изначально), но:
   - если `>NAME`/`>VALUE` НЕ найден в источнике → добавляется `(hide yes)` (раньше
     `(hide yes)` ставился только для `value`, для `reference` — никогда);
   - если найден → видимый, размер берётся из источника (`width=height=` реальный
     размер плейсхолдера, как и было).

   Проверено на `testData/IND80S28.IntLib`: `APHBM2012_T.kicad_mod` (нет `>NAME`/`>VALUE`
   в источнике) — оба поля присутствуют, оба `(hide yes)`, размер 1×1мм. Синтетический
   юнит-тест (footprint с реальным `>NAME` 0.6мм на `silk_top`) — reference видимый,
   `size 0.6 0.6`, без `hide`; value (не найден) — скрыт, дефолт 1мм. Полный прогон через
   KiCad/Eagle/Altium-экспортёры без ошибок.

## Сделано в этой сессии (power-символы, многострочный текст, footprint Properties)

1. **Многострочный текст KiCad → IR → Eagle.** KiCad хранит перевод строки в графическом
   `(text ...)` как буквальный escape `\n` (два ASCII-символа, НЕ настоящий байт перевода
   строки — подтверждено на реальных данных, `testData/phil/symlib.kicad_sym`). Eagle
   ожидает обратное — настоящий перевод строки (подтверждено пользователем напрямую в
   реальном Eagle: один и тот же текст с literal-escape отображался неправильно, с
   реальным `\n` — правильно). `_kicad_multiline_to_eagle()` в
   [kicad_parser.py](babel/kicad_parser.py) конвертирует на импорте, симметрично уже
   существовавшему `_kicad_overbar_to_eagle()`. Многострочность в IR — только в `<text>`
   content (значения `<attr>` однострочны по определению, как и в самом KiCad).
2. **Footprint-level `(property "Reference"/"Value" ...)` — геометрия терялась.**
   `kiutils.Footprint.from_sexpr` для этого токена сохраняет только значение, отбрасывая
   позицию/слой/`hide`/`effects` (подтверждено на `testData/phil/Library.pretty/
   SOT-23-5.kicad_mod` — современный формат хранит Reference/Value так, не через старый
   `FpText(type='reference'/'value')`). Новый `_footprint_name_value_geometry()` парсит
   токен напрямую (raw sexpr), берёт ТОЛЬКО геометрию (координаты/размер/justify/слой/
   hide) — содержимое НЕ копируется, поля становятся `>NAME`/`>VALUE` плейсхолдерами, как
   у символа. Decorative `fp_text user` (включая `${REFERENCE}`-переменные) транскрибируется
   как есть, отдельно. Подтверждено: на `SOT-23-5` оба текста с `F.Fab` теперь доходят до
   Eagle (было только 1 — терялся `>VALUE`).
3. **Power-флаг символы (`#PWR`, GND/+3V3/VCC...) теперь импортируются как полноценные
   `<component>`, не отбрасываются.** Подтверждено через klc.kicad.org (S7.1) и реальные
   данные: Reference=`#PWR`, ровно один pin `power_in`, Value называет И символ, И цепь.
   IR уже имел подходящую модель — `sup`-пин (`ir_schema.md` «Supply symbol»): код в
   [kicad_parser.py](babel/kicad_parser.py)/[kicad_project_parser.py](babel/kicad_project_parser.py)
   при `symbol.isPower` патчит единственный `<pin>` символа на `direction="sup"`,
   `name=<Value>` — компонент без footprint (footprint в IR опциональный). Раньше такие
   символы целиком пропускались (`return None`).
4. **`eagle_exporter.export_deviceset` не умел деревайс без footprint вообще** —
   `<devices/>` оставался пустым (невалидно для Eagle: deviceset должен иметь хотя бы один
   `<device>`). Добавлен синтез одного `<device name="">` без `<connects>` для
   footprint-less компонентов (Frame/Supply symbol) — стандартная Eagle-конвенция
   (как у её собственных `supply*.lbr`).
5. **Тот же `<device>` сначала ставил `package=""` — реальный Eagle ругался** (`invalid
   value '' for attribute 'package'`, поймано пользователем в живом Eagle). По
   `eagle.dtd`: `package` — `%String; #IMPLIED`, то есть допустим только при ссылке на
   реальный `<package>`; пустая строка не годится, атрибут просто не должен присутствовать.
   Исправлено — атрибут не выставляется вовсе, а не выставляется пустым.
6. **`eagle_parser.py` терял различие Eagle `sup`/`pwr` при импорте.** В `eagle.dtd`
   pin direction официально включает `sup` отдельно от `pwr`
   (`(nc | in | out | io | oc | pwr | pas | hiz | sup)`), но `DIR_MAP['sup']` маппился в
   IR `pwr`, теряя именно то отличие, которое IR только что закрепил для KiCad
   power-символов. Исправлено: `DIR_MAP['sup'] = 'sup'`. Round-trip Eagle→IR→Eagle
   проверен на синтетическом GND-символе.
7. **KiCad `extends` (derived/alias-символ) — крашил конвертер, не просто терял данные.**
   Символ без своих units (наследует тело у другого символа, например `BUSPCI-5V` extends
   `PCI_CONUNIV`, `testData/video`) приводил к `bodies=[None]` в `_group_gates` →
   `AttributeError`. Не связано с power-символами — всплыло при первом полном end-to-end
   прогоне `testData/video`. Полноценная поддержка `extends` не реализована (отдельная
   задача) — сейчас аккуратный пропуск с предупреждением вместо краша.
8. **Легаси power-символы (`power:VCC`/`+3.3V`/`+5V`/`+5F`/`PWR_FLAG`) теряли пин.**
   У этих символов пин и графика лежат в РАЗНЫХ `styleId` ОДНОГО `unitId=0`
   (`testData/video`, подтверждено напрямую — `unit 0 styleId 0`: 1 пин/0 графики;
   `unit 0 styleId 1`: 0 пинов/2 графики) — не настоящие альтернативы де Моргана (где
   каждый `styleId` самодостаточен), а механически расщеплённое старым `.lib`→`kicad_sym`
   конвертером тело (вероятно, легаси `convert`-флаг использовался не по назначению).
   `_group_gates` выбирал только `styleId 1` (графику) и терял пин целиком. Исправлено:
   если выбранное тело без пинов, а у соседнего `styleId` есть пины — оба тела
   объединяются, а не выбирается одно.

   Все 8 пунктов проверены на полном end-to-end прогоне всех трёх проектных фикстур
   (`testData/phil.zip`, `testData/video`, `testData/multichannel`) + Eagle-экспорт по
   каждой получившейся библиотеке — без падений, только ожидаемые предупреждения
   (не встроенные 3D-модели, овальные отверстия).

## Сделано в этой сессии (импорт СХЕМЫ: connectivity engine, инстансы, цепи)

Первый реальный проход по схемному импорту (KiCad → IR), а не только библиотек. Решения по
формату и связности подробно зафиксированы в [decisions.md](decisions.md) и
[ir_schema.md](ir_schema.md) — здесь только сводка и баги.

1. **Формат проекта `.swprj`** — отдельный корень `<project name="...">`, библиотеки
   (`.swlib`) остаются отдельной сущностью, но используемые в дизайне компоненты
   копируются в проект целиком (символ+footprint+pin-mapping), плюс секция `<schematic>`
   с `<instance>`/`<net>`. См. ir_schema.md «Формат файла: `.swlib` vs `.swprj`».
   `babel/kicad_project_parser.py:convert_project_full()`.
2. **Резолв символов/footprint'ов в проекте — hard-fail, не skip-and-continue.** По
   запросу пользователя: если символ/footprint не резолвится ни в одной из библиотек,
   зарегистрированных в `sym-lib-table`/`fp-lib-table` проекта — конвертация падает с
   ошибкой, указывающей что не хватает, вместо тихого пропуска компонента. Сам fallback-
   поиск по голому имени среди ЗАРЕГИСТРИРОВАННЫХ библиотек (нужен из-за реального кейса
   с нерелинкованным `lib_id`, см. module docstring) — оставлен, это не «угадывание».
3. **Connectivity engine — новый модуль [babel/kicad_schematic.py](babel/kicad_schematic.py).**
   Union-find (`_DSU`/`_build_nets`) по правилам, выведенным и подтверждённым на синтетической
   фикстуре `testData/junction/junction.kicad_sch` (4 кластера + пользователь лично
   проверял поведение в реальном KiCad, включая удаление auto-junction) — см. decisions.md
   «KiCad-специфика». Юнит-проверено отдельно от полного пайплайна.
4. **Transform размещения инстанса (rot/mirror) — выведен и перепроверен на двух реальных
   данных**, не только на бумаге: `Device:R` rot=90 без mirror (`testData/phil`) и
   `INDUCTOR` rot=270+mirror=x (`testData/video/modul.kicad_sch`) — вычисленные абсолютные
   позиции пинов совпали с реальными концами проводов в файле. `_mirror_and_angle`/
   `_abs_pin_pos_mm` в `kicad_schematic.py`.
5. **Четыре бага найдены на первом полном прогоне `testData/phil`** (63 инстанса, 180
   проводов, 32 junction, 43 label — после фиксов все посчитанные элементы доходят до IR
   без потерь):
   - **Имя/`is_sup` пина power-символа искались по строке, которую `_convert_schematic_symbol`
     уже переименовала** (GND/+3V3 и т.п. — единственный пин символа патчится на `sup`-имя
     ПОСЛЕ того, как `named_pins` уже вычислен со старым именем). Все GND/+3V3-цепи уходили
     в автоген `N$N` вместо настоящего имени. Исправлено: сопоставление пина в пуле с
     `named_pins` теперь позиционное (`zip`), не по имени.
   - **Изолированная метка без единого провода/пина не должна порождать `<net>`.** Найдено
     на дублирующихся декоративных метках "SWDIO" в файле, не касающихся ничего реального.
     `_build_nets` теперь требует хотя бы один pinref ИЛИ provod, иначе сегмент дропается
     (одинокий неподписанный пин без провода — тоже дропается; подписанный — остаётся).
   - **`_group_gates` теряла реальные пины у гигантского MCU-символа `MSPM0G3507SPTR`**
     (48 пинов) — тот же «legacy split body» баг, что уже был пофиксен для unit 0 в
     прошлой сессии (см. п.8 выше), но на уровень глубже: unit 1 сам расщеплён на два
     `styleId` (2 пина / 0 пинов), `_pick` брал графику без пинов. Обобщено в
     `_pick_bodies()` — применяется и для unit 0, и для любого реального unit.
   - **Метка на ТЕЛЕ провода (не на конце) не подхватывала цепь.** Правило «junction нужен
     для касания телом» относится к провод↔провод/пин↔провод (новое электрическое
     соединение, неоднозначность), а не к метке (она ничего не соединяет, только называет
     уже существующий проводник). Найдено на "NRST", сидящей ровно на середине длинного
     провода. См. decisions.md «KiCad-специфика» — дополнение про `<label>`.

   Итог на `testData/phil`: **34 цепи, все с реальными именами** (GND, +3V3, SPI0.*,
   I2C0.*, ...), 0 автогенерированных — неподключённые пины MCU (26 шт.) корректно не
   попадают в `<net>` вообще. Все счётчики источника совпадают с IR без потерь: 180
   проводов → 180 `<line>`, 32 → 32 `<junction>`, 43 → 43 `<label>`, 63 инстанса.

6. **SVG-рендерер для схемы (`<schematic>`) — новый, `render_schematic()` в
   [babel/svg_renderer.py](babel/svg_renderer.py)**: размещённые инстансы (transform
   rot/mirror, та же формула из `kicad_schematic.py`, без KiCad-специфичного Y-флипа —
   канвас IR сразу Y-up) + провода/junction/label поверх. Плюс `render_all_symbols()` —
   галерея SVG по одному файлу на компонент (работает и для `.swlib`, и для `.swprj`),
   подключена в CLI безусловно (раньше можно было посмотреть только один компонент за раз).
   По итогам визуальной проверки на `phil` пользователь нашёл и описал 3 отдельные дыры,
   все починены:
   - **Плейсхолдеры `>NAME`/`>VALUE` теперь резолвятся в реальное значение** (приоритет:
     override на `<instance>` → атрибут на `<component>` → литерал плейсхолдера, если
     нигде не задано). Потребовался новый **per-instance attr override** на `<instance>`
     (`<attr name="value" value="10k"/>`) — value родового R/C раньше не хранился НИГДЕ
     отдельно от device-level шаблона (см. ir_schema.md «Component instance»).
   - **`pinvis`/`padvis` теперь реально гейтят рендер.** Раньше имя пина рисовалось
     всегда, номер не рисовался вообще (для номера нет отдельного поля на `<pin>` —
     берётся из `<pin-mapping>` владеющего компонента, как в настоящем Eagle: номер —
     device-specific факт, не свойство символа).
   - **«Stacked pins» — KiCad-костыль «один пин символа → несколько падов» (KiCad сам
     этого не умеет), баг на реальных данных, не выдумка теста.** Пользователь объяснил
     механику (см. decisions.md «KiCad-специфика: stacked pins»), сам подготовил `testData/pintest.kicad_sym` (`USB_C_old`/`USB_C_new` — один
     разъём, старый и новый формат KiCad 10). Старый формат: N `<pin>` на одной
     координате, все кроме одного скрыты — но `hide` НЕ читается kiutils вообще (та же
     дыра, что у `Property`, третий раз в этой сессии), так что простой "respect hide"
     не годится. Новый формат: `pin.number` — буквально `"[A1,A12,B1,B12]"`. Оба сведены
     к одному и тому же IR-механизму (`<map pad="A1 A12 B1 B12">`, уже существовал для
     thermal pad) — `_collapse_stacked_pins()` (группировка по координате, без оглядки
     на `hide`) + `_pin_numbers()` (раскрытие `[...]`), оба в `kicad_parser.py`.
     Проверено на `USB_C_Receptacle_USB2.0_14P` (`testData/phil`): 15 `<pin>` → 9,
     `GND`/`VBUS` получили честный 4-падовый маппинг вместо отсутствующего.

## Сделано в этой сессии (KiCad flat multi-page: страницы, рамка, тайлинг)

Раньше `convert_project_full` жёстко падал на любом проекте больше одной страницы. Теперь
поддержан реальный случай — KiCad-проект с несколькими независимыми top-level страницами.
Решение прошло через одну итерацию пересмотра внутри той же сессии (см. decisions.md
«KiCad flat multi-page: `top_level_sheets`, не sheet-символ» — там же полная история):

**Первая попытка** (на `testData/pic_programmer.zip`, 2 страницы через sheet-символ +
`hierarchical_label`) — отличать «просто страницу» от настоящего модуля по числу
инстансов (1 = страница, 2+ = модуль). Заработала, проверена end-to-end.

**Пользователь решил иначе: иерархию не флэттим вообще**, и проверка на ВТОРОМ реальном
проекте (`testData/vimdrones.zip`, тоже 2 страницы) сразу показала — это было решение по
неполной картине. У KiCad есть ОТДЕЛЬНЫЙ, однозначный механизм «просто страница»:
`.kicad_pro`: `schematic.top_level_sheets` — список полностью независимых корневых файлов
(каждый свой `sheet_instances path="/"`), без единого `(sheet)`-символа или
`hierarchical_label` вообще. Связь между страницами — обычный `global_label` (142 шт., 0
локальных в обоих файлах). **Переписано на эту модель**: `_detect_pages()` теперь читает
`.kicad_pro` напрямую, не обходит `(sheet)`; `(sheet)`-символ — теперь ВСЕГДА hard reject,
независимо от числа инстансов (раз честный механизм существует отдельно, считать стало
не нужно). Sheet-pin-специфичный код в `convert_project_full` удалён как мёртвый.

Остальные решения не изменились с первой попытки:
- **Тайлинг — по настоящему размеру бумаги** (`_paper_dims_mm`, ISO A0–A5 + `User`), не по
  bbox компонентов — у KiCad размер листа задан структурно (уточнение общего правила
  «Импорт страниц источника» именно для KiCad). Зазор между страницами — те же 0.5".
- **Импорт рамки — новый механизм с нуля** (`_build_frame_component`): синтезирует
  `<component>`/`<symbol>` с `<shape layer="frame-boundary">` (НОВЫЙ атрибут — раньше
  `layer` был только у `<text>`) из `paper`+`title_block`. Title/Date/Rev/Company —
  per-instance атрибуты, не глобальные документа (на `pic_programmer.zip` у двух страниц
  разные `date`/`rev` — `title_block` в KiCad привязан к ФАЙЛУ, не к проекту).
- Cвязь между страницами (sheet-pin или `global_label`, не важно какой) сводится в одну
  `<net>` БЕЗ нового кода связности — совпадение имени уже обрабатывает существующий
  `by_name`-группировщик `_build_nets`.

**Проверено на ОБОИХ проектах — с разным, ОЖИДАЕМЫМ исходом на финальном коде:**
- `testData/pic_programmer.zip` (sheet-символ) — на ПЕРВОЙ итерации (число инстансов) прошёл
  end-to-end: 124 схемных символа (120 импортировано, 4 multi-unit/multi-gate пропущено),
  все счётчики без потерь (205 проводов, 47 junction, 39 меток), 39 цепей, межстраничные
  связи подтверждены (`CLOCK-RB6`/`DATA-RB7`/`VPP-MCLR`/`VCC_PIC`). **На финальном коде (после
  пересмотра) перепроверен повторно и корректно падает** — `(sheet) symbol(s) ... real
  hierarchy is not flattened` — это и есть правильное, ожидаемое поведение новой политики,
  не регрессия.
- `testData/vimdrones.zip` (`top_level_sheets`, финальная модель) — проходит end-to-end: 27
  компонентов, 153 инстанса, 132 цепи, десятки межстраничных связей через `global_label`
  подтверждены (`GND`, `PHASE_A`/`B`/`C`, `FD6288_*`...). Заодно нашёлся и исправлен соседний
  баг: `extends`-символ в `convert_project_full` падал hard fail вместо skip-with-warning,
  которым уже давно и осознанно обрабатывается в `kicad_parser.convert()` — несогласованность
  в собственном коде той же сессии, не из исходных данных.

Зазор между рамками — ровно 12700µm (0.5") в обоих прогонах. Title-block текст резолвится
через уже существующий placeholder-механизм (`_resolve_placeholder` в `svg_renderer.py`)
без единой новой строчки на стороне рендера.

Хронология сессии: пользователь попросил спроектировать IR→Eagle экспорт схемы; вопрос «как
разбивать на Eagle-листы» уперся в рамки/многостраничность KiCad — отсюда необходимость
сначала научиться ИМПОРТИРОВАТЬ многостраничные KiCad-проекты (этот раздел), что и было
сделано. Экспорт в Eagle с разбиением по рамкам реализован следом — см. ниже.

## Сделано в этой сессии (IR → Eagle: экспорт схемы)

`eagle_exporter.export_schematic()` — полноценный `.sch` (встроенная библиотека + parts +
sheets + nets) из IR `<schematic>`. Полная цепочка решений — decisions.md «IR → Eagle:
экспорт схемы». Кратко:

- Рамка → нативный Eagle `<frame>` в `<plain>` (не part/instance) — N рамок = N листов,
  разбиение по bbox, hard fail на stray-компонентах и на цепях, пересекающих листы.
- Найден и исправлен реальный баг **в импорте** (не в экспорте): `_build_frame_component`
  задвоила центр рамки (локальная геометрия `<shape>` и позиция инстанса обе считали себя
  центром) — рамки на самом деле стояли со сдвигом на половину своего размера. Пойман прямым
  вычислением полной композиции instance+local координат, не визуальной проверкой. Исправлено
  (origin символа рамки теперь сам центр, `(0,0)`), `testData/vimdrones.zip` перепроверен.
- Каждый Eagle-лист перебазируется в собственные координаты с (0,0) — иначе листы 2+ открывались
  бы в Eagle далеко за пределами видимой области (общий холст IR тайлит страницы вниз по Y).
- Побочный фикс: старый library-only `export()` создавал `<library>` без `name=` — нарушение
  DTD. CLI-диспетчер теперь выбирает режим по расширению выходного файла (`.sch` vs остальное),
  не по содержимому IR.
- Проверено на `testData/vimdrones.zip`: 151 part, 2 sheet (по 2 рамкам страниц), 132 цепи,
  оба файла (`.lbr` и `.sch`) подтверждены валидными напрямую по `eagle.dtd` (lxml).
- Известное ограничение: `device=""` всегда — IR `<instance>` не хранит, какой конкретно
  footprint-вариант использован у многофутпринтных компонентов.

**Найден баг при попытке реально открыть `vimdrones.lbr` в Eagle** (`invalid value '31'
for attribute 'layer' in tag <smd>`) — переросший в полный пересмотр модели падов после
того, как пользователь указал на скриншот KiCad Pad Properties: pad TYPE (есть медь или
нет) и pad SHAPE (прямоугольник/круг/трапеция/custom/...) — независимые оси, и у KiCad,
и у Eagle одно и то же (паста/маска как автоматика ИЛИ ручная геометрия) выражено через
РАЗНЫЕ механизмы. Подробная цепочка решений — decisions.md "KiCad: пады без меди и пады
произвольной формы — полная модель". Кратко:

- **Три новых булевых свойства на `<smd>`/`<pad>`**: `thermals`/`stopmask`/`paste`
  (по образцу Eagle `thermals`/`stop`/`cream`, умолчание у всех "1"). Слои IR: новый
  `mask_top`/`mask_bottom` (паяльной маски не было вообще), `cream_top`/`cream_bottom`
  переименованы в `paste_top`/`paste_bottom`.
- **KiCad: technical layers пада → флаги**, с умолчанием 0 при отсутствии слоя (не
  умолчанием IR =1) — KiCad выражает намерение явным списком слоёв, не отдельным свойством.
- **Aperture-пад (без меди вообще) → `<shape>` на тех же слоях**, не `<smd>` — paste-
  фрагменты `vimdrones.zip` теперь корректно становятся декоративной геометрией на
  `paste_top`, реальный медный exposed-pad получает `paste="0"` явно.
- **Форма пада**: `circle`/`oval`/`rect`/`roundrect`(без `chamfer`) — точно; всё
  остальное (`trapezoid`/`custom`/chamfered-варианты, включая "тихий" случай — chamfered
  rect на уровне файла это тот же `roundrect`, раньше терялся без единого сигнала) →
  прямоугольник + строка в лог, контакт не теряется, только точная форма.
- **Новый общий механизм — `babel/import_log.py`**, давно назревший: пишет
  `<output>.import.log` рядом с результатом, не подменяя консольные предупреждения.
- Полный конвейер (`vimdrones.zip` → `.swprj` → `.lbr`/`.sch`) и regression на
  `phil.zip`/`multichannel_mixer.kicad_sym` перепрогнаны, все файлы подтверждены
  валидными по `eagle.dtd`.

**Найден и исправлен баг (замечен пользователем визуально в выходном файле):**
`${REFERENCE}`/`${VALUE}` (KiCad text variables) лезли в IR буквальным текстом вместо
`>NAME`/`>VALUE`, когда сидели на простом декоративном `fp_text user` (а не на выделенном
`fp_text reference`/`value`, который уже обрабатывался правильно) — подтверждено реальными
данными (`testData/vimdrones.zip`, у нескольких футпринтов оба механизма на одном
футпринте одновременно). Исправлено в `babel/kicad_parser.py`; geometry/rotation не
менялись (использован обычный `_rot_fp`, не asymmetric `_rot_fp_placeholder` — та калибрована
только для выделенного типа, см. decisions.md). `vimdrones.swprj`/`vimdrones.lbr`
перегенерированы, regression на `phil.zip` пройден, оба файла валидны по `eagle.dtd`.

**Найден и исправлен баг при попытке реально открыть `vimdrones.sch` в Eagle** —
`attribute 'device' references undefined object ''`. Причина: `<part device="">` всегда
ставился вслепую, а у компонента с 2+ footprint (`<deviceset>` с несколькими `<device>`)
device `""` просто не существует. Расследование показало, что это не только баг экспорта —
KiCad per-instance `property "Footprint"` уже читается на импорте, но никуда не
прокидывается на сам инстанс, из-за чего фолбэк «взять первый footprint» молча присваивал
НЕВЕРНЫЙ footprint реальным инстансам (`testData/vimdrones.zip` "R11" — родовой резистор
`lib_id="lbr:R"` по факту с footprint предохранителя, `value="30A FUSE"`). Исправлено на
уровне импорта: новый `<instance footprint="...">` (только при 2+ footprint у компонента,
ir_schema.md "Component instance") — `babel/kicad_project_parser.py`. Экспортёр
(`babel/eagle_exporter.py`, новая `_device_names()`, общая с `export_deviceset`) резолвит
device по этому атрибуту; угадывание первого device остаётся только настоящим fallback'ом
(с записью в import_log), не основным путём. Полный конвейер перепрогнан, regression на
`phil.zip` пройден, все файлы (`.swprj`/`.lbr`/`.sch`) валидны по `eagle.dtd`.

**Найден и исправлен баг при реальном открытии `vimdrones.sch` в Eagle** — warning'и
`invalid value '8127.15' for attribute 'x1' in tag <wire>`. Причина: kiutils кладёт `wire`/
`bus`/`polyline` в один список `Schematic.graphicalItems`, а код безусловно трактовал
КАЖДЫЙ элемент как электрический провод — 83 декоративные `polyline` (KiCad "Graphic
Lines", скорее всего лого, координаты ~8000мм, далеко за пределами реальной схемы) стали
фиктивной гигантской `<net>` с 542+ микро-сегментами. Исправлено: только `type == 'wire'`
попадает в connectivity, остальное дропается с записью в `import_log` (decisions.md
"KiCad: `graphicalItems` — это НЕ только провода"). После фикса: 132 цепи → 63 (фиктивная
цепь исчезла), `.sch` валиден по `eagle.dtd`, координаты `<wire>` в разумных пределах
(`[-73.66, 188.41]` мм).

## Сделано в этой сессии (stray-валидация на импорте из KiCad)

Тот же лого-кейс натолкнул на более широкий вопрос: предыдущая stray-проверка существовала
ТОЛЬКО на экспорте в Eagle и только для `<instance>` — полная цепочка решений (включая
рассмотренную и отвергнутую мягкую альтернативу "хотя бы одна координата внутри") —
decisions.md "Stray-валидация — правило хорошего тона...". Реализовано для KiCad-импорта:

- Per-page bbox рамки (`frame_x0/x1/y0/y1`, из `_paper_dims_mm(sch.paper)` + `dy` страницы)
  вычисляется ДО сбора геометрии страницы, не после — нужен заранее для проверки каждого
  объекта по ходу накопления.
- **Instance** — полный bbox РАЗМЕЩЁННОГО символа (все pin/line/shape/arc/polygon/text
  углы, трансформированные поворотом/зеркалом инстанса), не точка `(x,y)`. Локальный bbox
  символа берётся через уже существующий `svg_renderer._bounds` (переиспользован, не
  продублирован), 4 угла трансформируются через уже существующий `kicad_schematic.
  _abs_pin_pos_mm`.
- **Wire** — оба конца сегмента (не один), **junction**/**label** — точка (текст без
  font-метрик не проверяется на экстент, известное ограничение).
- Hard-fail (не drop, не молчаливая корректировка позиции) с именем файла и списком ВСЕХ
  нарушивших объектов с их координатами и координатами рамки — `babel/kicad_project_parser.py`.
- Проверено: временный monkeypatch (отключение polyline-фильтра) подтвердил, что проверка
  реально ловит far-off декоративную графику самостоятельно, независимо от polyline-фикса
  выше (`ValueError: ...16 object(s) extend outside the page frame...`). На реальном
  `testData/vimdrones.zip` (после polyline-фикса, без искусственно оставленного мусора)
  ничего не падает — реальных stray-компонентов в проекте нет. Regression на `phil.zip`
  пройден, оба `.sch`/`.lbr` валидны по `eagle.dtd`.
- **Eagle-импорт — то же правило, но отложено**: в отличие от KiCad, на одном Eagle-листе
  может быть 0, 1 или много `<frame>`, перекрывающихся произвольно — нет единственной
  очевидной рамки для привязки проверки, нужно отдельное решение (decisions.md).

## Сделано в этой сессии (невидимый пин KiCad — четвёртый случай kiutils hide-бага)

Пользователь сформулировал явное правило: невидимый в KiCad пин всё равно копируется в IR
(связность не теряем), но с `pinvis="0"`/`padvis="0"`. Код уже пытался это делать через
`pin.hide`, но прямой тест показал — `pin.hide` всегда `False`, та же категория бага
kiutils 1.4.8 (`(hide yes)` как вложенный список, не голый атом), что уже чинили трижды для
`Property.hide`/`pin_numbers`/`pin_names`. Подтверждено на `testData/vimdrones/lbr.kicad_sym`
(`AP2112K-3.3`, реальный скрытый `NC`-пин — не спутан с похожим, но другим по природе
stacked-pin случаем у `USB_C_Receptacle_USB2.0_14P`, тоже найденным по ходу). Исправлено в
`babel/kicad_parser.py:_read_symbol_lib` (новая `_pin_hide_flags_from_symbol_nodes`,
привязка по позиции ДО `_collapse_stacked_pins`, иначе длины списков расходятся). Regression
на `phil.zip`/`multichannel_mixer.kicad_sym`/`vimdrones.zip` пройден, ничего не сломалось.

## Сделано в этой сессии (IR `direction="nc"` — совместимость с legacy ERC)

Расследование невидимого пина (выше) привело к вопросу: KiCad/Eagle `no_connect`/`nc` тип
пина сейчас сливается в `pas`, теряя ERC-семантику "это нормально, не предупреждай" (Eagle
ERC реально проверяет отсутствие цепи на `nc`-пине — подтверждено вырезкой из мануала Eagle,
раздел 8.2 Direction). Полная цепочка решений (включая отвергнутый и затем принятый заново
вариант) — decisions.md "IR `direction="nc"`". Кратко:

- **`direction="nc"` добавлен в IR**, явно отмечен как костыль ради совместимости с
  KiCad/Eagle ERC, не родное для IR понятие связности.
- **KiCad: скрытый `no_connect`-пин не импортируется вовсе** (весь стержень пина исчезает
  при `hide yes`, не только подпись — равносильно отсутствию пина). **Видимый — импортируется
  как обычный пин с `direction="nc"`** — подтверждено реальными данными, что видимые NC-пины
  частый случай у крупных ИС (`FD6288Q`, `SIM4X32` на 160 пинов), не редкость.
- **Eagle: `visible` НЕ затрагивает это решение** — управляет только подписями (имя
  пина/пада), стержень Eagle рисует всегда. Заодно нашёлся и исправлен отдельный баг:
  `eagle_parser.py` безусловно ДРОПАЛ все `nc`-пины на импорте (`DIR_MAP['nc'] = None`).
- **Altium: своего NC-типа физически нет** (проверено по `altium_monkey`'s `PinElectrical` —
  8 значений, ни одного NC) — на экспорт IR `nc` падает в `PASSIVE` через обычный fallback,
  имя пина сохраняется, ERC-семантика осознанно и неустранимо теряется (формату некуда её
  положить).
- Round-trip дополнен: `kicad_exporter.py`/`eagle_exporter.py` теперь обе стороны (`_PIN_DIR`)
  знают про `nc`. Regression на `phil.zip`/`vimdrones.zip` (оба направления, KiCad↔Eagle)
  пройден, `.sch`/`.lbr` валидны по `eagle.dtd`.

## Найден и исправлен реальный баг (символ схемы рисовался повёрнутым на 180°)

Пользователь заметил визуально в реальном Eagle: символ выглядит развёрнутым относительно
KiCad. Расследование — decisions.md "KiCad: `ir_rot` — БЕЗ инверсии". Кратко: `ir_rot =
(-eff_angle) % 360` был неверен, должно быть без минуса. Старая "перепроверка на двух
реальных фикстурах" не ловила этот баг МЕТОДОЛОГИЧЕСКИ — она сверяла позицию пина (через
отдельную, корректную переменную `eff_angle`), а не сам `ir_rot` (используется только для
поворота ТЕЛА символа). Опровергнуто и исправлено по прямому визуальному доказательству
(скриншоты KiCad+Eagle с одинаковым углом 90°, идентичная ориентация на экране в обоих).
Фикс — одна строка в `kicad_schematic.py:_mirror_and_angle`. Regression на `phil.zip`/
`vimdrones.zip` пройден (связность не изменилась, как и ожидалось — `eff_angle` не трогали).

**Подозревается такой же баг в `kicad_parser._rot_fp`** (footprint-поворот, PCB-инстансы) —
построен на той же логике инверсии, НЕ проверен и НЕ исправлен в рамках этой правки (другой
потребитель данных, нужна отдельная визуальная проверка прежде чем трогать).

## Найден и исправлен тот же баг — теперь для метки (`<label>`) на схеме

Подозрение из предыдущей правки подтвердилось для ВТОРОГО, независимого случая —
пользователь сам предложил эксперимент: убрать инверсию угла у метки и перегенерировать
`vimdrones.sch`, посмотреть глазами в реальном Eagle. Метки легли на место. decisions.md

`kicad_project_parser.py`, без вызова `_rot_fp`) — три оставшихся вызова `_rot_fp`
(footprint text/pad) по-прежнему не тронуты, своя отдельная проверка для каждого.

Заодно по просьбе пользователя — два независимых улучшения экспорта метки в Eagle

`xref` валиден именно в контексте `<net>`'s `<label>`). Regression на `phil.zip` пройден,
оба `.sch` валидны по `eagle.dtd`.

## Сделано в этой сессии (стиль метки `<label style="...">`)

Новый presentation-only атрибут на IR `<label>` — `crummy`/`input`/`output`/`bidir`/
`passive` (ir_schema.md "<label>"). Источник — KiCad `GlobalLabel`/`HierarchicalLabel`'s
`shape` (`input`/`output`/`bidirectional`/`passive`/`tri_state`) — прямое соответствие,
кроме `tri_state` (нет родного эквивалента среди наших 5 — маппится на `bidir`, ближайшее
визуально, решение пользователя). Обычный локальный `(label ...)` (`LocalLabel`) поля
`shape` не имеет вообще — всегда `crummy`. Подтверждено на реальных данных: все 142 метки
`testData/vimdrones.zip` — действительно `(shape input)` в исходнике (не маска дефолтного
значения kiutils), все 43 метки `testData/phil.zip` — локальные, корректно `crummy`. Eagle
не имеет собственного понятия стиля метки (`eagle.dtd`: `<label>` всегда просто текст) —
атрибут пока не участвует в экспорте, чистый задел на будущее. Regression на `phil.zip`/
`vimdrones.zip` пройден, оба `.sch`/`.lbr` валидны по `eagle.dtd`.

## Сделано в этой сессии (иерархия: KiCad `(sheet)` → IR `<module>` → Eagle)

Первая реализация иерархии по готовой модели ir_schema.md «Модуль (design block +
иерархия)». Снят hard reject для `(sheet)` глубины 1; глубина ≥2 — по-прежнему жёсткий
отказ (строгая проверка: файл модуля с собственными `(sheet)` валит конвертацию с
цепочкой файлов в сообщении; проверено синтетикой). Полные решения — decisions.md
«KiCad `(sheet)` → IR `<module>` — реализовано», маппинг — ir_schema.md «Импорт из
KiCad: `(sheet)` → `<module>`».

- **`babel/kicad_project_parser.py`**: `_collect_modules` (дедуп по файлу + depth check),
  `_sheet_ports` (sheet pins → `<port>`: ближайшая грань, coord от центра, Y-flip знака
  для left/right), `<instance module=...>` (имя из `Sheetname`, x/y = центр блока),
  портовые connection-точки в `pin_points` + `portref_keys` → `<portref>` на записи.
  Попутный рефакторинг: тело page-цикла `convert_project_full` вынесено дословно в
  `_collect_canvas` (+`_Canvas`-аккумулятор), запись XML — в `_write_canvas`; модуль =
  тот же код со своим аккумулятором (свой net-space), без рамки/stray/тайлинга.
- **`babel/eagle_exporter.py`**: `_export_module` (Eagle `<module>` со своими `<ports>`/
  `<parts>`/`<sheets>`, структура 1:1 с ground truth `outputs/multigate.sch` + `eagle.dtd`),
  `<moduleinsts>` между `<plain>` и `<instances>`, `<portref moduleinst= port=>`.
  Попутный рефакторинг: `_emit_part`/`_emit_instance`/`_emit_segment`/`_emit_deco` —
  общие для top-level и модуля. Для проектов без модулей новые элементы не эмитятся —
  выход байт-в-байт прежний.
- **`babel/svg_renderer.py`**: module-инстанс = блок dx×dy + порты (точка+имя) + подпись

   **Контекст решения:** в KiCad symbol↔footprint связь
   устроена иначе, чем в Eagle/Altium. У символа в `.kicad_sym` поле `Footprint` —
   ОДНА строка-ссылка (имя, не геометрия), не список. KiCad сам различает:
   - **atomic-символ** — `Footprint` заполнен конкретным именем; это полноценная,
     заказываемая деталь.
   - **generic-символ** — `Footprint` пуст; вместо реальных вариантов есть
     `ki_fp_filters` (wildcard-паттерны для UI-автокомплита, НЕ данные о геометрии).
     Реальная пара символ+footprint у generic возникает только в момент размещения
     на конкретной схеме (per-instance), библиотека сама её не несёт.

   Источник: KiCad Library Conventions (KLC), термин зафиксирован официально
   (https://klc.kicad.org/general/g2/g2.1.html — generic vs fully specified symbols).

   **План (два независимых пути импорта, дают разный результат из той же библиотеки):**

   **(a) Импорт ТОЛЬКО библиотеки (`.kicad_sym` + `.pretty`, без схемы) — ✓ Сделано.**

   Инструментарий: [`kiutils`](https://github.com/mvnmgrx/kiutils) (1.4.8, уже стоит в
   окружении) — аналог `altium_monkey` для KiCad, парсит `.kicad_sym`/`.kicad_mod`/

   явно — без этого ловят `UnicodeDecodeError` на не-ASCII (например лицензионный
   текст CC-BY-SA) на машине с не-UTF8 системной локалью (cp1251 в этой сессии).

   - Footprint-геометрия → читается из `.pretty/*.kicad_mod` (резолв имени из

     двухшаговое разрешение, симметрично уже сделанному для Altium).

     **с фоллбэком** — пробует зарегистрированный nickname первым, но реальные
     project-exported библиотеки (см. memory `project_kicad_real_world_libs`) часто

     явно из Altium-каталога, которого нет в локальном `fp-lib-table`, где
     зарегистрирована только ОДНА своя `.pretty`); если nickname не нашёлся —
     перебирает ВСЕ зарегистрированные библиотеки по голому имени файла. Подтверждено
     на `testData/multichannel` — без фоллбэка ни один footprint не резолвился бы.

   - Атрибуты (партномер и т.п.) пишем ТОЛЬКО на atomic — `<attributes>` висит на
     `<component>`, для generic (без `<component>`) физически некуда класть, даже
     если у символа какие-то поля заполнены (что для generic samo по себе странно).

   **Находка, не предусмотренная планом — семантика `unitId=0`.** KiCad-символ с
   несколькими units не всегда многогейтовый: `unitId=0` — зарезервированный «общий
   для всех юнитов» слот (подтверждено пользователем эмпирически в KiCad Symbol
   Editor — `TL072CD`, у которого по данным `unitId` 0/1/2 все три несут реальные
   пины, в реальном выпадающем списке юнитов показывает только 2 пункта, A/B, не 3).
   Правило (`_group_gates()`):
   - Несколько `unitId` → unit `0` (если есть) — НЕ отдельный гейт; его пины и
     графика дублируются в КАЖДЫЙ юнит `unitId≥1` (те и есть реальные гейты A/B/C...).
   - Если после вычитания `0` остался ровно один юнит (паттерн `GND`/`+12V`/`+1V1`:
     unit `0` = декоративная графика без пинов, unit `1` = единственный реальный пин)
     — это НЕ многогейтовый компонент, просто два тела сливаются в один обычный
     `<symbol>`.
   - `styleId`: предпочитаем `1` («Standard», когда есть альтернативы), иначе `0`
     (единственный стиль, когда альтернатив нет); `styleId≥2` (De Morgan) отбрасываем
     — тот же принцип «берём один вариант», что уже применяется к эллипсам.
   Подтверждено на `TL072CD`: гейты A/B получили по 5 пинов (3 свои + 2 смержённых
   V+/V- из unit 0), pin-mapping `A.V+`/`B.V+` оба корректно ведут на один и тот же
   пад (8) — стандартная практика для пары операционных усилителей в одном корпусе.

   **Property→placeholder (обратное преобразование к kicad_exporter).** KiCad хранит
   Reference/Value/Footprint/Datasheet/кастомные поля как `Symbol.properties`
   (позиция+стиль на каждом), а не как `>NAME`-плейсхолдеры в теле символа, как
   Eagle/Altium. Без синтеза `>NAME`/`>VALUE`/`>customattr` текстов в теле каждого
   гейта (одинаковая позиция дублируется в каждый гейт — тот же принцип, что для
   Altium-плейсхолдеров с `owner_part_id=-1`) позиция терялась бы при экспорте в
   Eagle/Altium, которые СВОЁ позиционирование Reference/Value читают только из такого
   текста. `Footprint`/`Datasheet` placeholder НЕ синтезируется (на это нет парного
   потребителя на экспорте — `kicad_exporter` их тоже не читает из тела символа).

   **Реальные данные оказались куда грязнее ожидаемого** (`testData/multichannel` —
   судя по полям `Library Path: SchLib\\...`, `Component Kind`, `Footprint Path:
   PcbLib\\...` это вообще Altium-библиотека, перегнанная в KiCad сторонним
   инструментом):
   - **`effects.hide` нельзя использовать как индикатор «это просто метаданные,
     визуально не значимо».** У `TL072CD` ~40 кастомных properties, ВСЕ с
     `hide=False`, просто составлены в вертикальный столбик далеко под символом
     (`y` от −18 до −99мм). Решение: довериться `hide` буквально, не гадать
     эвристикой «выглядит как мусор → скрыть» — раз источник пометил всё видимым,
     IR должен отразить это честно (принцип «не потворствовать шизе тулов», но в
     обратную сторону: не разглаживать тоже).
   - **Угол поворота `900°` в файле** (не баг парсинга — буквально в S-expression:
     `(at 5.08 -1.27 900)`). Видимо, артефакт того же Altium→KiCad конвертера.
     Добавлена защитная нормализация `_rot() = angle % 360` на все читаемые углы
     поворота (раньше нигде в проекте не требовалась, т.к. остальные парсеры читают
     честные source-данные).
   - **Овальные TH-отверстия** (`CLIFF_FC68148`, разъём питания) — подтвердили
     решение «вне области» (см. п. ниже «TH-пады»): warning + округление до
     `drill.diameter`, без потери самого пада.

   **TH-пады/формы падов — решение по итогам обсуждения (до реальных данных):**
   - Овальные/slot-отверстия и смещённые отверстия (`drill.oval`/`drill.offset`) —
     вне области (как BGA/400-pin корпуса) — round-фоллбэк + warning, без явного
     запроса перепроверки на реальных данных (см. находку выше — подтвердилось).
   - `roundrect`/`trapezoid`/`custom` формы пада → ближайший `rect` (для `<pad>`/
     `<hole>`); roundrect у `<smd>` — сохраняем честно через `roundness`
     (`= roundrectRatio * 200`, та же формула `/200` не `/100`, что чинили в
     kicad_exporter — см. выше).

   Round-trip подтверждён: `testData/multichannel` (`multichannel_mixer.kicad_sym` +
   `.pretty`, 11 исходных символов: 3 power-orphan, 1 generic без `<component>`,

   - **Баг найден ПОСЛЕ первого фикса видимости — `effects.hide` у `Property` в
     `kiutils` 1.4.8 всегда `False`, даже когда в файле явно стоит `hide`.**
     Пользователь поймал визуально: открыл `multichannel.lbr` в Eagle и увидел всё
     ту же гигантскую стену плейсхолдеров (`>Part_Number`, `>Library_Ref`, ...) —
     несмотря на «фикс видимости» из предыдущего пункта. Перепроверил эмпирически
     (искусственно поставил `hide=True` на свойства в Python) — логика РАБОТАЛА
     корректно. Спросил пользователя свериться в самом KiCad Symbol Editor — там
     поля видны, но БЛЕДНО, с снятым чекбоксом `Visible`. Значит источник
     (`prop.effects.hide`) врёт.

     Причина — в исходнике `kiutils`: `Property.from_sexpr()`
     (`site-packages/kiutils/items/common.py`) парсит только `id`/`at`/`effects`/
     `show_name` — токен `(hide yes)` у `<property>` — **сосед** `(effects ...)`,
     не вложен в него (в отличие от `Pin`/`FpText`, где `hide` — голый атом,
     тоже сосед, но эти kiutils парсит правильно). Подтверждено прямым чтением
     сырого S-expression (`(property "Library Ref" "..." (at ...) (show_name no)
     (do_not_autoplace no) (hide yes) (effects ...))`). Смежный, но не идентичный
     баг: [kiutils#120](https://github.com/mvnmgrx/kiutils/issues/120) — там о
     потере `hide` при пересохранении СХЕМЫ (`to_sexpr`), без воркэраунда от

     Проверена последняя версия `kiutils` (PyPI: 1.4.8 — уже установлена, новее нет).

     `'left'`/`'bottom'` для `None`. В `testData/multichannel` `vertically` ВСЕГДА

     экспортёра без ошибок.

     это «не задано, использовать настоящий дефолт редактора», а не «тонкая

   — весьма сомнительная по своей природе идея. Мы должны импортировать проект и уже
   из него сооружать нормальные eagle-подобные библиотеки». Новый план: пул
   footprint'ов берём прямо из `.kicad_pcb` (там уже лежит полная локальная геометрия

   разных footprint'ов на этой конкретной плате.

   **Связь footprint↔symbol — по `path`/UUID, НЕ по refdes.** Пользователь предложил
   очевидный на первый взгляд вариант — «R1 на плате и в схеме это один и тот же

   `sheetInstancePath`. Раз для refdes всё равно нужно резолвить иерархию листов,
   проще сразу использовать `path`, который `.kicad_pcb` и так даёт напрямую.

   **Формула ключа (подтверждена эмпирически, дважды — для top-level и для
   вложенного листа):** `Footprint.path` (на плате) = `'/' + '/'.join(segments)`, где
   `segments` — это `SymbolProjectPath.sheetInstancePath`, **с отброшенным первым
   элементом** (это всегда uuid самого корневого файла схемы, константа проекта,

   `R0603`/`R0603_1` (Value `6.8k`/`4.7k`) и `C0603`/`C0805` (Value `0.1uF`/`22uF`) схлопнулись
   в общие символы. IR прогнан через все три экспортёра (Eagle/KiCad/Altium) без ошибок.

   **Дополнительно (та же сессия) — дедуп на уровне КОМПОНЕНТА, не только символа.**
   IntLib даёт по одному `<component>` на каждую каталожную строку (Value), даже когда это
   один и тот же родовой деталь (резистор/конденсатор) — `R0603`/`R0603_1` были двумя
   IR-компонентами, хотя физически это одно устройство. Решение:
   - **Родовые детали** (schlib-символ имеет параметр `Value`, не только `Comment`) —
     `_convert_component()` возвращает info-словарь (`is_generic`, `prefix`, `symbol_name`,
     `footprints`, `attrs`), а `convert()` группирует их по `(prefix, symbol_name)` в ОДИН
     `<component name=prefix prefix=prefix symbol=...>` с несколькими `<footprint>` —
     по одному на уникальный пакет. `Value` не пишется в `<attributes>` (это
     schematic-instance данные, не свойство устройства).
   - **Не-родовые детали** (нет `Value` — ИС, фидуциалы, разъёмы) — имя остаётся как в
     Altium (`AS1115-BSST`), просто добавлен `prefix`.
   - **`prefix`** теперь везде берётся из designator-паттерна символа (`sym.designators[0].text`,
     `R?`→`R`, `DD?`→`DD`) — раньше IR вообще не писал `prefix`, хотя схема требует его
     обязательным.
   - **Баг `Comment="=Value"`**: Altium хранит в параметре буквальный текст `=ИмяПараметра`
     (ссылка на другой параметр символа, не литерал). `_is_param_alias()` детектит этот
     паттерн и не эмитит атрибут-дубликат, если параметр с таким именем существует на символе.
   - `_do_model_extraction()` теперь ищет `<component>` через явный маппинг
     `orig_to_compel: dict[original_intlib_name, Element]` вместо `lib_el.find(name=...)` —
     после слияния несколько исходных имён (`R0603`, `R0603_1`) ведут на один Element;
     добавлена защита от повторной вставки `<model3d>` в общий footprint.

   Итог на `testData/IND80S28.IntLib`: 8 → **6 компонентов**. `R0603`+`R0603_1` → один
   `<component name="R" prefix="R">` (1 footprint). `C0603`+`C0805` → один
   `<component name="C" prefix="C">` (2 footprint-варианта пакета). Round-trip через
   все три экспортёра подтверждён — Eagle даёт ожидаемую структуру: один `deviceset
   name="C" prefix="C"` с двумя `<device>` (по пакету на каждый).

   **Бонус-фикс той же сессии — переименование САМОГО СИМВОЛА в пуле для generic-групп.**
   Символ оставался под каталожным именем (`<symbol name="R0603">`) даже когда владеющий
   им компонент уже назывался `R` — несогласованность (`<component name="R" symbol="R0603">`
   вместо канонического `<component name="R" symbol="R">` из примера в ir_schema.md).
   При создании generic-группы `convert()` переименовывает `info['symbol_el']` (сам
   Element, не строку) в `prefix`, с защитой от коллизии имени с другим символом.
   Ключ группировки `generic_groups` — `(prefix, id(symbol_el))`, НЕ `(prefix, symbol_name)`:
   имя символа меняется in-place при первом слиянии, так что строковый ключ "сломался" бы
   между первым членом группы (читает имя до переименования) и вторым (читает уже после).
   Не-родовые дедуп-кейсы (например гипотетический LED, продублированный по геометрии, но
   без `Value`) переименование не затрагивает — для них нет источника общего имени
   (designator prefix типа `HL` — это не слово "LED"), поэтому действует прежнее решение
   «брать первое встреченное имя, не гадать лучшее».

9. ~~**ELLIPSE / ELLIPTICAL_ARC из Altium-символов отбрасывались при импорте.**~~ **✓ Сделано.**

   Разбор `altium_monkey`: `sym.arcs` — это `of_type(AltiumSchArc)`, `isinstance`-проверка,
   а `AltiumSchEllipticalArc` — ПОДКЛАСС `AltiumSchArc`. Значит elliptical arc уже попадал
   в цикл по дугам, но код брал только `arc.radius` (основной/primary радиус), игнорируя
   `secondary_radius_mils` (малая ось). А `AltiumSchEllipse` (полный эллипс/круг) — НЕ
   подкласс Arc, отдельный тип, и не обрабатывался вообще никак (молча терялся).

   Решение (по запросу пользователя — не вводить отдельный эллиптический примитив в IR,
   схлопывать к окружности/обычной дуге): радиус = `min(primary, secondary)` — меньшая ось,
   чтобы результат не выходил за пределы исходного эллипса.
   - В цикле `for arc in sym.arcs` (babel/altium_parser.py): если у `arc` есть атрибут
     `secondary_radius_mils` (т.е. это elliptical arc) — `radius_mils = min(primary, secondary)`.
   - Новый цикл `for ell in sym.ellipses`: эмитит `<arc start="0" sweep="360">` — та же
     конвенция «круг = дуга на 360°», что уже используется для PCB-кругов.

   **Попутный баг, найденный тем же тестом** (testData/IND80S28.IntLib, символ `FID` —
   фидуциал, реально содержит и ellipse, и elliptical_arc): дуга-полный-круг, заданная как
   `start=0 end=360`, схлопывалась в `sweep=(360-0)%360=0` — невидимая. В `_convert_footprint`
   (PCB-дуги) для этого же случая уже стоял фоллбэк `% 360 or 360`; в `_convert_symbol`
   (дуги символа) — не стоял. Приведено к единообразию.

   Проверено на `testData/IND80S28.IntLib`: символ `FID` теперь содержит
   `<arc cx="0" cy="0" r="2540" start="0" sweep="360">` (бывший elliptical_arc 100/100 mil)
   и `<arc cx="0" cy="0" r="1270" start="0" sweep="360">` (бывший ellipse 50/50 mil).
   Round-trip через все три экспортёра без ошибок.

   **Второй, более серьёзный баг (пользователь поймал визуально — круги не видны в
   IND80S28.lbr): все ТРИ экспортёра рисуют полную окружность (`<arc sweep="360">`) как
   ОБЫЧНУЮ дугу через тригонометрию (точка на угле `start` → точка на угле `start+sweep`).
   Для `sweep=360` это математически одна и та же точка (`cos`/`sin` периодичны) — все три

   - **Eagle** (`babel/eagle_exporter.py`): добавлен `_emit_arc()` — если `sweep>=360`,

     package-цикле; та же самая native-circle ветка уже существовала для
     `<shape roundness="100">`, просто не была переиспользована для `<arc>`).
   - **KiCad** (`babel/kicad_exporter.py`): то же самое — `sweep>=360` → `(circle ...)`
     (символ) / `(fp_circle ...)` (footprint) вместо вырожденного 3-точечного
     `(arc (start P) (mid M) (end P))` (start==end).
   - **Altium** (`babel/altium_exporter.py`): другой механизм той же болезни.
     `_altium_arc_angles(start, sweep)` мапит IR-дугу в пару `(start_angle, end_angle)` через
     `% 360` — для `sweep=360` получалось `(0, 0)` вместо `(0, 360)`. Реальная Altium-библиотека
     (тот же `FID`) использует именно явную пару `(0, 360)` для круга — `% 360` ломала её
     обратно в вырожденную. Поправлено: при `abs(sweep) >= 360` возвращать `(s, s+360)` без
     модуля на конец. Один фикс закрывает оба места, где функция используется (symbol-дуги
     и PCB-дуги footprint, строки ~294 и ~868).

   Проверено: `FID` (символ) → `<circle>`/`(circle)`/Altium-arc `0°→360°` во всех трёх
   форматах; PCB-дуги pin-1-маркера в `APHBM2012_T` и `QSOP-24` (тоже `sweep=360` в IR) —
   аналогично, `<circle>` в Eagle, Altium-arc `start=0 end=360` (было бы `0,0`).

10. ~~**Multi-gate (multi-part) Altium-символы при импорте терялись — все части
    рисовались поверх друг друга в один IR-символ.**~~ **✓ Сделано.**

    `APHBM2012SURKCGKC` (двухсветодиодный HL в одном корпусе, `IND80S28.IntLib`) —
    `sym.part_count=2`, геометрия/пины расщеплены по `owner_part_id` (1/2), общие
    designator/parameter-плейсхолдеры — `owner_part_id=-1`. Старый `_convert_symbol`
    тащил ВСЕ объекты в один `<symbol>` без учёта `owner_part_id` — оверлей.

    Решение в [babel/altium_parser.py](babel/altium_parser.py):
    - `_part_letter(n)` — 1→`A`, 2→`B`... (буквы выбраны по аналогии с тем, что реально
      видит инженер на схеме Altium — `HL1A`/`HL1B`; в данных altium_monkey самих букв нет,
      только числовой `owner_part_id`).
    - `_convert_symbol(sym, sym_name, part_id=None)` — новый параметр `part_id`: локальный
      `_keep(obj)` пропускает объект, если `owner_part_id` объекта совпадает с `part_id`
      ИЛИ объект общий (`None`/`-1`/`0`) — общие плейсхолдеры (`>NAME`/`>Value`) дублируются
      в КАЖДУЮ часть (решение пользователя: на схеме каждый gate должен сам нести подпись).
      `part_id=None` (одночастный символ) — поведение не меняется, фильтр всегда True.
    - `_iter_named_pins(sym, part_id=None)` — общая функция фильтрации+`@N`-нумерации пинов,
      используется И при рисовании пинов на символе, И при pin-mapping в footprint — чтобы
      имена пинов не могли «разойтись» между двумя местами.
    - `_register_symbol()` — вынесенный хелпер «зарегистрировать символ в пуле (дедуп по
      имени, потом по geometry-hash)», теперь общий для одночастных символов и для каждой
      части multi-gate.
    - `_convert_component()`: при `sym.part_count > 1` строит `info['gates'] = [(gate_name,
      part_symbol_name), ...]` вместо одиночного `symbol_name`; `is_generic` форсируется
      `False` для multi-gate (схлопывание по Value не имеет смысла для нескольких гейтов).
      Pin-mapping эмитит `pin="A.1"` / `pin="B.3"` (схема: `GATE.PIN`).
    - `convert()`: новая ветка `is_multi_gate` — компонент без атрибута `symbol`, с
      дочерними `<gate name="A" symbol="..._A"/>`.

    Round-trip подтверждён на всех трёх экспортёрах: Eagle — `deviceset` с двумя
    `<gate>`, ссылающимися на отдельные символы (multi-gate в Eagle-экспортёре уже был
    готов); Altium — **попутно обнаружилось, что Altium-экспортёр уже умеет полноценный
    multi-part** (`set_part_count`, `MAP_DEFINER`) — `IND80S28.SchLib` после экспорта:
    `APHBM2012SURKCGKC part_count=2`, без warning (см. правку пункта 1 в «Отложено» —
    этот TODO на самом деле уже был закрыт в прошлой сессии); KiCad — флэттит с явным
    warning (`multi-gate KiCad units not implemented`) — известное, ещё не закрытое
    ограничение (пункт 1c в «Отложено»).

    **Донастройка той же сессии — позиция гейтов на схеме.** Altium не хранит позицию
    гейта на листе (части различаются только `owner_part_id`, не координатами) — все
    `<gate>` получали `x=0 y=0`, и при ВИЗУАЛЬНО одинаковых гейтах (как у нашего
    двухдиодного LED) они рисовались друг на друге, выглядя как один гейт. Решение:
    в `convert()` (babel/altium_parser.py) гейты раскладываются по вертикали с шагом
    0.5″ (`y = i * 12700` мкм, `i` — индекс гейта). Проверено: Eagle `<gate name="B"
    .../>` теперь `y="12.7"` (мм) относительно `A` на `y="0"`.
10. ~~**Порты/пины иерархического (модульного) листа — НЕ спроектированы, отложено.**~~
    **✓ Спроектировано И реализовано** — модель: ir_schema.md «Модуль (design block +

    ниже. Ответы на вопросы ниже (сохранены для истории): порт — список метаданных
    модуля, не объект холста; НЕ метка (отдельная сущность); имя порта ОБЯЗАНО совпадать
    с именем внутренней цепи (единственный источник связи); направление — явное, не
    выводится; `sup`-пин наружу НЕ протекает (порт обязателен); рендер — точка+имя на
    грани блока на родительском холсте, внутри модуля порт не рисуется вообще (его
    представляет одноимённая цепь).

    Исходные вопросы (отвечены, оставлены для контекста):
    - Где живёт объявление порта — внутри файла модуля (как объект на холсте, аналог
      label) или как отдельный список метаданных модуля?
    - Как порт соотносится со **scope label** (уже описанным в `ir_schema.md`): порт —
      это просто метка особого вида, или отдельная сущность поверх обычной метки?
    - Именование: имя порта обязано совпадать с именем внутренней цепи модуля, или это
      два независимых факта (внешнее имя цепи на родительском холсте ≠ внутреннее имя
      в модуле)? Если независимы — где и как задаётся соответствие?
    - Направление (in/out/io) — нужно ли порту своё, отдельное от направления реальных
      пинов цепей, которые к нему подключены внутри модуля, или оно выводится?
    - Как `sup`-пин (supply symbol) взаимодействует с портом — может ли цепь, неявно
      именованная через `sup`-пин внутри модуля, "вытечь" наружу через порт, или для
      этого обязателен явный порт (см. «Scope label»: внутри модуля понятия глобальной
      метки нет вообще, GND/VCC там обычная локальная метка — значит порт ОБЯЗАТЕЛЕН,
      неявного протекания питания наружу быть не должно?).
    - Визуальное представление порта на холсте модуля и на холсте, где модуль размещён —
      одна и та же геометрия, или у каждой стороны свой рендер (как у KiCad: hierarchical
      pin внутри листа vs sheet pin на родителе — разные объекты с разной геометрией)?

## Полезные детали API
- `AltiumSchLib(path)` — конструктор; `AltiumSchLib.get_symbol_names(path)` — статик,
  нужен путь к файлу.
- `AltiumPcbLib.from_file(path)` + `find_footprint(name)` (нет `get_footprint`).
- cp1251-ошибка консоли на символе `→` безвредна, файл пишется корректно (UTF-8).
