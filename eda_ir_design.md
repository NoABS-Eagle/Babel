# EDA Universal IR Format — Design Decisions

**Репозиторий:** `babel` (в рамках организации на GitHub)
Метафора Вавилонской башни — много языков/форматов, инструмент устраняет непонимание.

## Цель проекта

Создать универсальный промежуточный формат (IR) для конвертации между EDA системами —
аналог LLVM, но для EDA. Поддерживаемые системы на первом этапе: **Eagle, KiCad, Altium**.

IR станет нативным форматом будущей собственной EDA системы, но конвертация будет
работать и без неё.

---

## Формат IR

### Синтаксис
- **XML** — читаемый, стандартные парсеры везде, Eagle уже использует XML
- S-expressions отвергнуты: это решение KiCad было инфраструктурным (C++ без зависимостей),
  для нашего стека не актуально
- Производительность Python на файлах до 5 МБ — не проблема, lxml парсит за миллисекунды

### Философия
- IR проектируется как **надмножество Eagle формата**
- Всё что есть в Eagle — отражается один к одному
- Поверх добавляется то чего в Eagle нет (3D модели и др.)
- Избыточные сущности Eagle — выбрасываются
- Eagle XML используется как отправная точка, не как полная копия

## Архитектура компонента

### Основная структура
**Компонент = Символ + Список футпринтов + Атрибуты**

- Связь символа и футпринтов устанавливается **один раз в библиотеке** (Eagle-подход)
- Один символ может иметь несколько футпринтов, один из них дефолтный
- Выбор футпринта происходит при добавлении компонента в схему

### Самодостаточность проекта
- **Eagle-подход**: проект содержит все данные внутри себя, без внешних зависимостей
- Нет глобальных библиотек футпринтов
- Дублирование (например SOIC-16 в разных библиотеках) — осознанный выбор в пользу
  надёжности и воспроизводимости через 10 лет

### Футпринт
- Геометрия падов
- Одна 3D модель (ссылка на `.step` файл) с параметрами позиционирования:
  offset, rotation, scale
- Один футпринт — одна 3D модель (вертикальный/горизонтальный монтаж = разные футпринты)

```xml
<footprint id="SOIC-16">
  <model3d ref="models/SOIC-16.step">
    <offset x="0" y="0" z="0"/>
    <rotation x="0" y="0" z="0"/>
    <scale x="1" y="1" z="1"/>
  </model3d>
</footprint>
```

### Маппинг пин → пад
- **Явная таблица** (Eagle/Altium подход), никакой магии по совпадению имён
- KiCad-подход (совпадение имён) отвергнут: ломается на дискретке (диоды, транзисторы)

```xml
<pin-mapping>
  <map pin="A" pad="1"/>
  <map pin="K" pad="2"/>
</pin-mapping>
```

### Пример структуры компонента

```xml
<component id="R_10k">
  <symbol ref="symbols/resistor_generic"/>
  <footprints default="0603">
    <footprint id="0402" ref="footprints/R_0402"/>
    <footprint id="0603" ref="footprints/R_0603"/>
    <footprint id="0805" ref="footprints/R_0805"/>
  </footprints>
  <pin-mapping>
    <map pin="1" pad="1"/>
    <map pin="2" pad="2"/>
  </pin-mapping>
  <attributes>
    <attr name="value" value="10k"/>
    <attr name="manufacturer" value="Yageo"/>
    <attr name="mpn" value="RC0603FR-0710KL"/>
    <attr name="datasheet" value="https://..."/>
  </attributes>
</component>
```

## Импорт сторонних библиотек

### Стратегия
- Импортировать символы и футпринты **вместе**, не по отдельности
- Автоматически резолвить связь символ→футпринт через поле `Footprint` (есть в KiCad и Altium)
- Если футпринт не найден — компонент импортируется с пометкой **"футпринт не разрешён"**
- Маппинг пин→пад из KiCad генерируется автоматически по совпадению имён,
  но **помечается как "сгенерировано автоматически"** для ручной проверки

### 3D модели Altium
- Встроенные бинарные блобы распаковываются в отдельные `.step` файлы
- Далее — стандартная ссылка как у всех

## Модель файла изделия

### Нет сущности "проект"
- Отдельный файл проекта (как `.PrjPcb` в Altium или `.kicad_pro`) **не нужен**
- KiCad/Altium завели проект потому что у них схема — россыпь файлов (`.SchDoc`),
  нужен файл-сборщик. У нас этой проблемы нет.
- Группировка нескольких изделий — через **директории файловой системы**
  (объединяющая абстракция уже есть, не дублируем её)

### Схема — один файл, страницы внутри
- Eagle-подход: схема = один файл, много страниц внутри если надо
- Никакой россыпи отдельных файлов на лист (в отличие от KiCad/Altium)
- Невозможно случайно потерять кусок схемы

### Слияние схемы и платы в один файл изделия
- Схема и плата — **два представления одного объекта**, не две разные вещи
- Объединяются в один файл изделия
- Связь схема↔плата перестаёт быть проблемой — связывать нечего, это один объект
- Невозможен рассинхрон, невозможно потерять половину
- Идеально ложится на модель компонента: инстанс компонента естественно имеет
  и символ (для схемы), и футпринт (для платы)
- Настройки (стек слоёв, DRC) хранятся внутри файла изделия
- Связь по UUID нужна **внутри** файла (компонент на схеме ↔ тот же на плате),
  не между файлами

**Структура файла изделия:** компоненты + схема (страницы) + плата.

```xml
<design>
  <!-- встроенные определения компонентов, добытые из исходного проекта -->
  <library>
    <component id="R_10k">
      <origin device-library="Device" symbol="R"
              footprint-library="Resistors_SMD" footprint="R_0603"/>
      <symbol .../>
      <footprints default="0603">
        <footprint id="0603" ref="footprints/R_0603"/>
      </footprints>
      <pin-mapping>
        <map pin="1" pad="1"/>
        <map pin="2" pad="2"/>
      </pin-mapping>
    </component>
  </library>

  <!-- инстансы на схеме -->
  <schematic>
    <sheet name="Page 1">
      <instance ref="R_10k" id="R1">
        <position x="100" y="200"/>
      </instance>
    </sheet>
  </schematic>

  <!-- инстансы на плате — ссылаются на инстанс схемы, не на определение -->
  <board>
    <instance ref="R1">
      <position x="50.0" y="30.0" rotation="0"/>
    </instance>
  </board>
</design>
```

### 3D модели — локальные ассеты рядом с изделием
- Модели физически не помещаются внутрь файла (степы по несколько-десятков МБ)
- Ссылки **относительные** от файла изделия, НЕ через переменные окружения
- Модели лежат в директории рядом с файлом изделия:

```
my_widget/
  widget.brd          ← файл изделия (схема + плата + компоненты)
  models/
    SOIC-16.step
    R_0603.step
```

- Передача проекта = передать директорию (та же объединяющая абстракция ФС)
- Отличие от KiCad: модели — **локальный ассет изделия**, не глобальный системный
  ресурс. Отсюда нет KiCad-боли с потерей моделей при передаче.
- Отличие от Altium: формат изделия остаётся текстовым и лёгким, без бинарных блобов
- Дублирование степов между проектами — та же осознанная цена самодостаточности
- "Экспорт изделия" пакует директорию в архив → Altium-надёжность когда нужна

### Позиционирование 3D модели — в футпринте, не в модели
- `offset`, `rotation`, `scale` принадлежат **футпринту**
- Модель `.step` — сырая геометрия корпуса в своём нулевом положении
- Два разных футпринта (например повёрнутый SOIC-16) ссылаются на одну общую модель,
  но каждый позиционирует её сам → конфликта нет, дублирование футпринтов не вредит

## Цепочка конвертации

```
Eagle / KiCad / Altium
        ↓ парсер
       IR (XML)
        ↓ генератор
Eagle / KiCad / Altium
```

IR — **явный формат**, не внутренняя деталь реализации. Пользователь работает с IR файлом
напрямую, хранит в git, редактирует.

## Представление полигонов (редактор платы)

### Выбор: штриховка (Eagle-модель), НЕ настоящая зона
- **Eagle**: полигон = штриховка линиями заданной толщины. Контур — замкнутая
  линия того же примитива. Заливка — горизонтальные штрихи до контура.
- **KiCad/Altium**: полигон = настоящая 2D-зона, булевы операции через Clipper2,
  тесселяция.
- **Решение babel: штриховка.** Полигон и дорожки — один и тот же примитив
  (линия с толщиной).

### Почему штриховка, а не зона
Происхождение Eagle-решения — слабое железо 1988 (мало вычислений, простые
примитивы). Но оно оказалось правильным выбором примитива: упрощает вещи,
о которых авторы не думали. Один примитив → пять следствий, ни одно не притянуто:

1. **Единый примитив.** Нет отдельной подсистемы зон. Полигон сводится к уже
   решённой задаче (линии с толщиной).
2. **Единый GPU-конвейер.** Планируется обсчёт дорожек в шейдерах. Полигон =
   те же сегменты = тот же шейдер, инстансирование, distance field почти даром.
   Возражение "объём данных" (тысячи отрезков) испаряется на GPU — он любит
   много одинаковых инстансов. Возражение было актуально только для CPU-рендера.
3. **PI-сетка даром.** Для power integrity медь всё равно дискретизируют в сетку
   резисторов. Штрих = резистор (R = ρ·L/(t·w)), пересечения = узлы. Граф
   резисторов уже есть, не нужен шаг "зона → mesh → выкинуть геометрию".
   Зона честнее как геометрия, штриховка честнее как физический объект.
4. **Контроль min-толщины меди по построению.** Производители не делают слишком
   тонкую медь. В зоне это отдельный DRC-проход (и именно там Clipper2 у нас
   глючил на тонких перемычках). В штриховке минимальный элемент = штрих с
   заданной толщиной → нарушение невыразимо, не нужно проверять.
5. **Нет булевой обрезки контура.** Контур = медь с толщиной. Штрихи заходят
   ПОД контурную линию, она их накрывает (перекрытие → сплошная медь, без
   зазоров). Не нужно пересекать заливку с границей — оба просто медь, медь
   поверх меди = медь. Операция, на которой Clipper2 тормозил/глючил, удалена.

Паттерн: штриховка не "решает задачу лучше", а **растворяет задачу** — то что
в модели зоны отдельная проблема со своим кодом и багами, в модели штриховки
не возникает. Признак правильного примитива.

Железо сделало круг: ограничения 1988 и природа GPU указывают в одну сторону —
много простых линий, никакой ветвящейся геометрии на универсальном процессоре.

### Реализация
- Шаг штриха = ширине контура (один размерный параметр на полигон, он же
  автоматически min-толщина меди → невозможно рассогласовать)
- Контур рисуется как замкнутая линия (осевая); полигон торчит на width/2 наружу —
  это не баг, а визуализация реальной кромки меди (раздражает пользователей,
  лечится пониманием "осевая, не кромка")
- Штриховка горизонтальная без затей (платы тяготеют к прямоугольникам)
- Clipper2 протестирован — глючил (некорректная тесселяция) и тормозил на средних
  проектах. Ещё один довод против модели зоны.

### Открытый вопрос на будущее (многослойный PI)
- Одинаковое горизонтальное направление штриха на соседних слоях → просветы
  встают стопкой по вертикали → межслойная ёмкость/PI отличаются от сплошной
  зоны. Возможно на чувствительных слоях чередовать направление слой-через-слой.
  Проверить числами когда дойдёт до многослойного PI.
- Прилегание штриховки к очень сложным/изрезанным границам — проверить на худшей
  реальной границе (но контур-линия и перекрытие в основном это закрывают).

## Library Manager (веб-прототип)

### Концепция
- Копируем Eagle Library Manager — он уже решил задачу правильно
- Одна библиотека в фокусе в любой момент (не дерево всех библиотек)

### Вкладка 1 — Обзор библиотеки
- Таблица всех устройств
- Колонки: имя, описание, символ (есть/нет), футпринты (сколько), статус маппинга пинов
- Сразу видно что полное, что неполное

### Вкладка 2 — Устройство
- Имя, описание, артикул, ссылка на даташит
- Рендер символа (SVG)
- Рендер футпринта(ов) — список с превью (SVG)
- Таблица пин→пад

### Анализ футпринтов (дедупликация)
- Формат **разрешает** дублирование (ради самодостаточности), он не полицейский
- **Менеджер** обнаруживает дубли и помогает консолидировать когда пользователь захотел
- Находит футпринты с одинаковым именем в разных библиотеках, показывает:
  - идентичные → кандидаты на схлопывание в один
  - различающиеся → подсвечивает чем отличаются (геометрия падов, поворот, keepout)
- Использует SVG-рендерер: наложение двух футпринтов с визуальной дельтой

### Рендеринг
- SVG генерация на Python из данных IR
- Отдаётся в браузер как картинка
- Никакого canvas/WebGL на этом этапе
- SVG рендерер — фундамент будущего нативного движка

## Стратегия импорта и экспорта

### Origin — метаданные источника компонента
Каждый компонент в IR хранит метаданные о том откуда он пришёл. Два отдельных
origin — для символа и для футпринта, потому что в KiCad/Altium они живут
в разных библиотеках:

```xml
<component id="R_10k">
  <origin device-library="Device" symbol="R"
          footprint-library="Resistors_SMD" footprint="R_0603"/>
</component>
```

- При экспорте в Eagle — используется `device-library` как имя `.lbr`
- При экспорте в KiCad — используются оба origin раздельно
- При экспорте в Altium — используются оба origin раздельно
- Компоненты без origin (созданные в babel) → fallback библиотека `project_name`
- Origin — не функциональная ссылка (проект не зависит от доступности источника),
  а метаданные для экспортёра и будущего механизма обновлений

### Принцип: данные храним, зависимость не создаём
Знаем откуда пришли, но не нуждаемся в источнике для работы проекта.

### Экспортёр всегда выдаёт два артефакта
Это не опция — это всегда, для всех трёх систем:
1. Файл изделия (схема + плата)
2. Набор библиотечных файлов с оригинальными именами

Библиотеки — обязательная часть экспорта, т.к. они нужны для работы с проектом. Они все равно ВСЕГДА экспортируются на практике вручную, мы это автоматизируем.

### Форматы библиотек по системам
- **Eagle** → набор `.lbr` файлов с оригинальными именами
- **KiCad** → `.kicad_sym` для символов + `.pretty` директории с `.kicad_mod`
  для футпринтов (имя библиотеки = имя директории)
- **Altium** → `.SchLib` + `.PcbLib` с оригинальными именами. `.IntLib`
  (скомпилированный пакет) пользователь собирает сам в Altium одной кнопкой —
  генерировать бинарный `.IntLib` напрямую нецелесообразно

### Почему сохранение имён библиотек важно
Большинство конвертеров сваливают все компоненты в одну безымянную библиотеку —
пользователь получает кашу и руками переназначает всё заново. Babel сохраняет
структуру библиотек через origin.

Бонус: если имена библиотек в экспортированном проекте совпадают с теми что уже
есть у пользователя — он может подменить библиотеку своей и обновить компоненты.
Механизм обновления компонентов получается бесплатно как следствие сохранения имён.
Пользователь делает это осознанно (сам подменил файл) — честнее чем магическая
кнопка "Update from Library".

### Импорт из KiCad — origin
- Символ: поле `lib_id` в `.kicad_sch` (формат `библиотека:имя`)
- Футпринт: поле `footprint` в том же файле (тот же формат)
- Оба поля всегда присутствуют, парсятся тривиально через split `:`

### Импорт из Altium — origin
- Символ: имя `.SchLib` файла + имя компонента внутри
- Футпринт: имя `.PcbLib` файла + имя футпринта
- Если проект использует `.IntLib` — всё в одном файле, символ и футпринт
  извлекаются вместе

### Импорт из Eagle — 3D модели (NoABS)
- NoABS хранит путь к директории 3D моделей в ini файле
- Babel читает этот ini при первом запуске (разовая настройка, не часть каждого
  импорта)
- Eagle без NoABS → пользователь указывает директорию вручную (редкий случай)
- KiCad → пользователь встраивает модели в проект перед импортом
  (`File > Archive Project`)
- Altium → модели уже встроены в библиотеку как бинарный блоб, распаковываем
  в `models/` и делаем относительную ссылку
- Если модель не найдена → `model3d status="missing" original-ref="..."` —
  никогда не теряем ссылку молча

## Порядок реализации

1. **IR формат** — XML схема (XSD) для компонента
2. **Парсеры** — Eagle → IR (отправная точка), затем KiCad и Altium
3. **SVG рендерер** — символ и футпринт из IR в SVG
4. **Library Manager** — веб-прототип на базе IR + SVG рендерер
